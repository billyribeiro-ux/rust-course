Workshop / Independent assessments

Demonstrate that you can change a specification, investigate a failure and defend an engineering choice. Rebuilding copied reference code is useful setup evidence, but it does not pass an independent assessment.

Before revealing an approach: write your interpretation of the contract, predict at least two outputs, propose competing hypotheses for one failure and choose an experiment that could disprove your preferred hypothesis. Work in your learner copy. Record the exact mise command, input, exit status and relevant output. Cite the primary documentation that justifies one important API assumption. Explain the fix and its limits in your own words.

All exercises run locally with synthetic data. Optional database and browser prerequisites are explicit in their project instructions. An unavailable tool means that check is not run; it does not mean it passed. Reference approaches are folded separately below each specification. They are not full unimplemented solutions presented as runnable code.

Assessment contract and scoring

The same rubric applies to every project assignment and each final scenario. Submit a small evidence packet: contract and prediction; a minimal fixture; at least two plausible competing hypotheses; one experiment that disproves a hypothesis; a regression test; source citation; design decision and alternative; exact verification results; and a short independent explanation without reading the reference. Negative results and failed initial experiments belong in the record.

DimensionPointsEvidence that earns credit
Contract and prediction10Defines edge behavior and predicts outcomes before execution.
Correct behavior25Meets the new specification without breaking existing invariants or hiding failures.
Boundary and regression tests15Tests a meaningful failure, observes it before the fix and preserves it afterward.
Investigation method15Separates observation from guess and records an experiment that disproves a plausible hypothesis.
Engineering judgment15Uses appropriate current Rust habits, explains an alternative and names a requirement that would justify changing design.
Sources and reproducibility10Cites a primary source, retains exact commands/fixtures and states verification limits.
Independent explanation10Explains ownership, state transition or resource policy and answers one changed-input question without copying prose.

A suggested pass is 75/100, with nonzero credit in every dimension and all mandatory acceptance criteria met. A safety or data-integrity defect blocks a pass regardless of total points. A reference build alone earns only setup evidence. A reviewer may change one input after submission to distinguish understanding from memorization. These thresholds are a course rubric, not a professional certification. Author self-review is recorded separately; independent review remains pending.

Independent project P01

P01 · Add a checked remainder operation

Prepare with 00-calculator. The specification below is a learner extension. Existing runnable reference code does not claim to implement the extension.

Specification and fixtures

Extend the integer calculator with %. Permit scalar remainder and same-unit remainder, preserving the left unit for the latter. Reject mixed units. Define signed behavior as Rust checked integer remainder, and document that choice. Fixtures: 17 % 5, -17 % 5, 17m % 5m, 17m % 5s, 5 % 0 and the minimum i64 value % -1. Predict every result before adding the match branch.

Acceptance criteria

Return structured errors for invalid units, zero divisor and overflow; do not panic or silently wrap. Existing arithmetic remains unchanged. The CLI distinguishes invalid input from a successful result through its exit status. Add table-driven cases and at least one test proving the unit validation runs even when numbers look harmless.

Required investigation evidence

Investigate a report that “negative remainder is wrong.” Compare the hypothesis of a parsing error with a mistaken assumption about mathematical modulo. Use a negative input with an independently documented expected result to disprove one. Cite checked_rem's contract and explain why the test belongs at the arithmetic boundary.

Reveal reference approach after recording your own design and evidence

A reasonable implementation extends the existing checked-operation dispatch and preserves CalcError. It defines unit compatibility before arithmetic, checks the zero case and maps a missing checked result to overflow. A separate modulo operation would need a different specification; changing signed semantics silently is not a repair.

The existing project directory supplies the baseline only. This revealed approach is a design discussion, not a hidden complete implementation or an assertion that extension tests have already run.

P03 · Filter a bounded log stream by time

Prepare with 01-logs. The specification below is a learner extension. Existing runnable reference code does not claim to implement the extension.

Specification and fixtures

Add an inclusive timestamp window to the streaming analyzer. Use the fixture “9 INFO api warmup”, “10 ERROR api timeout”, “12 WARN db retry”, “13 INFO api ready” and one malformed line. For the window 10..=12, count two included valid records while reporting malformed and excluded records separately. Required investigation evidence

Investigate differing filtered counts under small buffers. Contrast a window-boundary error with a streaming-boundary error and disprove one using the same fixed byte slice through a one-byte reader. Cite BufRead's buffering contract and document your accounting categories with a conservation equation.

Reveal reference approach after recording your own design and evidence

Parse each bounded line once, classify malformed data first, then apply a pure inclusive predicate to a valid borrowed Record. Aggregate only the category the contract names. A helper predicate is useful if it makes boundary tests clearer; a generic filtering framework is unnecessary for one explicit policy.

Independent project P05

P05 · Add bounded right-associative exponentiation

Prepare with 02-evaluator. The specification below is a learner extension. Existing runnable reference code does not claim to implement the extension.

Specification and fixtures

Extend the expression language with integer exponentiation using ^, right associativity and higher precedence than multiplication. For this assessment, unary minus has lower precedence than exponentiation: -2^2 is -4, and (-2)^2 is 4. Exponents must be nonnegative and at most 63; define 0^0 as 1. Fixtures include 2^3^2, 2*3^2, 2^-1, 0^0, 2^63 and a deeply nested expression.

Acceptance criteria

Preserve source-byte, token and nesting limits; reject arithmetic overflow with a useful byte span. Parse associativity structurally rather than relying on evaluation order by accident. Existing operators keep their semantics. Show AST or parenthesized interpretations for the two precedence-sensitive fixtures.

Required investigation evidence

Investigate an output of 64 for 2^3^2. Compare wrong associativity with overflow handling and a tokenizer problem. An AST-level observation should disprove at least one hypothesis before arithmetic is changed. Cite a primary Rust checked-arithmetic source and explain why parser and evaluator need separate tests.

Reveal reference approach after recording your own design and evidence

Introduce a dedicated precedence level or binding-power rule for the specified right-associative operator. Evaluate the bounded exponent using checked arithmetic, preserving source spans. Do not use floating-point pow and cast back to integers. This specification deliberately adds semantics beyond the runnable baseline expression language.

The existing project directory supplies the baseline only. This revealed approach is a design discussion, not a hidden complete implementation or an assertion that extension tests have already run.

P06 · Add a read-only record inspector

Prepare with 03-recovery. The specification below is a learner extension. Existing runnable reference code does not claim to implement the extension.

Specification and fixtures

Create an inspect operation that reports each validated record's starting offset, operation kind, key length and value length without printing key or value contents. It must never truncate or compact the input. Construct a log with an overwrite, an empty value and a deletion, then append a partial header. Acceptance criteria

Factor pure one-record decoding or expose a read-only replay observer, then keep file repair inside the existing mutation-owning Store::open path. Reusing a parser is appropriate; reusing a mutating open operation violates this new contract. The baseline's recovery implementation is not a read-only inspection command.

Independent project P08

P08 · Make retryable status policy explicit

Prepare with 04-monitor. The specification below is a learner extension. Existing runnable reference code does not claim to implement the extension.

Specification and fixtures

Change retry policy so transport failures, timeouts and HTTP 503 may retry, while other nonhealthy HTTP statuses and malformed responses return immediately. Retain the existing bounded attempt count and endpoint deadline. Local fixtures must provide 503 then 200, 404 then an unused 200, malformed bytes, and a connected socket that never responds.

Acceptance criteria

The 503 fixture becomes healthy after two attempts; 404 completes after one and never opens a second connection. Malformed input remains bounded and immediate. Backoff consumes the endpoint deadline, and shutdown aborts and drains all tasks. Reject every non-loopback endpoint before work starts.

Required investigation evidence

Investigate a fixture that hangs waiting for a second request. Hypotheses must include an incorrect retry policy and a test that expected an intentionally prohibited retry. Use acceptance notifications or counters, not arbitrary sleeps, to disprove one. Cite timeout or JoinSet semantics and identify requests that may already have reached a peer at cancellation.

Reveal reference approach after recording your own design and evidence

Put retry classification in a small pure policy function over Status and keep transport execution separate. Test the classification table independently, then test actual connection counts with local listeners. Do not solve a policy mismatch by increasing deadlines. This is a proposed policy refinement; the baseline retries all nonhealthy outcomes within its bounds.

Independent project P09

P09 · Add bounded named rooms to framed chat

Prepare with 05-chat. The specification below is a learner extension. Existing runnable reference code does not claim to implement the extension.

Specification and fixtures

Extend local chat with a room name in each application message, encoded as room|text inside the existing length-prefixed UTF-8 frame. Room names contain 1–12 ASCII lowercase letters; text is nonempty and may contain later | characters. A connection selects its room on its first message and cannot switch. Limit simultaneously active rooms to eight and retain the existing global connection and message budgets.

Acceptance criteria

Messages reach only peers in the same room. Reject malformed names and cross-room changes. Fragment headers and bodies across writes, test coalesced frames, and show a slow client cannot create unbounded queues. Remove an empty room or explain a bounded retention policy. Shutdown must own and finish all connection tasks.

Required investigation evidence

Investigate room leakage using two local rooms with distinct marker messages. Competing hypotheses include shared broadcast state, incorrect parsing and a reused client connection. Disprove one using an isolated frame-parser test before changing task management. Cite read_exact or broadcast lag semantics; no internet chat service is needed.

Reveal reference approach after recording your own design and evidence

Separate frame decoding from the new application-message parser and keep room routing state behind one clear owner or a small synchronized registry. Track room lifecycle as well as client lifecycle. The existing baseline has one broadcast room and no authentication/TLS; this extension must not claim to add either security property.

Ten stage gates

These gates are demonstrations to a reviewer, not automatic checkboxes. Each requires an independently stated prediction, one disproved plausible hypothesis, a primary-source citation and a limits statement. A learner may use documentation, but should close the reference implementation during the explanation.

Stage 0 · Predict, run and explain a checked CLI

Without the reference open, predict a normal result, a unit mismatch, zero division and an i64 boundary case. Run your own calculator modification through mise and identify the exact process exit status. Explain expressions versus statements and where parsing ends and domain arithmetic begins. The reviewer changes one sign or unit afterward. Submit one compiler diagnostic translated into plain language and one experiment disproving a mistaken arithmetic assumption. Passing requires correct behavior plus a reproducible explanation; memorizing a successful command is insufficient.

Return to the stage preparation lesson.

Workspace and language foundation check: create a new learner directory without replacing existing work, show its absolute path, and explain one relative source path and one parent-directory path. Initialize a local Git repository there, inspect a meaningful diff, commit a source change and its application lockfile, and explain why generated build output stays outside the commit. Show the mise-selected compiler, format the changed source and interpret one Clippy diagnostic. Given decimal 13, write its binary place-value decomposition; distinguish numeric value from its spelling. Add a small function with an expression return and an if or loop, predict a deliberate semicolon type error, and separate that compiler rejection from a valid program's runtime input error. Your evidence must include the commands, a prediction revised after an observation, and an explanation of how you decomposed input, computation and presentation.

Stage 1 · Own state and preserve failures

Draw owners and borrows in the journal or log analyzer. Demonstrate one borrowed field cannot outlive its input, then repair the design without unnecessary cloning. Show a saved state round trip and a malformed-input failure that remains visible. The reviewer injects an ordinary I/O error and asks whether it is equivalent to EOF. Submit your lifetime sketch, minimal failure fixture, competing hypotheses and a regression. Passing requires explicit cleanup and persistence limits, not a claim that Drop makes every save successful.

Return to the stage preparation lesson.

Core collection extension: choose an array, vector, slice, or keyed map for a changed journal summary requirement. Explain tuple fields and UTF-8 byte versus scalar counts. Demonstrate deterministic report order and separate the input-item cap from the distinct-key cap with a duplicate-key experiment. Identify who owns returned labels after source text is dropped.

Stage 2 · Specify a reusable boundary

Implement a small parser or configuration extension from a fresh specification. Explain one trait bound as a required capability and one lifetime as a relationship to an owner. Predict precedence or layer override behavior before running. The reviewer supplies an input at a size/depth limit and one malformed Unicode boundary. Submit a pure-function test, a source citation and a disproof experiment that locates a defect in parsing rather than evaluation or resolution. Passing requires stable domain semantics, useful errors and justified abstractions.

Return to the stage preparation lesson.

Conversion and API extension: implement a private validated newtype using fallible admission and lossless extraction, then preserve the first error in a batch pipeline. Translate that pipeline into a loop without changing order or duplicates. Demonstrate the public module path and a passing documentation example; explain one behavior change that could break callers despite an unchanged function signature.

Stage 3 · Recover only what evidence supports

Given one intact record followed by a partial record, predict recovered state and repaired file length. Given complete checksum damage, explain why the response differs. Draw the compaction write, sync, rename, handle-replacement and directory-sync sequence. The reviewer moves an interruption point and asks which file is authoritative. Submit a tested failure case and a hypothesis disproved by reopen behavior. Passing requires precise uncertainty about failed writes and filesystem guarantees; synthetic truncation must not be described as comprehensive power-loss testing.
