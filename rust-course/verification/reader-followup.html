The identified backup and navigation defects are corrected in the reviewed source. Five pure backup-data tests passed on Node v24.21.0, and both JavaScript files passed syntax checks. No browser, DOM simulation, visual inspection or accessibility acceptance is claimed.

RF01 · Import activation relied on a control that was not a straightforward keyboard-operable button.

The generated shell now provides a real type=button Import control that activates the hidden file input; it has an accessible progress-JSON label.

Evidence: Source relationship and JavaScript syntax checked; native file-picker interaction not observed.

RF02 · Import success messaging could hide a localStorage write failure.

save returns a Boolean. Import reports a successful persisted merge only when save succeeds; otherwise it identifies page-only data and tells the reader to export before leaving.

Evidence: Control-flow source review. Actual browser storage denial/quota behavior was not executed.

RF03 · The former import silently discarded notes of at least 100000 characters, although the reader could save and export those notes.

A shared pure parser validates every notes/completed entry and rejects an invalid map as a whole. It preserves long valid strings; the import event applies an explicit 64 MiB file limit instead of silently filtering long notes. Parsing completes before any state merge.

Evidence: Five pure Node tests passed, including exact long-Unicode round-trip, whole-import rejection for invalid entries and Boolean completion validation.

RF04 · After unreadable saved progress, an unrelated theme or note save could overwrite recoverable original storage.

The reader retains the original raw text and blocks ordinary writes with loadInvalid. A validated user import must save that original under a recovery key before replacement is allowed. If recovery storage fails, the original key remains untouched and imported data stays page-only. Export exposes both current JSON and the retained original recovery text.

Evidence: Source review of write order, guards and error paths. No synthetic Storage object or browser-storage test was used.

RF05 · The mobile overlay covered the topbar menu button even though sequential keyboard navigation reached that button after the last sidebar link. Closed off-screen navigation also needed exclusion from focus.

At widths up to 850px, the sidebar is a normal-flow disclosure: display:none while closed, display:block while open, position:static and max-height:65vh with inherited scrolling. It no longer overlays the following topbar. Opening requests focus on the first link; Escape closes it, updates aria-expanded and requests focus on Menu.

Evidence: CSS/DOM-order and event-handler source review only. Actual layout, scrolling, Tab order and focus visibility remain unobserved.

RF06 · A requested download was reported as exported without evidence that the browser saved it, and a manual fallback placed far down a lesson could be hard to reach.

Export always reveals a labeled readonly JSON textarea, opens its details panel and requests focus on that textarea. It reports Download requested and asks the user to confirm the file or copy the fallback. The original unreadable text is separately labeled for recovery; object URLs are revoked after use.

Evidence: Source review and syntax check. Download persistence, native dialog behavior and focus effects were not browser-verified.
