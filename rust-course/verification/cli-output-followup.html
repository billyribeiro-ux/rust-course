Fallible output from the first greeting

Author self-review, October 9, 2026. Independent review remains pending. The normal-output convenience macros println! and eprintln! can panic when their stream fails. A closed pipe is an expected environmental failure, so recommended programs now express it through Result from their first runnable output.

Changed source and teaching

The P01 greeting, packing-cost example, roundoff example and first calculator checkpoint use writeln! through a locked stdout handle and explicitly flush. Their Result-returning main reports failure using Rust's process boundary. The initial programming lesson explains io::Result, the writing handle, ? and flush when they first appear.

The final calculator, journal, configuration and expression CLIs preserve normal output and use explicit failure statuses for output errors. Final diagnostics are best effort if stderr itself is closed. Existing usage and domain statuses remain unchanged when their diagnostics succeed. README, decision records and affected canonical lessons explain the same contract. No dependency was added; calculator learner scaffold source has no printing code and needed no change.

Failure experiment and verification

Exact successful commands and results and the machine-readable record cover formatting, all-target checking, strict Clippy, 44 final-project native/documentation tests, three packing-rule tests, and four reconstructed early-checkpoint tests. The latter includes its own closed-output process regression. The executable example probe makes nine additional observations: each of three examples has its normal output checked, then runs with closed stdout, then with both stdout and stderr closed. The closed-pipe cases return status 1 rather than a panic exit.

The tests create an actual OS pipe and close its only reader before starting the child. This forces the failure before any output is attempted; there is no timing-dependent “pipe into head” approximation. P02 additionally adds a task through closed stdout, sees a failing acknowledgement, then reloads the one saved task. Saving already succeeded, so retrying add blindly can duplicate the user's intent. A failed output channel is not a rollback mechanism.

An experiment that exposed a tooling assumption

The initial probe failed against an older greeting binary still present in the shared target. It observed status 101 and a stdout panic. The source had changed, but mise's configured CARGO_TARGET_DIR overrode a shell environment value, placing fresh final executables in .local/native-target. The intermediate build directory had remained shared. This disproved the assumption that the named binary had just been rebuilt. The final commands place both target environment values after mise selection using mise exec -- env, then rebuild and rerun the probe. The earlier log is retained as investigation evidence, not recorded as a passing check. No unrelated cache or learner directory was deleted.

Primary sources and limits

The installed version-matched official documentation was inspected for Write, std::io::pipe and Result termination. The latter uses a best-effort diagnostic path; actual closed-stderr example checks exercise it here. Source hashes are in the JSON record.

Checks ran on macOS ARM with Rust 1.99.0 via mise. Windows behavior was not executed. A successful flush does not prove a downstream reader consumed the bytes, performed an action or durably stored them. Output can be partial on failure. These checks address process I/O boundaries; they do not establish domain correctness beyond the linked tests, browser behavior or independent acceptance.
