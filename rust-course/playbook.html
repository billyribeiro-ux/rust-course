A practical problem-solving playbook

When the answer is unclear, choose an experiment that can change your mind. Progress is better evidence, not simply more edits.

This method begins in the first lesson and grows with the systems you build. Early investigations show the whole chain. Later investigations deliberately withhold a cause, include a misleading clue, or require you to choose the next experiment. A compiler, a test runner, a database and a browser expose different evidence, but the reasoning loop is reusable.

The investigation loop

  1. State the problem. Write three short sentences: what should happen, what happened, and what would count as success. “The program is broken” hides the input, expected result and failure boundary. “Converting 25°C produces 45°F; it should produce 77°F” is specific. Separate observed output from explanations.
  2. Reproduce it. Record the exact command, current directory, input, Rust version and relevant configuration. Reduce the case until only the necessary parts remain. Preserve logs and event order for an intermittent failure; a smaller example that no longer fails may have removed the essential condition.
  3. Locate the boundary. Is the first failing step parsing, type checking, borrowing, application logic, configuration, a dependency, I/O, concurrency, persistence or another process? This is a working classification. A browser error could originate in an HTTP response, not the component that displays it.
  4. Read the evidence. Start with the earliest diagnostic that explains the cause. A later “could not compile” is often a consequence. Read the file location, the highlighted expression, the type or state expected, and the explanation. Follow a request ID or event ID across boundaries instead of joining unrelated messages by proximity.
  5. Name a testable hypothesis. State a cause and a prediction: “Integer division happens before multiplication; using 9.0 / 5.0 should change the result.” Name a competing cause and what observation would weaken it. Keep an uncertainty list rather than silently turning assumptions into facts.
  6. Run a small experiment. Change one relevant factor where practical. Predict both possible outcomes first. Prefer experiments that distinguish causes: print parsed input, test a pure function, query a specific row, or measure one stage. Consult version-matched primary documentation when a concept or API contract is missing.
  7. Implement the smallest sound fix. Restore the intended invariant. A clone can suppress a borrow error while hiding a poor ownership boundary; a sleep can hide a race while leaving it present. “No error message” is not the invariant.
  8. Verify and challenge it. Re-run the original reproducer, nearby boundaries and failure paths. Add a regression test when it guards a meaningful behavior. Distinguish the claim tested from untested environments, larger workloads and alternative schedules.
  9. Capture the lesson. Record the cause, decisive evidence, rejected hypothesis, fix and prevention. A useful investigation log is short enough to review and precise enough to repeat.

Worked case: a converter returns 45 instead of 77

Suppose a small converter uses celsius * (9 / 5) as f64 + 32.0. The program compiles. Compiling establishes type compatibility, not correctness of the formula. With 25.0°C, the observed output is 57.0°F, not 77.0°F. Notice that even our initial problem statement above used a different observed number, 45°F. Before reasoning further, replace a remembered symptom with the actual captured output. Accurate observation is part of the work.

The boundary is arithmetic inside a pure function. Parsing is a plausible alternative cause: perhaps the CLI reads 13 rather than 25. A first experiment calls the conversion function directly with 25.0 and prints the input. It still returns 57.0. That weakens the parsing hypothesis. A second experiment evaluates 9 / 5 and 9.0 / 5.0 independently; integer operands produce 1, floating operands produce approximately 1.8. The cast occurs after information has already been lost.

The smallest fix is to choose floating-point operands before division, then test 0°C → 32°F and 100°C → 212°F with an appropriate tolerance. Negative values and values close to zero should be included. Reject non-finite input where the domain requires a real measurement. This fixes the unit formula; it does not make binary floating point exact decimal arithmetic. In the workbench, prices instead use integer cents with checked arithmetic.

Tempting fix: round the output

Rounding cannot restore the fraction discarded by integer division. It changes presentation while preserving the incorrect scale. A good fix explains why the root cause disappears for a range of inputs.

Worked case: “borrowing is too restrictive”

Observation: a program borrows a task title, mutates the task collection, then prints the borrowed title. The compiler rejects the mutation. Hypothesis A: Rust disallows reading and changing the same collection anywhere in a function. Hypothesis B: the outstanding reference would overlap an operation that can invalidate it.

Move the print before the mutation. If the code now compiles, A is disproved: the ordering of uses matters. The second hypothesis better predicts the result. Decide whether the application should read before changing, return an owned summary, or find the task again after the change. Do not reach first for unsafe, reference counting or a global lock. Write the intended ownership relationship in a sentence and choose the simplest API that expresses it.

Evidence to keep: original and reduced source, compiler error code, successful alternative, and a test proving the required task transition still occurs. The corrected code's compilation supports borrow validity under the compiler's model; it does not prove task IDs are unique or saves are durable.

Middle case: the health checker stops making progress

Observation: one endpoint times out; all later checks appear stalled. The service CPU usage is low. A colleague proposes more worker threads. Competing hypotheses: a synchronous lock is held across await, a semaphore permit is leaked, a deadline wraps only the connection step, or the network is slow. Low CPU does not distinguish these explanations.

First draw the ownership of a permit from acquisition to every return path. Next run the local timeout fixture with concurrency one, then two, while counting started and completed checks. A low-cost experiment is to replace the network request with a timer that completes. If the stall remains, network latency is weakened as a cause. Record why this experiment is informative before running it.

Hint 1: look for a conservation rule

Available permits plus permits owned by active operations should equal the configured budget. A leaked permit violates this rule even when no data race exists.

Hint 2: separate cancellation from completion

Aborting an outer future need not stop already-running blocking work. Record which owner joins which task and which resource is released on drop.

Reference direction

Instrument resource acquisition and release. Put one total deadline around each operation, keep guards out of suspension points, and use ownership-based permit release. Only enlarge concurrency after the existing bound is understood. The monitor lesson contains executable local failure fixtures; this case describes a diagnostic strategy, not an asserted diagnosis of your run.

Middle case: an update disappeared

Two API clients both receive success. The final row contains only one change. A successful HTTP status proves the handler chose a success response; it does not tell you whether the intended transaction was atomic. Preserve request IDs, row versions, SQL parameters with secrets removed, and transaction boundaries.

Try a deterministic two-transaction schedule rather than hoping a load generator reproduces the race. Read the same version in T1 and T2; commit T1; then attempt T2's update. An optimistic version predicate should cause T2 to affect zero rows, which the API must report as a conflict. If both updates affect one row while replacing a value derived from the old version, investigate the predicate and the exact SQL. Do not assume “transaction” implies serial execution.

A database index is a separate hypothesis about speed, not a fix for lost updates. Compare the plan only after correctness is established. SQLx compile-time metadata describes queries against a checked schema; a migration mismatch in the live database remains possible.

Independent incident: a duplicated simulated order

Evidence packet: the client reports a timeout, the backend log includes one “committed” line, and the ledger has two purchases. A dashboard screenshot shows two clicks, but its timestamp precision is one second. You are told the database is “eventually consistent.” That phrase is a claim to examine, not an explanation.

Write at least three hypotheses. Identify which artifacts distinguish them: order IDs, transaction IDs, retry attempt IDs, request bodies, and the journal's sequence. Design one experiment where the response is lost after commit, then resend the same stable order ID. Design another with a different ID and the same business content. Predict the difference. Do not repair the ledger until its authority and recovery procedure are understood.

Reference approach, reveal after your report

Stable identity distinguishes retry from a new order. A same-ID repeat should return the recorded result or reject conflicting content, without another ledger mutation. A new ID usually denotes a new instruction, even if the visible fields match. If the browser creates a new ID for each retry, backend deduplication cannot recognize the retry. Commit the idempotency record and effect in the same transaction or deterministic event step. External effects require their own contract; a local dedup table cannot undo a remote effect.

Passing evidence includes a forced response-loss test, unchanged cash/quantity after replay, a conflicting-body test, and an explanation of the remaining crash window. A screenshot alone cannot establish exact event ordering.

The companion design loop

When building something unfamiliar, do not start by choosing every library. Write the user action, the invariant, the resource budget and the failure response. For the log tool: “Read a file larger than RAM, report matching lines, reject a line over the configured limit, and keep memory bounded.” Unknowns include input encoding, malformed lines and output consumer speed.

  1. Clarify requirements and constraints: who uses it, what is observable, and what is excluded?
  2. List unknowns and risky assumptions. Rank by how much a wrong answer would change the design.
  3. Define invariants: a task ID is unique; cash cannot become negative; a lease owner must match the current fencing token.
  4. Divide the system by responsibilities and ownership. Prefer boundaries that can be tested with ordinary data.
  5. Prototype the riskiest assumption. A 20-line framing experiment is more informative than a complete UI before the protocol is decided.
  6. Implement one thin end-to-end slice: one valid request, one stored record, one visible result.
  7. Verify success and a representative failure at every boundary. Then add scale, features and operational controls incrementally.

A useful next step either reduces an important uncertainty or delivers a small verifiable behavior. If you cannot say what the result would teach you, make the step smaller. Keep alternative designs in a short decision record: choice, context, alternatives, consequences and a condition that would justify revisiting it.

When you get stuck

Do not use a timer as a rule for asking for help. Ask when repeated experiments no longer distinguish hypotheses, the failure risks data or safety, or the next step depends on expertise you do not possess. Stop destructive experiments on valuable data; reproduce on a disposable fixture.

First action

Capture mise exec -- rustc --version, your working directory, the exact command and the earliest diagnostic. Reduce to one failing test or one input. Preserve the original failing case before changing it.

Second action

Write two plausible explanations and one experiment whose outcomes differ between them. If you cannot do that, identify the missing concept and read its versioned official documentation. Ask for an explanation, not a patch yet.

Request a useful review

Send: expected behavior; observed behavior; smallest reproducer; versions; exact error; two hypotheses; experiments and results; remaining uncertainty; and the specific decision you need help with. Remove credentials, personal data and irrelevant logs. “I tried everything” gives a reviewer nothing reproducible.

Use AI as a reviewer and hypothesis generator

Ask Codex or Claude: “Explain the first diagnostic; give two competing causes and an experiment to distinguish them.” Ask it to state assumptions and cite the API version. Inspect the proposed diff before running it. Reject changes unrelated to the hypothesis unless a reason is supplied. Run the checks yourself and explain the final ownership or failure boundary without reading the generated explanation.

AI can invent APIs, overgeneralize from passing tests, or fix a symptom by cloning, catching all errors or retrying forever. Your responsibility is the contract and the evidence. Keep an investigation where an AI suggestion was disproved; learning to revise that suggestion is a stronger assessment than accepting a large correct-looking patch.
