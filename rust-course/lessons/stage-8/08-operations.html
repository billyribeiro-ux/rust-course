Operate a service with evidence and a rollback plan

Turn failures into measurable symptoms, bounded responses, and recovery steps.

Purpose: make the next incident less mysterious

A service that works once is different from a service someone can operate. Operations means knowing what is running, what changed, what users experience, where work is waiting, and how to restore acceptable behavior. This lesson uses the scheduler and issue tracker because their failures cross process, database, and client boundaries. The goal is a reproducible local operating practice, not an invented uptime claim.

Plain-English model

An SLI, or service-level indicator, is a measured quantity tied to user experience. For the scheduler, “fraction of accepted jobs completed within30 seconds” is more useful than “process exists.” An SLO is a target for that indicator over a defined interval and workload. A target is a decision, not evidence that the system achieved it. An error budget expresses how much failure the target allows; it cannot be evaluated without a correct denominator and observation window.

Logs describe individual events, metrics summarize counts or distributions, and traces connect work across boundaries. Request IDs help correlate observations, but labels containing arbitrary job IDs can create unbounded metric cardinality. Log secrets must remain excluded. The reference prints bounded teaching events and errors but does not include a complete metrics backend, distributed tracing collector, alerting system, or measured SLO. Your operational extension should add only what answers a concrete question.

Prediction

The issue tracker's /health responds “ok” while every issue request fails to acquire a database connection. Is the service healthy? Does changing the health response to always query the database solve the entire operational problem?

Answer

The route proves only that a basic HTTP path responds. A readiness check can include a bounded dependency check, but health semantics should distinguish process liveness from readiness to serve domain requests. Aggressive dependency checks can amplify a struggling database. Neither route replaces user-facing success and latency measurements.

Small runnable investigation

Start the scheduler against its dedicated local database. In another terminal, enqueue a known fixture and inspect the row. Then repeat the same logical ID. Predict whether the accepted-job metric should count both HTTP calls as two new jobs. It should not if the indicator is about newly accepted logical work.

curl http://127.0.0.1:4114/health
psql "$SCHEDULER_DATABASE_URL" -c "SELECT id,status,attempts,token,due,lease_until FROM jobs ORDER BY id LIMIT 20"
psql "$SCHEDULER_DATABASE_URL" -c "SELECT count(*) FROM job_effects"

These are read-only observations. Do not inspect unrelated databases or print connection strings containing passwords. When reproducing failures, prefer the isolated test database and the deterministic lease test to killing a database shared with other applications.

Guided runbook checkpoint

Write a local runbook in your HTML project notes with five actions. First identify binary/toolchain version, configuration source, and database name. Second compare HTTP errors, queue age, attempts, and worker activity. Third determine whether work is rejected, queued, executing, or committed but unacknowledged. Fourth choose a bounded mitigation, such as pausing admission while preserving durable work. Fifth verify recovery with a known test job and an idempotent retry, then record unresolved effects requiring reconciliation.

Do not make “restart everything” the first step. Restarting can erase volatile evidence, interrupt in-flight responses, and trigger retries. If a restart is justified, record which process owns which work and how the durable state determines recovery. Ctrl-C in the reference stops accepting new requests, signals the owned worker, waits for it, and closes the pool. No claim is made that every external effect completes before shutdown because the reference effect is database-local.

Deliberate mistake

Define a success counter that increments before the completion transaction commits. Inject the audit/effect failure from the integration tests. The metric now reports a success that never became durable. Move the increment after the authoritative result, and define a separate attempted counter. This teaches that observability code itself has semantics and can lie even when every log line is syntactically valid.

Rollback and schema evolution

A rollback plan must specify compatible data, not merely an older binary filename. Prefer additive migrations that allow old and new code to coexist during a transition. Backfill separately when necessary. A destructive column removal may make the old binary unusable; reverting the executable cannot recreate removed data. Before changing the schema, run old and new readers against representative fixtures and document the recovery path. Backups are useful only when a restore procedure has been exercised against an appropriate environment.

Independent practice

Create a load scenario with 100 distinct jobs and repeated submissions of ten IDs. Measure acceptance latency, completion delay, failed attempts, and maximum queue depth. State host, build profile, database version, workload, and sample count. Compare the single-worker baseline with a two-worker extension only after correctness tests pass. Report results in a table generated from real measurements; this course supplies no fabricated throughput number.

Hint 1

Separate warm-up from measurement and report the distribution, not only the fastest request.

Hint 2

Count logical jobs and HTTP attempts separately. Include overload rejection in the denominator you chose.

Reference reasoning

Use deterministic payloads and IDs, fixed-duration or fixed-count scenarios, and a recorded seed if randomness is introduced. Add latency instrumentation around database acquisition and execution to locate waiting. Increasing workers may increase throughput, lock contention, or both; explain observed changes rather than assuming scaling is linear.

Playbook investigation

Incident evidence: completion latency rose, CPU fell, and retries increased after a deployment. A misleading guess is “the new code needs more CPU.” Compare pool wait, active transactions, lock waits, and dependency timeouts. Reproduce with an intentionally held lock in the isolated database. If waiting dominates and CPU remains idle, the CPU hypothesis is disproven. Mitigate by bounding admission and shortening the offending transaction, then validate with the same load. Record residual risk from uncertain acknowledgments.

Mastery check

Give another person only your runbook and incident evidence. They should identify the correct database, reproduce one failure safely, explain one rejected hypothesis, and restore a known scenario without consulting implementation details. Independent review remains pending until that actually happens.

When you get stuck

Begin with the named integration test and a read-only query of the dedicated database. Read PostgreSQL monitoring documentation for the wait you observe. Ask for review with a timeline, workload, before/after measurements, disproven hypothesis, and rollback compatibility notes; screenshots of a green dashboard are insufficient.
