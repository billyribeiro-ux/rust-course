Leases, retries, cancellation, and recovery

Specification before implementation

Build a queue backed by PostgreSQL. A job has an immutable ID and payload, a state, an attempt count, a lease token, a next-attempt time, and a lease deadline. At most one local worker executes at a time. Claiming a job increments its token and attempt count. A lease lasts five seconds. After three failed or abandoned attempts the job becomes dead. A stale worker must not record completion. Cancellation revokes a pending or running lease, but cannot undo an external action that already occurred.

Plain-English model: temporary authority

A lease is permission that expires. It is useful because a crashed process cannot voluntarily return its work. After the deadline, another worker may claim the same job. This creates an overlap risk: the original worker may be slow rather than dead. A fencing token is a monotonically increasing identifier that lets a resource reject an older owner. Our completion transaction compares the job's current token with the worker's token. An external service would need to enforce a corresponding rule or an idempotency contract; our database check cannot control an unrelated process.

The scheduler uses millisecond timestamps in an explicit time domain. Deterministic tests pass logical times to complete; complete_with_clock instead receives a clock function and calls it after acquiring the job row lock. The binary passes now_ms, so pool and row-lock waits cannot preserve an earlier unexpired timestamp for the authority decision. Claim time is sampled before its database operation, which can shorten the useful lease if admission waits. Neither path models multiple machines with skewed clocks. A real multi-host lease design should use a clearly chosen time authority and define clock-jump behavior. A lease timestamp is not the same thing as a duration measured by a monotonic timer.

Prediction

Worker A claims job J with token1 at time0. A pauses. At time5,000, B claims J with token2. A wakes at5,001 and tries to complete. Which worker may commit the effect? What if A already sent an email before pausing?

Answer

Only token2 matches current authority, so A's database completion returns false. That prevents stale database mutation. It cannot retract an email already sent. The two questions belong to different effect boundaries, which is why lease ownership and idempotency both matter.

Guided implementation and unfamiliar SQL

Implement enqueue with its serialized admission budget and duplicate semantics first. Then implement claim as a single update whose subquery chooses the earliest eligible row. FOR UPDATE SKIP LOCKED lets concurrent claimers skip already locked candidates instead of all waiting on the same job. It does not by itself guarantee fairness. The UPDATE records the new authority and returns a typed Lease. A JoinHandle owns the worker task; shutdown signals it and awaits its completion.

projects/reference/p14-scheduler/src/lib.rs
//! At-least-once leases; one idempotent database effect, not arbitrary exactly-once work.
use serde::Serialize;
use sqlx::{PgPool, Row};
pub const LEASE_MS: i64 = 5_000;
#[derive(Debug, Clone, Serialize, sqlx::FromRow)]
pub struct Lease {
    pub id: String,
    pub payload: String,
    pub token: i64,
    pub attempts: i32,
}
pub async fn enqueue(pool: &PgPool, id: &str, payload: &str) -> Result<bool, sqlx::Error> {
    if id.is_empty() || id.len() > 80 || payload.is_empty() || payload.len() > 1000 {
        return Err(sqlx::Error::Protocol("invalid job input".into()));
    }
    let mut tx = pool.begin().await?;
    // Serialize admission only, so concurrent insertions cannot exceed the durable budget.
    sqlx::query("SELECT pg_advisory_xact_lock(14001)")
        .execute(&mut *tx)
        .await?;
    if let Some(existing) = sqlx::query_scalar::<_, String>("SELECT payload FROM jobs WHERE id=$1")
        .bind(id)
        .fetch_optional(&mut *tx)
        .await?
    {
        if existing != payload {
            return Err(sqlx::Error::Protocol(
                "id reused with different payload".into(),
            ));
        }
        return Ok(false);
    }
    let count: i64 = sqlx::query_scalar("SELECT count(*) FROM jobs")
        .fetch_one(&mut *tx)
        .await?;
    if count >= 10_000 {
        return Err(sqlx::Error::Protocol("queue budget reached".into()));
    }
    sqlx::query("INSERT INTO jobs(id,payload) VALUES($1,$2)")
        .bind(id)
        .bind(payload)
        .execute(&mut *tx)
        .await?;
    tx.commit().await?;
    Ok(true)
}

pub async fn claim(pool: &PgPool, now: i64) -> Result<Option<Lease>, sqlx::Error> {
    // One atomic statement claims the oldest eligible job, skipping locked candidates.
    sqlx::query(
        "UPDATE jobs SET status='dead' WHERE status='running' AND lease_until<=$1 AND attempts>=3",
    )
    .bind(now)
    .execute(pool)
    .await?;
    sqlx::query_as::<_,Lease>("UPDATE jobs SET status='running',attempts=attempts+1,token=token+1,lease_until=$2 WHERE id=(SELECT id FROM jobs WHERE status IN ('queued','running') AND due<=$1 AND lease_until<=$1 AND attempts<3 ORDER BY due,id FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING id,payload,token,attempts").bind(now).bind(now.saturating_add(LEASE_MS)).fetch_optional(pool).await
}
/// Complete at an explicitly supplied logical time (deterministic models/tests).
pub async fn complete(pool: &PgPool, lease: &Lease, now: i64) -> Result<bool, sqlx::Error> {
    complete_with_clock(pool, lease, || Ok(now)).await
}
/// Sample the clock after acquiring the job row lock, before accepting authority.
/// The clock must use the same time domain as claim. This is not a clock-skew remedy.
pub async fn complete_with_clock(
    pool: &PgPool,
    lease: &Lease,
    clock: impl FnOnce() -> Result<i64, &'static str>,
) -> Result<bool, sqlx::Error> {
    let mut tx = pool.begin().await?;
    let row =
        sqlx::query("SELECT status,token,lease_until,payload FROM jobs WHERE id=$1 FOR UPDATE")
            .bind(&lease.id)
            .fetch_one(&mut *tx)
            .await?;
    let now = clock().map_err(|message| sqlx::Error::Protocol(message.into()))?;
    if row.get::<String, _>("status") != "running"
        || row.get::<i64, _>("token") != lease.token
        || row.get::<i64, _>("lease_until") <= now
    {
        return Ok(false);
    }
    sqlx::query(
        "INSERT INTO job_effects(job_id,payload) VALUES($1,$2) ON CONFLICT(job_id) DO NOTHING",
    )
    .bind(&lease.id)
    // The returned lease is caller-owned; durable input remains authoritative.
    .bind(row.get::<String, _>("payload"))
    .execute(&mut *tx)
    .await?;
    sqlx::query("UPDATE jobs SET status='done' WHERE id=$1")
        .bind(&lease.id)
        .execute(&mut *tx)
        .await?;
    tx.commit().await?;
    Ok(true)
}
/// Retry at a supplied logical time; the live worker does not use this model API.
/// A real external-effect worker needs an explicit clock/expiry policy at its effect boundary.
pub async fn fail(pool: &PgPool, lease: &Lease, now: i64) -> Result<bool, sqlx::Error> {
    // Derive backoff from the persisted attempt count, not mutable lease metadata.
    // Numeric arithmetic plus LEAST preserves saturation at the i64 timestamp limit.
    let result = sqlx::query("UPDATE jobs SET status=CASE WHEN attempts>=3 THEN 'dead' ELSE 'queued' END,due=LEAST(9223372036854775807::numeric,$3::bigint::numeric+(1000::bigint << LEAST(GREATEST(attempts,0),3)))::bigint,lease_until=0 WHERE id=$1 AND token=$2 AND status='running' AND lease_until>$3")
        .bind(&lease.id)
        .bind(lease.token)
        .bind(now)
        .execute(pool)
        .await?;
    Ok(result.rows_affected() == 1)
}
/// Cancellation revokes the lease. It cannot undo an external action already performed.
pub async fn cancel(pool: &PgPool, id: &str) -> Result<bool, sqlx::Error> {
    Ok(sqlx::query("UPDATE jobs SET status='cancelled',token=token+1 WHERE id=$1 AND status IN ('queued','running')").bind(id).execute(pool).await?.rows_affected()==1)
}
pub fn now_ms() -> Result<i64, &'static str> {
    let elapsed = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .map_err(|_| "system clock predates Unix epoch")?;
    i64::try_from(elapsed.as_millis()).map_err(|_| "system clock exceeds timestamp representation")
}

pub mod http;

Failure schedules the next attempt using a capped exponential delay. The reference has one worker, at most three attempts per job, and an admission cap of10,000 retained job rows. Enqueue takes a transaction-scoped advisory lock before checking capacity and inserting, so concurrent submissions cannot race past the limit. Exact retries still succeed at capacity; new jobs receive429. This simple serialized admission decision favors a checkable local budget over maximum enqueue throughput. Completed rows retain identity history; an archival and retention policy is required before this budget fills. The HTTP body and payload are separately bounded. A bounded execution count alone would not bound lifetime storage.

Deliberate mistake

Remove the token comparison from completion in a learner copy. The stale-worker assertion must fail. Next remove the lease deadline comparison while keeping the token. A worker whose lease has expired at the authority decision but has not yet been reclaimed could now be accepted. Decide whether that is acceptable in your specification; the reference deliberately rejects it. The row remains locked across the accepted database effect and completion; this does not promise that the eventual transaction commit occurs before the wall-clock deadline. These are application races, not Rust data races, so safe Rust still compiles.

Independent practice

Implement a paused state and replace the fixed retained-row budget with a reviewed retention policy. Specify whether paused jobs retain leases and whether cancellation wins against a completion transaction already holding the row lock. Then design a heartbeat renewal operation that cannot revive an expired lease. Use a deterministic timestamp in tests and avoid sleeping to “make the race happen.”

Hint 1

Write a transition table with source state, required token, time condition, destination, and durable writes.

Hint 2

A renewal must compare both token and unexpired deadline atomically. Updating only by job ID lets old workers steal authority back.

Reference reasoning

Renew with a conditional UPDATE requiring running status, the same token, and a deadline greater than now. Decide a maximum total lease age to stop permanent extension. For queue admission, make the limit race-safe with a serialized admission counter or another explicit transactional mechanism; a count-then-insert outside a transaction is insufficient.

Review and evidence

A deliberately incomplete design uses only a boolean running flag and has no crash recovery rule. The reference records enough state to recover authority after a crash. The database test demonstrates expiry, redelivery, stale rejection, one database effect, cancellation, and retry delay. It does not test arbitrary external effects, distributed clock skew, or sustained queue growth. Cancellation is best understood as a request that prevents future accepted completion under this database protocol, not as time travel.

Playbook investigation

Observation: jobs remain running longer than five seconds. Misleading evidence: the worker logged a successful claim. Hypotheses include no new claim scan, clock rollback, a long transaction, or an incorrect deadline comparison. Inspect persisted timestamps and run claim with a controlled later timestamp in the isolated test. If it recovers immediately, the durable transition logic works for that case and “corrupted job row” is disproven. Trace the worker's next polling point and clock source. Keep the fix narrow and document what happens during a future clock jump.

Mastery check

Implement heartbeat renewal without the reference, prove a stale token cannot renew, and explain why the same token rule must be checked at the resource that performs the effect. Provide one intentionally failing test that demonstrates the old design's defect.

When you get stuck

Run the scheduler PostgreSQL test explicitly. Query the isolated jobs row for status, attempts, token, due, and lease_until. Compare those observations with your transition table. In a review request include both worker timelines and the effect boundary; a timestamp alone does not explain authority.

Engineering decisions and evidence

Scope and invariants: one local worker; at-least-once leases; three attempts maximum;10,000 retained jobs; exact duplicate submission is harmless; current token and unexpired authority are required for completion. The only reference effect is a database row committed with completion. Why this design: PostgreSQL supplies durable uniqueness, locks, and atomic updates, while an explicit token makes stale-worker behavior testable. The admission advisory lock serializes only the small local queue's count-and-insert decision. Concrete habits: preserve logical IDs; reject conflicting payloads; use deterministic times in tests; propagate invalid system-clock errors instead of silently inventing a timestamp.

Alternative: a dedicated broker can supply delivery operations, but the application still owns effect idempotency and retention. A transactional counter can avoid repeatedly counting retained rows when measured enqueue throughput justifies more complexity. Evidence: actual database tests exercise expiry, fencing, cancellation, retries, deduplication, and full-budget admission. No external exactly-once guarantee or multi-host clock result is claimed. Evolution threshold: before multiple hosts, define a time authority, fair work selection, heartbeat limits, deployment connection/rate budgets, retention, and downstream effect contracts.

The API also admits at most16 handlers and imposes a five-second request/body deadline. Its runtime pool uses a three-second acquisition timeout and per-connection PostgreSQL statement timeout, so a worker blocked on database work has a finite statement wait before it can observe shutdown. The tests use isolated test pools; these operational settings are visible in the executable rather than asserted as database-server global configuration. A timeout remains an uncertain outcome; preserve the logical job ID when reconciling.

Investigate a lease that aged while waiting

Observation: a worker started completion before its lease expired but waited for a database row lock. A tempting hypothesis is that the fencing token alone makes the old timestamp safe. The delayed-lock test holds the row in another transaction, waits until PostgreSQL reports an actual blocked lock request, advances the injected clock to expiry, and releases the row. Completion returns false and produces no effect. It would wrongly accept if it sampled time before waiting. No guessed sleep is used to establish the interleaving.

The post-lock clock sample is the authority decision time, not a claim about every later hardware write. Once accepted, the same transaction retains the lock while writing the database effect. Clock rollback, multi-host time authority and external effects still need additional contracts. complete(pool, lease, now) and fail(pool, lease, now) remain logical-time APIs for deterministic models. The live worker does not call fail; its local database effect is attempted immediately and an uncertain storage failure leaves the job to expire. For completion, deployed workers should use the clock callback path rather than taking a stale timestamp before an asynchronous wait.

The conditional retry UPDATE computes its delay from the stored attempts column. A bounded integer shift gives 2,000, 4,000 and 8,000 milliseconds; the third failure becomes dead. The numeric intermediate and upper clamp prevent overflowing the signed timestamp on addition. Read the PostgreSQL 18 integer operator documentation and identify which cast preserves integer semantics. This arithmetic is part of an atomic predicate/update, not a Rust value supplied by the worker.

//! Real loopback route checks use a lazy pool and never contact PostgreSQL.
use tokio::io::{AsyncReadExt, AsyncWriteExt};
#[tokio::test]
async fn authorization_and_input_rejection_precede_database_work() {
    let pool = sqlx::postgres::PgPoolOptions::new()
        .max_connections(1)
        .acquire_timeout(std::time::Duration::from_millis(20))
        .connect_lazy("postgresql://localhost:9/unused_fixture")
        .unwrap();
    let listener = tokio::net::TcpListener::bind("127.0.0.1:0").await.unwrap();
    let address = listener.local_addr().unwrap();
    let (stop, stopped) = tokio::sync::oneshot::channel();
    let server = tokio::spawn(async move {
        axum::serve(listener, p14_scheduler::http::router(pool))
            .with_graceful_shutdown(async {
                let _ = stopped.await;
            })
            .await
            .unwrap();
    });
    let cases = [
        (
            "POST",
            "/jobs",
            "",
            r#"{"id":"a","payload":"work"}"#.to_owned(),
            401,
        ),
        (
            "POST",
            "/jobs",
            "Bearer demo-reader",
            r#"{"id":"a","payload":"work"}"#.to_owned(),
            401,
        ),
        ("POST", "/jobs/a/cancel", "", String::new(), 401),
        (
            "POST",
            "/jobs/a/cancel",
            "Bearer unknown",
            String::new(),
            401,
        ),
        (
            "POST",
            "/jobs",
            "Bearer demo-operator",
            r#"{"id":"","payload":"work"}"#.to_owned(),
            422,
        ),
        (
            "POST",
            "/jobs",
            "Bearer demo-operator",
            serde_json::json!({"id":"a","payload":"x".repeat(1001)}).to_string(),
            422,
        ),
        ("POST", "/jobs", "Bearer demo-operator", "{".into(), 400),
        (
            "POST",
            "/jobs",
            "Bearer demo-operator",
            "x".repeat(4097),
            413,
        ),
        ("GET", "/health", "", String::new(), 200),
    ];
    let mut observed = Vec::new();
    for (method, path, identity, body, expected) in cases {
        let response = tokio::time::timeout(std::time::Duration::from_secs(2), async {
            let mut stream = tokio::net::TcpStream::connect(address).await.unwrap();
            let request = format!("{method} {path} HTTP/1.1\r\nHost: {address}\r\nAuthorization: {identity}\r\nContent-Type: application/json\r\nContent-Length: {}\r\nConnection: close\r\n\r\n{body}",body.len());
            stream.write_all(request.as_bytes()).await.unwrap();
            let mut response = Vec::new();
            stream.take(8193).read_to_end(&mut response).await.unwrap();
            response
        }).await.unwrap();
        let response = String::from_utf8(response).unwrap();
        let status = response
            .split_whitespace()
            .nth(1)
            .unwrap()
            .parse::<u16>()
            .unwrap();
        observed.push((path.to_owned(), status, expected));
    }
    stop.send(()).unwrap();
    server.await.unwrap();
    for (route, status, expected) in observed {
        assert_eq!(status, expected, "{route}");
    }
}

Protect the disposable test boundary

The scheduler's opt-in database tests require the exact name rust_course_test_scheduler and a literal loopback address or absolute local socket path. A shared test helper parses the effective SQLx connection options and verifies SELECT current_database() on every new connection before migrations or resets. A string containing the test name elsewhere in a URL is insufficient. Tests still require a database you have established is disposable; the name and local transport alone do not establish ownership. The author verification creates a fresh private Unix-socket-only cluster and removes only that cluster after a successful shutdown.

Output policy and ownership at process boundaries

The listener bind and required startup banner now complete before spawning the worker. A closed stdout pipe is ordinary I/O failure; startup uses writeln! and flush with ? instead of a panic-producing printing macro. SCHEDULER_DATABASE_URL errors use a fixed message because the non-Unicode error type can otherwise retain the original credential-bearing value.

Worker observations have a different contract: they use best-effort Write calls, and an output error does not panic the task or decide whether a database effect committed. That means a lost log line is possible. Inspect durable job/effect state when reconciling outcomes; a log line is not a durable acknowledgment or audit record. A synchronous write can still block on a slow sink. This small local demonstration does not promise a hard shutdown deadline for logging; a stronger operational requirement would justify a bounded logging worker and an explicit dropped-message policy.

The main task owns the Ctrl-C future and a pinned server future. The same watch sender can stop both the server and worker. Every server exit signals the worker, awaits its handle, closes the pool, and only then returns saved server, worker or signal errors. It no longer uses an early ? after serving that could skip the join. The worker observes the current stop state before waiting, so an already-set stop is effective. Read the process evidence and remaining limits; a source review of this ordering is distinct from an injected accept-error execution.
