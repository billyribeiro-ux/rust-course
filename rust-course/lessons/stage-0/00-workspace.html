Files, terminal navigation, and a reviewed Git snapshot

Build a reliable local workflow: locate files, use the pinned toolchain, inspect Cargo checks, and commit exactly the changes you reviewed.

Purpose: know where your work lives

A program begins as ordinary text stored in files. Before changing that text, you need to identify the correct folder, run a command there, inspect its result, and preserve a change you understand. This lesson teaches those actions explicitly. You do not need to know Rust syntax yet. By the end you will have a separate practice package, run its generated greeting, and prepare a small Git commit whose contents you can explain. Keep the course reference files intact so they remain a reliable comparison.

Begin in the course root: the folder containing index.html, mise.toml, projects, and scripts. This is the inner course folder if your download has another folder around it. Use your editor's “Open Folder” command to open that folder, then open its integrated terminal. A terminal displays input and output; the shell is the program that interprets the commands you type. Run one command at a time. Do not type an illustrated prompt such as $.

Model: folders, paths, and the current directory

A file holds data; a directory, also called a folder, contains named files and other directories. A path describes how to find one. An absolute path starts from the filesystem root, written / on macOS and Linux. A relative path starts from the shell's current working directory. The same relative path can refer to different files after you change that directory. A file extension such as .rs helps tools recognize Rust source; it is part of the name, not proof that the contents are correct.

pwd
ls
ls projects
cd projects
pwd
ls reference
cd ..
pwd

pwd prints the current directory. ls lists names. ls projects lists another directory without moving into it. cd projects changes this shell's current directory; it does not move files. .. means the parent directory, so cd .. moves back up one level. A single dot means the current directory. Changing the directory in one terminal does not change a second terminal. These distinctions explain many apparent “missing file” problems.

Before running the sequence, predict which of its three pwd results will match. Write your prediction, then compare the actual paths. The first and last should match. If they do not, stop and reconstruct your navigation instead of guessing another path. Folder names containing spaces need quotes when typed as one shell argument: cd "practice notes" means one folder. That is a syntax example, not a folder you must create. Preserve filename capitalization; a path that works on one filesystem may fail on another.

Tools: one responsibility at a time

The course's mise.toml selects Rust 1.99.1. mise exec -- runs the following command with that configuration. The double dash separates mise's arguments from the command being launched. rustc is the Rust compiler: it checks Rust source and translates valid source into executable code. cargo manages a Rust package's build, dependencies, examples, and tests. A dependency is another package your code uses. You do not need to install a dependency for a basic greeting.

mise exec -- rustc --version
mise exec -- cargo --version
mise exec -- rustup show active-toolchain
git --version

Record the actual output rather than writing “latest.” A toolchain is the matched compiler and supporting tools. Its selected version is evidence about this command, not proof that every terminal on your computer uses it. We use mise for project selection and do not change a global Rust default. The course's configuration also puts normal native build artifacts under its shared .local/native-target folder. Build artifacts are generated files; source files are what you edit and review. A shared target reduces repeated compilation, but it is not a backup of your work.

Guided checkpoint: create a fresh practice package

Return to the course root and confirm its contents with pwd and ls. Create a new learner package using this exact sequence. If foundations-lab already exists, stop and choose another unused name consistently in the remaining commands. Cargo refuses an existing destination; do not delete or overwrite it to force this exercise through.

mkdir -p learner-work
mise exec -- cargo new --vcs none learner-work/foundations-lab
cd learner-work/foundations-lab
pwd
ls
ls src
mise exec -- cargo run

mkdir creates a directory; -p permits the parent directory to exist. Cargo's new creates a package. --vcs none asks it to leave version-control initialization to our explicit Git step. Open the new src/main.rs in your editor and read it without changing it. Cargo generated that file and Cargo.toml, its manifest, which describes the package. The run command builds the package and starts its program. Compiler progress lines are separate from the program's greeting, usually Hello, world!.

Now inspect the package again. Cargo.lock records the dependency resolution used by this application. Keep it in version control, even when the application has no third-party dependencies yet. Cargo maintains it; you should review changes to it but not edit dependency checksums by hand. The manifest states allowed requirements; the lockfile records the selected dependency versions. Neither file alone guarantees correct or secure behavior. An upgrade remains a deliberate change requiring review and appropriate checks.

mise exec -- cargo check --locked
mise exec -- cargo fmt --check
mise exec -- cargo clippy --all-targets --locked -- -D warnings
mise exec -- cargo test --locked

check performs compiler checks without producing the ordinary runnable executable. --locked rejects a build that would require changing the lockfile. fmt --check asks rustfmt, Rust's formatter, whether formatting matches its conventions without rewriting files. To format your own package, use mise exec -- cargo fmt, then review the difference. Clippy suggests improvements and detects selected suspicious patterns; -D warnings makes its warnings fail this check. Tests execute authored checks. A fresh greeting may report zero tests, which means exactly that: it does not establish a tested business rule. Inspect the greeting as the observable behavior here.

Git: preserve an inspected snapshot

Git stores a local history of selected file contents. A repository is that history together with its working files. A commit is a recorded snapshot with an author and explanatory message. Saving a file in your editor only changes the working copy; it does not commit. Git's staging area, also called the index, holds the exact contents you have selected for the next commit. Editing a staged file again does not automatically update the staged copy. That gives you a useful review boundary.

While still in the newly created learner-work/foundations-lab, confirm pwd. Create a new file named .gitignore in that package using your editor, containing the single line /target/. The leading dot makes it hidden in many file browsers; ls -a includes hidden names. This rule excludes a package-local build directory if the package is later used outside the course's shared-target configuration. Do not ignore Cargo.lock. Do not add credentials, private notes, or generated target files to history.

git init -b main
git status --short
git add .gitignore Cargo.toml Cargo.lock src/main.rs
git diff --cached
git status --short
git commit -m "Create runnable foundations practice package"
git log -1 --oneline

Initialize Git only after checking that you are inside this new practice package. The command creates its own local repository; it does not publish anything. git status --short summarizes changes. ?? marks an untracked file. The first status column describes staged changes; the second describes additional working-copy changes. git add selects the named files, and git diff --cached shows the content about to be committed. Read every line before committing. A commit message should explain this small change rather than claiming the entire course is complete.

If Git asks for an author identity, choose your own name and an email address you are comfortable recording in this repository. Repository-local configuration uses git config --local user.name and git config --local user.email, followed by your chosen value as a quoted argument. Do not copy someone else's identity or change your global configuration just to silence the message. A local commit has not been uploaded. Hosting services and remote collaboration arrive later; understanding local snapshots comes first.

Intentional mistake: inspect the wrong directory

This is a deliberate, harmless failure. In the practice package, run ls missing-workshop-folder. Predict whether the shell will create the folder, change directories, or report an error. It should report that the path does not exist and leave your current directory unchanged. Run pwd to verify. Do not respond by reinstalling Rust: the failure is a path lookup by ls, before Rust participates. The wording varies by operating system; the missing path and unchanged directory are the important evidence.

Playbook investigation: saved, staged, or committed?

Use the central investigation playbook. In your practice package, add a short comment above main with the editor and save. Your observation is that the greeting has not changed. Possible explanations are “the file was not saved,” “a comment does not change this output,” and “I ran another package.” Separate those hypotheses from facts. Run git diff -- src/main.rs to see whether the saved file differs from the committed snapshot. That experiment can disprove the unsaved-file explanation without modifying code again.

Record pwd, run the package, and identify its manifest. Stage just src/main.rs, then compare git diff with git diff --cached. An empty ordinary diff after staging does not mean the change disappeared; the staged diff should contain it. Review the comment and commit it if it accurately explains intent. Your evidence establishes the location and reviewed contents of this change. It does not prove future changes are harmless, and a clean Git status is not a correctness test.

Independent practice and tiered help

Without repeating the command list mechanically, create a new text file named investigation.txt in your practice package. Write the starting directory, toolchain version, your wrong-path prediction, observed result, and the command that disproved a hypothesis. Review and commit only that file. Then explain to a reviewer why editing, saving, staging, and committing are four different events. The acceptance criterion is an understandable evidence trail and a narrowly selected commit, not a particular commit hash.

Hint 1: identify the layer

For a path error, start with pwd and ls. For an unexpected Git result, start with git status --short. For a tool-version disagreement, run the version command through mise from the recorded directory.

Hint 2: select one file

git add investigation.txt selects the current saved contents of that file. Inspect git diff --cached -- investigation.txt before the commit. If you edit after staging, stage again only after reviewing that later edit.

Reference approach after your attempt

A successful investigation distinguishes current directory from file path, records the actual version output, and shows that ls did not create its missing argument. The staged diff contains only your intended report. A reviewer can reproduce the harmless failure and explain why Rust installation was an irrelevant hypothesis. There is no requirement to copy this wording or manufacture a successful observation.

Engineering decisions, review, and evidence

Our scope is one local practice application. The invariant is that course references remain available and every committed change has been inspected. A fresh destination, explicit filenames for staging, a versioned application lockfile, and a project-selected toolchain fit that scope. A graphical file manager and Git client are reasonable alternatives if you can still identify the current folder and review staged contents. A shared repository workflow would add branches, remote review, and conflict handling; those requirements do not justify hiding the local model now.

The author verified the companion examples with the pinned compiler; see the targeted execution log. Your new package and commits are independent learner work, so that log does not claim to have checked them. For review, supply the selected diff, commands, actual results, and one remaining uncertainty. A green formatter, lint check, or empty status is useful evidence within its own scope, not a substitute for explaining behavior.

When you get stuck

Write down the first failing command and its complete error, with private paths or identity details redacted if needed. Run pwd before retrying. Check mise exec -- cargo --help for command structure and git help status for the two status columns. Ask for review by stating what you predicted, what happened, and which hypothesis your last check ruled out. Never use a destructive reset or delete a folder merely to make your screen resemble an example.

Mastery check

Close this page and explain why ls projects and cd projects differ; locate a source file without guessing; show which Rust version mise selects; distinguish a manifest from its lockfile; and explain the exact contents of your next commit. You are ready to continue when you can recover from the harmless wrong-path experiment using observations and can demonstrate those actions on your own practice package.
