Convert fractional lengths with an honest numeric contract

Add a typed approximate length converter, preserve integer arithmetic, and investigate finite range and floating-point rounding.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Build a checked calculator with units and useful errors
  • Choose a numeric representation from the measurement requirement.
  • Parse bounded unit-bearing input into a validated private type.
  • Distinguish parsing, nonfinite values, overflow, underflow, and ordinary rounding.
  • Use one-factor experiments and library/CLI regressions to explain failures.

Key terms: enum · invariant · mise

Purpose: convert a measurement without weakening the calculator

A shelf is 1.5 meters wide, and the drawing asks for centimeters. The integer calculator cannot express that input. Its rejection is correct for its existing contract; the missing capability is a separate conversion command. This checkpoint adds convert 1.5m cm while keeping 7m / 2 equal to 3m. Requirements determine the representation. We need signed fractional measurements, so this operation uses f64, Rust’s 64-bit binary floating-point number. Integer arithmetic continues to use checked i64.

The supported units are millimeters (mm), centimeters (cm), meters (m), and kilometers (km). Negative values represent a signed displacement. The converter does not decide whether a particular physical object may have a negative size. That additional domain rule belongs in an application that knows what is being measured.

Plain model: approximate number, recognized unit, validated boundary

A Length contains a private finite number and a LengthUnit enum. Callers receive one only through validation or a successful conversion. Private fields prevent another module from constructing a length containing infinity. An enum limits units to four named choices. A Result describes ordinary failure: unknown unit, invalid numeric text, nonfinite input, overflow, or loss of a nonzero value to zero. The CLI translates that result into an exit status and a message; it never assumes user input succeeds.

Floating point is a deliberate fit for approximate measurement, not an exact decimal system. Many decimal fractions have no finite binary expansion. The stored value is a nearby representable number, and arithmetic can round again. Integers, money in a specified smallest unit, exact decimal records, and scientific measurements can require different representations. Choosing f64 here does not replace that requirements analysis.

use std::io::{self, Write};

fn main() -> io::Result<()> {
    let sum = 0.1_f64 + 0.2;
    let mut output = io::stdout().lock();
    writeln!(output, "0.1 + 0.2 = {sum:.17}")?;
    writeln!(output, "equal to 0.3: {}", sum == 0.3)?;
    output.flush()
}

Read the complete implementation

projects/reference/p01-calculator/src/conversion.rs
//! Approximate floating-point length conversion, separate from integer arithmetic.
//!
//! ```
//! use workshop_calculator::conversion::{convert, LengthUnit};
//! let converted = convert("1.5m", "cm")?;
//! assert_eq!(converted.value(), 150.0);
//! assert_eq!(converted.unit(), LengthUnit::Centimeters);
//! # Ok::<(), workshop_calculator::conversion::ConversionError>(())
//! ```
use std::fmt;

pub const MAX_INPUT_BYTES: usize = 128;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum LengthUnit {
    Millimeters,
    Centimeters,
    Meters,
    Kilometers,
}

impl LengthUnit {
    pub fn parse(input: &str) -> Result<Self, ConversionError> {
        match input {
            "mm" => Ok(Self::Millimeters),
            "cm" => Ok(Self::Centimeters),
            "m" => Ok(Self::Meters),
            "km" => Ok(Self::Kilometers),
            _ => Err(ConversionError::InvalidUnit),
        }
    }

    pub fn symbol(self) -> &'static str {
        match self {
            Self::Millimeters => "mm",
            Self::Centimeters => "cm",
            Self::Meters => "m",
            Self::Kilometers => "km",
        }
    }

    // All four integer factors are exactly representable in f64. Their ratios
    // can still be inexact, so the result is explicitly an approximation.
    fn millimeters(self) -> f64 {
        match self {
            Self::Millimeters => 1.0,
            Self::Centimeters => 10.0,
            Self::Meters => 1000.0,
            Self::Kilometers => 1_000_000.0,
        }
    }
}

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum ConversionError {
    InputTooLong,
    InvalidNumber,
    InvalidUnit,
    NonFinite,
    Overflow,
    Underflow,
}

impl fmt::Display for ConversionError {
    fn fmt(&self, formatter: &mut fmt::Formatter<'_>) -> fmt::Result {
        formatter.write_str(match self {
            Self::InputTooLong => "conversion input exceeds 128 bytes",
            Self::InvalidNumber => "expected a number immediately followed by mm, cm, m, or km",
            Self::InvalidUnit => "length unit must be mm, cm, m, or km",
            Self::NonFinite => "input must be finite; NaN and infinity are not lengths",
            Self::Overflow => "converted value exceeds the finite f64 range",
            Self::Underflow => {
                "a nonzero value rounded to zero; choose a different unit or representation"
            }
        })
    }
}

impl std::error::Error for ConversionError {}

/// Validated finite value and recognized length unit. Fields stay private so
/// conversion callers cannot bypass finite-value validation.
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct Length {
    value: f64,
    unit: LengthUnit,
}

impl Length {
    pub fn value(self) -> f64 {
        self.value
    }

    pub fn unit(self) -> LengthUnit {
        self.unit
    }

    pub fn parse(input: &str) -> Result<Self, ConversionError> {
        if input.len() > MAX_INPUT_BYTES {
            return Err(ConversionError::InputTooLong);
        }
        // Longest suffixes first: "1mm" must not become the number "1m".
        let (number, unit) = [
            LengthUnit::Millimeters,
            LengthUnit::Centimeters,
            LengthUnit::Kilometers,
            LengthUnit::Meters,
        ]
        .into_iter()
        .find_map(|unit| {
            input
                .strip_suffix(unit.symbol())
                .map(|number| (number, unit))
        })
        .ok_or(ConversionError::InvalidUnit)?;
        if number.is_empty() || number.trim() != number {
            return Err(ConversionError::InvalidNumber);
        }
        let value = number
            .parse::<f64>()
            .map_err(|_| ConversionError::InvalidNumber)?;
        if !value.is_finite() {
            return Err(ConversionError::NonFinite);
        }
        // Parsing an extremely tiny decimal can already round a nonzero input
        // to zero. Exponent digits do not determine whether the significand is zero.
        let significand = number.split(['e', 'E']).next().unwrap_or(number);
        if value == 0.0
            && significand
                .bytes()
                .any(|digit| matches!(digit, b'1'..=b'9'))
        {
            return Err(ConversionError::Underflow);
        }
        Ok(Self { value, unit })
    }

    pub fn to_unit(self, unit: LengthUnit) -> Result<Self, ConversionError> {
        let ratio = self.unit.millimeters() / unit.millimeters();
        // Scale once. (value * source_factor) / target_factor can overflow at
        // the intermediate product even when the requested result is finite.
        let value = self.value * ratio;
        if !value.is_finite() {
            return Err(ConversionError::Overflow);
        }
        if self.value != 0.0 && value == 0.0 {
            return Err(ConversionError::Underflow);
        }
        Ok(Self { value, unit })
    }
}

pub fn convert(input: &str, target_unit: &str) -> Result<Length, ConversionError> {
    Length::parse(input)?.to_unit(LengthUnit::parse(target_unit)?)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn common_fractional_signed_and_scientific_values() {
        for (input, target, expected) in [
            ("1.5m", "cm", 150.0),
            ("-2.5km", "m", -2500.0),
            ("+0.125m", "mm", 125.0),
            ("1.25e3mm", "m", 1.25),
            ("2.5E-2km", "m", 25.0),
        ] {
            let actual = convert(input, target).unwrap();
            assert_eq!(actual.value(), expected, "{input} -> {target}");
            assert_eq!(actual.unit().symbol(), target);
        }
    }

    #[test]
    fn every_unit_pair_agrees_with_independent_expected_values() {
        // Explicit expected conversions avoid deriving the oracle through the
        // implementation's factor-division algorithm.
        let cases = [
            ("1mm", [1.0, 0.1, 0.001, 0.000_001]),
            ("1cm", [10.0, 1.0, 0.01, 0.000_01]),
            ("1m", [1000.0, 100.0, 1.0, 0.001]),
            ("1km", [1_000_000.0, 100_000.0, 1000.0, 1.0]),
        ];
        for (input, expected_values) in cases {
            for (target, expected) in ["mm", "cm", "m", "km"].into_iter().zip(expected_values) {
                let actual = convert(input, target).unwrap().value();
                assert!(
                    (actual - expected).abs() <= expected * 1e-14,
                    "{input} -> {target}"
                );
            }
        }
    }

    #[test]
    fn invalid_units_numbers_and_nonfinite_inputs_are_errors() {
        for input in ["NaNm", "infm", "-infm", "1e309m"] {
            assert_eq!(
                convert(input, "cm"),
                Err(ConversionError::NonFinite),
                "{input}"
            );
        }
        for input in ["1m ", "1s", "1MM", "m", " 1m", "1 m", "1_000m", "1.2.3m"] {
            assert!(convert(input, "cm").is_err(), "{input}");
        }
        for target in ["", "s", "CM", " cm", "cm "] {
            assert_eq!(convert("1m", target), Err(ConversionError::InvalidUnit));
        }
        assert_eq!(
            convert(&format!("{}m", "1".repeat(128)), "m"),
            Err(ConversionError::InputTooLong)
        );
        let longest_accepted = format!("{}1m", "0".repeat(126));
        assert_eq!(longest_accepted.len(), MAX_INPUT_BYTES);
        assert_eq!(convert(&longest_accepted, "m").unwrap().value(), 1.0);
    }

    #[test]
    fn avoids_false_intermediate_overflow_and_rejects_real_range_loss() {
        assert_eq!(convert("1e308km", "km").unwrap().value(), 1e308);
        assert_eq!(convert("1e308m", "km").unwrap().value(), 1e305);
        assert_eq!(convert("1e308km", "mm"), Err(ConversionError::Overflow));
        assert_eq!(convert("-1e308km", "mm"), Err(ConversionError::Overflow));
        assert_eq!(convert("5e-324mm", "km"), Err(ConversionError::Underflow));
        assert_eq!(convert("1e-999m", "cm"), Err(ConversionError::Underflow));
        assert!(convert("1e-300m", "mm").unwrap().value().is_finite());
        assert!(convert("5e-324m", "mm").unwrap().value() > 0.0);
    }

    #[test]
    fn explicit_zero_is_valid_and_negative_zero_keeps_its_sign() {
        for input in ["0m", "0.0e-999m", "+0cm"] {
            assert_eq!(convert(input, "km").unwrap().value(), 0.0);
        }
        let negative_zero = convert("-0.0m", "cm").unwrap().value();
        assert_eq!(negative_zero, 0.0);
        assert!(negative_zero.is_sign_negative());
    }
}

Read Length::parse in boundary order. It rejects inputs longer than 128 bytes before numeric parsing. Suffix recognition checks two-letter units before m; otherwise 1mm could be split into the invalid number 1m. Numeric parsing accepts fractions and scientific notation such as 1.25e3. It rejects embedded whitespace, unsupported units, and separators such as 1_000. A Rust source literal and a runtime numeric string have different grammars.

Successful parsing alone is insufficient. f64 includes NaN and positive and negative infinity, so is_finite() enforces our domain. Extremely small decimal text can parse as zero. For a zero result, we inspect only the significand for a nonzero digit, excluding the exponent. Thus 1e-999m is rejected as underflow, while 0e-999m is a valid zero. The numeric parser has already established valid syntax before this check. Explicit negative zero remains valid and keeps its sign.

Conversion divides the two unit factors first, then multiplies the value by that ratio. Each factor is an exactly representable small integer measured in millimeters. A ratio may still be inexact. Scaling once avoids an unnecessary intermediate overflow: 1e308 * 1_000_000 / 1_000_000 overflows at the multiplication, even though the intended same-unit result is finite. Reordering arbitrary floating-point expressions is not automatically safe; here the four bounded, positive factors make the reason specific and reviewable.

The result must be finite. A nonzero input may not become zero during conversion. Finite nonzero subnormal results remain allowed; they can have poorer relative precision than ordinary normalized values. These checks detect range loss, not every rounding error. The converter does not claim a maximum physical measurement error.

Guided checkpoint: trace one success and three failures

Run the common command, then trace 1.5m: the suffix selects meters, parsing yields 1.5, the meter-to-centimeter ratio is 100, and the result is 150. The library returns a Length; main prints the approximate label and exits zero. Now run the following commands separately. Each failure should produce a diagnostic on stderr, no successful value on stdout, and exit status one.

mise exec -- cargo run -p workshop-calculator -- convert NaNm cm
mise exec -- cargo run -p workshop-calculator -- convert 1e308km mm
mise exec -- cargo run -p workshop-calculator -- convert 5e-324mm km
mise exec -- cargo test -p workshop-calculator

The first input is nonfinite before conversion. The second is finite at entry but too large after scaling. The third is a positive representable subnormal value whose scaled result rounds to zero. These are different boundaries with different errors. A missing target, such as convert 1.5m, is an argument-count error and exits two. Existing integer arithmetic still rejects 1.5m + 2m; the new fractional contract belongs specifically to conversion.

Intentional mistake: a mathematically equivalent formula

In a disposable learner copy, replace the ratio-first expression with (self.value * self.unit.millimeters()) / unit.millimeters(). Predict which existing regression fails, then run the range test. The same-unit 1e308km case detects false intermediate overflow. This deliberately incorrect implementation is an investigation exercise, not a suggested first checkpoint. Restore the ratio-first expression and confirm the regression passes.

Another tempting mistake is to permit every value that parse accepts. Remove the finite check only in that disposable copy and inspect the nonfinite test. A parser answers whether text describes an f64; domain validation answers whether that value is an accepted length. Neither responsibility replaces the other.

Apply the problem-solving playbook

Observation: the deliberate multiply-first version rejects a huge same-unit conversion. Expected behavior: a finite input converted to its own unit retains its value. Reproduce with the exact command, pinned compiler version, and changed expression recorded. Locate the boundary: argument parsing and unit recognition completed, while result validation sees a nonfinite value.

Hypothesis A is that the decimal parser cannot represent 1e308. Hypothesis B is that an intermediate multiplication overflows. Uncertainty remains until an experiment distinguishes them. Change only the units from km → km to mm → mm, keeping the numeric text. In the deliberately broken version the millimeter case succeeds and the kilometer case fails. That expected experimental result contradicts hypothesis A: identical numeric parsing occurs in both cases. Inspecting the intermediate factors supports B. Do not claim that this experiment was run unless you actually performed the mutation.

The smallest sound fix computes the bounded factor ratio first. The actual supplied tests pass for the repaired implementation, including same-unit extremes and true overflow. Keep both regressions: a fix that simply accepts infinity would satisfy neither contract. Capture the cause, distinguishing experiment, fix, and remaining rounding limitations. The problem-solving playbook provides the shared investigation template. An AI assistant can explain the competing hypotheses or suggest a discriminator; require it to account for observed values before accepting a patch.

When you get stuck

Start with mise exec -- cargo test -p workshop-calculator conversion to isolate library behavior. If it passes but the command differs, inspect argument order and then run mise exec -- cargo test -p workshop-calculator --test cli. Read the pinned standard-library f64 documentation for is_finite, infinity, and subnormal values. Do not guess that every number below MIN_POSITIVE is zero: that constant names the smallest positive normal value.

A useful review request is: “With Rust 1.99.1, this command produced this status and stderr; I expected this value. Library test X passes. I suspect argument routing or suffix parsing. Which one-input experiment distinguishes them?” Include a small reproducer and your uncertainty. Avoid sending only “floating point is broken” or asking a tool to replace every equality with an arbitrary tolerance.

Engineering decisions and evidence

The requirements are four length units, bounded numeric text, signed finite fractional values, honest approximate output, and explicit range failures. Separate Length and LengthUnit types keep this contract distinct from checked integer Quantity. Ordinary failures use typed errors. Private fields protect the invariant after construction. A direct subcommand branch is proportionate for one additional operation; a command parser becomes useful when options, help structure, and more commands make manual routing cumbersome.

A fixed decimal representation would be justified by an exact decimal interchange requirement with a specified scale and rounding policy. Rational arithmetic could preserve more exact conversion relationships but introduces numerator/denominator range and simplification decisions. A units library becomes attractive for more dimensions and compound calculations. None is needed merely to demonstrate four approximate length conversions correctly.

The scoped native run passed 15 tests: eight library tests, five CLI tests, and two doctests. Clippy passed for all package targets with warnings denied. The roundoff example was executed. Logs are verification/conversion-tests.log, conversion-clippy.log, and conversion-roundoff.log. Explicit conversion tables cover all 16 unit pairs; range and invalid-input regressions exercise failure boundaries. This evidence does not prove every floating-point rounding behavior, performance on other machines, or a physical accuracy guarantee. Independent review remains pending.
