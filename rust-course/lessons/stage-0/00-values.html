Values, expressions, and choosing arithmetic behavior

Build a reliable integer model before adding parsing and units.

Purpose: make numbers mean something

A calculator is small enough to understand completely and rich enough to expose important design choices. Its numbers are signed 64-bit integers. That means a finite representable range, exact integer results within that range, and a need to define behavior when the mathematical result does not fit. Saying “it adds numbers” is not a complete contract. Decide whether to reject overflow, wrap, saturate, or use an arbitrary-precision representation. This project rejects overflow because silently changing a measurement would mislead its user.

A binding gives a name to a value. The type determines what operations are available and what those operations mean. let count = 3_i64 creates an i64 value and an immutable binding. let mut permits assigning a new value through that binding; it does not make an integer infinitely large. Shadowing creates another binding, potentially with a different type. Use shadowing for a clear transformation, such as text to parsed quantity, and mutation for state that changes over time. These are design choices with different explanations.

Runnable model and prediction

Run these cases from rust-course/projects. Before running them, write the expected value or error and explain whether parsing, arithmetic, or formatting should decide it. Quoting the star protects it from shell expansion. The double dash forwards arguments to the binary.

mise exec -- cargo run -p workshop-calculator -- -7 / 2
mise exec -- cargo run -p workshop-calculator -- 9223372036854775807 + 1
mise exec -- cargo run -p workshop-calculator -- 8 '*' -3

Expected results are -3, an overflow error, and -24. Integer division truncates toward zero; it does not round to the nearest integer or compute a floating-point decimal. A value that prints as -3 is therefore correct for this contract. If the product required physical measurements with fractions, changing the numeric model would be a requirements decision, not merely a display adjustment. Give every surprising result a contract before judging it.

An expression evaluates to a value. A block can be an expression when its final expression is not followed by a semicolon. For example, let doubled = { let base = 4; base * 2 }; binds 8. Adding a semicolon after base * 2 changes the block result to (), the unit value. Unit means the expression provides no useful payload; it is not the same thing as a quantity's meters or seconds. Rust uses similar English words for different concepts, so read the type in context.

Guided checkpoint: preserve the failure

Read Quantity::apply in the reference. checked_add returns Some(result) or None. The code converts None into CalcError::Overflow with ok_or, keeping the reason a calculation failed available to its caller. Returning zero instead would make failure indistinguishable from a real zero result. Panicking would hand ordinary user input to a mechanism intended for a violated program assumption. Result is the appropriate shape when the caller should choose how to report a recoverable failure.

projects/reference/p01-calculator/src/lib.rs
//! Checked integer arithmetic with a deliberately small unit system.
//! ```
//! use workshop_calculator::calculate;
//! let result = calculate("12m", "+", "3m")?;
//! assert_eq!(result.to_string(), "15m");
//! assert!(calculate("12m", "+", "3s").is_err());
//! # Ok::<(), workshop_calculator::CalcError>(())
//! ```
use std::{fmt, str::FromStr};

pub mod conversion;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Unit {
    Scalar,
    Meters,
    Seconds,
}
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct Quantity {
    pub value: i64,
    pub unit: Unit,
}
#[derive(Clone, Debug, PartialEq, Eq)]
pub enum CalcError {
    InvalidNumber,
    UnknownOperator,
    IncompatibleUnits,
    Overflow,
    DivisionByZero,
}
impl fmt::Display for CalcError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(match self {
            Self::InvalidNumber => "expected an integer optionally followed by m or s",
            Self::UnknownOperator => "operator must be +, -, *, or /",
            Self::IncompatibleUnits => "units do not support this operation",
            Self::Overflow => "result is outside the i64 range",
            Self::DivisionByZero => "cannot divide by zero",
        })
    }
}
impl std::error::Error for CalcError {}
impl FromStr for Quantity {
    type Err = CalcError;
    fn from_str(input: &str) -> Result<Self, Self::Err> {
        let (number, unit) = if let Some(s) = input.strip_suffix('m') {
            (s, Unit::Meters)
        } else if let Some(s) = input.strip_suffix('s') {
            (s, Unit::Seconds)
        } else {
            (input, Unit::Scalar)
        };
        if number.is_empty() || number.trim() != number {
            return Err(CalcError::InvalidNumber);
        }
        Ok(Self {
            value: number.parse().map_err(|_| CalcError::InvalidNumber)?,
            unit,
        })
    }
}
impl fmt::Display for Quantity {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        let suffix = match self.unit {
            Unit::Scalar => "",
            Unit::Meters => "m",
            Unit::Seconds => "s",
        };
        write!(f, "{}{suffix}", self.value)
    }
}
impl Quantity {
    /// Integer division truncates toward zero. Products of two non-scalar units
    /// are deliberately unsupported; this is not a full dimensional algebra.
    pub fn apply(self, op: &str, rhs: Self) -> Result<Self, CalcError> {
        use CalcError::*;
        let (value, unit) = match op {
            "+" | "-" => {
                if self.unit != rhs.unit {
                    return Err(IncompatibleUnits);
                }
                (
                    if op == "+" {
                        self.value.checked_add(rhs.value)
                    } else {
                        self.value.checked_sub(rhs.value)
                    },
                    self.unit,
                )
            }
            "*" => {
                let unit = if self.unit == Unit::Scalar {
                    rhs.unit
                } else if rhs.unit == Unit::Scalar {
                    self.unit
                } else {
                    return Err(IncompatibleUnits);
                };
                (self.value.checked_mul(rhs.value), unit)
            }
            "/" => {
                let unit = if rhs.unit == Unit::Scalar {
                    self.unit
                } else if self.unit == rhs.unit {
                    Unit::Scalar
                } else {
                    return Err(IncompatibleUnits);
                };
                if rhs.value == 0 {
                    return Err(DivisionByZero);
                }
                (self.value.checked_div(rhs.value), unit)
            }
            _ => return Err(UnknownOperator),
        };
        Ok(Self {
            value: value.ok_or(Overflow)?,
            unit,
        })
    }
}
pub fn calculate(left: &str, operator: &str, right: &str) -> Result<Quantity, CalcError> {
    left.parse::<Quantity>()?.apply(operator, right.parse()?)
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn units_and_integer_division() {
        for (a, op, b, out) in [
            ("12m", "+", "3m", "15m"),
            ("3", "*", "4s", "12s"),
            ("7m", "/", "2m", "3"),
            ("-7", "/", "2", "-3"),
        ] {
            assert_eq!(calculate(a, op, b).unwrap().to_string(), out);
        }
    }
    #[test]
    fn recoverable_errors() {
        assert_eq!(
            calculate("1m", "+", "1s"),
            Err(CalcError::IncompatibleUnits)
        );
        assert_eq!(
            calculate("2m", "*", "2m"),
            Err(CalcError::IncompatibleUnits)
        );
        assert_eq!(calculate("1", "/", "0"), Err(CalcError::DivisionByZero));
        assert_eq!(
            calculate("9223372036854775807", "+", "1"),
            Err(CalcError::Overflow)
        );
        assert_eq!(
            calculate("-9223372036854775808", "/", "-1"),
            Err(CalcError::Overflow)
        );
        assert_eq!(calculate("1.5", "+", "2"), Err(CalcError::InvalidNumber));
    }
    #[test]
    fn exhaustive_small_addition_commutes() {
        for a in -20..=20 {
            for b in -20..=20 {
                let a = Quantity {
                    value: a,
                    unit: Unit::Meters,
                };
                let b = Quantity {
                    value: b,
                    unit: Unit::Meters,
                };
                assert_eq!(a.apply("+", b), b.apply("+", a));
            }
        }
    }
}

Complete the calculator scaffold one operation at a time. First parse signed scalar integers and support checked addition, returning a Result from the first runnable checkpoint. Make an ordinary successful-addition test pass, then add the maximum-plus-one assertion and verify it returns Overflow through the same checked implementation. Only after both work should you add units. This sequence creates a feedback loop in which a failure has a small likely cause. The full reference is a worked checkpoint; compare control flow after your own attempt rather than typing it without predictions.

Intentional mistake: debug success is not a policy

Temporarily write an isolated expression using ordinary addition of two runtime i64 values. A tempting claim is that Rust always panics on overflow. Overflow behavior depends on operation and compiler settings; debug checks are not a substitute for your public arithmetic contract. Do not teach a release-only behavior accidentally. checked_add expresses the choice directly and keeps it consistent across build profiles. Restore the scaffold to checked operations after observing the experiment.

Another tempting mistake is checking only a divisor equal to zero. i64::MIN divided by -1 also cannot fit in i64. The reference checks zero separately for its specific error and uses checked_div to detect the remaining overflow. Designing distinct errors does not require duplicating all arithmetic implementation details. Let a documented primitive enforce the range boundary.

Playbook application: a surprising negative quotient

Observation: -7 divided by 2 produces -3. Hypothesis A: the parser lost the minus sign. Hypothesis B: the program performs integer division with truncation toward zero. A distinguishing experiment is -8 divided by 2, followed by -7 multiplied by 1. Expected results are -4 and -7. Those results disprove the lost-sign explanation for these inputs while fitting B. Inspect checked_div documentation to connect the evidence to a specified rule. Changing output formatting would not repair a numeric-model mismatch.

For your investigation, record where information could first diverge: command arguments, parsed numeric values, arithmetic result, or formatted text. If you add temporary debug output, print to standard error and remove it after the experiment. One-factor experiments become less useful when you simultaneously change the type, parser, and operation. Ask AI to explain both candidate models and predict each experiment, then compare its claims with the actual command output.

When you get stuck: independent work and tiered help

Add table-driven cases for negative addition, zero multiplication, equal negative operands, i64 minimum subtraction, and minimum divided by -1. For every case, name the contract being tested. Then explain why adding 1 to an unsigned maximum differs from parsing a negative number into an unsigned type: the first concerns arithmetic, the second input representation. Do not merge these into a vague “bad number” story in your design notes.

Worked solution

self.value.checked_add(rhs.value).ok_or(CalcError::Overflow) preserves either the exact result or the explicit domain error. A useful review request is “Here are my boundary cases; which arithmetic failure can still escape as a panic?” Include the relevant branch, not the entire repository.

Recommended design and alternatives

A clear match expression is a good first implementation. Using ok_or becomes idiomatic when it shortens a direct Option-to-Result conversion without hiding a decision. Using several nested combinators merely to avoid local names is not an improvement. The reference's intermediate unit and value variables make the two independent questions visible: is this operation dimensionally permitted, and does its numeric result fit?

Mastery means explaining the value of every expression in one successful and one failing path, including the Result wrapper. Passing tests over a few small numbers is evidence about those cases. Boundary tests add evidence about representational edges, but still do not prove every property over every i64. You should be able to identify a missing case and justify why it matters before claiming the calculator is complete.
