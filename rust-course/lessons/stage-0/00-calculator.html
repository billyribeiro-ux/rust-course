Build a checked calculator with units and useful errors

Finish a small program whose types, parser, library, and CLI share one explicit contract.

Purpose and design boundary

The complete calculator accepts exactly three arguments: a quantity, an operator, and another quantity. A quantity is a signed i64 with an optional m or s suffix. No suffix means a scalar. This is deliberately a small language: 2m is valid, 2.5m is not, and kilograms are not recognized. A narrow documented contract lets you complete a program rather than expand forever into a general scientific calculator. Your deliverable includes the behavior, tests, and a short explanation of what remains outside the model.

Model the unit as an enum because exactly three states are supported. A string can contain any text, so a function accepting arbitrary strings must repeatedly ask whether those strings are recognized. Once parsing constructs Unit::Meters, later code can rely on that recognized state. A Quantity groups value and unit so callers cannot accidentally pass the numeric part while losing the dimension. Public fields keep this first model simple; later projects use private fields where construction invariants require stronger protection.

Prediction: valid syntax can still be invalid meaning

Predict these operations before execution: 3m * 2, 3m * 2m, 8s / 2s, and 8 / 2s. The expected answers are 6m, an incompatible-unit error, 4, and an incompatible-unit error. All operands can be parsed. The failures concern the deliberately supported dimensional algebra. The program has no square-meter or inverse-second unit. Rejecting those expressions honestly is better than silently returning a result with an incorrect unit.

Guided build: three functions, three responsibilities

Start with parsing. FromStr for Quantity receives borrowed text and either produces a complete Quantity or CalcError::InvalidNumber. strip_suffix identifies an allowed suffix without indexing into UTF-8 by guessed character positions. Parsing the remainder as i64 delegates integer syntax and range checks to the standard library. The reference rejects surrounding whitespace explicitly, so command-line quotes cannot quietly change the language. Parsing is a boundary where untrusted text becomes a constrained domain value.

Next implement Quantity::apply. For addition and subtraction, require identical units before arithmetic. For multiplication, preserve the non-scalar unit if either operand is scalar. For division, preserve the left unit when the divisor is scalar, and cancel equal units to Scalar. Write the accepted table before writing match arms. The type checker ensures that every enum pattern you actually match is handled; it does not invent the correct dimensional rules for you.

Finally connect calculate and the entry point. calculate composes parsing and applying with ?. The question-mark operator returns early on an error; it does not swallow the error or make the operation infallible. main chooses how to present the result and which exit status to return. The reference prints successful output on standard output and errors on standard error so other programs can consume the successful result without scraping messages.

projects/reference/p01-calculator/src/lib.rs
//! Checked integer arithmetic with a deliberately small unit system.
//! ```
//! use workshop_calculator::calculate;
//! let result = calculate("12m", "+", "3m")?;
//! assert_eq!(result.to_string(), "15m");
//! assert!(calculate("12m", "+", "3s").is_err());
//! # Ok::<(), workshop_calculator::CalcError>(())
//! ```
use std::{fmt, str::FromStr};

pub mod conversion;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Unit {
    Scalar,
    Meters,
    Seconds,
}
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct Quantity {
    pub value: i64,
    pub unit: Unit,
}
#[derive(Clone, Debug, PartialEq, Eq)]
pub enum CalcError {
    InvalidNumber,
    UnknownOperator,
    IncompatibleUnits,
    Overflow,
    DivisionByZero,
}
impl fmt::Display for CalcError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(match self {
            Self::InvalidNumber => "expected an integer optionally followed by m or s",
            Self::UnknownOperator => "operator must be +, -, *, or /",
            Self::IncompatibleUnits => "units do not support this operation",
            Self::Overflow => "result is outside the i64 range",
            Self::DivisionByZero => "cannot divide by zero",
        })
    }
}
impl std::error::Error for CalcError {}
impl FromStr for Quantity {
    type Err = CalcError;
    fn from_str(input: &str) -> Result<Self, Self::Err> {
        let (number, unit) = if let Some(s) = input.strip_suffix('m') {
            (s, Unit::Meters)
        } else if let Some(s) = input.strip_suffix('s') {
            (s, Unit::Seconds)
        } else {
            (input, Unit::Scalar)
        };
        if number.is_empty() || number.trim() != number {
            return Err(CalcError::InvalidNumber);
        }
        Ok(Self {
            value: number.parse().map_err(|_| CalcError::InvalidNumber)?,
            unit,
        })
    }
}
impl fmt::Display for Quantity {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        let suffix = match self.unit {
            Unit::Scalar => "",
            Unit::Meters => "m",
            Unit::Seconds => "s",
        };
        write!(f, "{}{suffix}", self.value)
    }
}
impl Quantity {
    /// Integer division truncates toward zero. Products of two non-scalar units
    /// are deliberately unsupported; this is not a full dimensional algebra.
    pub fn apply(self, op: &str, rhs: Self) -> Result<Self, CalcError> {
        use CalcError::*;
        let (value, unit) = match op {
            "+" | "-" => {
                if self.unit != rhs.unit {
                    return Err(IncompatibleUnits);
                }
                (
                    if op == "+" {
                        self.value.checked_add(rhs.value)
                    } else {
                        self.value.checked_sub(rhs.value)
                    },
                    self.unit,
                )
            }
            "*" => {
                let unit = if self.unit == Unit::Scalar {
                    rhs.unit
                } else if rhs.unit == Unit::Scalar {
                    self.unit
                } else {
                    return Err(IncompatibleUnits);
                };
                (self.value.checked_mul(rhs.value), unit)
            }
            "/" => {
                let unit = if rhs.unit == Unit::Scalar {
                    self.unit
                } else if self.unit == rhs.unit {
                    Unit::Scalar
                } else {
                    return Err(IncompatibleUnits);
                };
                if rhs.value == 0 {
                    return Err(DivisionByZero);
                }
                (self.value.checked_div(rhs.value), unit)
            }
            _ => return Err(UnknownOperator),
        };
        Ok(Self {
            value: value.ok_or(Overflow)?,
            unit,
        })
    }
}
pub fn calculate(left: &str, operator: &str, right: &str) -> Result<Quantity, CalcError> {
    left.parse::<Quantity>()?.apply(operator, right.parse()?)
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn units_and_integer_division() {
        for (a, op, b, out) in [
            ("12m", "+", "3m", "15m"),
            ("3", "*", "4s", "12s"),
            ("7m", "/", "2m", "3"),
            ("-7", "/", "2", "-3"),
        ] {
            assert_eq!(calculate(a, op, b).unwrap().to_string(), out);
        }
    }
    #[test]
    fn recoverable_errors() {
        assert_eq!(
            calculate("1m", "+", "1s"),
            Err(CalcError::IncompatibleUnits)
        );
        assert_eq!(
            calculate("2m", "*", "2m"),
            Err(CalcError::IncompatibleUnits)
        );
        assert_eq!(calculate("1", "/", "0"), Err(CalcError::DivisionByZero));
        assert_eq!(
            calculate("9223372036854775807", "+", "1"),
            Err(CalcError::Overflow)
        );
        assert_eq!(
            calculate("-9223372036854775808", "/", "-1"),
            Err(CalcError::Overflow)
        );
        assert_eq!(calculate("1.5", "+", "2"), Err(CalcError::InvalidNumber));
    }
    #[test]
    fn exhaustive_small_addition_commutes() {
        for a in -20..=20 {
            for b in -20..=20 {
                let a = Quantity {
                    value: a,
                    unit: Unit::Meters,
                };
                let b = Quantity {
                    value: b,
                    unit: Unit::Meters,
                };
                assert_eq!(a.apply("+", b), b.apply("+", a));
            }
        }
    }
}

The entry point receives native operating-system arguments with args_os and explicitly accepts only valid UTF-8 calculator text. Invalid text becomes a usage error rather than an implicit panic in argument collection. Later file-based projects preserve native path values and convert only fields whose grammar requires text. This is a boundary decision already present in the recommended first project.

Intentional mistake and a focused repair

Introduce a bug only in your learner copy: allow any multiplication and keep the left unit. Then 3m * 2m becomes 6m, which is numerically plausible and dimensionally wrong. A test that checks only the number 6 misses the defect. Repair the rule before changing formatting. Add an assertion on the full result, including its unit or its specific error. The lesson is broader than physical units: tests must observe the part of the contract you could violate.

A second mistake is accepting an unknown operator by treating it as addition. This produces a reasonable-looking answer for invalid input. Exhaustive matching of known operators with an explicit error fallback makes the boundary visible. Unknown input should not select a successful operation accidentally. If you later add exponentiation, specify its unit and overflow behavior before adding a new branch.

Playbook: distinguish parsing from dimensional rules

Observation: 3m * 2m fails while 3m * 2 succeeds. Hypothesis A: the parser cannot read m suffixes. Hypothesis B: the multiplication rule rejects two dimensional operands. Keep the first operand and operator fixed; vary only the second suffix. Expected result: the scalar case succeeds. Then run 3m + 2m, expected 5m. These observations disprove A for m-suffixed integers and support B. The relevant code boundary is Quantity::apply, not FromStr.

For the investigation record, quote '*' in both commands so shell expansion cannot become a confounding variable. Record whether the message says invalid number or incompatible units. A label is useful evidence only if the implementation maps errors faithfully; inspect the branch once the experiment narrows it. Ask an AI reviewer to propose a test that would distinguish a swapped-unit bug from numeric overflow. Require its predicted outcomes before running the test.

Output failures belong to the first CLI contract

The calculation can succeed while writing its answer fails. In src/main.rs, run returns io::Result<ExitCode>: it preserves usage status 2 and domain status 1 when diagnostics can be written, while fallible writeln! and flush propagate sink failures. Main makes one best-effort diagnostic attempt and returns failure even if stderr is also closed. Do not replace these calls with println! to shorten the code; that changes an ordinary broken pipe into a panic. The actual child-process tests close the pipe's only reader before starting the calculator, which removes a scheduling race from the experiment.

The early checked-add executable needs to report either its typed arithmetic error or an output error. Its Result<(), Box<dyn std::error::Error>> boundary can carry either error to process termination. Box owns that error value, and dyn Error means any type implementing the standard error interface; Stage 2 explains these types fully. This small executable boundary does not erase the library's Number versus Overflow distinction.

When you get stuck: independent work and tiered help

Implement a remainder operator in your scaffold under an explicit contract: same-unit operands produce a remainder in that unit; a zero divisor is rejected; overflow is handled with checked_rem. Write examples for negative operands and explain Rust's remainder behavior. Do not silently broaden multiplication while making this unrelated change. Review, evidence, and mastery

The recommended implementation gives parsing to FromStr, presentation to Display, and domain operations to a small library. These standard traits express familiar concepts and support testing without launching a process. Direct helper functions would also be sound for a private one-off calculation, but the public parse and formatting interfaces are useful here. A command-line parsing library becomes worthwhile when options, subcommands, or generated help replace the current exact three-argument contract.

Your mastery demonstration is a short change request: explain the current grammar, add a justified test, implement one well-scoped extension, and identify a non-goal. Run both unit tests and the CLI check after the change. Passing them demonstrates the asserted cases and process behavior; it does not establish a complete physical-units system. Explain that limit in the README as part of the implementation rather than treating it as an embarrassing omission.

Engineering decisions and evidence

Requirements and invariants

Three CLI arguments describe signed i64 quantities and one supported operator. Every successful result has a supported unit and representable numeric value. Addition and subtraction require equal units; products need a scalar; equal units cancel during division. Ordinary invalid input returns a typed error and a nonzero exit, without panicking.

Chosen design and concrete habits

Quantity and Unit carry the domain model; FromStr handles text; checked arithmetic enforces range; Display presents quantities and errors; main owns stdout, stderr, and exit status. The first runnable checkpoint already uses Result-based failure handling. Documentation examples propagate errors with ?, and assertion-only test unwraps express known expected successes. No dependency is needed to express this small contract.

Meaningful alternative and evolution threshold

A dimensional type system or units library would prevent more combinations statically, at the cost of a more complex generic model. Adopt one when quantities enter a larger scientific calculation or compound dimensions are required. A CLI framework becomes justified by options and subcommands; fractional measurements require a deliberately specified numeric representation, not a formatting patch.

Actual checks and remaining uncertainty

Native unit, CLI integration, and documentation tests passed in verification/native-tests.log. The patch audit reran all five foundation packages after documentation and CLI boundary changes; all 29 checks passed in verification/patch001-foundations-tests.log. Covered cases include overflow, minimum divided by -1, unit rejection, truncating division, argument count, and exit streams. Finite small-domain checks do not prove all i64 arithmetic or all shell invocations. Independent review is pending.
