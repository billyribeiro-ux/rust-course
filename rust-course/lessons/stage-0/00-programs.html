Your first Rust programs: values, functions, choices, and loops

Trace a greeting and a checked whole-cent calculation, then use predictions and boundary tests to explain how small Rust programs execute.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Files, terminal navigation, and a reviewed Git snapshot
  • Read and run a minimal main function and distinguish compiler errors from runtime outcomes.
  • Explain bindings, integer types, mutability, and decimal versus binary notation.
  • Write small typed functions and explain expression returns and semicolons.
  • Trace if, match, for, and while, including branch boundaries and loop termination.
  • Test an independent rule change and disprove a plausible explanation for wrong output.

Purpose: turn a small rule into an executable program

Before building the calculator, we will make Rust's basic building blocks visible. You will read a tiny greeting, then a small packing-cost demonstration with named values, functions, choices, and repetition. Every line has a purpose you can explain. The input is fixed inside the example so you can concentrate on execution. Reading arbitrary terminal input is a separate problem taught later. The recommended calculation already handles its integer boundary explicitly; correctness is part of the first version.

Keep the practice package created in the workspace lesson. Reference-run commands below start in the course's projects directory. Learner-edit commands start in learner-work/foundations-lab, which is a separate package. Check pwd at every transition. A program is not the text visible in whichever editor tab happens to be active; Cargo reads saved files belonging to the package you select.

The smallest runnable example

projects/reference/p01-calculator/examples/hello.rs
use std::io::{self, Write};

fn main() -> io::Result<()> {
    let mut output = io::stdout().lock();
    writeln!(output, "Hello, Rust workshop!")?;
    output.flush()
}

mise exec -- cargo run -p workshop-calculator --example hello

fn introduces a function, a named piece of work. main starts this executable. Empty parentheses mean no parameters; braces enclose the body. Double quotes enclose text. writeln! formats text and adds a newline; the exclamation mark identifies a macro, a Rust facility accepting code-like input. Here it writes to the explicitly named output. Predict the greeting before running: Hello, Rust workshop!.

Output is an operation that can fail: the next program in a terminal pipeline may close its read end. use std::io::{self, Write}; makes the standard I/O module and its writing methods available. stdout() identifies normal process output; lock() gives this small program a writing handle. let mut output names the handle and permits writing through it. The arrow and io::Result<()> say main returns either success without extra data or an I/O error. ? continues on success and returns the error on failure. The last expression, output.flush(), sends any pending buffered output onward and becomes main's result. Rust reports a returned error and a failing process exit; it does not turn this ordinary failure into a panic.

You do not need to invent an error framework for this greeting. This small Result boundary is enough. The familiar println! convenience macro panics if its output write fails, so our recommended commands use fallible writeln! from their first output. A successful flush does not prove a downstream program read or acted on the message. Detailed Result matching comes in the calculator; keep the immediate rule now: an operation that may fail needs an explicit path for that failure.

Cargo first asks the compiler to build when necessary, then launches the resulting executable. A compiler error prevents that new program from running. A runtime result happens after a valid executable starts: it might print a greeting, reject an input, or encounter an environmental failure. Successful compilation establishes important language rules, but it cannot establish that a delivery fee matches your intended policy. That requires a clear rule and evidence from examples or tests.

Values, bindings, and types

A value is a particular item of data, such as the integer 3 or the Boolean true. A binding gives a value a name. In let quantity: u32 = 3;, let introduces the binding, the colon supplies its type, and = initializes it. u32 means an unsigned, 32-bit integer: a whole number from zero through 4,294,967,295. “Unsigned” means it has no negative values. A type describes which values and operations are valid; it is not just a display label.

Ordinary bindings are immutable: you cannot assign a different value to that same binding unless you declared it mut. Use mutability when the algorithm actually changes state, such as a countdown. Avoid adding it everywhere “just in case.” Rust can often infer a type from surrounding code, but we write important units and integer types explicitly here. A name ending in _cents records the unit for a human reviewer. It does not magically stop another integer unit being passed; stronger domain types arrive later.

Decimal and binary are two ways to write an integer

Decimal notation uses powers of ten: 125 means one hundred, two tens, and five ones. Binary notation uses powers of two and only the digits zero and one. In 0b0011, the prefix 0b tells Rust to read binary digits. The four positions represent eight, four, two, and one. Thus 0011 means zero eights plus zero fours plus one two plus one one: three. Leading zeroes do not increase the value.

Writing 3 or 0b0011 with the same integer type produces the same value. Binary notation does not make this program run faster. In formatting, {quantity} prints ordinary decimal digits and {quantity:b} prints binary digits. The displayed characters differ; the stored value has not changed. Do not confuse a decimal base with a fractional number: 125 is an integer written in decimal, while 1.25 is fractional. This example represents money in whole cents, so 125 cents is represented exactly without introducing floating-point rounding.

Decompose the problem before reading the implementation

Our rules are small and explicit. Each item costs 125 cents. The demonstration contains three items. A nonempty order has a 250-cent delivery fee; an empty order has no fee. Multiplying price by quantity must return either the exact representable subtotal or an explicit absence of a subtotal. Printing a packing step does not actually move a package or charge a customer. This is a fixed-data teaching executable, not an order-processing service.

Separate the work into three questions: how to compute a subtotal, how to choose a delivery fee, and how to present the steps. Those become two small calculation functions plus main. A function should have an understandable contract: the meaning of its inputs and result. The calculations do not print, read files, or change shared state, so we can check their rules directly. Before running, write down the expected quantity, subtotal, fee, packing numbers, and countdown numbers.

Run and trace the complete example

projects/reference/p01-calculator/examples/workshop_basics.rs
use std::io::{self, Write};

// Monetary amounts in this example are whole cents; fractions are not accepted.
fn subtotal_cents(unit_price_cents: u32, quantity: u32) -> Option<u32> {
    unit_price_cents.checked_mul(quantity)
}

fn delivery_fee_cents(quantity: u32) -> u32 {
    if quantity == 0 { 0 } else { 250 }
}

fn main() -> io::Result<()> {
    let mut output = io::stdout().lock();
    let unit_price_cents: u32 = 125;
    let quantity: u32 = 0b0011;
    writeln!(output, "quantity: {quantity} (binary {quantity:b})")?;

    let subtotal = match subtotal_cents(unit_price_cents, quantity) {
        Some(value) => value,
        None => {
            return Err(io::Error::new(
                io::ErrorKind::InvalidInput,
                "subtotal does not fit in u32 cents",
            ));
        }
    };
    writeln!(output, "subtotal cents: {subtotal}")?;
    writeln!(output, "delivery cents: {}", delivery_fee_cents(quantity))?;

    for item_number in 1..=quantity {
        writeln!(output, "pack item {item_number}")?;
    }

    let mut remaining = 2_u32;
    while remaining > 0 {
        writeln!(output, "checks remaining: {remaining}")?;
        // The loop condition proves that subtracting one cannot underflow.
        remaining -= 1;
    }
    writeln!(output, "ready")?;
    output.flush()
}

#[cfg(test)]
mod tests {
    use super::{delivery_fee_cents, subtotal_cents};

    #[test]
    fn subtotal_uses_whole_cents_and_handles_zero_quantity() {
        assert_eq!(subtotal_cents(125, 3), Some(375));
        assert_eq!(subtotal_cents(u32::MAX, 0), Some(0));
    }

    #[test]
    fn subtotal_rejects_overflow_without_wrapping() {
        assert_eq!(subtotal_cents(u32::MAX, 1), Some(u32::MAX));
        assert_eq!(subtotal_cents(u32::MAX, 2), None);
    }

    #[test]
    fn delivery_is_charged_only_for_nonempty_orders() {
        assert_eq!(delivery_fee_cents(0), 0);
        assert_eq!(delivery_fee_cents(1), 250);
        assert_eq!(delivery_fee_cents(u32::MAX), 250);
    }
}

mise exec -- cargo test -p workshop-calculator --example workshop_basics --locked

subtotal cents: 375
delivery cents: 250
pack item 1
pack item 2
pack item 3
checks remaining: 2
checks remaining: 1
ready

Each parameter is named and typed in the function definition. Calling subtotal_cents(125, 3) supplies arguments for those parameters in that order. The arrow -> announces the return type. Option<u32> describes two possibilities: Some(number) contains a subtotal, while None contains no subtotal. Here checked_mul, a standard integer method, returns None if multiplication would exceed u32. Zero remains a valid subtotal, distinct from failure.

The last expression in subtotal_cents is the checked multiplication, with no trailing semicolon. Its resulting value becomes the function's result. Adding a semicolon there would discard that value as a statement and leave the body returning (), the unit value. Unit is useful when there is no result data, but it does not satisfy the promised Option<u32>. A function's result is therefore part of its contract, not whatever happened to be printed.

main uses match to handle both possible results. The Some(value) arm names the successful number; its expression supplies the surrounding subtotal binding. The None arm constructs an explicit invalid-input error and returns it. io::Error::new records an error category and a human-readable cause. Returning Err(...) makes the command fail; returning the final successful flush makes it succeed. Double colons separate items in a Rust path. The calculation functions remain independent of output, so their numeric tests do not need a terminal.

Choices and loops, with their stopping conditions

delivery_fee_cents uses if as an expression. The test quantity == 0 produces a Boolean, either true or false. Double equals compares; a single equals initializes or assigns. The selected branch returns either zero or 250. Both branches supply the same type, u32. Rust does not treat an arbitrary integer as a Boolean condition. Writing if quantity is a type error rather than an implicit test for nonzero.

The for loop visits each number in 1..=quantity. The equals sign makes the upper end inclusive, so three items produce steps one, two, and three. By contrast, 1..quantity excludes the upper end and would print only one and two here. A range is a description of values to visit, not a preallocated array containing every number. For a zero quantity, this ascending inclusive range produces no packing steps.

The while loop repeats while its condition is true. remaining starts at two and is declared mutable because it changes. Each iteration prints the current number and subtracts one. The condition proves the subtraction cannot go below zero: the body runs only when the unsigned integer is positive. Reaching zero makes the next condition false and stops repetition. A loop repeats until an explicit break or function return; we prefer the bounded range for known item counts and the visible condition for this countdown. Every loop deserves an explanation of progress and stopping.

Guided checkpoint: rebuild understanding in your own package

In your learner-work/foundations-lab package, create an examples directory if it does not exist. Add a new examples/hello.rs using the complete greeting above; do not replace an existing file of that name. Run mise exec -- cargo run --example hello from that package. Change only the greeting text in your newly created file, save, predict its output, and rerun. Review the diff to verify which file changed. You now have a direct connection from a saved source edit to an observable result.

Next create a new examples/workshop_basics.rs in that same learner package and enter the reference example in sections. First add the two calculation functions and explain their contracts. Then add main and the I/O import, pausing to predict each written line and explain each ?. Finally add the tests. A test is a function marked #[test]; assert_eq! requires two values to match. The #[cfg(test)] module is compiled for testing, and use super::... gives its tests access to the surrounding functions. You are not expected to design module systems yet; use this small grouping to keep checks beside their rules.

Check that the test names describe the intended rule, including zero quantity and overflow. Explain why testing the largest representable price times one and times two probes a boundary. Passing only the familiar 125-times-three example would leave the overflow policy unexamined. Keep the helper functions independent of printing so that these tests observe their actual returned values.

Intentional mistake: a semicolon changes the result

Only in your learner copy, deliberately add a semicolon after unit_price_cents.checked_mul(quantity). Predict whether it changes the arithmetic, prints another line, or prevents compilation. Run mise exec -- cargo check --example workshop_basics. Expect error E0308, a mismatch between the declared result and the unit result. Read the expected and found types, then remove that one semicolon and check again. This exercise is intentionally broken code; retaining the broken variant is not a recommended implementation.

Playbook investigation: why did an item disappear?

Use the central playbook and deliberately change the learner copy's inclusive range to 1..quantity. The observation is “quantity prints three, but only two packing lines appear.” Plausible hypotheses are “the binary literal meant two,” “the range excludes its last value,” and “the loop stopped because arithmetic overflowed.” First print the quantity in decimal and binary as the example already does. Its value of three disproves the first hypothesis without changing the loop. The successful checked subtotal and normal exit also make the proposed overflow explanation inconsistent with this execution.

Now change only the range back to inclusive and rerun the same input. Three packing lines support the boundary explanation. Test quantity zero and one in your learner copy as additional cases; record the predicted count before each run. The fix is justified by the policy “one step for every item,” not by a wish to obtain a green terminal. These observations cover chosen inputs. They do not establish that an unlimited user-supplied quantity would be an acceptable workload; adding user input would require a deliberate quantity limit.

Independent practice and tiered hints

In your learner copy, change the delivery rule: empty orders cost zero, one through three items cost 250 cents, and four or more cost 400 cents. State the rule in your own words before editing. Add checks at zero, one, three, and four, then explain why three and four are more informative than two ordinary middle values. Keep the result type and whole-cent unit explicit. Make a reviewed commit containing the rule, code, tests, and your investigation note. This is an extension to the current runnable reference, whose nonempty fee remains 250.

Hint 1: identify the boundaries

The first boundary separates zero from positive quantities. The second separates three from four. List the expected fee for both sides of each boundary before choosing syntax.

Hint 2: choose branches in order

Use an initial empty-order test, then else if quantity <= 3, then the remaining branch. All branches must produce a u32. A match with ranges is another reasonable approach after you have learned its syntax.

Reference approach after your attempt
fn delivery_fee_cents(quantity: u32) -> u32 {
    if quantity == 0 {
        0
    } else if quantity <= 3 {
        250
    } else {
        400
    }
}

This proposed extension leaves the subtotal's checked arithmetic unchanged. Boundary checks should require fees 0, 250, 250, and 400 for quantities 0, 1, 3, and 4. A reviewer should ask why the branch order matters and what a quantity cap would change, rather than accepting copied code as proof of understanding.

Engineering decisions, evidence, and limits

The implementation uses immutable bindings for fixed inputs, a mutable binding only for the countdown, whole-cent integers for exact units, checked multiplication for a real boundary, and explicit success or failure at the process boundary. These choices fit a small fixed-data executable. A wider integer type would move the multiplication boundary without removing it. A decimal library might fit fractional monetary requirements, but it would add machinery with no current requirement. Accepting external orders would require validation, workload limits, and stronger domain modeling before calling this an application.

The companion example has three meaningful tests covering normal arithmetic, zero quantity, overflow, and fee boundaries, and its exact reference output was executed through mise; the verification log records the commands and results. The deliberate semicolon diagnostic is separately recorded. The later output follow-up executes the actual greeting, packing example and roundoff example with a pipe whose only read end was closed before process startup. Each returns failure without a panic; ordinary output is checked separately. This is author verification, with independent review pending. Neither these tests nor compilation proves an unrestricted shop system correct; no such system is claimed.

When you get stuck

Reduce the question to one saved file and one command. Use mise exec -- rustc --explain E0308 for a type mismatch, then compare the function's arrow type with its final expression. For wrong output, write a paper trace of the values before and after one iteration. Consult the pinned Book chapters on functions and control flow. Ask for review with the expected output, actual output, smallest changed diff, and one hypothesis you have already disproved. “It doesn't work” omits the evidence a reviewer needs.

Mastery check

Without the reference open, explain the difference between a value and its printed notation; convert binary 101 to decimal five; predict the result of adding a semicolon to a returned expression; choose an inclusive or exclusive range for a stated rule; and explain why the countdown terminates safely. Then write and test the new fee rule independently. You are ready for the calculator when you can connect the policy, the function's types, the branch boundaries, and the observed evidence.
