Fuzz the parser, and test your own assumptions

Run bounded coverage-guided fuzzing, investigate a false oracle, preserve a minimal reproducer and turn evidence into a regression.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Evaluate safely and test properties without overstating them
  • Tests are executable claims
  • Stream logs with bounded lines and honest accounting
  • Distinguish finite property checks from coverage-guided fuzzing
  • Write contract-based fuzz oracles for spans, depth and determinism
  • Reproduce and reduce a failure while revising a false UTF-8 assumption
  • Keep nightly instrumentation, evolving corpora and finite resource limits explicit

Purpose: find inputs you did not think to write

The expression parser accepts text from a caller. Ordinary examples cover arithmetic we already understand; malformed text is a much larger space. Fuzzing repeatedly changes inputs and looks for a violated property, panic or other configured failure. It is useful when a small deterministic function has many possible inputs and can be exercised cheaply. This lesson applies a real coverage-guided fuzzer to the parser rather than calling a loop over a few hand-picked cases fuzzing.

Plain-English model: a generator and a judge

A fuzz target is a small program that receives generated bytes and calls the code under investigation. The engine here is libFuzzer, driven by cargo-fuzz. Instrumentation records parts of the compiled program reached by each input, helping the engine retain interesting inputs and mutate them. A corpus is that collection of useful inputs. A seed is an initial example. Neither word implies random inputs are uniformly distributed.

The target's assertions are its oracle: the rules used to judge behavior. An oracle can be wrong. A crash report establishes that the executed program failed under that input; it does not establish that the library under test caused the defect. This distinction matters when an AI writes a plausible but false assertion. Read the invariant and the assertion before changing working library behavior to make a test pass.

Property tests and fuzzing overlap in purpose but use different exploration strategies. The parser's existing finite integer loops enumerate a small domain and compare evaluation with independent Rust arithmetic. This fuzz target explores byte sequences and checks diagnostic ranges, bounded tree depth and repeated evaluation. It does not have an independent implementation of every grammar rule. Passing it would not detect a consistently wrong precedence rule unless another assertion exposed that rule.

Prediction: what should happen to Unicode?

The input is 2+🦀. The language does not accept that character as an operand. Predict whether parsing should panic, return an error spanning one byte, or return an error spanning the complete character. Then predict whether rejecting invalid UTF-8 at the target boundary prevents all Unicode inputs from reaching the parser.

Prediction explained

The parser should return an ordinary error. The crab occupies four UTF-8 bytes, so its byte span is 2..6. A byte and a character are different units. Valid UTF-8 includes multibyte characters; rejecting invalid UTF-8 merely matches the parser's &str input contract. It does not restrict inputs to ASCII. A one-byte assertion can fail even when the parser's diagnostic is correct.

An environmental compiler error is a failed setup step, not a discovered parser input.

experiments/expression-fuzz/fuzz_targets/expression.rs
#![no_main]
use expression_language::{MAX_DEPTH, Span, parse};
use libfuzzer_sys::fuzz_target;

fn valid_span(source: &str, span: Span) {
    assert!(span.start <= span.end && span.end <= source.len());
    assert!(source.is_char_boundary(span.start));
    assert!(source.is_char_boundary(span.end));
    // Rendering this range is safe when the diagnostic contract is satisfied.
    let _highlight = &source[span.start..span.end];
}
fuzz_target!(|data: &[u8]| {
    let Ok(source) = std::str::from_utf8(data) else {
        return;
    };
    match parse(source) {
        Ok(tree) => {
            valid_span(source, tree.span());
            assert!((1..=MAX_DEPTH).contains(&tree.depth()));
            let first = tree.evaluate();
            assert_eq!(first, tree.evaluate());
            if let Err(error) = first {
                valid_span(source, error.span);
            }
        }
        Err(error) => valid_span(source, error.span),
    }
});

Explain each boundary and assertion

#![no_main] lets the harness provide the executable entry point. The fuzz_target macro arranges for libFuzzer to call the closure with each byte slice. from_utf8 checks the boundary required by &str without allocating a replacement string; lossy conversion would test altered input and obscure the original bytes. Invalid UTF-8 is outside this particular parser API and returns from the target.

On parser success, the target checks that the exposed tree span is ordered, inside the original input and aligned to UTF-8 boundaries. It also checks the documented depth bound. Evaluating the same immutable tree twice must give the same Result because this evaluator has no clock, randomness or external state. Arithmetic errors are valid outputs. The target checks their ranges rather than insisting every syntactically valid expression has a successful value.

On parser failure, a diagnostic span still must be safe for a caller to highlight. The target actually slices that range after validating it. This links the assertion to a real consumer operation. An empty range at end of input can be correct for a missing token, so an assertion demanding a nonempty range would be another false oracle. Each assertion expresses the public contract; it does not restate an internal branch merely to improve a test count.

Deliberate mistake: an incorrect test oracle

The separate bad-oracle target is intentionally wrong and must not become recommended test code. It claims an unexpected character always spans one byte. Run it explicitly:

python3 scripts/fuzz-expression.py --target bad-oracle --runs 100

Expected result: a nonzero exit and a saved crash input. The recorded seed 2+🦀 failed immediately with left 4 and right 1; the harness process reported status 77 and cargo-fuzz returned failure. This is expected evidence for the exercise. It does not contradict the successful recommended campaign.

Inspect the intentionally wrong target
experiments/expression-fuzz/fuzz_targets/bad_oracle.rs
#![no_main]
// INTENTIONAL TEST-ORACLE BUG. The parser supports UTF-8 diagnostic byte spans.
// A Unicode character may occupy more than one byte. Do not adopt this assertion.
use libfuzzer_sys::fuzz_target;
fuzz_target!(|data: &[u8]| {
    let Ok(source) = std::str::from_utf8(data) else {
        return;
    };
    if let Err(error) = expression_language::parse(source) {
        if error.message == "unexpected character" {
            assert_eq!(
                error.span.end - error.span.start,
                1,
                "INTENTIONALLY WRONG: each character occupies one byte"
            );
        }
    }
});

Playbook investigation: challenge the first hypothesis

Observation: a fuzz log says assertion failure in bad_oracle.rs. Initial hypothesis: the lexer advanced too far and should report one byte. Competing hypothesis: the assertion confuses character count with byte count. Preserve the failing input before editing. Reproduce with that exact file, inspect the span and measure the UTF-8 length. The byte sequence f0 9f a6 80 represents the crab; taking just one byte would create an invalid string boundary.

Reduce the input manually to 🦀. The prefix 2+ is unnecessary to reproduce the false assertion. The smaller case weakens the theory that operator precedence or the parser's binary-node handling caused the failure. The smallest sound fix is to remove the one-byte assumption and check valid byte boundaries, as the recommended target does. Altering the lexer to emit a one-byte range would hide the assertion failure while breaking diagnostic rendering.

Capture the lesson as a report: expected ordinary error, observed failing oracle, exact input bytes, versioned command, competing hypotheses, decisive UTF-8 evidence, corrected invariant and regression. A useful review request includes that report and a minimal input rather than thousands of console lines. Seek review when the asserted contract remains ambiguous or a safety boundary is involved, rather than repeatedly editing unrelated parser code.

Guided project checkpoint: make a finding reproducible

Retain the recommended target unchanged and run its corpus. Locate the saved bad-oracle artifact in the helper's printed directory. To replay a particular input, pass that file as the corpus argument to cargo fuzz run, preserving the same fuzz directory and target directory options printed by the helper. It executes the input without relying on rediscovery. For automatic reduction, cargo fuzz tmin uses the target and failing file; first read its version-matched --help and keep a copy of the original evidence.

Add an ordinary deterministic regression assertion to your learner parser tests for the minimized case: parsing a crab returns a range of 0..4 that can be sliced safely. A unit test preserves a particular discovered boundary with a quick stable-toolchain check. Keep the fuzz oracle for future exploration. The reference already tests a multibyte unexpected character; your task is to justify its expected range independently.

Independent practice and tiered hints

Add seeds that approach source length, token count, unary nesting and left-associated tree depth independently. Explain why a 100-byte input need not have 100 tokens. Design a property that detects a wrong associativity rule without rejecting legitimate division-by-zero errors. Decide whether another target should generate syntactically valid expressions instead of arbitrary bytes, and name the coverage tradeoff.

Hint 1: separate validity from evaluation

A string can be valid UTF-8, valid language syntax, and still evaluate to an error. Write three examples, one failing each boundary. Do not flatten these categories into one Boolean success assertion.

Hint 2: use an independent expected value

Choose a bounded small integer domain where Rust operations cannot overflow. Subtraction is not associative: compare unparenthesized operations a-b-c with the independently computed Rust value (a-b)-c. Parentheses around an individual negative operand are fine; do not parenthesize the operation grouping you want to test. Avoid using the parser to calculate both expected and actual values.

Reference approach

A structured target can derive a, b and c from small input bytes and compare a-b-c with the independently computed value (a-b)-c. For example, 8-3-2 should be 3; a right-associative evaluator gives 7. The finite property test in the reference now covers this subtraction relationship across its small integer domain. A separate (a+b)*c property tests grouping, not associativity. A byte target remains useful for malformed text and diagnostic boundaries. Keep both because generating only valid syntax can miss error-path panics, while arbitrary bytes may rarely reach deep valid syntax. When input limits change, extend tests at the new boundary before increasing campaign size.

When you get stuck

Read the earliest failing boundary: tool installation, instrumented compilation, seed execution, or target assertion. Use mise exec cargo:cargo-fuzz@0.13.2 -- cargo fuzz run --help for this installed version. Preserve a crash artifact and its command; a later randomized run may not rediscover it. The two source files make the difference between a recommended oracle and a deliberate mistake explicit.

Engineering decisions, evidence and mastery

The parser is deterministic, bounded and free of external I/O, making a focused fuzz harness inexpensive. The target borrows input and uses the public API. There is no service, database or asynchronous runtime to distract from the contract. A separate workspace and dated nightly keep instrumentation flags out of ordinary stable builds; exact dependency versions and a lockfile preserve the experiment's dependency graph.

Evidence includes the 10,000-input instrumented campaign and the intentionally failing oracle with its preserved input. AddressSanitizer and assertions can find defects reached during this run; they do not prove all inputs safe, all grammar rules correct, or all unsafe code sound. Longer campaigns, structure-aware generation and additional independent semantic oracles would be justified if this language accepted untrusted production workloads.

Mastery requires explaining the wrong hypothesis, reproducing the finding, defending a corrected oracle, writing the regression without copying its expected value blindly, and naming an untested claim. A green fuzz exit alone does not pass this lesson.
