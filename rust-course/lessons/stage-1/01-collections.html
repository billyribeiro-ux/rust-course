Tuples, arrays, vectors, and maps with explicit contracts

Choose a container by ownership, operations, ordering, and bounds; build a deterministic label report and explain scalar versus compound values.

Purpose: choose a collection by the question it answers

The journal owns several tasks, and the log analyzer will count repeated categories. Before building those larger operations, learn the containers themselves. A fixed set of four measurements, an expandable sequence of tasks, and counts indexed by a label are different requirements. This lesson gives each a small explicit model, then connects ownership, lookup, ordering, and bounds to that choice. We will also fill in the scalar and compound vocabulary used throughout Rust documentation.

The runnable lab accepts at most 64 labels with at most eight distinct names. Names contain one through sixteen lowercase ASCII letters. It returns owned count rows in lexical order. Those limits are part of the contract, not assumptions hidden in a test fixture. The function builds a local result and publishes it only on success, so a rejected batch cannot expose a half-finished report.

Model: a scalar value or a compound value

A scalar represents one value: an integer, a floating-point number, a Boolean, or a char. You have used signed i64, unsigned u32, and bool. Signed integers permit negative values; unsigned ones do not. The number in an integer type is its bit width. usize is an unsigned, target-sized integer used for lengths and indexes. It is not a portable file-format field whose width you can assume. The earlier fractional converter introduces f64 and its approximation limits.

A Rust char, written with single quotes such as 'é', is one Unicode scalar value. A string, written with double quotes, contains UTF-8 encoded text. One scalar can occupy several UTF-8 bytes, and one user-perceived symbol can contain several scalars. Therefore “one char,” “one byte,” and “one visible symbol” are different claims. The example prints two UTF-8 bytes for 'é'. Our category grammar deliberately accepts ASCII letters, making its byte limit and accepted-character count coincide. The journal's broader UTF-8 title policy remains a separate contract.

A compound value groups other values. A tuple has a fixed number of positions, and its positions can have different types: (String, u32) pairs an owned label with its count. Access positions with .0 and .1, or destructure with let (label, count) = row;. A one-element tuple needs a comma, (value,); parentheses around value alone merely group an expression. The empty tuple () is the unit value encountered in function returns.

Arrays, vectors, and slices

An array has a fixed length and one element type. [i32; 4] means four signed 32-bit integers; [12, -8, 15, 9] constructs such an array. Length is part of its type, so an array of three values cannot replace an array of four in a parameter requiring exactly four. A vector, Vec<i32>, owns a growable sequence. vec![12, -8] creates one, and push appends. Its length is the number of initialized elements; its capacity concerns allocated room. They are related but not interchangeable.

A slice, &[i32], borrows a sequence without owning it or fixing its length in the function signature. Both an array and a vector can supply that view. Our sample_bounds needs to inspect values, not resize or retain their container, so it accepts a slice. This is a useful API habit: request the capability you need. Do not require &Vec<i32> when an array-backed caller can satisfy the same operation.

Indexing with values[index] requires a valid index and panics if it is out of bounds. A user-chosen index should normally go through get, returning Option. The lab's extrema function uses split_first to distinguish an empty slice before reading an element. It then compares each remaining value. This avoids inventing a “minimum” of zero, which would be wrong for an all-positive input, and avoids assuming there is always a first element.

projects/reference/p18-core-labs/src/collections.rs
use std::collections::HashMap;
use std::fmt;

pub const MAX_ITEMS: usize = 64;
pub const MAX_LABELS: usize = 8;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum LabelError {
    TooManyItems,
    InvalidLabel,
    TooManyLabels,
}
impl fmt::Display for LabelError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(match self {
            Self::TooManyItems => "at most 64 input items are supported",
            Self::InvalidLabel => "labels must contain 1 to 16 lowercase ASCII letters",
            Self::TooManyLabels => "at most 8 distinct labels are supported",
        })
    }
}
impl std::error::Error for LabelError {}

/// The borrowed slice can come from an array or a Vec. Empty input has no extrema.
pub fn sample_bounds(samples: &[i32]) -> Option<(i32, i32)> {
    let (&first, rest) = samples.split_first()?;
    let mut low = first;
    let mut high = first;
    for &sample in rest {
        low = low.min(sample);
        high = high.max(sample);
    }
    Some((low, high))
}

/// Count a bounded batch and return owned rows in lexical label order.
/// Input borrows stay local; rejected input exposes no partial result.
pub fn count_labels(labels: &[&str]) -> Result<Vec<(String, u32)>, LabelError> {
    if labels.len() > MAX_ITEMS {
        return Err(LabelError::TooManyItems);
    }
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for &label in labels {
        if label.is_empty() || label.len() > 16 || !label.bytes().all(|b| b.is_ascii_lowercase()) {
            return Err(LabelError::InvalidLabel);
        }
        if !counts.contains_key(label) && counts.len() == MAX_LABELS {
            return Err(LabelError::TooManyLabels);
        }
        let count = counts.entry(label).or_insert(0);
        // Every increment corresponds to one input item, and MAX_ITEMS is 64.
        *count += 1;
    }
    let mut rows = Vec::with_capacity(counts.len());
    for (label, count) in counts {
        rows.push((label.to_owned(), count));
    }
    rows.sort_unstable_by(|left, right| left.0.cmp(&right.0));
    Ok(rows)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn arrays_and_vectors_share_a_slice_contract() {
        let fixed = [12, -8, 15, 9];
        let variable = vec![12, -8, 15, 9];
        assert_eq!(sample_bounds(&fixed), Some((-8, 15)));
        assert_eq!(sample_bounds(&variable), sample_bounds(&fixed));
        assert_eq!(sample_bounds(&[]), None);
        assert_eq!(sample_bounds(&[i32::MIN]), Some((i32::MIN, i32::MIN)));
    }

    #[test]
    fn repeated_labels_are_counted_and_rows_are_deterministic() {
        let expected = vec![("api".to_owned(), 2), ("worker".to_owned(), 1)];
        assert_eq!(
            count_labels(&["worker", "api", "api"]),
            Ok(expected.clone())
        );
        assert_eq!(count_labels(&["api", "worker", "api"]), Ok(expected));
        assert_eq!(count_labels(&[]), Ok(vec![]));
    }

    #[test]
    fn item_distinct_and_text_boundaries_are_independent() {
        assert_eq!(
            count_labels(&["api"; MAX_ITEMS]),
            Ok(vec![("api".into(), 64)])
        );
        assert_eq!(
            count_labels(&["api"; MAX_ITEMS + 1]),
            Err(LabelError::TooManyItems)
        );
        let eight = ["a", "b", "c", "d", "e", "f", "g", "h"];
        assert_eq!(count_labels(&eight).unwrap().len(), MAX_LABELS);
        assert_eq!(
            count_labels(&["a", "b", "c", "d", "e", "f", "g", "h", "i"]),
            Err(LabelError::TooManyLabels)
        );
        for bad in ["", "API", "a b", "é", "abcdefghijklmnopq"] {
            assert_eq!(count_labels(&["valid", bad]), Err(LabelError::InvalidLabel));
        }
        assert!(count_labels(&["abcdefghijklmnop"]).is_ok());
    }

    #[test]
    fn result_owns_its_labels_after_input_is_gone() {
        let rows = {
            let label = String::from("api");
            count_labels(&[label.as_str()]).unwrap()
        };
        assert_eq!(rows, [("api".into(), 1)]);
    }
}
projects/reference/p18-core-labs/examples/collections.rs
use core_rust_labs::collections::{LabelError, count_labels, sample_bounds};

fn main() -> Result<(), LabelError> {
    let fixed = [12, -8, 15, 9];
    let mut variable = vec![12, -8];
    variable.push(15);
    variable.push(9);
    let marker: char = 'é';
    let same_length: bool = fixed.len() == variable.len();
    println!(
        "same length: {same_length}; marker UTF-8 bytes: {}",
        marker.len_utf8()
    );
    println!("array bounds: {:?}", sample_bounds(&fixed));
    println!("vector bounds: {:?}", sample_bounds(&variable));
    for (label, count) in count_labels(&["worker", "api", "api"])? {
        println!("{label}: {count}");
    }
    Ok(())
}

HashMap associates a key with a value. Here a borrowed label is the key and a count is the value. Lookup asks “what count belongs to this label?” rather than “what sits at sequence position three?” The map's iteration order is not a stable presentation contract. We explicitly sort the final rows before returning them. That makes report order independent of the map's internal arrangement and of the input order for this counting task.

entry(label).or_insert(0) finds the existing count or inserts zero and returns access to that count. The dereference *count updates the number, not the local reference itself. The increment cannot overflow here: at most 64 input items can contribute. That local proof justifies ordinary addition. It would need revisiting if the API became an unbounded stream with a retained counter. A checked operation is necessary when the declared bounds do not establish the arithmetic range.

The map borrows labels only while the input remains available. Building the returned rows uses to_owned once per distinct label because callers should retain the report after the original strings disappear. This allocation serves a stated ownership requirement. The final comparison is a closure: |left, right| ... names two arguments to a small function supplied to sorting. It compares the first field of each tuple. We will study closure capture and iterator pipelines more deeply in the conversion lesson.

Intentional mistake: use container order as business order

In a disposable learner edit, remove the explicit sorting step. This is deliberately outside the recommended contract. Your count totals may still be correct, and one run may even happen to print the expected order. Do not try to prove the problem by repeatedly running until luck produces a failure. The code now relies on an order the HashMap API does not promise. Review the documented iteration contract, restore sorting, and test equality after permuting input. A passing observation cannot strengthen an unspecified guarantee.

Playbook investigation: nine items exceed an eight-key limit

A report says nine labels were rejected even though “only eight are allowed.” That statement omits whether the limit concerns items or distinct names. Hypothesis A says the ninth item always fails. Hypothesis B says the ninth new key fails. Use eight different names plus a duplicate for one experiment, and the same prefix plus a new ninth name for another. The accepted duplicate disproves A. Preserve the input-item limit at 64 in both cases so it cannot explain the result.

Use the central playbook to record exact inputs, predicted result categories, and observed results. The repair may be a clearer error message or correcting a caller's expectation, rather than changing the bound. If a product now needs nine distinct categories, increasing the cap is a requirement change that needs memory and acceptance review. Your experiment distinguishes two policies for these inputs; it does not prove all possible text is valid.

Hint 1: write the return contract first

Zero can be a useful display value, but None preserves the distinction between absent and explicitly stored zero. Choose one meaning before selecting a standard-library method.

Hint 2: separate observation from mutation

A query should not use an insertion path merely to obtain a default. For the fixed status enum, an exhaustive match can update the corresponding counter without allocating keys.

Reference approach after your attempt

A borrowed-map helper can use get and copy the small count, returning Option<u32>. For returned sorted rows, a simple bounded search is also appropriate; replacing the representation solely to optimize eight rows needs evidence. The two-status summary can use a pair of named counters and exhaustive matching. These are proposed extensions, not claims that the current reference already exposes those APIs.

Engineering decisions, evidence, and mastery

The slice parameter avoids unnecessary ownership requirements, local construction prevents partial-result publication, borrowed keys avoid repeated intermediate string allocation, and owned sorted output establishes lifetime and order guarantees. A BTreeMap is a reasonable alternative when ordered iteration is itself useful; it changes lookup and traversal costs. A small linear vector can also be appropriate at this bounded size. No timing comparison is asserted. The choice should follow required operations and measured scale, not a rule that hash maps are always faster.

Four focused tests cover slice sources, empty input, deterministic counts, independent resource limits, invalid text, and output ownership. Actual author checks are in the lab test log; independent review remains pending. To demonstrate mastery, choose a container for a changed requirement, explain the resulting ownership and ordering promises, and debug one failing boundary without reading the reference. A clean compile does not establish the business meaning of a count.
