An issue API you can test at its boundaries

Integrate routes, database migrations, pagination, and operational failure handling.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Purpose and independent specification

Complete the issue tracker using the contracts from the previous lessons. A writer creates a trimmed, nonempty title of at most 200 Unicode scalar values. A reader lists only its team's issues. Results are ordered by ascending ID, with a positive limit no greater than 100 and an optional exclusive after cursor. Closing requires a matching revision and produces one audit row. Read these criteria first, then implement against your own tests before opening the reference source.

Plain-English model: boundaries compose

A boundary is where one set of assumptions becomes another: HTTP bytes become a typed request, an identity becomes permissions, a domain transition becomes SQL, and rows become JSON. Testing the pure title validator is useful but does not prove that the route calls it. Testing SQL alone does not prove the handler applies the right actor team. An integration test deliberately crosses several boundaries and checks the behavior visible to a caller.

Pagination limits one response's work. Offset pagination skips a number of rows, which can become costly and unstable when earlier rows change. Our keyset cursor says “give me IDs greater than this known ID.” Together with ORDER BY id, it defines a predictable continuation. It is not a frozen snapshot across pages: newly inserted issues may appear later, and filters can change membership. Say which user experience you support instead of calling every ordered page consistent.

Predict

The last returned ID is 20. Between page requests, someone deletes ID 3 and inserts ID 30. With after=20, should the next page repeat ID20? Does deleting ID3 shift the meaning of the cursor? What would an offset of 20 mean instead?

Reasoning

The cursor excludes20 and compares key values, so deleting3 does not shift it. ID30 may appear if it belongs to this team. An offset counts currently visible rows before the response and can skip or repeat logical positions as data changes. Neither method alone guarantees a snapshot of an earlier moment.

Runnable service checkpoint

Use a separate local application database, not the disposable integration-test database. The server runs embedded migrations on startup, limits its pool to five connections, and binds loopback port4110. This default makes migrations convenient locally; a deployment may use a separate migration step with narrower runtime permissions.

createdb rust_course_issues
export DATABASE_URL="postgresql:///rust_course_issues?host=/tmp&user=$USER"
mise exec -- cargo run -p p10-issues
# Another terminal:
curl -H "Authorization: Bearer demo-team1-writer" -H "Content-Type: application/json" -d '{"title":"Investigate timeout"}' http://127.0.0.1:4110/issues
curl -H "Authorization: Bearer demo-team1-reader" "http://127.0.0.1:4110/issues?limit=20"

Expected behavior: create returns201 with a generated issue ID and revision0; list returns an array visible to team1. A reader's create returns403. Do not paste real credentials into these fixture commands. Start with the pure validation example if PostgreSQL is unavailable.

Explain the integration test

The test uses Tower's oneshot to send a real request through the Axum router without opening a network port. This exercises routing, extraction, permission checks, handlers, and response construction. It still uses an actual isolated PostgreSQL database. The test inserts a title containing an apostrophe, checks another team's empty list, denies cross-team close, checks a successful close, rejects a stale retry, and verifies pagination. Finally it forces an audit uniqueness failure and confirms rollback.

projects/reference/p10-issues/tests/postgres.rs
//! Opt-in destructive tests: use only the documented disposable local fixture.
mod support;
use axum::{
    body::{Body, to_bytes},
    http::{Request, StatusCode},
};
use serde_json::Value;
use tower::ServiceExt;
#[tokio::test]
#[ignore = "requires COURSE_TEST_DATABASE_URL pointing to a disposable course database"]
async fn postgres_authorization_transaction_pagination() {
    let pool = support::isolated_pool("COURSE_TEST_DATABASE_URL", "rust_course_test_issues").await;
    sqlx::migrate!().run(&pool).await.unwrap();
    // Test database is explicitly disposable; only these teaching tables are cleared.
    sqlx::raw_sql("TRUNCATE issue_audit,issues RESTART IDENTITY")
        .execute(&pool)
        .await
        .unwrap();
    let app = p10_issues::router(pool.clone());
    async fn call(
        app: axum::Router,
        method: &str,
        path: &str,
        token: &str,
        body: &str,
    ) -> (StatusCode, Value) {
        let response = app
            .oneshot(
                Request::builder()
                    .method(method)
                    .uri(path)
                    .header("authorization", format!("Bearer {token}"))
                    .header("content-type", "application/json")
                    .body(Body::from(body.to_owned()))
                    .unwrap(),
            )
            .await
            .unwrap();
        let status = response.status();
        let bytes = to_bytes(response.into_body(), 65536).await.unwrap();
        (status, serde_json::from_slice(&bytes).unwrap())
    }
    assert_eq!(
        call(
            app.clone(),
            "POST",
            "/issues",
            "demo-team1-reader",
            r#"{"title":"deny"}"#
        )
        .await
        .0,
        StatusCode::FORBIDDEN
    );
    let (status, issue) = call(
        app.clone(),
        "POST",
        "/issues",
        "demo-team1-writer",
        r#"{"title":"Alice's bug"}"#,
    )
    .await;
    assert_eq!(status, StatusCode::CREATED);
    let id = issue["id"].as_i64().unwrap();
    assert_eq!(
        call(app.clone(), "GET", "/issues", "demo-team2-writer", "")
            .await
            .1,
        serde_json::json!([])
    );
    assert_eq!(
        call(
            app.clone(),
            "POST",
            &format!("/issues/{id}/close"),
            "demo-team2-writer",
            r#"{"expected_revision":0}"#
        )
        .await
        .0,
        StatusCode::NOT_FOUND
    );
    assert_eq!(
        call(
            app.clone(),
            "POST",
            &format!("/issues/{id}/close"),
            "demo-team1-writer",
            r#"{"expected_revision":0}"#
        )
        .await
        .0,
        StatusCode::OK
    );
    assert_eq!(
        call(
            app.clone(),
            "POST",
            &format!("/issues/{id}/close"),
            "demo-team1-writer",
            r#"{"expected_revision":0}"#
        )
        .await
        .0,
        StatusCode::CONFLICT
    );
    assert_eq!(
        call(
            app.clone(),
            "GET",
            &format!("/issues?after={id}&limit=1"),
            "demo-team1-reader",
            ""
        )
        .await
        .1,
        serde_json::json!([])
    );
    let count: i64 = sqlx::query_scalar("SELECT count(*) FROM issue_audit")
        .fetch_one(&pool)
        .await
        .unwrap();
    assert_eq!(count, 1);
    // A failing audit write must roll back the preceding issue update.
    let (_, second) = call(
        app.clone(),
        "POST",
        "/issues",
        "demo-team1-writer",
        r#"{"title":"rollback"}"#,
    )
    .await;
    let second = second["id"].as_i64().unwrap();
    sqlx::query(
        "INSERT INTO issue_audit(issue_id,revision,actor,action) VALUES($1,1,1,'injected')",
    )
    .bind(second)
    .execute(&pool)
    .await
    .unwrap();
    assert_eq!(
        call(
            app.clone(),
            "POST",
            &format!("/issues/{second}/close"),
            "demo-team1-writer",
            r#"{"expected_revision":0}"#
        )
        .await
        .0,
        StatusCode::SERVICE_UNAVAILABLE
    );
    let closed: bool = sqlx::query_scalar("SELECT closed FROM issues WHERE id=$1")
        .bind(second)
        .fetch_one(&pool)
        .await
        .unwrap();
    assert!(!closed);
    let (_, concurrent) = call(
        app.clone(),
        "POST",
        "/issues",
        "demo-team1-writer",
        r#"{"title":"race"}"#,
    )
    .await;
    let concurrent = concurrent["id"].as_i64().unwrap();
    let path = format!("/issues/{concurrent}/close");
    let (a, b) = tokio::join!(
        call(
            app.clone(),
            "POST",
            &path,
            "demo-team1-writer",
            r#"{"expected_revision":0}"#
        ),
        call(
            app.clone(),
            "POST",
            &path,
            "demo-team1-writer",
            r#"{"expected_revision":0}"#
        )
    );
    assert!(
        (a.0 == StatusCode::OK && b.0 == StatusCode::CONFLICT)
            || (b.0 == StatusCode::OK && a.0 == StatusCode::CONFLICT)
    );
    let count: i64 = sqlx::query_scalar("SELECT count(*) FROM issue_audit WHERE issue_id=$1")
        .bind(concurrent)
        .fetch_one(&pool)
        .await
        .unwrap();
    assert_eq!(count, 1);
    pool.close().await;
}

Deliberate mistake and guided increment

Remove ORDER BY id in your learner query and run the test. It may still pass on a tiny table. This is an instructive limitation of example-based tests: observed order is not a promised order. Restore the explicit ordering, then write a three-page test with multiple teams, enough rows to cross boundaries, and IDs tracked in a set. Assert no duplicates and the specified ascending order. The implementation checkpoint is the complete router plus migration; the improvement checkpoint is your expanded pagination evidence.

Independent design decisions

Add a closed/open filter while preserving cursor semantics. Decide whether the cursor should be reusable with a different filter. Write the API rule, a client example, and a test before implementing. Then design a second migration adding an optional assignee. Explain what old binaries do when the new column exists, whether new binaries can read old rows, and when backfill work must happen.

Hint 1

The cursor is part of a query, not just an integer. Consider encoding filter context if accidental reuse matters.

Hint 2

An additive nullable column allows old rows and old writers during a transition. Enforcing a new required value immediately can break them.

Reference approach

For this small API, document that clients must preserve filters across pages and reject invalid filter values. Add a nullable assignee through a new migration and keep authorization based on team membership, not assignee identity. For a larger public API, use an opaque cursor carrying versioned query context and validate it with a maintained mechanism if tamper resistance is required.

Review and evidence

A happy-path curl session is a useful smoke test, but insufficient boundary evidence. A stronger review asks what authorization predicate protects every query, what bounds every collection, what happens when acquiring a connection times out, and how deployment schema is known. The five-connection pool bounds active database connections. A separate16-request semaphore and five-second handler/body deadline bound admitted HTTP work; they do not replace operating-system connection limits or a deployment rate policy. This reference has no deployment TLS/authentication integration. Its local scope and remaining limits must remain visible.

Playbook investigation

Observation: requests stall while CPU stays low. Misleading evidence: the database process is alive and /health returns200. Hypothesize exhausted pool, slow queries, lock waits, or a handler retaining a transaction. Distinguish them with pool acquisition timing and PostgreSQL activity/lock inspection in the test environment. A responsive health route only proves the runtime can answer that route. If an intentionally held row lock reproduces close latency while reads work, “CPU shortage” is disproven. Fix the transaction lifetime and add request deadlines; do not increase pool size without measuring the database budget.

Mastery check

Demonstrate a denied request, a rolled-back transition, and a paginated traversal. Review the API as if its author were absent. Name one guarantee established by each test and one important behavior not covered.

When you get stuck

Run mise exec -- cargo test -p p10-issues --test postgres -- --ignored --nocapture with the isolated database URL. Compare actual status and JSON before reading server logs. Include schema version, actor role, cursor, expected revision, and the minimal failing request in a review request.

Engineering decisions and evidence

Scope and invariants: local two-team issue state, permission checks on every domain operation, bounded page/body/pool sizes, atomic issue-and-audit transitions, revision conflict detection. Why this design: pure validation can run without infrastructure, while SQL constraints and transaction-scoped row locks protect durable facts under concurrent requests. Concrete habits: derive authority server-side; bind SQL values; keep all transaction statements on the same connection; test denied requests and injected rollback through the actual router.

Alternative: an optimistic conditional UPDATE can reduce explicit lock code for a simple transition, but the associated audit and returned conflict semantics still require a transaction. Evidence: actual PostgreSQL integration tests and prepared query metadata are recorded separately from pure unit checks. Neither verifies a production identity provider or live deployment schema. Evolution threshold: add maintained authentication/TLS, deployment connection/rate limits, query-plan measurement, and migration rollout checks before multiuser deployment. Public fixture tokens are not secret credentials or a security claim.

Keep startup and shutdown failures visible

The binary reads DATABASE_URL through a deliberately redacted conversion: both missing and non-Unicode values produce a fixed configuration message. A VarError::NotUnicode contains the original operating-system value, so forwarding its Debug representation could expose a credential. Do not solve an encoding failure by logging the entire value. The child-process regression uses a synthetic marker and invalid byte, and confirms neither the marker nor a panic appears before any database connection.

Required startup output uses fallible Write operations. The main task retains one server future, selects it against Ctrl-C, and signals a watch channel to request graceful shutdown. IntoFuture converts Axum's awaitable server builder into the future that select! polls explicitly; tokio::pin! lets the same in-progress future be awaited afterward. After either normal or error completion, the pool is closed before the saved server or signal error is returned. A signal-registration failure requests shutdown too. No detached signal watcher is needed. See the scoped output evidence for the actual checks and the database-service runtime limits.
