Bounded chat, slow clients, and shutdown

Own connection tasks and make overload behavior explicit.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

  • Trace message ownership through reader, channel and writer
  • Enforce connection/message/time budgets
  • Explain cancellation versus graceful application delivery

Key terms: allocation · authentication · backpressure · cancellation · capacity · closure · deadline · enum

Purpose and service specification

Before reading the reference server, implement this specification: accept at most 32 simultaneous clients on loopback, retain at most 32 chat messages in a shared broadcast queue, reject frames over 1,024 bytes, and disconnect clients whose writes exceed two seconds or whose reads exceed 30 seconds. Disconnect a receiver that has missed messages. Ctrl-C must stop accepting connections and terminate owned tasks. There is no durable history, identity, confidentiality, or delivery acknowledgment. Those are explicit protocol limits, not unfinished error handling.

Plain-English model: admission and backpressure

A resource budget limits work a service is willing to hold. A semaphore is a collection of permits; a live connection owns one until its task ends. A bounded broadcast channel retains a limited sequence of messages for subscribers. Its capacity does not bound everything: each task also owns a read buffer, a write buffer or in-progress frame, runtime state, and operating-system socket buffers. Budget each layer separately before multiplying by connection count.

Backpressure means a downstream limit affects upstream acceptance or speed. This chat chooses disconnects rather than indefinitely slowing every sender for one reader. That is reasonable for disposable chat, but would be wrong for a financial ledger stream that promised every event. A lag notification means a subscriber missed history. Continuing without surfacing that fact would present an incomplete conversation as complete.

Prediction

A broadcast channel holds two messages. A reader has received none when the producer sends three. Does the third send wait forever, does the reader get all three later, or does the reader learn it missed data?

Answer and tempting alternatives

The reader gets a lag error before resuming from retained data. A broadcast channel is not an acknowledgment queue. The third send does not wait for every reader. Our application ends that client's task on lag, so later frames are not silently displayed after a gap.

Run the checkpoint

In rust-course/projects, run the server in one terminal and a client in each of two others. The Python helper uses only the standard library and speaks the actual wire protocol. A browser cannot connect to arbitrary TCP sockets directly.

mise exec -- cargo run -p p09-chat
python3 reference/p09-chat/client.py

Type a short message. Both connected clients should receive it, including the sender. Ctrl-C in the server should end the service. The byte-slice decoder example from the prerequisite remains your small deterministic example. Run mise exec -- cargo test -p p09-chat lag_is_visible to observe the queue policy without relying on socket-buffer timing.

Guided implementation and ownership

Start from your tested frame functions. Add serve with a listener and a watch receiver. The listener owns admission; a JoinSet owns all client tasks. After accept, try_acquire_owned either transfers a permit into a task or rejects that connection immediately. Using an owned permit makes release follow task lifetime, including errors and cancellation. Clone the broadcast sender and subscribe before spawning. Split the stream into read and write halves because independent asynchronous operations need independent ownership.

The reader future is pinned once. Pinning here ensures the future remains at a stable address while being polled; it does not make the stream reliable. The writer selects between that same reader future and incoming broadcast messages. A frame read can consume bytes before returning Pending, so recreating it every time a write wins would lose framing progress. Timeout cancels a read only when the entire connection is being abandoned, which makes that partial state safe to discard.

Deliberate mistake

Replace the bounded channel with an ever-growing Vec per client. A slow reader now makes memory increase with producer speed and elapsed time. This compiles and may look faster in a short test. The failure is operational: overload changes from an explicit disconnect into eventual process memory exhaustion. Restore a finite queue and document what happens when it fills.

Independent practice with staged hints

Measure a client's idle lifetime and implement a different policy: a 10-second deadline for completing the first frame, followed by 60 seconds for later frames. Decide whether outbound traffic should reset the read deadline. Do not just shorten all constants and call the result tested.

Hint 1

Track protocol state explicitly; “connected” and “sent first frame” are different states.

Hint 2

Put a timeout around a whole frame, not each individual byte, or a peer can keep a connection indefinitely by sending one byte per deadline.

Reference reasoning

The timeout belongs to an application phase. Keep a boolean or enum in the dedicated reader and choose the next complete-frame deadline from that phase. Outgoing traffic does not prove the peer is sending valid input, so it should not refresh an inbound deadline unless the specification deliberately says so.

Review, tests, and mastery

A rejected design is to detach tasks and trust them to end. The clearer design retains ownership until shutdown. The current server aborts its connection tasks and drains the JoinSet; it does not wait for application acknowledgments. The loopback test establishes one complete message lifecycle and server termination. Queue tests establish lag semantics, not an OS-specific threshold for a slow socket. Add a targeted short-deadline integration harness if you change those policies. Explain where a message can be lost, why sync locks are unnecessary here, and why finite message size is necessary even with a finite queue.

Playbook investigation

Observation: memory is stable but one client stops receiving under bursts. Guess: “the runtime lost a task.” Capture channel lag counts and connection close reasons, then reduce the producer rate. If lag disappears while the same task structure remains, the lost-task hypothesis lacks support. Reproduce using the deterministic two-slot test before investigating TCP packet captures. The intended fix may be a clearer reconnect notice rather than a larger queue. Larger queues trade delay and memory for tolerance; they cannot rescue a permanently slower consumer.

When you get stuck

Start with mise exec -- cargo test -p p09-chat loopback_and_shutdown -- --nocapture. If it hangs, add temporary tracing at accept, frame completion, broadcast receive, and shutdown. Share the lifecycle trace and your predicted owner of each task. Use the Tokio broadcast documentation to check whether lag closes a receiver automatically; application code decides that.

Engineering decisions and evidence

Scope and invariants: a loopback text broadcast service,32 clients,32 retained messages,1,024-byte validated frames, finite read/write deadlines. No authentication, TLS, durable delivery, or historical replay is promised. Why this design: explicit framing and owned connection tasks make partial reads, resource release, and shutdown traceable. An owned permit couples admission to connection lifetime. Concrete habits: validate before allocation; retain partially consumed decoder state; bound task and message counts; identify deliberate failures separately from the recommended implementation.

Alternative: per-client bounded mpsc queues allow individual policies and accounting but require more queue ownership and fan-out code. For a durable stream, use sequence IDs and a persistent replay protocol instead of enlarging a disposable chat queue. Evidence: fragmented bytes, oversize, truncation, lag, and loopback shutdown tests establish selected protocol cases. They do not prove every transport failure or denial-of-service scenario. Evolution threshold: add a maintained authentication/TLS boundary before any nonlocal use; add explicit delivery semantics before users depend on history.

Observe shutdown state before waiting

A watch channel retains the latest state; it is not just a sequence of notifications. The initial value is considered seen by a new receiver, so waiting for changed() alone misses a stop already set to true. The server now inspects borrow_and_update() before each wait. A true value stops admission, false only means keep running, and losing every sender also requests shutdown. The borrowed guard ends before any await.

Predict what happens for an initially true channel, then run the two shutdown regressions. One requires the server to finish without a second change; the other exchanges real frames after false notifications and checks that sender closure drains the server. Their two-second deadlines detect a stalled test; they do not claim an operational latency bound. The main function owns a pinned server future and selects it against Ctrl-C in the same task. On Ctrl-C it signals shutdown and awaits that same server future, avoiding a detached signal-watcher task. If signal registration fails, it still drains the server before returning the error.

Read the pinned Tokio watch documentation and select! cancellation rules. Explain why retaining the future matters, and why a false state notification must not mean stop. Working directory: projects. Run mise exec -- cargo test -p p09-chat --locked.

Startup output is an ordinary I/O boundary

A startup message can fail when a pipe closes or an output device rejects a write. The entry point now uses a locked stdout writer, writeln! and flush, propagating I/O errors with ? before it begins the server future. Printing macros such as println! panic on output errors; they are not the error-handling policy for this service. A write failure therefore exits unsuccessfully without a detached connection or signal task. The locked writer's scope ends before any await.

Predict the closed-pipe result before reading the real process evidence: it is an ordinary BrokenPipe error, not a panic. The separate lifecycle experiment exchanges a valid framed message, sends SIGINT only to the owned server process, and observes exit zero. These are tested paths, not a proof of every operating-system shutdown schedule.
