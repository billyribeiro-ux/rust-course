Middleware order, cookies, CSRF, and TLS boundaries

Trace a real Axum pipeline and distinguish browser policy, credentials, permission checks, and encrypted transport using executable rejection tests.

Purpose: follow a request across boundaries

An API can use correct SQL and still apply checks in the wrong order. A dashboard can receive a browser error even though the server completed a mutation. This lesson connects the Issue Tracker's Axum pipeline to the browser that will later call it. You will distinguish parsing, resource admission, authentication, authorization, cross-origin rules, and encrypted transport. Each protects a different property. Your deliverable is an executable boundary test and a short threat analysis, not a homemade login system.

Prerequisites: finish HTTP contracts and transactional Issue Tracker. You need to recognize request headers, JSON, a status code, and an async function. No live PostgreSQL database is needed for this lesson's test command: every application request used here is rejected before executing SQL.

Plain-English model: nested request handlers

Middleware is a wrapper around the next request-processing step. It may inspect or change a request, stop with a response, or pass the request onward and inspect the returning response. Imagine a sequence of functions calling one another. This is more accurate than imagining independent security filters that magically run together. An early return prevents inner layers from running; an outer timeout can stop waiting while other work already started continues.

With repeated Axum Router::layer calls, the last layer added wraps previously registered routes and layers. In our trace fixture, outer receives the request, inner receives it, the handler produces a response, and that response passes through inner then outer. This describes these particular calls; tower::ServiceBuilder composes its listed layers in request order. Do not transfer one ordering rule to the other without checking. Route registration timing also matters: a layer applies to routes already registered. See the Axum 0.8.9 ordering documentation.

Our Issue Tracker first admits at most sixteen requests and applies a five-second deadline around inner processing. Its body limit configures JSON extraction to accept at most 4096 bytes. Axum extracts function arguments before calling a handler; the handler then checks the demo actor and permissions before SQL. Consequently an unauthenticated request with malformed JSON can receive 400 instead of 401. A bounded parser rejects a bad body without running the handler. This is an intentional observable contract, not evidence that authorization was bypassed.

Predict before running

Write down the exact trace after registering inner, then outer, with two .layer(...) calls. Now predict these responses: a valid JSON create request using the reader fixture; a request with only a cookie named session; a malformed JSON body with no identity; an OPTIONS request asking for cross-origin access. Explain whether each response says anything about database contents. Resist predicting 401 for every missing identity: locate the check in the actual pipeline.

Prediction answer and tempting mistakes

The trace is outer request, inner request, handler, inner response, outer response. The reader receives 403; the cookie-only request receives 401 because this application does not interpret cookies as identity. Malformed JSON receives 400 before the in-handler check. The OPTIONS request receives 405 without an Access-Control-Allow-Origin header. None reaches SQL. The tempting claim that the last registered layer runs last confuses response order with request order.

Dependencies come from the pinned workspace: Axum 0.8.9, Tokio 1.53.3, Tower 0.5.3, and SQLx 0.9.0. //! No live database or browser is needed: every application request below is
//! rejected before SQL. These assertions describe public local demo identities,
//! never a production authentication protocol.
use axum::{
    Router,
    body::Body,
    extract::{Request, State},
    http::{Method, StatusCode},
    middleware::{self, Next},
    response::Response,
    routing::get,
};
use std::sync::{Arc, Mutex};
use tower::ServiceExt;

type Trace = Arc<Mutex<Vec<&'static str>>>;
fn note(trace: &Trace, event: &'static str) {
    // Tests fail immediately on poisoned state. The guard ends before any await.
    trace.lock().expect("test trace lock").push(event);
}
async fn inner(State(trace): State<Trace>, request: Request, next: Next) -> Response {
    note(&trace, "inner request");
    let response = next.run(request).await;
    note(&trace, "inner response");
    response
}
async fn outer(State(trace): State<Trace>, request: Request, next: Next) -> Response {
    note(&trace, "outer request");
    let response = next.run(request).await;
    note(&trace, "outer response");
    response
}
async fn handler(State(trace): State<Trace>) -> &'static str {
    note(&trace, "handler");
    "ok"
}

#[tokio::test]
async fn repeated_router_layers_wrap_in_reverse_request_order() {
    let trace = Trace::default();
    let app = Router::new()
        .route("/", get(handler))
        .layer(middleware::from_fn_with_state(trace.clone(), inner))
        .layer(middleware::from_fn_with_state(trace.clone(), outer))
        .with_state(trace.clone());
    let response = app
        .oneshot(Request::builder().uri("/").body(Body::empty()).unwrap())
        .await
        .unwrap();
    assert_eq!(response.status(), StatusCode::OK);
    assert_eq!(
        *trace.lock().unwrap(),
        [
            "outer request",
            "inner request",
            "handler",
            "inner response",
            "outer response"
        ]
    );
}
fn app() -> Router {
    // connect_lazy opens no connection. All exercised paths reject before SQL.
    let pool = sqlx::postgres::PgPoolOptions::new()
        .connect_lazy("postgresql://unused@127.0.0.1:1/course_no_connection")
        .unwrap();
    p10_issues::router(pool)
}
#[tokio::test]
async fn ambient_cookie_and_spoofed_proxy_headers_do_not_identify_an_actor() {
    let response = app()
        .oneshot(
            Request::builder()
                .uri("/issues")
                .header("cookie", "session=demo-team1-writer")
                .header("x-forwarded-user", "demo-team1-writer")
                .header("x-forwarded-proto", "https")
                .body(Body::empty())
                .unwrap(),
        )
        .await
        .unwrap();
    assert_eq!(response.status(), StatusCode::UNAUTHORIZED);
}
#[tokio::test]
async fn recognized_reader_is_still_forbidden_to_mutate() {
    let response = app()
        .oneshot(
            Request::builder()
                .method(Method::POST)
                .uri("/issues")
                .header("authorization", "Bearer demo-team1-reader")
                .header("content-type", "application/json")
                .body(Body::from(r#"{"title":"valid but forbidden"}"#))
                .unwrap(),
        )
        .await
        .unwrap();
    assert_eq!(response.status(), StatusCode::FORBIDDEN);
}
#[tokio::test]
async fn extraction_can_reject_before_in_handler_identity_checks() {
    for (body, expected) in [
        ("{".to_owned(), StatusCode::BAD_REQUEST),
        ("x".repeat(4097), StatusCode::PAYLOAD_TOO_LARGE),
    ] {
        let response = app()
            .oneshot(
                Request::builder()
                    .method(Method::POST)
                    .uri("/issues")
                    .header("content-type", "application/json")
                    .body(Body::from(body))
                    .unwrap(),
            )
            .await
            .unwrap();
        assert_eq!(response.status(), expected);
    }
}
#[tokio::test]
async fn no_cross_origin_preflight_permission_is_granted() {
    let response = app()
        .oneshot(
            Request::builder()
                .method(Method::OPTIONS)
                .uri("/issues")
                .header("origin", "https://untrusted.invalid")
                .header("access-control-request-method", "POST")
                .header(
                    "access-control-request-headers",
                    "authorization,content-type",
                )
                .body(Body::empty())
                .unwrap(),
        )
        .await
        .unwrap();
    assert_eq!(response.status(), StatusCode::METHOD_NOT_ALLOWED);
    assert!(
        response
            .headers()
            .get("access-control-allow-origin")
            .is_none()
    );
}
#[tokio::test]
async fn an_origin_header_is_not_an_identity_or_authorization_check() {
    let response = app()
        .oneshot(
            Request::builder()
                .uri("/issues")
                .header("origin", "http://127.0.0.1:4173")
                .body(Body::empty())
                .unwrap(),
        )
        .await
        .unwrap();
    assert_eq!(response.status(), StatusCode::UNAUTHORIZED);
}

The trace is an Arc<Mutex<Vec<&'static str>>>: multiple cloned service values share one test recorder. A short helper locks only to push one event, then releases the guard before any await. A test panic on a poisoned recorder is appropriate because poisoning means this test fixture already failed. The application itself reports routine storage failures as responses. State supplies the recorder, Next owns the next processing step, and next.run(request).await returns the inner response.

connect_lazy constructs pool configuration without opening a connection. The intentionally unusable loopback address ensures this fixture cannot accidentally use your normal database configuration. The exercised paths stop before SQL; a new success-path assertion belongs in the isolated PostgreSQL integration suite. The tests inspect actual statuses and headers, so changing authentication placement or introducing a CORS layer requires a deliberate contract update.

Cookies, origins, CSRF, and TLS

An origin consists of scheme, host, and port. Two localhost services on different ports are different origins. A browser restricts how scripts read cross-origin responses. CORS is the server's protocol for granting selected cross-origin access; a preflight asks permission before certain requests, including our cross-origin JSON request with an Authorization header. A native HTTP client is not constrained by browser CORS. Furthermore, some browser requests can be sent without a preflight even when their response cannot be read. Therefore the absence of CORS permission is not a general authorization or mutation barrier. The primary source is the Fetch standard's CORS protocol.

A cookie is browser-managed state that can be attached automatically to matching requests. That convenience creates a different threat from explicitly supplying a bearer header. Cross-site request forgery, or CSRF, tricks an authenticated browser into sending a state-changing request the user did not intend. An attacker may not need to read the response. If you later adopt cookie sessions, use the selected maintained authentication framework's CSRF protections: suitable anti-CSRF tokens or an established equivalent, origin checks where appropriate, and carefully scoped cookies. Do not invent token signing or use a predictable form field as a secret.

HttpOnly prevents ordinary page JavaScript from reading a cookie; it does not prevent the browser from sending it. Secure restricts its transmission to secure channels; it does not decide which user may close an issue. SameSite controls some cross-site attachment behavior, with details that differ from the stricter origin concept. Treat it as a defense within a complete design. Avoid broad Domain scope when host-only scope is enough. Do not record session values in logs. Read the cookie specification and OWASP's CSRF prevention guidance before choosing a real session design.

TLS protects a network channel against eavesdropping and tampering and authenticates the server when certificate and hostname validation succeed. It does not grant application permissions or prevent a malicious authenticated client from making valid-looking requests. Never fix a certificate error by disabling validation in application code. If a trusted reverse proxy terminates TLS, document the protected hop and which proxy identities may supply forwarding headers; arbitrary clients must not become trusted merely by writing X-Forwarded-Proto: https. Our test proves that header grants no identity in this fixture. It does not perform a TLS handshake. This course's loopback teaching server uses clear HTTP and public demo identities; exposing it remotely requires a separate reviewed deployment and authentication design. See TLS 1.3's specification.

Deliberate mistake: treating an unreadable response as no effect

Intentional design failure: “The page saw a CORS error, so repeat the create request with a new identifier.” The browser might have sent a request that the server committed before access to its response was blocked. Likewise, a timeout means the caller stopped waiting; it does not roll back a transaction or a blocking append already in progress. Diagnose transport, browser policy, and application state separately. The capstone retains one logical order ID through an uncertain outcome and queries that exact ID. In the Issue Tracker, reconciliation must use its actual operation contract rather than assuming every endpoint is idempotent.

A second deliberate mistake is moving the reader check after INSERT because the UI hides its button. A denied response would then conceal a real unauthorized side effect. The existing reader test is valuable, but pair it with the isolated database authorization tests to prove unchanged durable state. The UI is an aid to the user; the server owns permission decisions.

Independent browser-boundary exercise

A proposed deployment serves the UI at https://console.example.invalid and the API at https://api.example.invalid. The designer wants cookie sessions, an all-origins CORS policy, and no CSRF token because the cookie is HttpOnly. Write a review that identifies which claims are unsupported, what legitimate browser flow must work, and which negative tests must precede deployment. Choose a maintained session/authentication integration after checking its current official documentation; implementation of that new integration is an optional specialization, not hidden functionality of this local fixture.

Your acceptance criteria must distinguish a denied preflight, an authenticated forbidden request, an allowed same-origin request, a missing or invalid anti-CSRF token, and a native client bypassing browser restrictions. Include a certificate hostname failure and a spoofed proxy header. Specify expected status, state change, and evidence for each. Do not merely list attack names.

Reference review

The sibling hosts have different origins; sharing a registrable domain does not make them same-origin. Cookie attachment and response reading are distinct decisions. HttpOnly does not prevent forged browser requests. Select an explicit origin allowlist if cross-origin access is necessary; credentialed CORS has additional rules, so a wildcard is not a universal solution. Keep server authorization on every operation. Use the framework's established CSRF defenses and test them with the browser credential behavior actually selected. Reject unexpected forwarding headers at the trust boundary. Certificate validation failure should stop the client before application requests are trusted. A simpler alternative is serving UI and API through one origin, while retaining authorization and the session design's CSRF defenses.

Playbook investigation: a misleading 400

Observation: a request missing Authorization receives 400; the reviewer expected 401. Guess A says the identity check failed open. Guess B says parsing happened first. Before editing security code, record the method, path, content type, bounded body, and status without copying secrets. Distinguishing experiment: send valid JSON with the same missing header, then malformed JSON with a valid reader header. The first receives 401 and the second 400. That disproves the claim that the observed 400 alone proves an identity bypass.

Now inspect whether any handler or SQL ran. The no-database test distinguishes these paths, while durable-state tests address actual writes. A reasonable fix for a requirement to authenticate before parsing is a parts-only actor extractor or route middleware, applied consistently and tested with body limits. Do not make that change merely to match an inaccurate guess. Resource admission must remain bounded, public health routes need an explicit policy, and error responses must avoid leaking secrets. State the changed contract before implementing it.

Engineering decisions and evidence

The recommended local design has explicit public fixture identities, server permission checks, bounded extraction, and a documented admission/deadline wrapper. A parts-only actor extractor is a reasonable alternative when many handlers repeat actor parsing; maintained session middleware becomes appropriate when introducing actual browser login. Neither choice eliminates team predicates in SQL. The evolution threshold is a real identity provider or remotely reachable deployment, not the desire for more abstractions.

The six tests establish layer order and selected request rejection behavior for these pinned library versions. They do not prove browser cookie handling, TLS configuration, absence of every authorization defect, or database rollback. The runtime audit adds real TCP/HTTP evidence for body deadlines and admission in the capstone; the isolated PostgreSQL tests cover protected mutations. Independent security and instructional review remain pending. Evidence has to match the claim.

When you get stuck

First rerun mise exec -- cargo test -p p10-issues --test web_boundaries -- --nocapture. Read the first status assertion, not only the final failure count. Then open the pinned Axum ordering section and mark where extraction and actor checks occur in the source. If your test reaches the deliberately unusable pool, revise the test to target a rejecting boundary or move it to the isolated database suite. For review, provide a minimal request with fixture credentials, expected and actual statuses, the layer order, and whether durable state changed. Never paste real session cookies.
