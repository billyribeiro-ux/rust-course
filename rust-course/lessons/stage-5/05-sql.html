Tables, indexes, transactions, and migrations

Make state changes correct when requests overlap and storage fails.

Purpose and acceptance criteria

Closing an issue must update its state and write an audit record together. If the audit insert fails, the issue must remain open. Two simultaneous requests with the same expected revision must not both claim to close it. Before looking at the implementation, write those two criteria as timelines. This is the point where “save some data” becomes a concurrency contract.

Plain-English model: related facts

A relational database stores rows in tables. A column has a type and may have constraints. A primary key uniquely identifies a row; a foreign key ties one table's value to a referenced row. Our issue audit points to the issue it describes. A CHECK constraint rejects invalid persisted values even when a future client forgets application validation. SQL is the language for selecting and changing these rows. Its evaluation model is about sets of rows, not the iteration order of a Rust vector.

An index is an auxiliary search structure. The (team_id,id) index supports locating one team's issues after a cursor. It costs storage and update work; adding every imaginable index can slow writes. A transaction groups statements into an atomic committed unit. Atomicity does not mean every intermediate read is globally isolated from all concurrent activity. PostgreSQL's default Read Committed isolation gives statement snapshots. Explicit row locking in our transition makes competing closers wait and recheck the relevant state.

Prediction with a transaction timeline

A starts a transaction, changes the issue, and attempts an audit insert that violates a uniqueness constraint. A then returns an error and drops its transaction. B reads the issue afterward. Does B see the changed state? Now consider A committing successfully but losing its HTTP response. Is the client entitled to assume the close failed?

Answer

The failed transaction does not commit the change, so B sees the previously committed state. A lost HTTP response is different: the database may have committed. The client must reconcile state or use a persisted idempotency key. Network uncertainty cannot be converted into proof of rollback.

Small runnable schema checkpoint

Read the migration, then run the database integration test against an explicitly disposable database named rust_course_test_issues. Never point this test at a real application database; it intentionally clears the two test tables. The fixture parses SQLx connection options and requires the exact database name, a literal loopback IP or an absolute local Unix socket path. Each connected session checks SELECT current_database() before migrations or table resets. These checks catch common wrong-target mistakes; a name alone does not prove the database is disposable.

projects/reference/p10-issues/migrations/0001_issues.sql
CREATE TABLE issues (
 id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 team_id BIGINT NOT NULL CHECK (team_id > 0),
 title TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
 closed BOOLEAN NOT NULL DEFAULT false,
 revision BIGINT NOT NULL DEFAULT 0
);
CREATE INDEX issues_team_cursor ON issues(team_id,id);
CREATE TABLE issue_audit (
 issue_id BIGINT NOT NULL REFERENCES issues(id),
 revision BIGINT NOT NULL,
 actor BIGINT NOT NULL,
 action TEXT NOT NULL,
 PRIMARY KEY(issue_id,revision)
);

createdb rust_course_test_issues
export COURSE_TEST_DATABASE_URL="postgresql:///rust_course_test_issues?host=/tmp&user=$USER"
mise exec -- cargo test -p p10-issues --test postgres -- --ignored

If the database already exists, do not recreate or drop it blindly. Inspect its ownership and contents. If ownership is uncertain, use a fresh isolated PostgreSQL cluster; do not repurpose or drop that database. The fixture guard accepts the exact documented name in that separate cluster, not a substring embedded elsewhere in a URL. The quoted URL uses your shell user as the PostgreSQL role; replace $USER if your database role differs. On systems whose socket directory differs, adjust the URL. PostgreSQL is an external local prerequisite; a passing ordinary Cargo test does not imply these ignored database tests ran.

Guided project step

Implement the migration exactly, then walk through close_issue in the reference. Begin a transaction; select the row using both ID and actor team with FOR UPDATE; compare its revision; update the issue; insert the audit row; commit. Every operation uses the same transaction connection. Accidentally calling execute(pool) for the audit would move it outside the transaction and break the guarantee.

Values are passed with .bind() into PostgreSQL placeholders $1, $2, and so on. Do not interpolate titles into SQL text. Parameters represent values, not table names or arbitrary SQL fragments. The title “Alice's bug” is a useful test because the apostrophe is ordinary data and should not change query syntax. The SQLx 0.9 API accepts static SQL strings directly and deliberately makes dynamic SQL construction explicit.

Deliberate mistake

Temporarily remove the transaction and execute the state update before an audit insert that will fail. The rollback assertion should fail because the issue is already closed. Restore the transaction, then verify the same injected audit conflict leaves the issue open. Compilation cannot detect this semantic difference.

Query verification and offline metadata

The default project uses runtime queries so it builds without a running database. This does not provide compile-time SQL verification. The optional verified-query feature contains a real query! example that checks a count query against the schema visible at build time. With the schema migrated, run the following command. SQLx CLI0.9.0 is the matching tool. From projects/reference/p10-issues, run mise exec -- cargo sqlx prepare -- --features verified-query to generate package-local metadata, then mise exec -- cargo sqlx prepare --check -- --features verified-query to compare it with the current preparation schema. The package includes the actual generated .sqlx/query-*.json file for the count query. Run SQLX_OFFLINE=true mise exec -- cargo check --features verified-query from that package to build using the metadata without contacting PostgreSQL. Generated metadata must be reviewed and committed with schema changes; an empty metadata directory proves nothing.

export DATABASE_URL="postgresql:///rust_course_test_issues?host=/tmp&user=$USER"
mise exec -- cargo check -p p10-issues --features verified-query

Offline metadata describes the schema used during preparation. It cannot inspect the live deployment database, prove migrations ran there, or prove transactional business rules. The verification report records actual metadata preparation, prepare --check, and forced offline recompilation for this optional feature. The default runtime queries still rely on database integration tests for schema validation.

Practice, review, and evidence

Add a title-change transaction with revision checking. Decide whether the audit stores the old title, the new title, or both. Then explain the retention and privacy implications. A limited alternative puts all validation in Rust; a robust design also uses constraints for durable invariants and parameter binding for SQL syntax separation.

Hint 2

Reference reasoning

Use the same lock-and-revision transition, add the chosen audit fields through a new migration, and test both successful history and forced rollback. Do not edit an applied migration just to hide a mismatch; migration checksums exist to expose changed history.

Playbook investigation and mastery

Observation: an issue is closed with no audit. The first hypothesis is a database durability failure. Inspect transaction IDs and the code's executor arguments before blaming storage. If the audit uses the pool while the update uses a transaction, a controlled constraint failure reproduces the symptom without crashing PostgreSQL. That disproves the crash hypothesis for this reproduction. Fix the transaction boundary, document that a lost commit acknowledgment remains uncertain, and explain the distinction without the reference.

When you get stuck

Run the ignored integration test explicitly and read the exact SQLSTATE in the local log. Use psql "$COURSE_TEST_DATABASE_URL" only for the isolated database. Consult PostgreSQL 18 transaction isolation and SQLx0.9 transaction docs. Ask for review with the two-request timeline, SQL statements, transaction boundaries, and failed assertion.

Investigate the test target before changing it

A URL can contain rust_course_test in a username or application_name while selecting an unrelated database. Predict whether that old substring guard would reject the wrong target; the pure guard tests demonstrate that it would not. The corrected helper reads SQLx's effective database and transport after parsing URL overrides, rejects a mismatched name before connecting, and checks the server-reported database on every connection. The regression matrix uses strings only and does not contact those rejected hosts. A separate fresh Unix-socket-only PostgreSQL cluster verifies the accepted integration path.

Read SQLx 0.9 connection options and PostgreSQL 18's current_database function. These are defensive checks against mistakes, not an ownership proof or permission to reset a database containing learner data. Prefer the owned fixture runner in the verification evidence when repeating destructive acceptance tests.
