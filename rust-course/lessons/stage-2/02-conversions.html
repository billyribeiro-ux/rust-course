Validated conversions, standard traits, closures, and iterators

Design a private validated type and preserve its meaning across From, TryFrom, parsing, formatting, and lazy batch processing.

Purpose: conversion is a contract, not a convenient cast

Configuration values often arrive as strings or general integers, while the application needs a smaller valid domain. A percentage is a useful example: the storage type u8 accepts values through 255, but our whole-percentage contract permits only zero through one hundred. Merely changing an integer's type does not establish that rule. This lesson builds a validated percentage, gives standard traits distinct responsibilities, and then uses closures and iterators to process a batch without dropping errors.

This is a focused library checkpoint supporting the configuration project. It has no environment access, files, or networking. Input grammar is one through three ASCII decimal digits, with leading zeroes permitted. Fractions, signs, surrounding whitespace, and non-ASCII digits are rejected. The result is a whole percentage; the fractional length converter remains a separate domain with a different numeric model.

Plain model: lossless conversion, fallible conversion, and parsing

From<Source> for Destination describes an infallible conversion that fits the type's intended meaning. Our valid Percent always fits in a u16, so converting out is infallible. TryFrom returns a Result because converting a general u16 into a percentage can fail. These traits say more than the method name “convert”: callers can see whether failure must be handled. Implementing From also supplies the corresponding Into conversion through standard blanket implementations; normally implement the source-to-destination trait once.

FromStr handles parsing text. It separates accepted spelling from the numeric domain boundary. Display supplies the chosen user-facing spelling, and Debug supports developer inspection. Our error implements Display and std::error::Error so ordinary callers can preserve a structured error while choosing presentation. Those traits have different purposes; adding every standard trait automatically can accidentally promise behavior the type should not expose.

Percent(u8) is a newtype: a distinct type wrapping one value. Its field is private. External callers cannot construct Percent(255) directly, so the validation boundary is meaningful. It derives equality and ordering because ordinary numeric comparison matches the domain. It derives Copy and Clone because copying this tiny independent value has no ownership or resource-management consequence. A file handle or shared connection would require a different decision.

These reference commands run from projects. The example selects 25 and 100 percent, printing basis points [2500, 10000]. One basis point is one hundredth of a percentage point. The code multiplies a validated whole percentage by one hundred, so its maximum result is 10,000 and fits in u16. That bound justifies the arithmetic without adding a fallible operation that cannot fail under this type's invariant.

Read the complete conversion boundary

projects/reference/p18-core-labs/src/conversions.rs
use std::fmt;
use std::str::FromStr;

/// A whole percentage in 0..=100. Safe callers cannot bypass validation.
///
/// ```
/// use core_rust_labs::conversions::{Percent, PercentError};
/// let percent = Percent::try_from(25u16)?;
/// assert_eq!(u16::from(percent), 25);
/// # Ok::<(), PercentError>(())
/// ```
///
/// The tuple field remains private even though the type itself is public:
/// ```compile_fail
/// use core_rust_labs::conversions::Percent;
/// let invalid = Percent(255);
/// ```
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
pub struct Percent(u8);

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum PercentError {
    Syntax,
    OutOfRange(u16),
}
impl fmt::Display for PercentError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Self::Syntax => f.write_str("expected 1 to 3 ASCII decimal digits"),
            Self::OutOfRange(value) => write!(f, "percentage {value} is outside 0..=100"),
        }
    }
}
impl std::error::Error for PercentError {}

impl TryFrom<u16> for Percent {
    type Error = PercentError;
    fn try_from(value: u16) -> Result<Self, Self::Error> {
        if value > 100 {
            return Err(PercentError::OutOfRange(value));
        }
        // The validated 0..=100 range is a subset of u8's range.
        Ok(Self(value as u8))
    }
}
impl From<Percent> for u16 {
    fn from(value: Percent) -> Self {
        u16::from(value.0)
    }
}
impl FromStr for Percent {
    type Err = PercentError;
    fn from_str(text: &str) -> Result<Self, Self::Err> {
        if text.is_empty() || text.len() > 3 || !text.bytes().all(|b| b.is_ascii_digit()) {
            return Err(PercentError::Syntax);
        }
        let value = text.parse::<u16>().map_err(|_| PercentError::Syntax)?;
        Self::try_from(value)
    }
}
impl fmt::Display for Percent {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}", self.0)
    }
}

/// Parse the whole batch or return its first error; no partial result is published.
pub fn parse_percentages(texts: &[&str]) -> Result<Vec<Percent>, PercentError> {
    texts.iter().map(|text| text.parse()).collect()
}

/// Keep input order and return basis points for values at or above the threshold.
/// Result length is at most input length; no sorting or deduplication is implied.
pub fn selected_basis_points(values: &[Percent], threshold: Percent) -> Vec<u16> {
    values
        .iter()
        .copied()
        .filter(|value| *value >= threshold)
        .map(|value| u16::from(value) * 100) // At most 10,000, which fits u16.
        .collect()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn conversions_preserve_the_declared_range() {
        for value in [0, 1, 99, 100] {
            let percent = Percent::try_from(value).unwrap();
            assert_eq!(u16::from(percent), value);
        }
        for value in [101, 300, u16::MAX] {
            assert_eq!(
                Percent::try_from(value),
                Err(PercentError::OutOfRange(value))
            );
        }
    }

    #[test]
    fn parsing_and_display_have_explicit_normalization() {
        let percent: Percent = "003".parse().unwrap();
        assert_eq!(percent.to_string(), "3");
        assert_eq!(percent.to_string().parse::<Percent>(), Ok(percent));
        for bad in ["", "+3", "-1", "1.0", " 3", "3 ", "0000", "３"] {
            assert_eq!(bad.parse::<Percent>(), Err(PercentError::Syntax));
        }
        assert_eq!("101".parse::<Percent>(), Err(PercentError::OutOfRange(101)));
    }

    #[test]
    fn collection_reports_first_failure_instead_of_dropping_it() {
        assert_eq!(
            parse_percentages(&["25", "101", "bad"]),
            Err(PercentError::OutOfRange(101))
        );
        assert_eq!(
            parse_percentages(&["bad", "101"]),
            Err(PercentError::Syntax)
        );
        assert_eq!(parse_percentages(&[]), Ok(vec![]));
    }

    #[test]
    fn filter_is_inclusive_and_preserves_order_and_duplicates() {
        let values = parse_percentages(&["100", "24", "25", "25", "0"]).unwrap();
        assert_eq!(
            selected_basis_points(&values, Percent::try_from(25).unwrap()),
            [10000, 2500, 2500]
        );
        assert!(selected_basis_points(&[], Percent::try_from(0).unwrap()).is_empty());
    }
}
projects/reference/p18-core-labs/examples/conversions.rs
use core_rust_labs::conversions::{
    Percent, PercentError, parse_percentages, selected_basis_points,
};

fn main() -> Result<(), PercentError> {
    let values = parse_percentages(&["0", "025", "100"])?;
    let threshold: Percent = 25u16.try_into()?;
    println!("threshold percent: {threshold}");
    println!(
        "selected basis points: {:?}",
        selected_basis_points(&values, threshold)
    );
    let numeric: u16 = threshold.into();
    println!("lossless numeric conversion: {numeric}");
    Ok(())
}

The TryFrom implementation checks the domain range before converting to the smaller storage type. Its remaining as u8 cast is justified by the immediately preceding proof: every admitted number is at most one hundred. A cast performed before that check could truncate a larger integer. The difference is the order of validation, not a blanket prohibition on the syntax as.

The parser first checks length and accepted digits. It then parses a u16, converts any syntax failure to the domain's syntax category, and calls the same validated constructor. It does not reproduce the range test in a second place. A future constructor can reuse TryFrom rather than creating another path into private storage. The Display implementation prints the numeric value, so "003" normalizes to "3". Value round-tripping holds; original-byte round-tripping is not promised.

In the example, let numeric: u16 = threshold.into(); gives type inference the destination. Without context, several conversions might be possible and the compiler can ask for an annotation. Such a diagnostic is not evidence that conversion failed at runtime. The program has not yet run. State the intended destination instead of adding arbitrary casts until compilation succeeds.

TryInto: the same checked conversion from the value side

The example writes let threshold: Percent = 25u16.try_into()?;. Read this as “try to convert this u16 into the destination type Percent.” The destination annotation matters because many types could accept an integer. Implementing TryFrom<u16> for Percent supplies the matching TryInto<Percent> through a standard-library blanket implementation: an implementation that applies to every type satisfying its stated trait bounds. We do not implement both sides separately. Percent::try_from(25u16) and 25u16.try_into() reach the same validation rule and return the same error for 101. Similarly, our From<Percent> for u16 supplies Into<u16>. Choose the spelling that makes the destination clearest in context. Neither spelling authorizes narrowing before checking, and the question-mark operator still propagates failure rather than inventing a replacement percentage.

Predict which annotation disappears if you write let threshold = Percent::try_from(25u16)?;, then make only that edit in your reconstructed example. The observed output and boundary tests should remain unchanged. This is a controlled comparison of two API spellings, not evidence that arbitrary numeric casts preserve the contract.

Closures: small functions that can capture context

A closure is a function-like value written with parameters between vertical bars: |value| expression. It can use values from its surrounding scope. The filter closure uses the threshold argument without receiving it as a second closure parameter; that is capture. Capture may borrow, mutably borrow, or own a value depending on use and explicit move. Adding move changes how captures enter the closure; it does not mean every captured value is deeply cloned.

The common callable traits describe how a closure can be invoked. FnOnce permits a call that consumes captured ownership; FnMut permits mutation of captured state between calls; Fn permits calling through shared access. A closure that only reads a copied threshold can satisfy the stronger reusable behavior. Choose bounds according to how the receiving function uses the callback. A one-time observation API should not demand an unnecessary reusable callback merely because a familiar example did so.

Iterators: a lazy sequence of operations

iter() visits borrowed elements. iter_mut() can visit mutable references when the container is mutably borrowed. into_iter() commonly consumes an owned container and yields owned elements. Always inspect the actual implementation and receiver type; an iterator is a protocol for obtaining items, not a promise that every method with a similar name moves the container. In this lab, keeping the caller's vector available is part of the contract, so we begin with borrowed iteration.

copied() changes references to our Copy percentages into independent small values. filter asks a predicate whether to retain an item; its predicate borrows the candidate, which explains the dereference in *value >= threshold. map transforms each retained value into basis points. These adapters are lazy: constructing the pipeline alone does not produce a new vector. collect() consumes it into the requested destination. Input order and duplicates survive unless an operation explicitly changes them.

The parser's destination is Result<Vec<Percent>, PercentError>. Collecting iterator items that are Results returns the first error instead of publishing a partial success. Compare this with a deliberately inappropriate filter_map(|text| text.parse().ok()): that would silently discard failed parses. A compact pipeline is only helpful when it preserves the required semantics. An ordinary loop returning early on error is equally valid and can be clearer when control flow grows.

Intentional mistake: narrowing before validation

In your learner copy, intentionally narrow the input to u8 before comparing it with one hundred. Predict the result for the original u16 value 300. Integer narrowing retains only the representable low bits, producing 44 here, so the defective check admits an invalid original input. Run the constructor boundary test, observe the failing assertion, and restore validation before narrowing. Do not change the test to accept 44; the declared input was 300 percent.

Playbook investigation: the batch became shorter

A colleague changes Result collection to filter_map and reports that “the parser is more tolerant.” The observation is that three supplied strings produce two successful values without an error. Hypothesis A says iteration skipped a valid item. Hypothesis B says a parse failure was discarded. Compare an all-valid batch with a batch containing one invalid middle value, while keeping lengths equal. If only the invalid batch loses an item, the general iteration-skip explanation is disproved.

Use the playbook to record both returned values and error categories. Restore all-or-error behavior if that remains the requirement. If partial success is desired instead, return explicit per-item outcomes with positions; silently deleting an item changes correspondence to the caller's input. Your tests establish the chosen failure order for these cases. They do not establish that a future parallel implementation preserves that order automatically.

Hint 1: list construction routes

A private field is useful only if all public constructors enforce the same invariant. Write the accepted range beside every conversion direction.

Hint 2: make failure observable

The source integer can be invalid, so use TryFrom there. Every valid retry limit fits in u16, so From is appropriate in the other direction. Filter only validated values; do not filter away constructor errors.

Reference approach after your attempt

Validate (1..=5).contains(&value) before storing the value. Keep range rejection separate from text syntax if you also add parsing. Modules, public boundaries, and executable documentation

A Cargo package can contain a library crate and executable crates. A crate is a unit compiled by Rust; a module organizes names within that unit. In this lab, src/lib.rs declares pub mod conversions;, which loads the sibling src/conversions.rs module and exposes its name to users of the library. The example executable imports the public type through core_rust_labs::conversions::Percent. Cargo package names can contain hyphens; the Rust crate path uses underscores here. A module is not automatically another package or a network service.

The pub keyword makes an item visible through an accessible public path. Leaving a field private prevents outside callers from bypassing its constructor. pub(crate) can expose a helper across the current crate without promising it to downstream users. A use declaration brings a name into scope; it does not copy a module or install a dependency. Paths beginning crate:: start at the current crate root, while super:: refers to the parent module. The tests beside the implementation can reach details that external callers cannot, so they do not alone verify the public boundary.

Lines beginning /// document the following item. Rustdoc renders that documentation, and Cargo can compile its fenced Rust examples as documentation tests. Percent's example constructs a valid value and propagates its ordinary error with ?. The hidden final Result line gives the example an appropriate return type. Its separate compile_fail example tries to construct Percent(255) from outside the module; that is supposed to be rejected. Run mise exec -- cargo test --doc in the reconstructed package. A documented example that no longer compiles is a concrete interface defect, not a cosmetic documentation issue.

For a guided API change, add a named read-only getter to your learner type and add a documentation example calling it. Keep the private-field compile-fail test. Then review a proposal to change the accepted maximum from 100 to 80. It can preserve the Rust method signature while rejecting formerly valid callers, so signature compatibility alone does not establish behavioral compatibility. Conversely, adding a new public error variant can affect downstream exhaustive matches. State the old contract, affected clients, migration path, and tests before declaring an API change harmless. A private helper refactor that preserves the public contract has a narrower compatibility obligation.

Your independent review should distinguish four evidence sources: a module-local unit test can exercise internal cases; a separate executable or integration test uses exported paths; a documentation test checks the published example; and a compile-fail example checks a prohibited use. None establishes every future client behavior. For this small lab, the existing example executable and documentation examples exercise the public surface without adding an unnecessary separate framework.

Engineering decisions, evidence, and mastery

The chosen newtype makes a real range rule reusable; standard conversion and formatting traits let callers use familiar interfaces. Private storage and one fallible constructor prevent drift between entry points. The batch API preserves failure rather than hiding it behind a default. A simple validation function would be adequate for a one-off local calculation; a type earns its place when many functions should accept only validated values. Expanding to fractional percentages would require an explicit scale or numeric-model decision, not merely a formatting change.

Four unit tests cover constructor boundaries, normalization, first-error behavior, inclusive filtering, order, and duplicates. The actual lab checks are author evidence, not independent acceptance. For mastery, explain conversion direction, design a newtype for a different rule, translate a pipeline into a loop, and diagnose lost errors without copying the solution. Record both behavior and the reason that behavior is required.

Edition 2024: readable conditional bindings

Rust 1.88 stabilized let chains for edition 2024. A chain evaluates left to right and stops at the first failed match or false condition. Earlier bindings are available to later conditions and the successful branch. Use this when the conditions form one readable decision; use a match when the distinct failure cases need distinct handling.

projects/reference/p18-core-labs/examples/let_chains.rs
//! Edition 2024 let chains: a binding is available only after its pattern matches.
use core_rust_labs::conversions::Percent;

fn positive_percentage(text: Option<&str>) -> Option<Percent> {
    if let Some(text) = text
        && let Ok(value) = text.parse::<Percent>()
        && u16::from(value) > 0
    {
        Some(value)
    } else {
        None
    }
}

fn main() {
    // This example deliberately treats absence, malformed input, and zero alike.
    // A user-facing validator should retain a Result when those causes matter.
    assert_eq!(positive_percentage(Some("25")).map(u16::from), Some(25));
    for text in [None, Some("0"), Some("101"), Some("bad")] {
        assert_eq!(positive_percentage(text), None);
    }
}

From projects/, run mise exec -- cargo run -p core-rust-labs --example let_chains. Predict the outcome for missing, malformed, zero and positive input before running its assertions. This example intentionally collapses rejection causes into None; preserve Result in validation APIs when callers need those causes. Nested if-let remains valid Rust.
