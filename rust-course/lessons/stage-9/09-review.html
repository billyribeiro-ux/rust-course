Purpose: independence is observable work

This assessment asks you to explain, change, debug, test, and review a system without following a sequence of reference edits. A course completion checkbox is a self-report. Your evidence is a specification, implementation, tests, measurements, operational notes, and another person's review. The reference milestone is intentionally bounded; a strong submission identifies missing capabilities and completes chosen extensions without pretending that earlier passing tests prove them.

The change request

Researchers need multiple named experiments. Each experiment has its own starting cash, watchlist, replay range, and simulated orders. A reader can inspect only experiments shared with its team; an operator can submit orders and start replay jobs. A replay job may be cancelled. Users may retry after losing a response. A restart must preserve accepted orders and the current job state. Historical charts must support bounded pagination. No real market account or paid data may be introduced.

Do not open the reference approach yet. Write a plain-English domain model, permission matrix, event ordering policy, numeric rules, and API contract. Decide whether the first implementation remains one process. Add another process only if a measured bottleneck or specific educational isolation requirement justifies it. Explain who owns each transaction, which state is authoritative, and how the UI learns that a cached view is stale.

Prediction and adversarial acceptance criteria

Two operators send distinct orders against the same remaining cash while a replay job changes the current quote. What outcomes are legal? A client receives a timeout immediately after the database commits. What retry is safe? A cancelled worker later tries to publish its report. Which token or status rule rejects it?

Your tests must cover duplicate IDs with identical and conflicting payloads, out-of-order ticks, insufficient cash, role and team boundaries, reconnect after response loss, bounded slow-client behavior, overload rejection, cancellation, restart recovery, rollback after an injected transaction failure, and schema migration from a previous fixture. Define these before implementation so the tests express a contract rather than mirror whatever code you happen to write.

Small baseline you can actually run

Use the existing domain example and deterministic synthetic scenario as a baseline. Record their outputs before making changes. The commands below verify the delivered milestone; they do not verify your future multi-experiment implementation.

mise exec -- cargo run -p p16-workbench --example domain
mise exec -- cargo test -p p16-workbench
mise exec -- cargo test -p p14-scheduler --test postgres -- --ignored
mise exec -- cargo test -p p10-issues --test postgres -- --ignored

The last two commands require their separate disposable database environment variables. A report that says “all tests passed” while these remained ignored must state that limitation. Preserve the exact commands, tool versions, database version, result counts, and relevant logs in your verification record.

Incident packet: incomplete and misleading evidence

After a deployment, users report duplicated paper orders and stale charts. CPU is low. The health route returns200. One log says an order was accepted twice, but the screenshot hides its ID. A database chart shows more connections than yesterday, but workload also doubled. Do not immediately add locks or retry everything.

State at least three competing hypotheses and the observations that would distinguish them. Ask for or generate missing evidence: stable logical IDs, event positions, response timing, database lock waits, client request order, and deployment schema. Reproduce one failure with a minimal deterministic scenario. Disprove at least one plausible hypothesis explicitly. Implement the smallest supported fix, retain the regression, and document what uncertainty remains.

Performance inquiry

Users want a faster replay of one million synthetic ticks. Establish a correctness-preserving baseline before optimizing. Record hardware, Rust version, release profile, input generator, event count, symbol count, ordering distribution, and output digest or exact aggregates. Measure elapsed time and peak memory using tools available on your platform. Compare serial domain processing with any proposed pipeline under the same input and output semantics. A faster implementation that drops duplicates differently or changes order is a different computation.

The current10,000-event journal cap means a million-event experiment requires a deliberate architecture change, not merely passing a larger file. Consider streaming aggregation, bounded chart downsampling, and durable command identity separated from transient tick history. Profile before choosing unsafe code or another process. If the bottleneck is synchronous storage latency, micro-optimizing an enum match is unlikely to matter.

Architecture review and runbook

Submit two alternative designs and their tradeoffs. One should preserve a modular single process; another may isolate replay workers if you can justify queue, lease, and operational costs. Include transaction diagrams, expected resource budgets, migration rollout, old-binary compatibility, rollback limitations, backup/restore rehearsal, and a local failure runbook. Explain authentication separately from authorization; replacing the public fixture identities is required before any deployment outside the local teaching environment.

Tiered hints

Hint 1: reduce the change

Separate experiment identity, account state, command identity, replay input, and display data. Avoid one giant mutable dashboard object shared by every subsystem.

Hint 2: choose atomic boundaries

A submitted order's identity, cash change, holdings change, and fill should commit together. Background-job authority belongs to a lease token, while browser freshness belongs to a monotonically comparable snapshot position.

Separately revealed reference approach

Use PostgreSQL experiment and membership tables, account-scoped row locking or an equivalent intentional concurrency strategy, and a unique command key scoped to experiment. Persist the command fingerprint and result with the ledger mutation in one transaction. Use the scheduler's leased-job pattern for replay reports, with bounded batches and cancellation checked between batches. Give reports immutable IDs and publish completion only from the current token. Serve chart pages by experiment and event position with maximum limits. Use additive migrations, fixtures from the old schema, and an explicit rollback compatibility table. Keep the browser a read model and preserve logical command IDs across retry. These are design directions, not a claim that this entire extension is already implemented.

Evaluation rubric

Score each dimension0 through3: specification and invariants, independent implementation, meaningful tests, failure investigation, authorization and data boundaries, measured performance, operational recovery, and communication. Zero means missing; one means a happy-path demonstration; two means justified behavior with relevant failure tests; three means strong evidence, alternatives, and independent review feedback incorporated. A total is useful for planning practice but is not a professional credential. Any unexplained invariant violation or cross-team write blocks acceptance regardless of total.

Final playbook and mastery check

Before asking for review, separate observations from guesses, list hypotheses and distinguishing experiments, report the disproven hypothesis, and state the fix's remaining limits. Have a reviewer change one requirement and explain the consequences without consulting the reference. The assessment is complete only when your work and its limitations can be understood by someone who did not watch you build it.

When you get stuck

Use the baseline tests to identify the first boundary that differs from your prediction. Consult the earlier transaction, lease, and domain lessons by the failing invariant. Request review with your specification, one minimal failure trace, competing designs, test results, measurements, and a direct question about the decision you cannot yet justify.
