Purpose and milestone boundary

The working capstone milestone combines the earlier Rust browser console with an Axum service, deterministic domain engine, append-only event journal, watchlist, cash, positions, and recent fills. Use the selected Leptos interface from Stage6 as the client and this project's JSON routes as its backend. The delivered modular application uses one local journal writer and one owned background replay worker. It includes persisted job state and cursor recovery, a bounded chart-history endpoint, and a tested read migration from version1 journal records to version2 position-checked records. PostgreSQL-backed multi-experiment transactions and a deployment rollout pipeline remain the independent specification change in the final review; the single-account local application does not claim those capabilities.

Plain-English model: command and read model

A command asks the service to change authoritative state. A snapshot describes state for display. The browser may cache a snapshot, but it cannot decide that an order is valid by checking cached cash alone. The server validates against current state, persists the event, applies it, and returns a result. After a timeout, the browser has uncertainty, not permission to create a new logical order. It retries with the same order ID or refreshes authoritative state.

Leptos owns reactive browser state, while Rust on the server owns domain state. They are different processes with different memory. A signal update does not create a server transaction. Browser WebAssembly cannot use arbitrary server filesystem paths or TCP sockets; it crosses the boundary through browser networking APIs. The course proxy serves UI and API under one local origin, simplifying browser permissions without inventing a cross-origin authentication design.

Prediction

The server appends an event, calls sync_data successfully, and applies it in memory. The network disconnects before the client sees the response. After restart, should the event replay? Should the UI automatically submit a fresh ID?

Answer

The complete accepted record should replay under the stated filesystem assumptions. The client should preserve the original logical ID. A fresh ID creates another command. A successful sync_data is evidence about the file operation, not a universal guarantee against every hardware or filesystem failure.

Guided integration

Begin with read-only snapshot polling. Display loading before the first response, empty state when no quote exists, an error with a retry action when fetching fails, and stale-state information if an earlier snapshot remains visible. Add a labeled order form only after that flow works. Validate obvious input locally for usability, but retain server validation as authority. Disable repeated submission while a request is pending, and keep the same logical order ID until its outcome is resolved.

Inspect the HTTP module. Public demo-reader and demo-operator identities exercise read/write boundaries on loopback. Unauthorized requests fail; reader mutations are forbidden. This is not a login implementation. The JSON body is limited to16,384 bytes to accommodate bounded replay specifications. An outer semaphore admits at most16 active requests and applies a five-second handler/body deadline. A second semaphore admits at most eight snapshot, mutation, or replay blocking jobs; excess requests receive429. A deadline can expire while already-started blocking work continues, so408 means an uncertain command outcome and retries must preserve logical identity. File operations run through spawn_blocking so a synchronous disk sync does not block a Tokio worker thread. The standard mutex protects the complete validation-persist-apply operation and is never held across an await point in async code.

pub struct Error(StatusCode, &'static str);
impl IntoResponse for Error {
    fn into_response(self) -> Response {
        (self.0, Json(serde_json::json!({"error":self.1}))).into_response()
    }
}
fn authorize(headers: &HeaderMap, write: bool) -> Result<(), Error> {
    match headers.get("authorization").and_then(|v| v.to_str().ok()) {
        Some("Bearer demo-operator") => Ok(()),
        Some("Bearer demo-reader") if !write => Ok(()),
        Some("Bearer demo-reader") => Err(Error(StatusCode::FORBIDDEN, "operator required")),
        _ => Err(Error(
            StatusCode::UNAUTHORIZED,
            "local demo identity required",
        )),
    }
}
#[derive(Clone)]
struct Admission {
    permits: Arc<tokio::sync::Semaphore>,
    deadline: std::time::Duration,
}
async fn admit(State(budget): State<Admission>, request: Request, next: Next) -> Response {
    let Ok(_permit) = budget.permits.try_acquire_owned() else {
        return Error(StatusCode::TOO_MANY_REQUESTS, "request budget full").into_response();
    };
    match tokio::time::timeout(budget.deadline, next.run(request)).await {
        Ok(response) => response,
        Err(_) => Error(
            StatusCode::REQUEST_TIMEOUT,
            "request deadline; retry with same logical identity",
        )
        .into_response(),
    }
}
pub fn router(store: Shared) -> Router {
    router_with_admission(
        store,
        Admission {
            permits: Arc::new(tokio::sync::Semaphore::new(16)),
            deadline: std::time::Duration::from_secs(5),
        },
    )
}
fn router_with_admission(store: Shared, admission: Admission) -> Router {
    Router::new()
        .route("/health", get(|| async { "simulated workbench ok" }))
        .route("/api/snapshot", get(snapshot))
        .route("/api/ticks", post(tick))
        .route("/api/orders", post(order))
        .route("/api/orders/{id}", get(order_result))
        .route("/api/watchlist", put(watchlist))
        .route("/api/history", get(history))
        .route("/api/jobs", get(jobs))
        .route("/api/jobs/replay", post(schedule))
        .route("/api/jobs/{id}/cancel", post(cancel))
        .layer(DefaultBodyLimit::max(16384))
        .layer(middleware::from_fn_with_state(admission, admit))
        .with_state(store)
}
async fn snapshot(State(s): State<Shared>, h: HeaderMap) -> Result<Json<crate::Snapshot>, Error> {
    authorize(&h, false)?;
    let permit = WORK
        .try_acquire()
        .map_err(|_| Error(StatusCode::TOO_MANY_REQUESTS, "work budget full"))?;
    let value = tokio::task::spawn_blocking(move || {
        let _permit = permit;
        s.lock().map(|s| s.engine.snapshot()).map_err(|_| ())
    })
    .await
    .map_err(|_| Error(StatusCode::SERVICE_UNAVAILABLE, "worker unavailable"))?
    .map_err(|_| Error(StatusCode::SERVICE_UNAVAILABLE, "state unavailable"))?;
    Ok(Json(value))
}
async fn commit(s: Shared, event: Event) -> Result<Json<serde_json::Value>, Error> {
    let permit = WORK
        .try_acquire()
        .map_err(|_| Error(StatusCode::TOO_MANY_REQUESTS, "work budget full"))?;
    let applied = tokio::task::spawn_blocking(move || {
        let _permit = permit;
        s.lock()
            .map_err(|_| crate::CommitError::Storage("state unavailable".into()))?
            .commit(event)
    })
    .await
    .map_err(|_| Error(StatusCode::SERVICE_UNAVAILABLE, "worker unavailable"))?
    .map_err(|error| match error {
        crate::CommitError::Rejected(reason) => Error(StatusCode::UNPROCESSABLE_ENTITY, reason),
        crate::CommitError::Conflict(reason) => Error(StatusCode::CONFLICT, reason),
        crate::CommitError::Storage(reason) => {
            eprintln!("workbench storage outcome uncertain: {reason}");
            Error(
                StatusCode::SERVICE_UNAVAILABLE,
                "storage unavailable; preserve logical identity and reconcile",
            )
        }
    })?;
    Ok(Json(
        serde_json::json!({"applied":applied,"simulated":true}),
    ))
}
async fn tick(
    State(s): State<Shared>,
    h: HeaderMap,
    Json(t): Json<Tick>,

    authorize(&h, true)?;
    commit(s, Event::Tick(t)).await
}

#[derive(serde::Deserialize)]
struct HistoryPage {
    after: Option<u64>,
    limit: Option<usize>,
}
async fn inspect<T: Send + 'static>(
    s: Shared,
    read: impl FnOnce(&crate::Engine) -> Result<T, &'static str> + Send + 'static,
) -> Result<T, Error> {
    let permit = WORK
        .try_acquire()
        .map_err(|_| Error(StatusCode::TOO_MANY_REQUESTS, "work budget full"))?;
    tokio::task::spawn_blocking(move || {
        let _permit = permit;
        let store = s
            .lock()
            .map_err(|_| Error(StatusCode::SERVICE_UNAVAILABLE, "state unavailable"))?;
        read(&store.engine)
            .map_err(|_| Error(StatusCode::BAD_REQUEST, "invalid request or expired cursor"))
    })
    .await
    .map_err(|_| Error(StatusCode::SERVICE_UNAVAILABLE, "worker unavailable"))?
}
async fn history(
    State(s): State<Shared>,
    h: HeaderMap,
    Query(p): Query<HistoryPage>,
) -> Result<Json<crate::replay::History>, Error> {
    authorize(&h, false)?;
    inspect(s, move |e| {
        e.history(p.after.unwrap_or(0), p.limit.unwrap_or(100))
    })
    .await
    .map(Json)
}
async fn jobs(
    State(s): State<Shared>,
    h: HeaderMap,
) -> Result<Json<Vec<crate::replay::JobView>>, Error> {
    authorize(&h, false)?;
    inspect(s, |e| Ok(e.jobs())).await.map(Json)
}
async fn schedule(
    State(s): State<Shared>,
    h: HeaderMap,
    Json(spec): Json<crate::replay::ReplaySpec>,
) -> Result<Json<serde_json::Value>, Error> {
    authorize(&h, true)?;
    commit(s, Event::ScheduleReplay(spec)).await
}
async fn cancel(
    State(s): State<Shared>,
    h: HeaderMap,
    Path(id): Path<String>,
) -> Result<Json<serde_json::Value>, Error> {
    authorize(&h, true)?;
    commit(s, Event::CancelReplay { job_id: id }).await
}
/// One worker, one durable tick per poll; shares the request admission budget.
pub async fn worker(store: Shared, mut stop: tokio::sync::watch::Receiver<bool>) {
    let mut interval = tokio::time::interval(std::time::Duration::from_millis(100));
    loop {
        tokio::select! {_=stop.changed()=>break,_=interval.tick()=>{
         let Ok(permit)=WORK.try_acquire() else{continue;};let state=store.clone();
         match tokio::task::spawn_blocking(move||{let _permit=permit;state.lock().map_err(|_|crate::CommitError::Storage("state unavailable".into()))?.advance_replay()}).await{Ok(Ok(_))=>{},Ok(Err(error))=>{eprintln!("replay worker stopped after storage error: {error}");break;},Err(error)=>{eprintln!("replay worker join error: {error}");break;}}
        }}
    }
}

async fn order_result(
    State(s): State<Shared>,
    h: HeaderMap,
    Path(id): Path<String>,
) -> Result<Json<crate::Fill>, Error> {
    authorize(&h, false)?;
    let result = inspect(s, move |e| Ok(e.fill(&id).cloned())).await?;
    result
        .map(Json)
        .ok_or(Error(StatusCode::NOT_FOUND, "order not found"))
}

Persistence and intentional failure

Each new journal record carries version2, a contiguous record position, and one event. The reader accepts legacy version1 fixtures, supplies their historical position while replaying, and writes subsequent records in version2. A migration test loads a real version1 fixture, appends a version2 record, reopens it, then rejects a deliberately corrupted position. Startup reads at most16,384 bytes per record and rejects incomplete or oversized records. It also enforces a10,000-record session limit. There is no checksum or automatic tail repair in this capstone store. It rejects detected framing, schema, position, and domain violations and asks you to preserve the file for diagnosis. Valid-looking alterations can still pass: without a checksum, changing a price to another legal price may produce a different valid replay. It does not authenticate history or detect every corruption. The earlier key-value project teaches more elaborate corruption handling; reusing its lessons here requires explicit engineering and tests.

In a copied disposable journal, append an incomplete JSON fragment. Restart should fail, not silently ignore the record. Never perform this experiment on your only learner history. If a live append or sync fails, the Store marks itself uncertain and rejects later writes. That prevents compounding an ambiguous partial write. Recovery requires inspection and a tested policy, not simply clearing the error flag.

Independent practice

Extend the existing chart endpoint with time-bucket aggregation, preserving its event-position cursor and maximum response size. Then add experiment-scoped replay reports while retaining the current persisted job cursor and cancellation semantics. Decide whether a report represents every accepted tick or an aggregation, and how input identity prevents a retry becoming a new job. Write acceptance criteria first and include reconnect, duplicate submission, slow client, and restart scenarios.

Hint 1

Chart rendering should not force the server to return an unbounded lifetime history.

Hint 2

A replay job should emit deterministic domain events or a versioned report, not mutate UI state directly.

Reference approach

Keep immutable source events, a bounded query result, and a clear cursor contract. A job owns its input range and parameters; retries reuse that job ID. Publish progress as an observed value, and distinguish a cancellation request from proof that no work occurred. If migrating to PostgreSQL, atomically persist command identity and domain changes together.

Review and evidence

Tests establish domain invariants, HTTP role boundaries, restart from complete records, persisted job cursor/cancellation recovery, history bounds, legacy migration, injected append failure, overload rejection before mutation, an actual slow-body deadline, and worker shutdown. The concurrency budgets protect active handlers and blocking work, while pre-handler network connections and OS-level disk quotas remain separate operational concerns. Polling full bounded snapshots supports simple reconnection, but it does not provide a continuous event stream or guarantee no intermediate quote is missed. Do not call this a real-time market feed.

Playbook investigation and mastery

Observation: the UI shows old cash after a successful order. Tempting hypothesis: persistence failed. Compare the HTTP command result, a fresh snapshot, and a reopened journal. If both server views agree, persistence failure is disproven for this case; inspect reactive state replacement, fetch caching, and request ordering. An older poll response can overwrite a newer one unless the client compares event counts or sequences requests. Implement that guard, then explain its limits under multiple independent accounts and future snapshot versions.

When you get stuck

Run the domain example first, then python3 reference/p16-workbench/synthetic.py with the backend running. Compare raw snapshot JSON with displayed values. Consult the Stage6 Leptos resource/action guidance for client state. Ask for review with request order, event counts, journal path, and one minimal stale-render reproduction.

Historical replay and persistent background work

POST /api/jobs/replay accepts {"job_id":"replay-1","ticks":[{"event_id":"replay-1-t1","symbol":"LAB","price_cents":125,"sequence":1}]} under the operator fixture. Each job holds1 through64 validated tick descriptions; at most16 jobs are retained. An identical submission returns applied:false, and conflicting reuse of a job ID is rejected. The worker processes one tick per100ms poll. A ReplayStep journal event identifies the job and expected cursor; replay of that event updates the quote/history and cursor together. Restart resumes the next persisted cursor. An invalid domain tick becomes a persisted failed job without partially changing the quote.

GET /api/jobs returns bounded progress summaries. POST /api/jobs/{id}/cancel records cancellation and rejects later unprocessed steps. A cancellation racing with a step is serialized by the same store ownership: an already committed step remains real, while later steps stop. This job performs only local deterministic domain work, so it does not need an external-effect lease protocol; use Project14 when execution crosses process/effect boundaries.

GET /api/history?after=0&limit=100 returns chart points with event_position, symbol, integer price, and per-symbol sequence. At most1,024 points are retained in the read model and a page returns at most256. Old cursors are rejected rather than silently returning a gap. The complete bounded journal reconstructs this read model on startup. These positions order accepted events; they are not wall-clock timestamps. Multi-source physical-time analysis is a further domain choice.

//! Persisted, bounded replay jobs inside the single-writer modular application.
//! Every step journals the job cursor and tick effect together; no external effects.
use crate::{Engine, Event, Store, Tick};
use serde::{Deserialize, Serialize};
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct ReplaySpec {
    pub job_id: String,
    pub ticks: Vec<Tick>,
}
#[derive(Debug, Clone, Serialize, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum ReplayStatus {
    Queued,
    Running,
    Completed,
    Cancelled,
    Failed,
}
#[derive(Debug, Clone)]
pub(crate) struct ReplayJob {
    pub spec: ReplaySpec,
    pub next: usize,
    pub status: ReplayStatus,
    pub error: Option<String>,
}
impl ReplayJob {
    pub fn active(&self) -> bool {
        matches!(self.status, ReplayStatus::Queued | ReplayStatus::Running)
    }
}
#[derive(Debug, Clone, Serialize, PartialEq, Eq)]
pub struct JobView {
    pub job_id: String,
    pub next: usize,
    pub total: usize,
    pub status: ReplayStatus,
    pub error: Option<String>,
}
#[derive(Debug, Clone, Serialize, PartialEq, Eq)]
pub struct ChartPoint {
    pub event_position: u64,
    pub symbol: String,
    pub price_cents: i64,
    pub sequence: u64,
}
#[derive(Debug, Clone, Serialize, PartialEq, Eq)]
pub struct History {
    pub points: Vec<ChartPoint>,
    pub oldest_position: Option<u64>,
    pub latest_position: Option<u64>,
}
impl Engine {
    pub fn jobs(&self) -> Vec<JobView> {
        self.jobs
            .values()
            .map(|j| JobView {
                job_id: j.spec.job_id.clone(),
                next: j.next,
                total: j.spec.ticks.len(),
                status: j.status.clone(),
                error: j.error.clone(),
            })
            .collect()
    }
    pub fn history(&self, after: u64, limit: usize) -> Result<History, &'static str> {
        if !(1..=256).contains(&limit) {
            return Err("history limit outside 1..=256");
        }
        let oldest = self.history.front().map(|p| p.event_position);
        if after != 0 && oldest.is_some_and(|p| after < p.saturating_sub(1)) {
            return Err("history cursor expired; restart from after=0");
        }
        Ok(History {
            points: self
                .history
                .iter()
                .filter(|p| p.event_position > after)
                .take(limit)
                .cloned()
                .collect(),
            oldest_position: oldest,
            latest_position: self.history.back().map(|p| p.event_position),
        })
    }
}
impl Store {
    /// Executes one bounded, durable cursor increment. A process restart resumes the cursor.
    /// No retry timer is needed for CPU-only deterministic work; invalid domain input becomes failed.
    pub fn advance_replay(&mut self) -> Result<bool, crate::CommitError> {
        let Some(job) = self.engine.jobs.values().find(|j| j.active()) else {
            return Ok(false);
        };
        let event = Event::ReplayStep {
            job_id: job.spec.job_id.clone(),
            index: job.next,
        };
        let event = match self.engine.validate(&event) {
            Ok(_) => event,
            Err(reason) => Event::FailReplay {
                job_id: job.spec.job_id.clone(),
                reason: reason.to_owned(),
            },
        };
        self.commit(event)
    }
}

Migration and rollback checkpoint

Copy the legacy fixture into a new disposable learner-data path, start the service on it, and inspect the restored cash and holdings. Submit a watchlist change and confirm the new record has version2 and position3. Preserve a backup before the experiment. The old version1-only binary cannot read the new records, so binary-only rollback after a new write is incompatible. Rollback requires the preserved old journal or an explicitly tested reverse migration that accounts for new job event kinds; the course does not silently discard those events.

Engineering decisions and evidence

Scope and invariants: one simulated account, whole units/integer cents, bounded symbol/event/job/history sizes, immutable logical identity, one journal owner, persisted replay cursor, reader/operator route boundary. Why this design: a modular process and deterministic engine make invariant and restart reasoning direct; a bounded blocking pool keeps synchronous journal operations out of runtime threads. The mutex spans validation, durable append, and application so those checked facts cannot change between steps. No synchronous guard crosses await.

Concrete habits: validate every mutation first; use checked arithmetic; preserve command IDs after timeout; fail closed on incomplete records; bound history pages and worker steps; test authorization at HTTP boundaries. Every expect in domain application describes an invariant just checked under exclusive ownership, while untrusted input returns an error. Alternative: PostgreSQL is appropriate when independent writers, richer transactions, or queryable histories become requirements; Project10 supplies the transaction pattern. Evidence: tests cover domain invariants, migration, restart, cancellation, append failure, overload and slow bodies; no hardware durability, authentication, or unmeasured capacity claim follows. Evolution threshold: move beyond one writer only with a new transaction/identity contract and concurrency tests. Production identity, TLS, OS connection/disk limits, and a full restore rehearsal remain explicit deployment work.

Preserving the storage boundary and reconciling old commands

Store exposes commit for mutation and a read-only snapshot; its engine is not a public mutable field. A compile-fail documentation test demonstrates that external callers cannot bypass the journal through that field. During recovery, a duplicate already-applied logical command is rejected as malformed journal history rather than silently counted. This preserves agreement between physical records and accepted events, and the writer independently enforces its physical10,000-record limit.

GET /api/orders/{id} returns the original persisted fill even after it leaves the latest100 snapshot entries. This gives a reconnecting client a precise reconciliation path. IDs are identity, not chronology: newest fills are tracked by acceptance order. Read permission is checked before lookup, and an unknown ID returns404. A timeout followed by a found fill establishes an accepted command; absence alone still needs the application’s current uncertainty policy if a write may be in progress.

A definite rejection is different from an uncertain commit

The store now returns a typed CommitError. Expected validation failures detected before append—such as a missing quote, insufficient simulated cash, or a full budget—produce HTTP422 and a safe domain explanation. Reusing a known event, order, or job ID with different content produces409. An I/O failure, a poisoned store, or any inconsistency after append produces503; the store stops further writes when its journal state is uncertain. No failure after the append boundary is reported as a definite input rejection.

For a first attempt,422 means that attempt did not commit and the form can be edited. After an earlier unknown outcome, a retry receiving422 or429 does not prove the earlier attempt failed: its retained identity must remain until exact result reconciliation. API regression tests distinguish missing-quote and insufficient-cash422 responses, conflicting identity409, and injected writer failure plus poisoned-store503 responses. Tests also assert that definite rejection leaves domain state unchanged.

Configuration is an input boundary too

The executable reads WORKBENCH_LOG as a native path with var_os and PathBuf: a native filename must not silently become the default journal merely because text conversion fails. WORKBENCH_ADDR is text and must parse as a loopback socket address. Only absence selects its default; invalid text is an error before journal I/O. A focused executable fixture rejects malformed and non-loopback addresses without creating state, then starts successfully with a Unicode native filename. This macOS filesystem rejected a non-UTF-8 byte filename; the executable propagated that I/O failure without creating a fallback journal. This checks the local configuration boundary; it is separate from the HTTP acceptance suite.

Read failures retain their meaning

Jobs, history and exact order lookup share a bounded inspect helper. A bad history limit or expired cursor is HTTP400; an unavailable or poisoned state owner is HTTP503. Combining those errors would tell a caller to change a valid request when the service actually needs recovery. The api_contract regression deliberately panics while holding the mutex in an owned fixture, then checks all four read routes. Ordinary snapshot reads and mutation errors already used503; the audit corrected the other readers to match. This injected panic tests classification, not a claim that every application panic is recoverable.

Replay requests need retained identity too

The Leptos console retains the exact replay job ID and tick payload after an ambiguous response and offers Retry retained replay. Later quotes cannot change that retry. A later422 or429 cannot erase uncertainty from an earlier attempt; acceptance or a definite rejection of the first attempt clears the retained submission. New replay identity stays blocked while it is unresolved. This state belongs to the open page and does not persist across reload: keep the page open and reconcile durable jobs before creating another instruction. The shared native model tests these transitions, while real browser interaction remains a separate check. See the console retry evidence.

A server banner must not launch unobserved work

Both required startup lines are written and flushed before spawning the replay worker. If stdout is closed, startup returns an ordinary I/O error; opening the configured journal may have created an empty file, but the worker has not been launched to commit replay steps. A child-process check uses a private journal, observes BrokenPipe without a panic, and confirms the empty journal remains empty.

The main task retains the shutdown sender even if serving fails. It selects one pinned server future against Ctrl-C, signals graceful shutdown, and awaits that same future. After serving ends for any reason, it signals and joins the replay worker before returning a saved server, worker or signal-registration error. The owned-process smoke test fetches health and then sends SIGINT, while the larger runtime audit separately covers replay, overload and restart behavior. These scopes are distinguished in the output/lifecycle report.
