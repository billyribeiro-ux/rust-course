Pinning and preserving progress across await

Keep one future alive across repeated polls, and distinguish a total deadline from an idle timeout.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Purpose: a busy input must not postpone its deadline forever

A service operation should collect messages for at most ten milliseconds of runtime time. Messages arrive every four milliseconds. If receiving a message starts a fresh ten-millisecond timer, the operation can continue indefinitely under steady input. That program implements an idle timeout rather than the promised total deadline. This lesson gives the operation one timer whose state survives each trip through the selection loop, then uses that concrete need to explain pinning.

Plain-English model: a paused computation is a value

Calling an async function creates a future: a value that represents work and its progress. An executor polls that future. Poll can return Ready with its result, or Pending after arranging for useful progress to cause a wakeup. A wakeup asks the executor to poll again; it does not promise immediate execution. State needed after await is retained in the future. Some such states can contain relationships that would become invalid if the stored value moved after polling began.

Pin is an API contract for a pointer to a value whose location must remain stable when that type requires it. It does not freeze every field, select a physical stack address in advance, or automatically make a program faster. Unpin marks types that do not need this restriction. Most ordinary types are Unpin; a particular future, such as Tokio's Sleep, may not be. Moving a pinned owning pointer is different from moving the value it points to. A Pin<Box<T>> can move its handle while retaining the allocation holding T.

The standard Future polling interface receives a pinned mutable reference. That lets an executor honor the future's contract while the future advances its internal state. This lesson does not implement raw-pointer projection or unsafe pinning. We use the runtime's documented pinning macro and the safe APIs of an existing future. Knowing when not to implement a custom Future is useful engineering judgment.

Prediction: total time versus silence between messages

At virtual time zero, collection begins with a deadline at 10. Input arrives at 4,8,12 and16. Predict the accepted items if the timer is created once at the beginning. Then predict the deadline if a fresh ten-unit sleep is created after each input. State whether these are two implementations of the same contract or two different contracts.

Prediction explained

The absolute-deadline implementation collects the first two items and stops at 10. Recreating a relative sleep after each item postpones expiration; with an open channel and no more input, it can stop at 26. That can be a valid inactivity policy when explicitly required. It is a defect when the specification promises a total operation budget. Do not call every simple timer reset unprofessional; name the requirement that makes it wrong here.

projects/reference/p19-concurrency-labs/src/deadlines.rs
use tokio::{
    sync::{mpsc, watch},
    time::{Instant, sleep_until},
};

pub const MAX_ITEMS: usize = 1024;
#[derive(Debug, PartialEq, Eq)]
pub enum Stop {
    Deadline,
    Cancelled,
    Closed,
    Limit,
}
#[derive(Debug, PartialEq, Eq)]
pub struct Report {
    pub items: Vec<u8>,
    pub stop: Stop,
}
#[derive(Debug, PartialEq, Eq)]
pub struct InvalidBudget;
impl std::fmt::Display for InvalidBudget {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.write_str("maximum item count exceeds 1024")
    }
}
impl std::error::Error for InvalidBudget {}

/// Reuse one pinned timer for the entire collection operation.
/// An observed true shutdown wins; a ready deadline is checked before data or
/// false-valued watch updates. A dropped shutdown owner also ends collection.
/// The caller retains receiver ownership and any unread queued items.
pub async fn collect_until(
    receiver: &mut mpsc::Receiver<u8>,
    deadline: Instant,
    shutdown: &mut watch::Receiver<bool>,
    maximum: usize,
) -> Result<Report, InvalidBudget> {
    if maximum > MAX_ITEMS {
        return Err(InvalidBudget);
    }
    let mut items = Vec::with_capacity(maximum);
    let timer = sleep_until(deadline);
    tokio::pin!(timer);
    loop {
        if *shutdown.borrow() {
            return Ok(Report {
                items,
                stop: Stop::Cancelled,
            });
        }
        if items.len() == maximum {
            return Ok(Report {
                items,
                stop: Stop::Limit,
            });
        }
        tokio::select! {
            biased;
            _ = &mut timer => {
                let stop = if *shutdown.borrow() { Stop::Cancelled } else { Stop::Deadline };
                return Ok(Report { items, stop });
            }
            changed = shutdown.changed() => {
                if changed.is_err() || *shutdown.borrow() { return Ok(Report { items, stop: Stop::Cancelled }); }
            }
            next = receiver.recv() => match next {
                Some(value) => items.push(value),
                None => return Ok(Report { items, stop: Stop::Closed }),
            }
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::time::Duration;
    #[tokio::test(start_paused = true)]
    async fn steady_arrivals_do_not_restart_the_absolute_deadline() {
        let (sender, mut receiver) = mpsc::channel(4);
        let (shutdown_owner, mut shutdown) = watch::channel(false);
        let producer = tokio::spawn(async move {
            for value in 1..=4 {
                tokio::time::sleep(Duration::from_millis(4)).await;
                if sender.send(value).await.is_err() {
                    return;
                }
            }
        });
        let start = Instant::now();
        let report = collect_until(
            &mut receiver,
            start + Duration::from_millis(10),
            &mut shutdown,
            10,
        )
        .await
        .unwrap();
        assert_eq!(
            report,
            Report {
                items: vec![1, 2],
                stop: Stop::Deadline
            }
        );
        assert_eq!(Instant::now() - start, Duration::from_millis(10));
        producer.abort();
        assert!(producer.await.unwrap_err().is_cancelled());
        drop(shutdown_owner);
    }
    #[tokio::test(start_paused = true)]
    async fn limit_preserves_unread_channel_items() {
        let (sender, mut receiver) = mpsc::channel(2);
        sender.send(7).await.unwrap();
        sender.send(8).await.unwrap();
        let (owner, mut shutdown) = watch::channel(false);
        let report = collect_until(
            &mut receiver,
            Instant::now() + Duration::from_secs(1),
            &mut shutdown,
            1,
        )
        .await
        .unwrap();
        assert_eq!(
            report,
            Report {
                items: vec![7],
                stop: Stop::Limit
            }
        );
        assert_eq!(receiver.recv().await, Some(8));
        drop(owner);
    }
    #[tokio::test(start_paused = true)]
    async fn closed_cancelled_and_invalid_are_distinct() {
        let (sender, mut receiver) = mpsc::channel(1);
        drop(sender);
        let (owner, mut shutdown) = watch::channel(false);
        assert_eq!(
            collect_until(
                &mut receiver,
                Instant::now() + Duration::from_secs(1),
                &mut shutdown,
                2
            )
            .await
            .unwrap()
            .stop,
            Stop::Closed
        );
        owner.send(true).unwrap();
        assert_eq!(
            collect_until(&mut receiver, Instant::now(), &mut shutdown, 2)
                .await
                .unwrap()
                .stop,
            Stop::Cancelled
        );
        assert_eq!(
            collect_until(&mut receiver, Instant::now(), &mut shutdown, MAX_ITEMS + 1).await,
            Err(InvalidBudget)
        );
    }
}

Explain the retained future

sleep_until(deadline) creates one Sleep future outside the loop. tokio::pin!(timer) pins that local value safely. Each select call borrows it again with &mut timer; it does not create another timer or take ownership away from the operation. The selected temporary reborrow can end while the original timer and its registration remain alive. Dropping the whole operation ends the owner's lifetime and drops its timer.

Compare this with Box::pin. Boxing would create an owned pinned allocation that can be returned or stored beyond a local scope. It is unnecessary for this local operation. Pinning does not inherently require a heap allocation. Neither a browser animation nor the presence of a Box proves a type's safety obligations; the Rust types and the implementation's invariants establish what callers may do.

The collection function borrows the receiver and shutdown watcher. The caller still owns the channel endpoints. Successfully received items move into the report, while unread queued values remain in the receiver when the operation returns. Capacity is at most 1,024, validated before allocation. A zero maximum completes immediately with Limit unless shutdown was already observed. A future deadline, a closed data channel, a reached item limit and cancellation have distinct result variants. Distinguishing them makes a caller's retry or shutdown decision reviewable.

The selection uses an explicit priority. A shutdown value already observed as true stops collection. Otherwise a ready deadline is checked before ordinary watch updates or data; its branch rechecks the shutdown value. This avoids letting repeated false-valued watch updates postpone an expired deadline. Closing the shutdown sender also ends collection when that event is selected. No synchronous mutex guard crosses await. The example holds its shutdown sender until collection ends: dropping it early would be a real control message, not an irrelevant local cleanup.

Cancellation safety is about retained progress

Tokio documents receiving from its bounded mpsc receiver as cancellation safe for use in select: canceling an uncompleted receive does not remove a message from the channel. That property is specific to the operation. A composite future that has already consumed half a network frame may retain progress only inside itself. If a loop drops and recreates that future whenever another branch wins, consumed bytes do not reappear on the socket. The chat project's persistent reader future exists for that reason.

Keeping the future alive preserves its state; pinning satisfies the constraints required to poll that value in place. These are connected ideas, not synonyms. A type can be Unpin while still holding important progress that must not be thrown away. Conversely, pinning a future does not make its externally visible effects reversible. If cancellation follows a database commit, dropping the client future cannot uncommit the transaction.

Deliberate mistake: demanding an unrestricted mutable reference

The intentionally failing file exercises/concurrency/pinned_get_mut.rs creates a value containing PhantomPinned, pins it in a Box and then calls get_mut on the pinned reference. From the course folder run mise exec -- rustc --edition 2024 exercises/concurrency/pinned_get_mut.rs. Expected result: E0277 because the type does not satisfy Unpin. This fixture demonstrates a type boundary; it is not a sound self-referential container implementation.

Do not repair the error by adding unsafe pointer code you cannot justify or by declaring Unpin without understanding the type. For an ordinary value that does not require address stability, choose an ordinary mutable reference from the start. For Sleep, use its documented pinned methods, such as reset when intentionally implementing a new deadline policy. The safe reference collector needs no raw pointers.

Playbook investigation: the deadline keeps moving

Observation: a monitor under steady input does not stop at the promised total budget. Hypothesis A says runtime scheduling is occasionally late. Hypothesis B says the program recreates a relative timer whenever another branch completes. Instrument creation and expiry instants with synthetic timestamps; reduce to one receiver and four planned messages. Under Tokio's paused test clock, the reference stops exactly at virtual10 with two items. A recreated relative timer has a different expected timeline. That controlled experiment weakens scheduling delay as the explanation for this minimal reproduction.

The tests enable Tokio's test-util feature only for development. Paused time controls Tokio's clock in the test runtime; it does not virtualize arbitrary OS threads, blocking filesystem calls or remote servers. An exact virtual-time assertion checks our timer ownership and selection logic, not a promise about ten-millisecond wall-clock latency on a loaded machine. The producer task is explicitly aborted and awaited after the deadline test, so it cannot silently keep running in the background.

Guided project increment

Trace the health monitor's endpoint deadline from argument validation to each retry attempt. Write which instant bounds the whole operation and which duration bounds one attempt. In a learner copy, extract a small bounded receiver collection step using this reference's signature. Begin with the closed-channel example; then add the already-cancelled case and the steady-arrival timeline before connecting real network I/O. Use a separately retained timer or a fixed absolute instant whenever the budget belongs to the entire operation.

Do not introduce spawning merely to call select. Its branches are polled concurrently on the current task; they do not automatically execute on different OS threads. Blocking CPU work inside a branch can prevent the timer from being polled at all. Move genuinely blocking work to an appropriate bounded worker design and explain what cancellation can interrupt. A deadline future is cooperative scheduling, not an operating-system kill switch.

Independent practice and tiered hints

Implement an explicitly named idle-timeout variant, and test how its timeline differs. Specify the result when cancellation, channel closure, a full item limit and deadline all become observable together. Add a test proving that unread values remain available after Limit. Finally, explain how a partially decoded frame could be lost even though each individual socket read is memory safe.

Hint 1

Write an event timeline before editing. Decide whether a successfully received item is supposed to extend the allowed time.

Hint 2

For idle time, retain one pinned Sleep and reset it through its documented pinned API after accepting a message. Keep a separate absolute deadline if both limits are required.

Reference approach

An idle variant can reset its timer to now plus the idle interval after each accepted value. Its contract must name that extension. A combined policy keeps a fixed total deadline and uses the earlier of that instant and the current idle deadline. Tests need a steady stream, a long silent interval and simultaneous stop conditions. For framed I/O, retain the parser future or move partially consumed bytes into a persistent decoder buffer rather than discarding them whenever another branch wins.

Engineering decisions, evidence and mastery

The implementation uses a borrowed bounded receiver, one locally pinned timer, a bounded output vector and an explicit stop enum. Pinning is justified by an actual !Unpin timer; heap pinning and unsafe projection are omitted because they add no capability this operation needs. Seven laboratory tests cover atomic and temporal contracts, including the controlled deadline, unread items and cancellation distinctions. The intentional compiler fixture separately confirms the expected trait restriction. These checks do not establish browser timing, remote service behavior or every scheduler interleaving.

When you get stuck, identify which value owns the progress and which value is dropped when a branch loses. Share the smallest timer/channel program, predicted timeline, observed stop reason and pinned API documentation. You are ready to move on when you can explain why the timer survives each selection, change the deadline policy without accidental resets, and debug a lost-progress example without treating Pin as a magic performance annotation.
