Atomic operations, application races, and publication

Choose synchronization from the invariant: one atomic operation is not a transaction over your whole algorithm.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Ownership crosses thread boundaries
  • Distinguish a data race from a race in application logic
  • Use compare-exchange to preserve a single-counter reservation invariant
  • Explain Relaxed versus Release/Acquire and the limits of SeqCst
  • Prevent deadlock through ownership and a consistent lock order

Purpose: reserve work without inventing capacity

An indexer has room for one more job. Two workers each inspect the remaining capacity, decide there is room, and reserve it. Every memory access can be legal Rust while the application admits two jobs into one slot. This lesson separates memory safety from the business invariant, then asks what synchronization actually protects that invariant. Do not replace the indexer's channels with atomic counters merely because atomics sound faster. Its bounded channel already combines admission, waiting and ownership transfer. The focused lab makes the smaller decision visible.

Plain-English model: indivisible does not mean everything happens together

An atomic operation on a supported atomic type appears indivisible to other accesses to that same atomic object. Another thread does not observe half of one atomic integer store. A data race is a particular conflict involving concurrent memory accesses to the same location, at least one write and at least one non-atomic access, without the required synchronization; it is undefined behavior. Safe Rust's ownership rules and safe synchronization interfaces prevent data races within their sound contracts. A race condition in application logic is broader: a result depends on an ordering that violates your intended contract. Atomics can eliminate a data race while leaving a check-then-act race.

Our invariant is: successful reservations consume exactly their requested units, and the available count never goes below zero. A separate load, arithmetic operation and store do not form one atomic reservation. Picture two people copying the same ticket count before either changes it. The analogy explains the check-then-act conflict, but it says nothing about processor caches, compiler transformations or Rust's memory model. We will use the documented ordering rules for those.

Prediction: can the strongest ordering repair the algorithm?

The deliberately wrong executable uses an atomic count initialized to one and SeqCst loads and stores. A barrier makes both workers finish their loads before either stores zero. Predict the number of accepted reservations. Is a stronger ordering than Relaxed enough to make the pair of operations indivisible?

Prediction and its cause

Both workers report success, leaving zero available. Each operation participates in the required ordering, but the legal order is load1, load1, store0, store0. There is no data race on the atomic count. There is an application bug because two separate operations do not reserve conditionally as one transition. The barrier makes this particular bad interleaving reproducible instead of relying on unlucky timing.

projects/reference/p19-concurrency-labs/src/atomics.rs
use std::sync::{
    Arc,
    atomic::{AtomicBool, AtomicU32, AtomicU64, Ordering},
};

/// A single-counter budget. No other memory is published by taking a unit.
pub struct Budget(AtomicU32);
impl Budget {
    pub fn new(units: u32) -> Self {
        Self(AtomicU32::new(units))
    }
    pub fn remaining(&self) -> u32 {
        self.0.load(Ordering::Relaxed)
    }
    pub fn try_take(&self, amount: u32) -> bool {
        let mut observed = self.0.load(Ordering::Relaxed);
        loop {
            let Some(next) = observed.checked_sub(amount) else {
                return false;
            };
            match self
                .0
                .compare_exchange_weak(observed, next, Ordering::Relaxed, Ordering::Relaxed)
            {
                Ok(_) => return true,
                Err(actual) => observed = actual,
            }
        }
    }
}

struct Shared {
    files: AtomicU64,
    bytes: AtomicU64,
    ready: AtomicBool,
}
/// Exactly one publication: this owner is intentionally not Clone.
pub struct Publisher(Arc<Shared>);
pub struct Reader(Arc<Shared>);
pub fn publication() -> (Publisher, Reader) {
    let shared = Arc::new(Shared {
        files: AtomicU64::new(0),
        bytes: AtomicU64::new(0),
        ready: AtomicBool::new(false),
    });
    (Publisher(Arc::clone(&shared)), Reader(shared))
}
impl Publisher {
    /// Consuming self prevents a second write after ready becomes true.
    pub fn publish(self, files: u64, bytes: u64) {
        self.0.files.store(files, Ordering::Relaxed);
        self.0.bytes.store(bytes, Ordering::Relaxed);
        self.0.ready.store(true, Ordering::Release);
    }
}
impl Reader {
    /// Nonblocking. None means no published summary has been observed.
    pub fn snapshot(&self) -> Option<(u64, u64)> {
        if !self.0.ready.load(Ordering::Acquire) {
            return None;
        }
        Some((
            self.0.files.load(Ordering::Relaxed),
            self.0.bytes.load(Ordering::Relaxed),
        ))
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn budget_never_admits_more_than_available() {
        let budget = Budget::new(100);
        let accepted: u32 = std::thread::scope(|scope| {
            let handles: Vec<_> = (0..16)
                .map(|_| scope.spawn(|| (0..50).filter(|_| budget.try_take(1)).count() as u32))
                .collect();
            handles
                .into_iter()
                .map(|h| h.join().expect("bounded fixture worker does not panic"))
                .sum()
        });
        assert_eq!(accepted, 100);
        assert_eq!(budget.remaining(), 0);
        assert!(!budget.try_take(1));
        assert!(budget.try_take(0));
    }
    #[test]
    fn oversized_reservation_leaves_the_budget_unchanged() {
        let budget = Budget::new(3);
        assert!(!budget.try_take(u32::MAX));
        assert_eq!(budget.remaining(), 3);
        assert!(budget.try_take(3));
    }
    #[test]
    fn no_partial_summary_is_exposed_by_the_api() {
        let (publisher, reader) = publication();
        assert_eq!(reader.snapshot(), None);
        publisher.publish(3, 120);
        assert_eq!(reader.snapshot(), Some((3, 120)));
        assert_eq!(reader.snapshot(), Some((3, 120)));
    }
    #[test]
    fn reader_survives_publisher_drop_without_fabricating_a_summary() {
        let (publisher, reader) = publication();
        drop(publisher);
        assert_eq!(reader.snapshot(), None);
    }
}

Explain the conditional transition

Budget keeps its AtomicU32 private so callers cannot increase the remaining count behind its API. checked_sub rejects requests larger than the observed count before mutation. compare_exchange_weak means: replace the count only if it still equals the value we observed. Success is the instant at which this reservation takes effect. If another worker changed the count, the operation returns the actual observed value; the loop recomputes the subtraction from that value. Weak compare-exchange may also fail spuriously, so the same loop handles a failure even without an intervening writer.

The successful compare-exchange is a useful linearization point: one instant that lets us explain a concurrent operation as though reservations happened in some sequential order. That does not make the whole program deterministic. Which worker wins is unspecified. There is no fairness or wait-free guarantee for an individual worker under arbitrary contention. Our tests use a fixed number of workers and attempts, not an unbounded producer loop.

Ordering follows the information being communicated

Relaxed preserves atomicity and the per-object modification rules but does not publish unrelated memory. It fits this single-counter budget: correctness comes from the conditional atomic update, and no reader infers anything about a separate payload from the count. It also fits the indexer's stop hint when the flag communicates only a boolean. Using Relaxed because it benchmarks faster without first defining what the flag means is not a sound rule.

The summary has a different contract. A writer stores two counts, then announces that the pair is ready. Release on the ready store and Acquire on a reader load that observes that publication establish the synchronization needed for the preceding count writes to be observed afterward. The individual count accesses remain atomic and use Relaxed; the publication flag carries the ordering relationship. Acquire is not a command to fetch the universally newest value. A load can still observe false and return None. The API promises a valid summary if it observes publication, not an arbitrary deadline for doing so.

The Publisher is not Clone and publishing consumes it. That ownership rule is essential: the counts are never overwritten after ready becomes true. Reusing a true flag for later updates would allow readers to combine different generations. Supporting repeated publication needs a different contract, such as a mutex-protected snapshot or a channel carrying owned snapshots. A memory-ordering change alone does not create that generation protocol. The reader deliberately returns None when the publisher is dropped without publishing; it does not spin forever or invent a result.

AcqRel combines acquire and release effects for a read-modify-write operation. SeqCst adds a single ordering for sequentially consistent operations, subject to Rust's documented model. Neither makes a sequence of loads and stores a multi-object transaction. Not every ordering is valid for every operation: a load cannot publish a prior write using Release, and a store cannot acquire a later observation. Read the operation's signature and documentation rather than trying orderings until compilation succeeds.

Deliberate mistake and the playbook investigation

Observation: the barrier fixture accepts two reservations. Hypothesis A says the failure comes from weak visibility and SeqCst will fix it. Hypothesis B says the gap lies between checking and changing. The fixture already uses SeqCst, so its repeated wrong result disproves A for this reproduction. Next, replace the two-step transition with Budget::try_take while keeping the same initial budget and number of callers. The relevant claim is the number accepted, not whether threads happened to run in a pleasing order.

For publication, do not claim that a Relaxed-only variant is correct because a million runs showed the expected counts. The missing observation is a allowed-but-unseen execution under the memory model. Separate the normative argument from dynamic evidence. A model checker such as Loom can explore a bounded model when a custom concurrent algorithm justifies that extra work; this lab does not claim an executed Loom proof.

Guided project checkpoint and deadlock reasoning

Read the indexer's cancellation flag and receiver lock next to this lab. Write the invariant protected by each. Retain its channel-based admission: the channel does more than count. Add a diagnostic counter only if you need that measurement, keeping the counter distinct from authoritative admission. Run mise exec -- cargo test -p p07-indexer and explain why an atomic progress count need not establish that a result has been safely stored.

A mutex is often the clearer alternative when several fields must change together. It protects a critical section; its guard releases the lock when dropped. With two locks, opposite acquisition order can deadlock: thread A holds X waiting for Y while B holds Y waiting for X. Stronger atomics elsewhere do not break that cycle. First ask whether one owner can receive commands through a channel or one small mutex can cover the invariant. If multiple locks are justified, define one acquisition order, such as ascending stable account ID, and follow it on every path. Do not hold a synchronous guard across await. A lock's scope should follow the invariant, not simply the largest convenient block.

Independent practice

Specify whether taking zero units succeeds; explain why the reference permits it. Implement a bounded return operation that cannot exceed an initial capacity, or explain why storing that second invariant makes a mutex simpler. Draw the state transitions before coding. Independently diagnose a two-lock transfer design with opposite caller argument orders; give a safe design without relying on a timing test to happen to hang. For the publication lab, explain why adding Clone to Publisher changes its correctness argument.

Hint 1

For returning units, prevent both numeric overflow and exceeding the configured capacity. Distinguish a reported progress metric from authority to admit work.

Hint 2

Try a small capacity such as two and enumerate take/return sequences. For locks, give the resources stable identities independent of the caller's source/destination order.

Reference approach

A private immutable capacity plus a compare-exchange loop can bound a single available count on return, but it cannot by itself prove that a caller legitimately owns units to return. A reservation token whose Drop returns its units can express that ownership; this introduces lifetime and cancellation choices that need review. A small mutex-protected ledger may be more appropriate. For transfers, acquiring lower-ID then higher-ID locks makes ordering consistent; reject a self-transfer or handle its single-lock case explicitly. Tests should cover invalid returns, same-resource operations and concurrent conservation, not merely final formatting.

Engineering decisions and evidence

The lab uses a private atomic budget and a one-use publication owner because those types make their narrow invariants explicit. It uses Arc only for the two genuine shared owners of publication state. The indexer keeps its higher-level channel. Native tests check reservation conservation under sixteen bounded workers, oversized requests and publication API states; the intentional fixture forces the counterexample even with SeqCst. These observations do not prove every hardware execution or fairness. Expanding to repeated snapshots, resource tokens or a wait-free algorithm would require a new design argument and stronger testing.

When you get stuck and mastery check

Write the smallest forbidden outcome first. List the memory operations that could produce it and identify the exact synchronization edge you believe rules it out. Bring a reviewer the invariant, one controlled interleaving and the relevant standard-library ordering documentation. Explain, without the reference, why a data-race-free program can still overspend a budget, why Acquire/Release is appropriate for the one-use summary, and why a mutex may be the more professional choice for a larger state transition.
