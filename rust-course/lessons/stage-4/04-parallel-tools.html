Compare serial, scoped threads and bounded Rayon work

Apply Rayon to an explicitly bounded CPU batch, preserve ordered outputs, and distinguish that choice from blocking file I/O.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Bound memory and make concurrent results reproducible
  • Compare three scheduling models against the same complete output contract.
  • Configure an explicit Rayon pool and bound retained input.
  • Distinguish CPU parallelism from blocking I/O policy.
  • Explain why correctness evidence does not establish a speedup.

Purpose: choose parallel tools for the work being scheduled

P07 combines blocking file reads with per-byte counting and fingerprinting. Its bounded worker pool is one reasonable design, but learning Rust concurrency also requires knowing when a parallel iterator is a better fit. This focused experiment compares serial iteration, explicitly scoped threads, and Rayon over the same already-read bounded batch. It adds a maintained parallel tool without replacing the file indexer's I/O and cancellation policy.

The distinction matters. CPU work keeps a worker busy computing. Blocking I/O occupies a worker while it waits for an external event. Increasing worker count may help one workload, saturate a device in another, or add overhead to a small calculation. Start by identifying which resource limits the actual task.

Plain model: the same function, three scheduling choices

Each input buffer represents one file already read into memory. All three strategies apply the same deterministic noncryptographic fingerprint function and return one result per input in input order. Serial iteration processes the batch on the calling thread. Scoped threads divide it into a bounded number of chunks and join every started worker. Rayon splits independent iterator work inside an explicitly constructed local thread pool.

The experiment limits the batch to 128 buffers, each at most 64 KiB: at most 8 MiB of input payload. It limits requested worker counts to one through eight. This payload bound excludes vector metadata, worker stacks, and runtime allocations. Unlike the streaming reference, it retains the complete input batch. That memory tradeoff is part of the design, not an invisible convenience.

ChoiceUseful propertyCost or obligation
Serial iteratorSimple ordered baseline, no worker schedulingIndependent CPU work stays on one caller
Scoped threadsExplicit partition and lifetime boundaryThread creation, joining, load balance, and failures are application responsibilities
Rayon parallel iteratorComposable CPU parallelism and runtime work distributionPool budget, task granularity, input ownership, and blocking behavior still need decisions

Runnable implementation and dependency choice

projects/experiments/p07-rayon/src/lib.rs
//! CPU-only fingerprints over an explicitly bounded, already-read batch.
//! This experiment does not perform file I/O or replace the streaming indexer.
use rayon::prelude::*;
use std::{fmt, io, thread};

pub const MAX_FILES: usize = 128;
pub const MAX_FILE_BYTES: usize = 64 * 1024;
pub const MAX_WORKERS: usize = 8;

#[derive(Debug)]
pub enum Error {
    InvalidBounds,
    ThreadSpawn(io::Error),
    ThreadPanicked,
    PoolBuild(rayon::ThreadPoolBuildError),
}
impl fmt::Display for Error {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Self::InvalidBounds => f.write_str(
                "batch exceeds 128 files or 64 KiB per file, or workers are outside 1..=8",
            ),
            Self::ThreadSpawn(error) => write!(f, "could not start scoped worker: {error}"),
            Self::ThreadPanicked => f.write_str("a scoped CPU worker panicked"),
            Self::PoolBuild(error) => write!(f, "could not construct Rayon pool: {error}"),
        }
    }
}
impl std::error::Error for Error {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            Self::ThreadSpawn(error) => Some(error),
            Self::PoolBuild(error) => Some(error),
            _ => None,
        }
    }
}

fn validate(inputs: &[Vec<u8>]) -> Result<(), Error> {
    if inputs.len() > MAX_FILES || inputs.iter().any(|bytes| bytes.len() > MAX_FILE_BYTES) {
        Err(Error::InvalidBounds)
    } else {
        Ok(())
    }
}
fn validate_workers(workers: usize) -> Result<(), Error> {
    if (1..=MAX_WORKERS).contains(&workers) {
        Ok(())
    } else {
        Err(Error::InvalidBounds)
    }
}

pub fn fixture(files: usize, bytes_per_file: usize) -> Result<Vec<Vec<u8>>, Error> {
    if files > MAX_FILES || bytes_per_file > MAX_FILE_BYTES {
        return Err(Error::InvalidBounds);
    }
    Ok((0..files)
        .map(|file| {
            (0..bytes_per_file)
                .map(|index| ((file * 17 + index * 31) % 251) as u8)
                .collect()
        })
        .collect())
}

/// Same noncryptographic FNV-1a fingerprint convention as the reference indexer.
/// A fingerprint can collide; it is not evidence that unknown files are identical.
pub fn fingerprint(bytes: &[u8]) -> u64 {
    bytes.iter().fold(0xcbf2_9ce4_8422_2325, |hash, byte| {
        (hash ^ u64::from(*byte)).wrapping_mul(0x100_0000_01b3)
    })
}

pub fn serial(inputs: &[Vec<u8>]) -> Result<Vec<u64>, Error> {
    validate(inputs)?;
    Ok(inputs.iter().map(|bytes| fingerprint(bytes)).collect())
}

pub fn scoped_threads(inputs: &[Vec<u8>], workers: usize) -> Result<Vec<u64>, Error> {
    validate(inputs)?;
    validate_workers(workers)?;
    if inputs.is_empty() {
        return Ok(Vec::new());
    }
    let chunk_size = inputs.len().div_ceil(workers);
    thread::scope(|scope| {
        let mut handles = Vec::with_capacity(workers);
        let mut error = None;
        for (index, chunk) in inputs.chunks(chunk_size).enumerate() {
            let task = thread::Builder::new()
                .name(format!("fingerprint-{index}"))
                .spawn_scoped(scope, move || {
                    chunk
                        .iter()
                        .map(|bytes| fingerprint(bytes))
                        .collect::<Vec<_>>()
                });
            match task {
                Ok(handle) => handles.push(handle),
                Err(cause) => {
                    error = Some(Error::ThreadSpawn(cause));
                    break;
                }
            }
        }
        let mut output = Vec::with_capacity(inputs.len());
        // Join every started worker, even if startup or another worker failed.
        // Joining in chunk order preserves the input order in the output.
        for handle in handles {
            match handle.join() {
                Ok(values) => output.extend(values),
                Err(_) => {
                    if error.is_none() {
                        error = Some(Error::ThreadPanicked);
                    }
                }
            }
        }
        match error {
            Some(error) => Err(error),
            None => Ok(output),
        }
    })
}

pub struct ParallelResult {
    pub fingerprints: Vec<u64>,
    pub pool_threads: usize,
}
pub fn rayon_pool(inputs: &[Vec<u8>], workers: usize) -> Result<ParallelResult, Error> {
    validate(inputs)?;
    validate_workers(workers)?;
    let pool = rayon::ThreadPoolBuilder::new()
        .num_threads(workers)
        .build()
        .map_err(Error::PoolBuild)?;
    let fingerprints = pool.install(|| inputs.par_iter().map(|bytes| fingerprint(bytes)).collect());
    Ok(ParallelResult {
        fingerprints,
        pool_threads: pool.current_num_threads(),
    })
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn every_strategy_returns_the_same_ordered_output() {
        for (files, bytes) in [(0, 0), (1, 1), (3, 37), (17, 1025), (128, 3)] {
            let inputs = fixture(files, bytes).unwrap();
            let expected = serial(&inputs).unwrap();
            for workers in [1, 2, 4, 8] {
                assert_eq!(scoped_threads(&inputs, workers).unwrap(), expected);
                let actual = rayon_pool(&inputs, workers).unwrap();
                assert_eq!(actual.fingerprints, expected);
                assert_eq!(actual.pool_threads, workers);
            }
        }
    }
    #[test]
    fn bounds_are_enforced_before_scheduling() {
        for workers in [0, 9, usize::MAX] {
            assert!(matches!(
                scoped_threads(&[], workers),
                Err(Error::InvalidBounds)
            ));
            assert!(matches!(
                rayon_pool(&[], workers),
                Err(Error::InvalidBounds)
            ));
        }
        assert!(fixture(129, 0).is_err());
        assert!(fixture(0, MAX_FILE_BYTES + 1).is_err());
        assert!(serial(&vec![vec![]; 129]).is_err());
        assert!(serial(&[vec![0; MAX_FILE_BYTES + 1]]).is_err());
    }
    #[test]
    fn fingerprint_convention_has_fixed_oracles() {
        assert_eq!(fingerprint(b""), 0xcbf2_9ce4_8422_2325);
        assert_eq!(fingerprint(b"a"), 0xaf63_dc4c_8601_ec8c);
    }
}

This is a separate Cargo workspace with an exact rayon = "=1.12.0" dependency and its own lockfile. The published crate page dates that stable release to April 14, 2026, before the course's October 8 cutoff; its release notes are dated April 13. The declared minimum compiler is 1.80, and the actual course checks used Rust 1.99.1. The separate workspace keeps this optional experiment from changing the native reference workspace's dependency graph.

The scoped version uses Builder::spawn_scoped so an operating-system thread-start failure can return an error. If startup or a worker fails, it still joins every worker already started before returning. Joining chunk results in input order preserves the requested output order. Chunk size uses ceiling division, so the number of chunks respects the worker budget and an uneven final chunk is retained.

The Rayon version constructs a local pool with a nonzero explicit thread budget and runs par_iter().map(...).collect() inside pool.install. The input is an indexed slice iterator; the collection preserves its logical order even though task execution can be scheduled differently. This is not a claim that arbitrary side effects from parallel closures occur in input order. Pool construction failure is propagated, and no global pool configuration is changed.

Guided checkpoint: compare complete outputs

Read fingerprint, then trace the three callers. Confirm that they share the same borrowed input and do not mutate it. The binary rejects a mismatch before printing success. Comparing only the sum of fingerprints would be weaker because it could hide reordered or compensating results. The test compares the complete vector, and fixed empty-string and one-byte oracles check the fingerprint convention itself.

A fingerprint can collide; equality of fingerprints is not a proof that two unknown files contain identical bytes. Here the strategies receive the same immutable buffers by construction, and the required output is the ordered fingerprint vector. Keep that evidence boundary clear when reusing this pattern for a synchronization or integrity tool.

Why the blocking file pipeline keeps its own workers

The reference must stream files of bounded size, report I/O failures, observe cancellation between reads, and cap queued paths and concurrent open work. Putting the complete read-and-count operation directly into a CPU-oriented parallel iterator would make those blocking reads occupy that pool's workers. It would not automatically provide the reference's queue policy, byte limits, or cancellation contract.

For this application, retain the explicit bounded I/O worker design. Rayon becomes a useful alternative when a substantial independent CPU stage can operate on already-bounded input. If the real task benefits from both, define a bounded handoff between I/O and CPU processing and budget the total threads and retained buffers across both pools. Avoid starting a fresh CPU pool per file. The example builds a pool per finite comparison call to make ownership clear; a long-lived service can own and reuse one pool when its lifecycle requires that.

Intentional mistake: silently omit the final chunk

In a disposable learner copy, modify the scoped implementation to process only a floor-divided number of complete chunks. Predict a failure for a batch not divisible by its chunk size, then run the equality test. The expected failure demonstrates lost work. This mutation was not part of the recorded verification run; label its outcome as expected until you execute it. Restore complete chunk iteration and preserve the regression.

Another deliberate mistake is to call the global parallel iterator outside the configured pool and assume the local builder still controls it. A pool object does not redirect unrelated work merely by existing. The install boundary is the relevant mechanism.

Apply the problem-solving playbook

Observation: the actual tests requested pools of 1, 2, 4, and 8 workers and reported the matching pool sizes while preserving output. Hypothesis A says every Rayon call must use one global pool sized to all logical CPUs. Hypothesis B says an explicitly constructed local pool governs the work installed in it. Holding the fixture fixed and changing only the configured count distinguishes them; the observed pool reports disprove A for this implementation.

This result does not prove all configured workers were simultaneously active or that more workers improved throughput. A next experiment, if speed matters, would hold the fixture and release profile fixed and compare repeated serial and parallel runs, accounting for pool construction separately or including it in both request boundaries as appropriate. Use the investigation template to record the question before collecting times. Ask an AI reviewer to identify the actual pool and memory bounds rather than accepting “parallel means faster.”

Independent work, tiered hints, and solution

Add a bounded batch with uneven buffer lengths and compare all three complete outputs. Then propose a CPU transform expensive enough to justify profiling, while preserving a serial oracle. Finally write a short design decision for a workload dominated by slow file reads versus one dominated by repeated in-memory parsing. Include a total thread and payload budget.

Hint 1: separate input equality from execution order

Keep one immutable batch and pass references to every strategy. Give files different contents as well as different lengths so ordering mistakes are visible.

Hint 2: keep the bounds at the boundary

Validate the entire batch and requested worker count before creating threads. A task count is not a byte budget.

Hint 3: choose a representative timing boundary

Decide whether a real request reuses an existing pool. Do not exclude pool construction from one strategy while quietly including its equivalent setup in another.

Worked direction

Build several distinct buffers below 64 KiB, including an empty file and a larger file, and assert complete vector equality at worker counts 1 and 4. Retain serial processing as the correctness baseline. Prefer the reference's bounded workers when blocking reads dominate; investigate Rayon when an independent CPU stage dominates and a bounded in-memory batch is acceptable. If measurements show no useful improvement, keep the simpler serial stage.

When you get stuck

Run the isolated test command and inspect the first differing vector index. Check the chunk count, pool install boundary, and exact Rayon version. Read the pinned ThreadPoolBuilder and indexed parallel iterator documentation. A review request should include the batch dimensions, worker budget, expected ordered results, observed mismatch, and whether the operation blocks on external I/O.

Engineering decisions, evidence limits, and mastery

The first working implementation already bounds resources, propagates ordinary startup failures, joins scoped workers, and keeps reference input immutable. The optional dependency is exact-pinned and locked. Three tests passed, all targets passed strict Clippy, the release demonstration ran successfully, and the cached advisory scan reported no known vulnerabilities or warnings for this graph. See the command and source record. An advisory snapshot is not a security proof, and equal results on a finite fixture family do not establish every possible input.
