Bound memory and make concurrent results reproducible

Complete a streaming file indexer with explicit resource limits, cooperative cancellation, live progress and stable final output.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Ownership crosses thread boundaries
  • Derive memory bounds across input, queues, workers and output
  • Keep streaming parser state across arbitrary read boundaries
  • Define cancellation as a cooperative protocol
  • Produce deterministic results despite nondeterministic scheduling
  • Report bounded live progress without treating failed or abandoned jobs as successful files

Key terms: allocation · atomic · authentication · cancellation · capacity · closure · deadline · generic

Purpose: put a resource budget in the design

A worker count alone does not bound a program's memory. A producer might retain millions of paths, an unbounded queue might hold millions of jobs, a worker might read an entire huge file, and a collector might accumulate every result forever. P07 addresses each category. It accepts a finite batch capped at 4096 paths, caps each encoded path length, uses bounded channels, permits at most 32 workers, reads through an 8192-byte buffer, limits bytes read per file and collects at most one result per submitted path. This is a bounded-batch design, not a claim of constant total memory independent of input count.

Model: streaming state is smaller than streaming input

The counter tracks total bytes, newline count, word count, whether the previous byte was inside a word, the last byte seen, and a rolling fingerprint. Words use ASCII whitespace boundaries, which is an explicit definition rather than a Unicode linguistic tokenizer. A long word may span several reads; in_word carries its state across those reads. Lines count newline bytes plus one final unterminated nonempty line. An empty file has zero lines. The fingerprint helps compare results, but it is not cryptographic authentication and does not prove two files are identical.

Predict before running

Predict the line and word counts for an empty file, a single newline, “a b” without a trailing newline, and a nine-thousand-byte word followed by another word. Decide whether a read boundary creates a new word. It must not. Now predict the oversize result if the maximum is four bytes and the source yields five. File metadata is only a preliminary observation; the reader itself must enforce the budget because files can change and some readers have no reliable metadata. The implementation reads at most the remaining budget plus one byte so it can detect an excess.

//! Bounded batch file indexer. Files are streamed; results and path metadata are capped.
use std::{
    fs::File,
    io::{self, Read},
    path::PathBuf,
    sync::{
        Arc, Mutex,
        atomic::{AtomicBool, AtomicUsize, Ordering},
        mpsc,
    },
    thread,
};

#[derive(Clone, Copy, Debug)]
pub struct Config {
    pub workers: usize,
    pub queue: usize,
    pub max_files: usize,
    pub max_bytes: u64,
}
impl Default for Config {
    fn default() -> Self {
        Self {
            workers: 4,
            queue: 8,
            max_files: 4096,
            max_bytes: 16 * 1024 * 1024,
        }
    }
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Status {
    Indexed,
    TooLarge,
    Cancelled,
    Failed(io::ErrorKind),
}
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Entry {
    pub path: PathBuf,
    pub input_index: usize,
    pub bytes: u64,
    pub lines: u64,
    pub words: u64,
    pub fingerprint: u64,
    pub status: Status,
}
#[derive(Debug)]
pub struct Report {
    pub entries: Vec<Entry>,
    pub submitted: usize,
    pub cancelled: bool,
    pub peak_workers: usize,
}

/// A coordinator-owned observation, not an estimate of bytes or time remaining.
/// `received` includes failed/partial results; only `indexed` counts whole files.
/// Counts are monotonic within a run. Completion order is not deterministic.
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub struct Progress {
    pub total: usize,
    pub received: usize,
    pub indexed: usize,
    pub too_large: usize,
    pub failed: usize,
    pub cancelled: usize,
    /// Known only after the producer has joined; queued work may have no result.
    pub submitted: Option<usize>,
    pub cancellation_requested: bool,
    /// All scoped work has joined and results have been sorted.
    pub finished: bool,
}
impl Progress {
    fn observe(&mut self, status: &Status) {
        // Input is capped at 4096 and each input has at most one returned entry.
        self.received += 1;
        match status {
            Status::Indexed => self.indexed += 1,
            Status::TooLarge => self.too_large += 1,
            Status::Failed(_) => self.failed += 1,
            Status::Cancelled => self.cancelled += 1,
        }
    }
}

fn count(path: PathBuf, input_index: usize, max_bytes: u64, cancel: &AtomicBool) -> Entry {
    let mut result = Entry {
        path,
        input_index,
        bytes: 0,
        lines: 0,
        words: 0,
        fingerprint: 0xcbf2_9ce4_8422_2325,
        status: Status::Indexed,
    };
    let run = |result: &mut Entry| -> io::Result<()> {
        let mut file = File::open(&result.path)?;
        let mut buf = [0u8; 8192];
        let mut in_word = false;
        let mut last = None;
        loop {
            if cancel.load(Ordering::Relaxed) {
                result.status = Status::Cancelled;
                return Ok(());
            }
            // Read at most the remaining budget plus one byte to detect an oversize file.
            let allowance = (max_bytes - result.bytes + 1).min(buf.len() as u64) as usize;
            let n = match file.read(&mut buf[..allowance]) {
                Err(e) if e.kind() == io::ErrorKind::Interrupted => continue,
                other => other?,
            };
            if n == 0 {
                break;
            }
            if result.bytes + n as u64 > max_bytes {
                result.status = Status::TooLarge;
                return Ok(());
            }
            result.bytes += n as u64;
            for &byte in &buf[..n] {
                result.lines += u64::from(byte == b'\n');
                let word = !byte.is_ascii_whitespace();
                result.words += u64::from(word && !in_word);
                in_word = word;
                result.fingerprint =
                    (result.fingerprint ^ u64::from(byte)).wrapping_mul(0x100_0000_01b3);
                last = Some(byte);
            }
        }
        result.lines += u64::from(last.is_some_and(|byte| byte != b'\n'));
        Ok(())
    };
    if let Err(error) = run(&mut result) {
        result.status = Status::Failed(error.kind());
    }
    result
}

pub fn index(paths: Vec<PathBuf>, config: Config, cancel: Arc<AtomicBool>) -> io::Result<Report> {
    index_with_progress(paths, config, cancel, |_| {})
}

/// Index with an initial snapshot, one snapshot per received entry, and a final snapshot.
/// Invalid configuration returns before callbacks or threads start. The callback runs
/// synchronously on the calling coordinator, with no lock held and no extra queue.
/// A slow callback applies backpressure through the bounded result queue; it should
/// not wait for this same run to finish. Panics are programmer failures, not IO errors.
/// A caller can request cancellation through its retained `Arc<AtomicBool>`; pending
/// regular-file reads remain cooperative. On final progress, `submitted - received`
/// counts accepted jobs without a returned entry, and `total - submitted` counts jobs
/// never submitted. Neither category is silently counted as a successful file.
pub fn index_with_progress(
    paths: Vec<PathBuf>,
    config: Config,
    cancel: Arc<AtomicBool>,
    mut on_progress: impl FnMut(Progress),
) -> io::Result<Report> {
    if !(1..=32).contains(&config.workers)
        || !(1..=1024).contains(&config.queue)
        || config.max_files > 4096
        || paths.len() > config.max_files
        || config.max_bytes > 64 * 1024 * 1024
        || paths
            .iter()
            .any(|p| p.as_os_str().as_encoded_bytes().len() > 4096)
    {
        return Err(io::Error::new(
            io::ErrorKind::InvalidInput,
            "configuration or input exceeds documented bounds",
        ));
    }
    let mut progress = Progress {
        total: paths.len(),
        cancellation_requested: cancel.load(Ordering::Relaxed),
        ..Progress::default()
    };
    on_progress(progress);
    let (job_tx, job_rx) = mpsc::sync_channel::<(usize, PathBuf)>(config.queue);
    let (result_tx, result_rx) = mpsc::sync_channel(config.queue);
    let job_rx = Arc::new(Mutex::new(job_rx));
    let active = AtomicUsize::new(0);
    let peak = AtomicUsize::new(0);
    let (mut entries, submitted) = thread::scope(|scope| {
        let producer_cancel = cancel.clone();
        let producer = scope.spawn(move || {
            let mut submitted = 0;
            for (index, path) in paths.into_iter().enumerate() {
                if producer_cancel.load(Ordering::Relaxed) || job_tx.send((index, path)).is_err() {
                    break;
                }
                submitted += 1;
            }
            submitted
        });
        for _ in 0..config.workers {
            let jobs = job_rx.clone();
            let results = result_tx.clone();
            let cancel = cancel.clone();
            let active = &active;
            let peak = &peak;
            scope.spawn(move || {
                loop {
                    if cancel.load(Ordering::Relaxed) {
                        break;
                    }
                    // The receiver lock protects dequeue only; file I/O is outside the lock.
                    let next = jobs.lock().expect("receiver lock poisoned").recv();
                    let Ok((index, path)) = next else { break };
                    let now = active.fetch_add(1, Ordering::Relaxed) + 1;
                    peak.fetch_max(now, Ordering::Relaxed);
                    let entry = count(path, index, config.max_bytes, &cancel);
                    active.fetch_sub(1, Ordering::Relaxed);
                    if results.send(entry).is_err() {
                        break;
                    }
                }
            });
        }
        drop(job_rx);
        drop(result_tx);
        let mut entries = Vec::new();
        for entry in result_rx {
            progress.observe(&entry.status);
            progress.cancellation_requested = cancel.load(Ordering::Relaxed);
            entries.push(entry);
            on_progress(progress);
        }
        (entries, producer.join().expect("producer panicked"))
    });
    entries.sort_by(|a, b| a.path.cmp(&b.path).then(a.input_index.cmp(&b.input_index)));
    progress.submitted = Some(submitted);
    progress.cancellation_requested = cancel.load(Ordering::Relaxed);
    progress.finished = true;
    on_progress(progress);
    Ok(Report {
        entries,
        submitted,
        cancelled: progress.cancellation_requested,
        peak_workers: peak.load(Ordering::Relaxed),
    })
}

Config validation occurs before spawning. count owns the path and produces one Entry, including an explicit Status. Opening a missing file becomes a per-file failure rather than aborting all valid files. TooLarge means counters and fingerprint are partial; callers should not display them as completed-file measurements. The read loop preserves word state and checks cancellation between reads. The result collector sorts by path and then original input index. That second key makes repeated paths deterministic too. Thread completion order may change between runs, but the sorted entries for unchanged files should remain equal.

Live progress: observations belong to the collector

A final report cannot tell someone whether a longer run is still making progress. The collector already receives one result for each returned file job, so it is the natural owner of progress counts. The new index_with_progress function takes an FnMut callback: a function-like value that can update its captured state each time it is called. The callback runs on the calling thread before workers start, after each received Entry, and once after all scoped work has joined and output has been sorted. It receives a small copied Progress value; no progress thread, shared counter lock, timer, or additional queue is needed. The existing index function calls the same implementation with a callback that does nothing, preserving the earlier API and benchmark's output-free measurement boundary.

Predict this snapshot: total=3, received=2, indexed=1, failed=1, finished=false. Have two files been indexed successfully? No. Two results arrived, but one is an error. Does the remaining file necessarily run now? No: it might still be queued. The equation received = indexed + too_large + failed + cancelled holds at every observation. Only the final snapshot supplies submitted, after joining the producer. Then submitted - received counts accepted jobs without a returned result, and total - submitted counts jobs never submitted. These are distinct from returned Status::Cancelled entries. Cancellation need not make received equal total, and the interface must not turn that gap into false success.

The callback receives at most total + 2 snapshots, with total capped at 4096. The indexer retains one progress value. A caller choosing to keep snapshots owns that additional bounded storage; the CLI prints each observation instead. Result-arrival order depends on scheduling, while each category count increases monotonically and the final entries remain sorted. A slow callback deliberately slows collection: the existing bounded result queue eventually blocks workers. Do not wait inside the callback for this same indexing run to finish; that would prevent the collector from doing the work required for completion. The callback has no hard deadline, and a blocked filesystem read can still postpone cancellation.

Guided checkpoint: keep status separate from data

Read the complete CLI below, then run it from the course projects directory. Compared with the previous thin entry point, it passes a retained cancellation flag and a small closure to index_with_progress. Progress goes to standard error; sorted entries and the final report go to standard output. The status writer uses Write and returns an ordinary I/O error. If progress output fails, the closure records that first error and requests cancellation. The indexer still drains returned results and joins scoped work, then the CLI returns the error without printing a successful report. A callback panic remains a programmer failure, not a normal output-error policy.

projects/reference/p07-indexer/src/main.rs
use std::{
    io::{self, Write},
    sync::{
        Arc,
        atomic::{AtomicBool, Ordering},
    },
};

fn write_progress(output: &mut impl Write, progress: p07_indexer::Progress) -> io::Result<()> {
    let phase = if progress.finished {
        "finished"
    } else if progress.received == 0 {
        "started"
    } else {
        "running"
    };
    writeln!(
        output,
        "progress {phase} received={}/{} indexed={} too_large={} failed={} cancelled={} cancellation_requested={}",
        progress.received,
        progress.total,
        progress.indexed,
        progress.too_large,
        progress.failed,
        progress.cancelled,
        progress.cancellation_requested
    )?;
    if let Some(submitted) = progress.submitted {
        writeln!(
            output,
            "progress submitted={submitted} without_result={} unsubmitted={}",
            submitted - progress.received,
            progress.total - submitted
        )?;
    }
    output.flush()
}

fn main() -> std::io::Result<()> {
    let paths = std::env::args_os()
        .skip(1)
        .map(Into::into)
        .collect::<Vec<_>>();
    if paths.is_empty() {
        let _ = writeln!(io::stderr().lock(), "usage: p07-indexer FILE ...");
        std::process::exit(2);
    }
    let cancel = Arc::new(AtomicBool::new(false));
    let mut progress_error = None;
    let mut progress_output = io::stderr().lock();
    let report = p07_indexer::index_with_progress(
        paths,
        p07_indexer::Config::default(),
        Arc::clone(&cancel),
        |progress| {
            if progress_error.is_none()
                && let Err(error) = write_progress(&mut progress_output, progress)
            {
                // Stop further work but still let index_with_progress drain and join.
                progress_error = Some(error);
                cancel.store(true, Ordering::Relaxed);
            }
        },
    )?;
    if let Some(error) = progress_error {
        return Err(error);
    }
    let mut output = io::stdout().lock();
    for e in report.entries {
        writeln!(
            output,
            "{} bytes={} lines={} words={} {:016x} {:?}",
            e.path.display(),
            e.bytes,
            e.lines,
            e.words,
            e.fingerprint,
            e.status
        )?;
    }
    writeln!(
        output,
        "submitted={} peak_workers={} cancelled={}",
        report.submitted, report.peak_workers, report.cancelled
    )?;
    output.flush()
}

It also prints the sorted file results. The relative interleaving of the two terminal streams is not part of the contract. Progress is per returned file, not a byte-level timer: a single slow file may produce no intermediate line. The CLI does not install a Ctrl-C handler; library callers can set the retained cancellation flag, and the CLI does so if its progress sink fails.

Cancellation needs an honest boundary

The cancellation flag uses relaxed atomic operations because it is only a stop hint; it is not publishing some other protected data structure. A worker checks it before waiting for another job and between reads. Cancellation cannot forcibly interrupt a blocking regular-file read through this API. A special file or problematic filesystem may block longer than expected, so use ordinary local files in the course exercises. The producer may already have submitted a job when cancellation arrives. Therefore submitted, completed entries and canceled state can differ. Do not interpret submitted as a guaranteed number of completed indexes.

The producer and workers still have to close channels correctly. A canceled worker drops its receiver clone and result sender. Once all job receivers disappear, a blocked producer send returns an error. The collector drains finished results until all senders disappear, and the scope waits for thread completion. This protocol bounds outstanding work but does not promise a hard wall-clock shutdown deadline for synchronous file I/O. That limitation motivates the different I/O model in the next project.

Playbook investigation: word counts change with buffer size

Observation: a learner's indexer counts the same bytes differently with one-byte reads and eight-kilobyte reads. Hypothesis A says the operating system changes the file contents. Hypothesis B says the tokenizer resets in_word at every read. Hypothesis C says the final unterminated line is counted as a word. Choose a reader adapter that returns one byte per call while holding the underlying byte slice fixed. If the result still changes, that disproves the operating-system-content hypothesis without involving threads at all. Then use a single long word to separate boundary-state mistakes from line-ending logic.

The likely repair is to move parser state outside the read loop, but make that conclusion only after the minimal experiment. Engineering decisions and evidence

Current scope and invariants. At most the configured fixed number of workers count files, both channels are bounded, each file uses a fixed-size read buffer, and input paths plus collected results have explicit batch limits. Live progress uses one coordinator-owned value and no new channel; received results are partitioned into indexed, oversized, failed, and cancelled categories.

Why this is the current recommended shape. Owned jobs move through channels; Arc is used only for shared cancellation and receiver ownership. Mutex scope covers dequeue, not file I/O. A pure streaming counter preserves state across reads, per-file status preserves partial failures, and final sorting makes entries deterministic.

Reasonable alternative and tradeoff. A work-stealing library is a reasonable alternative for CPU-heavy independent jobs and may simplify scheduling. The explicit fixed worker pool is a good fit here because its bounded queues and shutdown dependencies are the subject and are small enough to inspect. Unbounded thread-per-file spawning is a deliberate rejected design, not an early recommended step.

Evidence and limits. Native reference tests were run through mise in the coordinated course verification; inspect the current verification record for exact results. Chunk-boundary counts; empty files; oversize and missing paths; cancellation before submission; queue-one termination; repeatable entries; invalid configuration. The total bound includes capped path/result metadata, not just the 8192-byte buffers. Ordinary file reads can block cancellation. Files may change during a run. Partial counts from failed or oversized files are not complete-file statistics.

Requirement that would justify evolution. For recursive or effectively unbounded discovery, stream results to a sink and use bounded or external sorting instead of collecting an unlimited list. For hard shutdown deadlines, revisit the synchronous I/O boundary and supported file types. For time-based or per-byte progress, define sampling and synchronization costs first; the present observer is per returned file and has no timing promise.

In your review, explain this choice in your own words, preserve the behavioral contract during changes, and name the evidence that would make you choose the alternative. Deliberately broken variants above are diagnostic exercises, never recommended implementation stages.
