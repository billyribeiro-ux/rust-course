Macros generate code, not correctness

Build and inspect one declarative macro and one narrowly scoped derive.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Purpose: remove repetition without hiding the contract

Macros are useful when the repeated structure is syntax rather than an ordinary runtime value. A derive can produce an implementation for a declared type. A declarative macro can accept a repeated list of expressions. Neither mechanism makes the generated code correct by definition. It creates another source of code that must be read and tested.

Plain model: transformation before ordinary checking

A declarative macro matches tokens against patterns and expands to Rust syntax. A procedural macro is compiled host code that consumes and returns token streams. The compiler then checks the expanded program. Procedural macros are build-time dependencies capable of executing code during compilation, so dependency review matters even when the final program has a small runtime surface.

Use a function when a function expresses the need. A function has ordinary parameter types, return types and call behavior. Use a macro only when its syntax or generated implementation provides a concrete benefit. Our checked_sum example accepts any number of expressions and emits a checked accumulation. The TypeName-like derive implements one small, stable trait without duplicating generic parameter handling at every type.

Predict evaluation count

A macro invocation supplies two expressions that each increment a counter. What must be true for the counter to end at two rather than four? If the first addition overflows, should the second supplied expression still be evaluated? Predict the current reference's explicit policy before reading it.

Prediction explained

The macro stores each supplied expression in a local before using it, so each is evaluated once, left to right. It still evaluates later expressions after an earlier overflow because expansion contains those let statements. The arithmetic result remains None. That evaluation policy is part of the API; a short-circuit alternative could be valid but must be documented and tested.

Run the macro lab

Working directory projects/: mise exec -- cargo test -p rust-specializations macro_once_and_overflow. Inspect checked_sum! in the actual source. The test checks both the returned sum and the side-effect count, so it guards a property that a result-only test would miss.

//! Focused specialization examples. None is required to write every Rust application.
use std::ffi::c_int;
pub trait KindName {
    fn kind_name() -> &'static str;
}
#[derive(course_kind_derive::KindName)]
pub struct Packet<T, const N: usize> {
    pub values: [T; N],
}

/// A higher-ranked bound: the callback works for every input lifetime.
/// ```
/// use rust_specializations::with_first;
/// assert_eq!(with_first("alpha beta", |s|s.split_whitespace().next().unwrap_or("")), "alpha");
/// ```
pub fn with_first<'a, F>(input: &'a str, select: F) -> &'a str
where
    F: for<'b> Fn(&'b str) -> &'b str,
{
    select(input)
}

/// The associated output is fixed by each implementor.
pub trait Source {
    type Item;
    fn next_item(&mut self) -> Option<Self::Item>;
}
pub struct Countdown(pub u8);
impl Source for Countdown {
    type Item = u8;
    fn next_item(&mut self) -> Option<u8> {
        let value = self.0.checked_sub(1)?;
        self.0 = value;
        Some(value)
    }
}
pub fn drain(source: &mut dyn Source<Item = u8>) -> Vec<u8> {
    let mut out = Vec::new();
    while let Some(item) = source.next_item() {
        out.push(item);
    }
    out
}

/// Each supplied expression is evaluated exactly once, left to right.
#[macro_export]
macro_rules! checked_sum {
    ($($value:expr),* $(,)?) => {{
        let mut total=Some(0i64);
        $(let next: i64=$value; total=total.and_then(|old|old.checked_add(next));)*
        total
    }};
}

unsafe extern "C" {
    fn abs(value: c_int) -> c_int;
}
/// A narrow C ABI example. Prefer `i32::checked_abs` in ordinary Rust code.
/// Returns None for the only input whose C absolute value is not representable.
pub fn c_checked_abs(value: c_int) -> Option<c_int> {
    if value == c_int::MIN {
        return None;
    }
    // SAFETY: abs has the declared C ABI, has no pointer/lifetime contract,
    // and its result is representable because INT_MIN was excluded above.
    Some(unsafe { abs(value) })
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn generic_derive_retains_parameters() {
        assert_eq!(Packet::<u8, 4>::kind_name(), "Packet");
        let p = Packet { values: [1; 0] };
        assert!(p.values.is_empty());
    }
    #[test]
    fn trait_object_associated_item() {
        assert_eq!(drain(&mut Countdown(3)), [2, 1, 0]);
    }
    #[test]
    fn macro_once_and_overflow() {
        let mut n = 0;
        assert_eq!(
            checked_sum!(
                {
                    n += 1;
                    n
                },
                {
                    n += 1;
                    n
                }
            ),
            Some(3)
        );
        assert_eq!(n, 2);
        assert_eq!(checked_sum!(i64::MAX, 1), None);
    }
    #[test]
    fn ffi_boundary() {
        for x in [-2, 0, 1, i32::MAX, i32::MIN] {
            assert_eq!(c_checked_abs(x), x.checked_abs());
        }
    }
}

Read the declarative expansion

$value:expr matches one expression. The repetition accepts comma-separated expressions and an optional trailing comma. Double braces make the result a block expression with its own local names. Each next value is constrained to i64. and_then combines a prior successful total with checked addition. It preserves None after overflow without wrapping or panicking.

Macro hygiene helps prevent accidental interaction between generated local bindings and caller names, but it is not a universal promise about every path. Exported macros should use deliberate paths, often $crate for their own crate's items. Our example uses no helper items beyond language and standard prelude names. If you generalize it, test expansion in a separate consumer crate rather than only inside the defining module.

The procedural derive

projects/reference/p17-derive/src/lib.rs
//! A deliberately small derive: generated code implements the caller's KindName trait.
use proc_macro::TokenStream;
use quote::quote;
use syn::{DeriveInput, parse_macro_input};
#[proc_macro_derive(KindName)]
pub fn kind_name(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as DeriveInput);
    let name = &input.ident;
    let (impl_generics, type_generics, where_clause) = input.generics.split_for_impl();
    quote! {
        impl #impl_generics crate::KindName for #name #type_generics #where_clause {
            fn kind_name() -> &'static str { stringify!(#name) }
        }
    }
    .into()
}

The crate has proc-macro = true and runs on the compiler host, even when the consuming crate targets WASM. The maintained syn parser converts tokens into a DeriveInput. This avoids inventing a partial Rust parser. quote constructs output tokens while preserving Rust identifiers. split_for_impl separates declaration parameters, use-site arguments and where clauses; omitting those would break generic consumers.

The generated implementation names crate::KindName. This is an intentional lab contract: the consuming crate defines that trait at its root. A reusable published derive should usually target a documented companion trait crate and account for renamed dependencies. The explicit restriction is more honest than claiming a tiny derive is universally portable.

Deliberate mistake: repeating an expression

In a learner copy, use the supplied expression twice in an expansion, such as once to log and once to add. Run the side-effect test. A macro can type-check while changing how many times the caller's operation runs. The sound correction binds the expression once and reuses the value or reference according to its ownership needs. Do not merely remove the failing test.

Guided checkpoint

First run the handwritten KindName implementation on a simple struct. Then replace that exact implementation with the derive and preserve the same observable test. Next test Packet<T, N> so generic arguments and const parameters pass through. Finally add a where-constrained type. Each step expands the supported syntax with a concrete test; it does not claim to support arbitrary advanced syntax by inspection alone.

Independent work and tiered hints

Add a documented empty invocation behavior to checked_sum, then test a caller variable named total. Design a compile-fail consumer where the required trait is absent and explain whether the resulting diagnostic is clear enough. Propose one improvement without hiding errors behind a catch-all panic.

Hint 1

The identity value for a sum is zero, but the output type should remain explicit. The macro's local variable should not mutate the caller's similarly named variable.

Hint 2

Generated code errors point into expansion or invocation spans. A procedural macro can report a structured syn error for unsupported input rather than panicking.

Reference direction

Specify Some(0i64) for no values and assert the caller's total is unchanged after a nonempty call. If the derive's trait path is part of the supported contract, document it next to installation instructions. A fuller library can accept a helper attribute naming the trait path and parse it with syn; that is a new requirement, not a reason to complicate this lab preemptively.

Engineering decisions and evidence

The procedural macro depends on exact syn 3.0.9 and quote 1.0.47 because parsing Rust syntax and preserving token structure are concrete requirements. The ordinary runtime examples remain standard-library based. Tests cover single evaluation, overflow, generic and const parameter preservation. A downstream compile-fail test would add evidence about diagnostics; the manifest must not imply one ran unless its command is recorded. An ordinary function is the preferred alternative when token-level flexibility is unnecessary.

Playbook investigation: the derive breaks only generic types

Observed: a unit struct derives successfully, but Packet<u8,4> fails with missing generics. Hypothesis A: derives cannot support const generics. Hypothesis B: the expansion discarded type arguments. Write the equivalent handwritten impl. If it compiles, A is disproved. Inspect generated syntax or the quote expression and restore the split generic pieces. Re-run both simple and generic cases; fixing one must not silently narrow the other.

When you get stuck

Reduce the generated program

Write the expansion you expect as ordinary Rust in a temporary test crate. Compile it before debugging token construction. Provide the input, expected expansion and earliest compiler error to a reviewer. Prefer current official macro documentation over random examples using an incompatible syn major version.

Mastery check

Explain evaluation order, ownership and the trait-path limitation without reading the macro body. Diagnose a double-evaluation defect and justify whether a new request belongs in a function, a declarative macro or a derive. Passing the expansion test is one piece of that judgment.
