Choose ownership and dispatch without hidden cost claims

Trace borrowed and owned parsing, qualify zero-copy claims, and compare static and dynamic dispatch as design choices.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Profile data layout and distinguish memory from locality
  • Distinguish a borrowed symbol slice from an allocation-free program.
  • Choose retention ownership from required lifetimes.
  • Explain static and dynamic dispatch separately from heap allocation.
  • Preserve behavior while deciding which cost would justify measurement.

Key terms: allocation · borrow · capacity · drop · generic · heap · iterator · lifetime

Purpose: separate ownership, allocation, and dispatch costs

A tick report reads a small bounded text buffer, calculates totals, and sometimes retains records after the buffer is released. Three design questions arise: can symbol text be borrowed, when must it become owned, and how should callers select a calculation? These questions concern different boundaries. A trait object does not inherently allocate, and a borrowed string does not make an entire program allocation-free. This checkpoint keeps those distinctions visible in executable code.

The layout investigation measured a repeated scan. This lesson complements it with ownership and abstraction reasoning. It does not invent a static-versus-dynamic speed result. First establish the behavior and lifetime requirements; then measure only if dispatch or allocation cost is material to the real workload.

Plain model: ownership is a duration requirement

A borrowed &str identifies existing valid UTF-8 bytes without owning their storage. Its lifetime constrains how long a caller may use them. A String owns a growable buffer and can survive the source from which its contents were copied. Our parser borrows symbol slices from one input String, parses prices and quantities into integers, and returns a Vec of typed rows. The vector allocates storage for row descriptors even though the symbol bytes are shared.

“Zero-copy” therefore needs a named boundary: symbol extraction creates slices into the existing buffer. Reading a file or network body may already have copied bytes into that buffer; parsing numeric text computes new integer values; storing the row vector requires memory. Retaining one tiny slice can also keep its entire backing buffer alive. Avoid a broad zero-copy claim when the evidence establishes only one avoided copy.

Runnable example: a bounded borrowed parser

projects/reference/p12-replay/examples/dispatch_allocation.rs
//! A borrowed parser and two dispatch choices, with no speed claim.
use std::fmt;

const MAX_BYTES: usize = 4096;
const MAX_ROWS: usize = 64;

#[derive(Debug, PartialEq, Eq)]
struct Tick<'a> {
    symbol: &'a str,
    price: u64,
    quantity: u64,
}

#[derive(Debug, PartialEq, Eq)]
struct OwnedTick {
    symbol: String,
    price: u64,
    quantity: u64,
}

#[derive(Debug, PartialEq, Eq)]
enum ParseError {
    InputLimit,
    RowLimit,
    Fields,
    Symbol,
    Number,
    Range,
}
impl fmt::Display for ParseError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(match self {
            Self::InputLimit => "input exceeds 4096 bytes",
            Self::RowLimit => "input exceeds 64 rows",
            Self::Fields => "each row must have symbol,price,quantity",
            Self::Symbol => "symbol must contain 1 through 8 uppercase ASCII letters",
            Self::Number => "price and quantity must be unsigned decimal integers",
            Self::Range => "price must be 1..=1000000000000; quantity 1..=1000000000",
        })
    }
}
impl std::error::Error for ParseError {}

fn parse(input: &str) -> Result<Vec<Tick<'_>>, ParseError> {
    if input.len() > MAX_BYTES {
        return Err(ParseError::InputLimit);
    }
    let mut rows = Vec::new();
    // The entire borrowed input is already bounded; this is not unbounded I/O.
    for line in input.lines() {
        if rows.len() == MAX_ROWS {
            return Err(ParseError::RowLimit);
        }
        let mut fields = line.split(',');
        let symbol = fields.next().ok_or(ParseError::Fields)?;
        let price = fields.next().ok_or(ParseError::Fields)?;
        let quantity = fields.next().ok_or(ParseError::Fields)?;
        if fields.next().is_some() {
            return Err(ParseError::Fields);
        }
        if symbol.is_empty() || symbol.len() > 8 || !symbol.bytes().all(|b| b.is_ascii_uppercase())
        {
            return Err(ParseError::Symbol);
        }
        if price.is_empty()
            || quantity.is_empty()
            || !price.bytes().all(|b| b.is_ascii_digit())
            || !quantity.bytes().all(|b| b.is_ascii_digit())
        {
            return Err(ParseError::Number);
        }
        let price: u64 = price.parse().map_err(|_| ParseError::Number)?;
        let quantity: u64 = quantity.parse().map_err(|_| ParseError::Number)?;
        if !(1..=1_000_000_000_000).contains(&price) || !(1..=1_000_000_000).contains(&quantity) {
            return Err(ParseError::Range);
        }
        rows.push(Tick {
            symbol,
            price,
            quantity,
        });
    }
    Ok(rows)
}

fn retain(rows: &[Tick<'_>]) -> Vec<OwnedTick> {
    rows.iter()
        .map(|row| OwnedTick {
            symbol: row.symbol.to_owned(),
            price: row.price,
            quantity: row.quantity,
        })
        .collect()
}

trait Metric {
    fn score(&self, tick: &Tick<'_>) -> u128;
}
struct Notional;
impl Metric for Notional {
    fn score(&self, tick: &Tick<'_>) -> u128 {
        u128::from(tick.price) * u128::from(tick.quantity)
    }
}
struct Quantity;
impl Metric for Quantity {
    fn score(&self, tick: &Tick<'_>) -> u128 {
        u128::from(tick.quantity)
    }
}

fn total_static<M: Metric>(rows: &[Tick<'_>], metric: &M) -> u128 {
    rows.iter().map(|row| metric.score(row)).sum()
}
fn total_dynamic(rows: &[Tick<'_>], metric: &dyn Metric) -> u128 {
    rows.iter().map(|row| metric.score(row)).sum()
}

fn main() -> Result<(), ParseError> {
    let input = String::from("ABC,1200,3\nXYZ,2050,2\n");
    let rows = parse(&input)?;
    let static_total = total_static(&rows, &Notional);
    // These trait objects borrow two stack-resident values; dyn does not require Box.
    let metrics: [&dyn Metric; 2] = [&Notional, &Quantity];
    let totals = metrics.map(|metric| total_dynamic(&rows, metric));
    println!(
        "rows={} static_notional={static_total} dynamic_totals={totals:?}",
        rows.len()
    );
    let owned = retain(&rows);
    drop(rows);
    drop(input);
    println!(
        "retained {} owned rows after dropping the source buffer",
        owned.len()
    );
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn borrowed_fields_alias_input_and_owned_fields_survive_it() {
        let owned = {
            let input = String::from("ABC,1200,3\nXYZ,2050,2\n");
            let rows = parse(&input).unwrap();
            assert!(std::ptr::eq(rows[0].symbol.as_ptr(), input.as_ptr()));
            assert_eq!(total_static(&rows, &Notional), 7700);
            assert_eq!(total_dynamic(&rows, &Notional), 7700);
            assert_eq!(total_dynamic(&rows, &Quantity), 5);
            retain(&rows)
        };
        assert_eq!(
            owned,
            [
                OwnedTick {
                    symbol: "ABC".into(),
                    price: 1200,
                    quantity: 3
                },
                OwnedTick {
                    symbol: "XYZ".into(),
                    price: 2050,
                    quantity: 2
                }
            ]
        );
    }
    #[test]
    fn invalid_input_and_resource_bounds_are_explicit() {
        for input in [
            "abc,1,1",
            "ABCDEFGHI,1,1",
            "A,0,1",
            "A,1,0",
            "A,1,-2",
            "A,1,2,3",
            "A,1",
            "A,18446744073709551616,1",
        ] {
            assert!(parse(input).is_err(), "{input}");
        }
        assert_eq!(parse(&"A,1,1\n".repeat(65)), Err(ParseError::RowLimit));
        assert_eq!(parse(&"x".repeat(4097)), Err(ParseError::InputLimit));
        assert!(parse("").unwrap().is_empty());
        assert_eq!(parse(&"A,1,1\n".repeat(64)).unwrap().len(), 64);
    }
}

The parser checks a 4096-byte input bound and a 64-row limit. Each nonempty record has exactly three comma-separated fields. Symbols contain one through eight uppercase ASCII letters; positive price and quantity have explicit integer limits. Invalid fields produce a typed error. Empty input yields no rows. str::lines() is appropriate here because the complete borrowed input is already bounded; this is different from reading an arbitrarily long file line into memory.

The returned Tick<'_> values carry borrows from the supplied input. The library does not clone the source to appease a compiler error. At the retention boundary, retain explicitly creates owned symbols because the requirement changes: those records must remain usable independently. Both choices are sound first implementations for their respective lifetimes. Borrowing is not automatically superior to ownership.

Follow allocations through the design

The input String owns storage. The parser's row vector can grow as rows are pushed. A vector has a length and capacity; reserving capacity can reduce growth reallocations when a useful bound or accurate estimate is known. Reserving the maximum for every tiny request may waste memory, while requesting exactly one additional slot repeatedly can create needless work. Here at most 64 rows makes ordinary vector growth a proportionate choice.

Each nonempty owned symbol created by to_owned needs independent string storage, and the retained vector owns its own element buffer. These are code-level allocation opportunities, not instrumented allocator-call counts. Compiler transformations, allocator behavior, and capacity policy affect actual requests and operating-system mappings. If allocation is the suspected bottleneck, use an allocation profiler appropriate to the target and measure the chosen request boundary.

Alternatives include processing borrowed rows immediately, retaining the full input together with offsets, sharing a buffer through an ownership type, or copying only records that must survive. Each has a duration and memory tradeoff. A small copy that lets a large network buffer be released may reduce retained memory. Adding reference counting everywhere can introduce metadata, synchronization, and API complexity without serving the current requirement.

Static and dynamic dispatch: the selection boundary

total_static<M: Metric> takes a concrete metric type selected at compile time. The compiler can generate code for the concrete instantiations and may inline their operations. total_dynamic accepts a trait object, enabling a common interface for metric implementations selected at runtime. Its reference carries access to the underlying value and the information needed to call the appropriate methods. The small array can contain both a notional metric and a quantity metric.

Dynamic dispatch does not imply that the metric is boxed: these objects are borrowed. Conversely, a generic function may operate on heap-owned data. Allocation and dispatch are orthogonal decisions. Runtime flexibility can be worth an indirect call; generic specialization can improve optimization opportunities while increasing generated code and compilation work across many instantiations. A compiler may sometimes devirtualize a visible trait-object call, so source syntax alone is not a measured instruction trace.

Neither mechanism is a universally professional or universally fast choice. Use a concrete or generic type when the implementation is naturally fixed. Use a trait object when heterogeneous implementations or runtime selection simplify a real boundary. In a hot path, consider dispatching once around a batch instead of once per element, but preserve the same behavior and measure the change.

Guided checkpoint: retain only when necessary

Trace the input's ownership through main. Calculate the borrowed totals while the input remains alive. Then inspect retain and identify each field copied into the owned representation. Drop the borrowed rows and input and access the owned records. The passing test checks complete expected owned rows, not only their count, so a retention function that accidentally drops a symbol or swaps a quantity is detected.

Now choose a consumer requirement. A report rendered immediately can use the borrowed rows. A background queue that outlives the request needs an appropriate owned representation. Write that lifetime requirement in plain language before selecting String, references, or reference-counted buffers. An API should make the required ownership transition visible instead of hiding an expensive clone inside a convenient accessor.

Intentional mistake: drop the owner too early

In a disposable learner copy, move drop(input) to immediately after parsing, then use the borrowed rows. Predict a borrow-checker rejection because the owner would be moved while references remain in use. This mutation is an expected diagnostic exercise, not an executed check recorded in the supplied logs. Restore the valid lifetime ordering. Changing every field to owned text would satisfy the compiler but would also change the allocation and ownership design; do that only when the retention requirement calls for it.

Apply the problem-solving playbook

Observation: the reference calculates both metrics through &dyn Metric and retains owned records after the source is dropped. Hypothesis A says dynamic dispatch requires boxing and therefore caused the symbol copies. Hypothesis B says the copies occur because the retained records must outlive the input. Inspect the actual boundary: the dynamic metric array borrows values, while to_owned appears specifically in retain. The executed tests verify the totals and retained contents. A's necessary-allocation claim is disproved by this concrete borrowing interface.

For a further distinguishing experiment, remove the retention step in a learner copy while keeping dynamic dispatch. The expected totals stay the same and the explicit symbol-copy step disappears. Conversely, keep retention and use only static totals; ownership still requires those owned strings. Mark these latter experiments as expected until you execute them. Record the result and limitations in the shared investigation template. Ask an AI assistant to identify the owning allocation and relevant lifetime before accepting a proposed clone or lifetime annotation.

Independent tasks, tiered hints, and worked solution

Investigate adding a maximum-price metric: decide whether the summation interface can express it correctly, and design a corresponding aggregation if it cannot. Then change the application to retain only rows whose quantity exceeds two. Specify whether order is preserved and whether the original input may be released afterward. Add a test containing zero retained rows and another containing two symbols with different quantities.

Hint 1: check the aggregation contract

A metric's return value must fit the existing result contract; a sum interface does not compute a maximum. A maximum operation needs a corresponding aggregation function, returning Option for empty input.

Hint 2: follow the owner

Filtering borrowed rows does not extend their lifetime.

Hint 3: place the ownership transition

Perform the filter before copying symbols if the goal is selective retention.

Worked solution direction

The worked direction is to add a separate maximum-price function using Iterator::max, with static or dynamic field selection only if that abstraction helps. For selective retention, iterate in source order, filter by quantity, and construct owned rows only for matches. An empty result is a valid empty vector. The fixture retains ABC and discards XYZ at a threshold greater than two, and the retained ABC remains valid after the input is dropped. This avoids shoehorning a different operation into an unsuitable abstraction.

When you get stuck

Run the example tests, then reduce a borrowing failure to one symbol and one owner. Write down which value owns each buffer and the last use of each reference. Read the standard Vec and String documentation for allocation behavior, and the Reference for trait objects. A useful review request includes the smallest failing lifetime example, the required retention duration, your proposed ownership boundary, and whether your concern is compile time, memory, or runtime. Avoid asking for a performance patch before identifying the cost.

Engineering decisions, evidence limits, and mastery

This small parser uses no external dependency, accepts bounded input, preserves typed failures, and explicitly transitions from borrowed to owned records. Separate static and dynamic functions make dispatch choices visible for teaching; a real API may choose only one. The two example tests passed and the executable output was recorded in the example log. All P12 targets passed strict Clippy. No allocator instrumentation or static-versus-dynamic timing was collected, and no dispatch speedup is claimed.

Mastery means defending an ownership choice from a duration requirement, narrowing a zero-copy statement to the operation actually verified, and explaining why a borrowed trait object need not allocate. You should also recognize when the metric abstraction fails to express a new operation and simplify or reshape it instead of adding a misleading implementation.
