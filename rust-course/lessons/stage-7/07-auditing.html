Audit cleanup, panics and evidence limits

Review the unsafe wrapper as a state machine, including destructor panics and zero-sized elements.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • A small unsafe boundary with explicit invariants
  • Explain cleanup ordering when user destructors panic
  • Distinguish leaks, double drops and invalid references
  • Use differential tests and dynamic checking as evidence with limits
  • Write a review that separates observed behavior from unproved claims

Key terms: allocation · capacity · drop · invariant · lifetime · mise · move · ownership

Purpose: inspect the path that ordinary examples avoid

A container can behave correctly for integers and still mishandle owned resources, zero-sized values or a destructor that panics. An unsafe audit must consider every safe caller permitted by the API, not only the sample main function. P13 therefore includes exactly-once drop tests, over-aligned values, zero-sized values with destructors, repeated operations against a safe baseline and a single destructor panic during clear. This lesson asks you to evaluate what those tests establish, what the invariant argument establishes, and which questions remain. Reviewing is a distinct activity from authoring; a self-review does not become independent acceptance because the tests pass.

Model: cleanup is another state transition

clear first replaces len with zero and remembers the old length. It then asks slice drop glue to drop the old initialized prefix. Publishing the empty state before invoking user Drop code matters because a destructor can panic. If control later returns through catch_unwind and the container is dropped again, len zero prevents a second drop of those values. Slice drop glue handles cleanup of remaining elements during unwinding from a single element destructor panic. If another destructor panics while unwinding, the process may abort. The container cannot promise recovery from every sequence of panicking destructors or from a panic-abort build.

Predict three different failures

Predict what happens if pop reads a value without shrinking len, if clear shrinks len but forgets to drop the old prefix, and if as_slice exposes the uninitialized suffix. These are not equivalent mistakes. The first can cause duplicate ownership and double drop. The second can leak resources while remaining memory-safe under the relevant assumptions. The third can construct references to invalid values and cause undefined behavior. A review that labels all three “memory leak” loses the distinctions needed to choose tests and repairs. Write the invariant each mutation violates before running any deliberately broken version.

The panic test intentionally triggers a destructor panic inside catch_unwind. The panic hook may print a message even though the test succeeds after checking recovery. Do not interpret the printed word “panic” alone as a failed test. Inspect the exit status and final assertions. Conversely, a caught panic is not evidence that arbitrary undefined behavior would be safely caught; those are fundamentally different failure categories.

//! Tiny fixed-capacity stack for auditing unsafe boundaries, not a faster-Vec claim.
#![deny(unsafe_op_in_unsafe_fn)]
use std::mem::MaybeUninit;

/// Invariant: len <= N; exactly slots[0..len] contain live T values.
/// Safe callers cannot alter slots or len directly. No references survive a mutation
/// because all mutation requires &mut self. Uninitialized storage is never exposed as T.
pub struct FixedSlots<T, const N: usize> {
    slots: [MaybeUninit<T>; N],
    len: usize,
}
impl<T, const N: usize> Default for FixedSlots<T, N> {
    fn default() -> Self {
        Self::new()
    }
}
impl<T, const N: usize> FixedSlots<T, N> {
    pub fn new() -> Self {
        Self {
            slots: [const { MaybeUninit::uninit() }; N],
            len: 0,
        }
    }
    pub fn len(&self) -> usize {
        self.len
    }
    pub fn is_empty(&self) -> bool {
        self.len == 0
    }
    pub fn push(&mut self, value: T) -> Result<(), T> {
        if self.len == N {
            return Err(value);
        }
        self.slots[self.len].write(value); // Initialize before publishing the new length.
        self.len += 1;
        Ok(())
    }
    pub fn pop(&mut self) -> Option<T> {
        if self.len == 0 {
            return None;
        }
        self.len -= 1; // Remove from live prefix before transferring ownership.
        // SAFETY: old len was positive, so this slot was initialized. Shrinking len
        // ensures this value is moved out exactly once and never dropped by self.
        Some(unsafe { self.slots[self.len].assume_init_read() })
    }
    pub fn as_slice(&self) -> &[T] {
        // SAFETY: MaybeUninit<T> has T's size/alignment. The prefix is initialized,
        // within this one array allocation, and borrowed for exactly self's lifetime.
        // Array pointers are non-null/aligned even for N=0 or a zero-sized T.
        unsafe { std::slice::from_raw_parts(self.slots.as_ptr().cast::<T>(), self.len) }
    }
    pub fn as_mut_slice(&mut self) -> &mut [T] {
        // SAFETY: same layout/initialization/range reasoning as as_slice; &mut self
        // gives exclusive access for the returned slice's lifetime, including ZSTs.
        unsafe { std::slice::from_raw_parts_mut(self.slots.as_mut_ptr().cast::<T>(), self.len) }
    }
    pub fn get(&self, index: usize) -> Option<&T> {
        self.as_slice().get(index)
    }
    pub fn clear(&mut self) {
        let len = std::mem::take(&mut self.len); // Publish empty state before user Drop code.
        // SAFETY: old prefix contained len initialized owned Ts. The mutable borrow
        // excludes references. Slice drop glue drops each element, including cleanup
        // during a single destructor panic; len=0 prevents a later double drop.
        unsafe {
            std::ptr::drop_in_place(std::ptr::slice_from_raw_parts_mut(
                self.slots.as_mut_ptr().cast::<T>(),
                len,
            ));
        }
    }
}
impl<T, const N: usize> Drop for FixedSlots<T, N> {
    fn drop(&mut self) {
        self.clear();
    }
}

/// Safe comparison implementation: same capacity policy, heap-backed storage.
pub struct SafeSlots<T, const N: usize>(Vec<T>);
impl<T, const N: usize> Default for SafeSlots<T, N> {
    fn default() -> Self {
        Self(Vec::with_capacity(N))
    }
}
impl<T, const N: usize> SafeSlots<T, N> {
    pub fn push(&mut self, value: T) -> Result<(), T> {
        if self.0.len() == N {
            Err(value)
        } else {
            self.0.push(value);
            Ok(())
        }
    }
    pub fn pop(&mut self) -> Option<T> {
        self.0.pop()
    }
    pub fn as_slice(&self) -> &[T] {
        &self.0
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::{
        cell::Cell,
        panic::{AssertUnwindSafe, catch_unwind},
        rc::Rc,
    };
    #[test]
    fn empty_zero_capacity_and_bounds() {
        let mut zero = FixedSlots::<String, 0>::new();
        assert_eq!(zero.push("owned".into()), Err("owned".into()));
        assert_eq!(zero.pop(), None);
        assert_eq!(zero.get(0), None);
        assert!(zero.as_mut_slice().is_empty());
        let mut one = FixedSlots::<u32, 1>::new();
        one.push(7).unwrap();
        assert_eq!(one.get(1), None);
        assert_eq!(one.push(8), Err(8));
        assert_eq!(one.pop(), Some(7));
        assert_eq!(one.pop(), None);
    }
    #[test]
    fn agrees_with_safe_baseline_under_many_operations() {
        let mut actual = FixedSlots::<u64, 7>::new();
        let mut expected = SafeSlots::<u64, 7>::default();
        let mut seed = 19u64;
        for _ in 0..10_000 {
            seed = seed.wrapping_mul(6364136223846793005).wrapping_add(1);
            if seed & 3 == 0 {
                assert_eq!(actual.pop(), expected.pop());
            } else {
                assert_eq!(actual.push(seed), expected.push(seed));
            }
            assert_eq!(actual.as_slice(), expected.as_slice());
        }
    }
    #[test]
    fn values_are_dropped_exactly_once_and_rejected_value_is_returned() {
        struct Count(Rc<Cell<usize>>);
        impl Drop for Count {
            fn drop(&mut self) {
                self.0.set(self.0.get() + 1);
            }
        }
        let count = Rc::new(Cell::new(0));
        {
            let mut slots = FixedSlots::<Count, 2>::new();
            assert!(slots.push(Count(count.clone())).is_ok());
            assert!(slots.push(Count(count.clone())).is_ok());
            let rejected = slots.push(Count(count.clone())).err().unwrap();
            assert_eq!(count.get(), 0);
            drop(rejected);
            drop(slots.pop());
            assert_eq!(count.get(), 2);
        }
        assert_eq!(count.get(), 3);
    }
    #[test]
    fn zero_sized_values_are_logical_elements() {
        let mut slots = FixedSlots::<(), 3>::new();
        for _ in 0..3 {
            slots.push(()).unwrap();
        }
        assert_eq!(slots.as_slice().len(), 3);
        assert_eq!(slots.push(()), Err(()));
        assert_eq!(slots.pop(), Some(()));
        slots.clear();
        assert!(slots.is_empty());
    }
    #[test]
    fn zero_sized_destructors_run_for_every_element() {
        thread_local! { static DROPS: Cell<usize> = const { Cell::new(0) }; }
        struct Z;
        impl Drop for Z {
            fn drop(&mut self) {
                DROPS.with(|n| n.set(n.get() + 1));
            }
        }
        DROPS.with(|n| n.set(0));
        {
            let mut slots = FixedSlots::<Z, 3>::new();
            for _ in 0..3 {
                assert!(slots.push(Z).is_ok());
            }
        }
        DROPS.with(|n| assert_eq!(n.get(), 3));
    }
    #[test]
    fn alignment_is_preserved() {
        #[repr(align(64))]
        struct Aligned(u8);
        let mut slots = FixedSlots::<Aligned, 2>::new();
        assert!(slots.push(Aligned(4)).is_ok());
        assert_eq!(slots.as_slice().as_ptr() as usize % 64, 0);
        slots.as_mut_slice()[0].0 = 9;
        assert_eq!(slots.get(0).unwrap().0, 9);
    }
    #[test]
    fn a_single_destructor_panic_leaves_empty_reusable_storage() {
        struct Bomb {
            drops: Rc<Cell<usize>>,
            explode: bool,
        }
        impl Drop for Bomb {
            fn drop(&mut self) {
                self.drops.set(self.drops.get() + 1);
                assert!(!self.explode, "injected destructor panic");
            }
        }
        let drops = Rc::new(Cell::new(0));
        let mut slots = FixedSlots::<Bomb, 3>::new();
        for explode in [false, true, false] {
            assert!(
                slots
                    .push(Bomb {
                        drops: drops.clone(),
                        explode
                    })
                    .is_ok()
            );
        }
        assert!(catch_unwind(AssertUnwindSafe(|| slots.clear())).is_err());
        assert_eq!(drops.get(), 3);
        assert!(slots.is_empty());
        assert!(
            slots
                .push(Bomb {
                    drops: drops.clone(),
                    explode: false
                })
                .is_ok()
        );
        drop(slots);
        assert_eq!(drops.get(), 4);
    }
}

The owned-value test shares a counter through Rc<Cell<usize>> on one test thread. It fills the container, receives a rejected value, drops that returned value, pops another and finally drops the container. Each step predicts an exact count. The zero-sized destructor test uses logical element count rather than pointer differences. The alignment test checks a deliberately over-aligned type. The differential test follows a deterministic operation sequence and compares the live slice with SafeSlots after every step. None of these requires exposing the private representation to ordinary callers.

Dynamic tools find counterexamples, not universal proofs

Miri can execute Rust code under an interpreter that checks many forms of undefined behavior. Use it as an additional investigation tool when an isolated nightly toolchain with the Miri component is available. Playbook investigation: a red panic log and a green suite

You receive incomplete evidence: a screenshot containing “injected destructor panic,” a green summary, and a patch moving len=0 after drop_in_place. Hypothesis A says the test harness ignored a real failure. Hypothesis B says the expected panic was caught and assertions passed in the old version. Hypothesis C says the patch creates a double-drop risk only when clear unwinds. Reproduce the exact test command, inspect catch_unwind and track len at the unwind boundary. A passing test with the original ordering disproves the claim that every printed panic necessarily means test failure. It does not justify the patch.

Investigate the changed ordering without assuming ordinary execution will reliably expose invalid behavior. Reason from the state transition: if a destructor panics before len is cleared, later container cleanup can revisit already-dropped values. Restore empty-state publication before calling user destructors. Evidence includes drop counts, empty reusable storage after one caught panic, and a reviewed invariant trace. Its limits explicitly exclude survival from a second panic during unwinding and do not equate resource-leak freedom with all aspects of memory safety.

Guided checkpoint: perform a review without rewriting first

For each unsafe block, record the pointer origin, alignment, initialized range, exclusivity, lifetime and cleanup obligations that apply. Mark any obligation irrelevant to that particular operation instead of pasting the same checklist blindly. Trace new, successful push, rejected push, pop, borrowed slices, clear and Drop. Then inspect every early return and possible user-code invocation. You may discover that the smallest helpful change is a clearer invariant comment or a missing regression rather than a new abstraction. Review claims and evidence before changing implementation.

Engineering decisions and evidence

Current scope and invariants. len never exceeds capacity; precisely the prefix below len contains owned initialized values. Borrowed slices expose only that prefix with self-tied lifetimes and appropriate exclusivity. A moved-out value is excluded from later cleanup.

Why this is the current recommended shape. A safe Vec-based model comes first. The compact unsafe representation uses private MaybeUninit storage, capacity checks before writes, initialization before length publication, and length removal before move-out. clear publishes empty state before user Drop code. Every unsafe expression has a local justification.

Reasonable alternative and tradeoff. A Vec or an established fixed-capacity collection is the preferred general application choice when its contract meets requirements. This custom wrapper is appropriate only for studying a small auditable boundary; no speed advantage or universal soundness proof is claimed. Adding more operations increases the audit surface and should be justified by an actual requirement.

Evidence and limits. Native reference tests were run through mise in the coordinated course verification; inspect the current verification record for exact results. Zero capacity; bounds and ownership on full push; deterministic comparison with safe baseline; exactly-once non-Copy destruction; ZST counts and destructors; over-alignment; one caught destructor panic with reuse. Passing native tests or Miri is evidence for executed cases, not a universal soundness proof. A second panic while unwinding can abort. Independent review remains pending; author self-review cannot grant acceptance.

Requirement that would justify evolution. Use an established collection for production needs unless stack storage or another measured requirement justifies ownership of an unsafe implementation. Any new removal, iteration, interior-mutability or raw-pointer feature requires a renewed invariant review.

In your review, explain this choice in your own words, preserve the behavioral contract during changes, and name the evidence that would make you choose the alternative. Deliberately broken variants above are diagnostic exercises, never recommended implementation stages.

Safety contract: byte extent and what tests establish

The Rust 1.99.1 slice-construction contract also requires the total byte extent to fit within isize::MAX and its address calculation not to wrap. The pointer here comes from one live array object, and the private length stays within that array. A prefix therefore stays within that object's valid allocation extent; zero-sized elements have zero byte extent but still require an aligned, non-null pointer. State this argument alongside initialization, aliasing, and lifetime obligations. Adding a debug assertion alone would not establish the safe interface's contract.

Boundary tests demonstrate their chosen executions. The invariant argument must account for every permitted safe caller, and independent review remains separate. The earlier follow-up audit checked the installed Rust 1.99.0 primary documentation locally, reviewed all four unsafe sites, and reused the existing native, optimized, and Miri evidence; it does not claim a new universal soundness proof. See the narrow boundary audit.

Ownership transfer is different from leaking

The Rust 1.99 release guidance discourages reclaiming allocations after Box::leak. When a foreign API must eventually return ownership, begin with Box::into_raw or Box::into_non_null and reconstruct exactly once under their documented safety preconditions. An ordinary Box remains the simpler choice when Rust can retain ownership throughout. P13 does not leak and reclaim allocations.
