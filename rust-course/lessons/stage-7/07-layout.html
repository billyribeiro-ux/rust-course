Profile data layout and distinguish memory from locality

Compare complete AoS and SoA records with bounded release profiling, separate phase costs, and measured process memory.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Rendering, security and alternative clients
  • Traits as required capabilities, not decoration
  • Explain hot-field locality without claiming a universal cache result.
  • Preserve complete records while changing layout.
  • Interpret phase timings, payload capacity, allocation requests and peak RSS separately.
  • Design a controlled experiment that can disprove a favored explanation.

Key terms: allocation · capacity · checksum · lockfile · mise · ownership · replay · stack

Purpose: locate a cost before changing the representation

A snapshot service repeatedly totals price times quantity across many records. Its records also contain timestamps, account identifiers, symbols, and audit tags. Those fields remain required, but this query does not read them. The question is precise: does grouping the queried fields into separate contiguous arrays reduce the time for this read-mostly operation while preserving every logical record? This lab investigates that question without changing P12's replay engine or claiming to model an exchange.

The earlier projects taught bounded processing and correct state transitions. Those constraints still apply. A representation change must preserve data, respect memory limits, and produce the same result. Performance is an additional requirement with a named workload, not permission to remove validation or silently discard fields.

Plain model: useful bytes and neighboring bytes

An array of structures, abbreviated AoS, stores complete records consecutively. Here each record occupies 64 bytes on the measured target. A structure of arrays, SoA, stores prices together, quantities together, and cold metadata together. The price and quantity columns together occupy 16 bytes per logical record; all metadata is still retained in another vector. Both layouts hold the same 48,000,000 bytes of reserved element storage for 750,000 records.

Processors transfer memory in blocks and exploit nearby accesses. A scan that needs only two fields may fetch less irrelevant data when those fields are grouped. That is a reason to investigate locality, not a guaranteed speedup. Compiler vectorization, prefetching, cache capacities, alignment, and access order also matter. A query that consumes complete records or frequently inserts and removes rows may favor a different organization.

The example uses repr(C) to make its illustrative field order explicit and prints size_of::<Row>(). Ordinary Rust struct field order is not a wire-format promise. Even a known in-memory layout is not permission to serialize raw padding or reinterpret arbitrary bytes as a valid value. This safe example accesses fields through Rust values throughout.

Predict before measuring

Predict whether SoA must use less total memory, whether it must allocate fewer buffers, and whether its construction phase must be faster. Then identify exactly what the scan timer includes. A useful prediction separates three quantities: retained payload, bytes relevant to a query, and elapsed time. They are related but are not interchangeable.

# Working directory: rust-course/projects
mise exec -- cargo test -p p12-replay --examples
mise exec -- cargo build --release -p p12-replay --examples
mise exec -- cargo run --release -p p12-replay --example layout_profile -- aos 750000 80
mise exec -- cargo run --release -p p12-replay --example layout_profile -- soa 750000 80

The retained payload is equal because SoA preserves the cold fields. AoS makes one vector reservation; SoA makes three. The measured SoA construction median was higher, even though its repeated scan was faster. Thus neither “more allocations always means slower overall” nor “a faster scan means less resident memory” explains the complete observation.

Runnable example and its boundaries

projects/reference/p12-replay/examples/layout_profile.rs
//! Bounded synthetic snapshot analytics: identical records, different layouts.
//! Run in release mode; stdout is one machine-readable measurement row.
use std::{hint::black_box, mem::size_of, process::ExitCode, time::Instant};

const MAX_ROWS: usize = 1_000_000;
const MAX_PASSES: usize = 200;

#[repr(C)]
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Cold {
    timestamp: u64,
    account: u64,
    symbol: [u8; 16],
    audit_tag: [u8; 16],
}

#[repr(C)]
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct Row {
    price: u64,
    quantity: u64,
    cold: Cold,
}

fn fixture(index: usize) -> Row {
    let i = index as u64;
    Row {
        price: 10_000 + i % 90_000,
        quantity: 1 + i % 100,
        cold: Cold {
            timestamp: 1_000_000 + i,
            account: i % 997,
            symbol: [(i % 26) as u8 + b'A'; 16],
            audit_tag: [(i % 251) as u8; 16],
        },
    }
}

fn reserved<T>(rows: usize) -> Result<Vec<T>, std::collections::TryReserveError> {
    let mut values = Vec::new();
    values.try_reserve_exact(rows)?;
    Ok(values)
}

enum Data {
    Aos(Vec<Row>),
    Soa {
        prices: Vec<u64>,
        quantities: Vec<u64>,
        cold: Vec<Cold>,
    },
}

impl Data {
    fn new(mode: &str, rows: usize) -> Result<Self, Box<dyn std::error::Error>> {
        match mode {
            "aos" => {
                let mut values = reserved(rows)?;
                values.extend((0..rows).map(fixture));
                Ok(Self::Aos(values))
            }
            "soa" => {
                let mut prices = reserved(rows)?;
                let mut quantities = reserved(rows)?;
                let mut cold = reserved(rows)?;
                for i in 0..rows {
                    let row = fixture(i);
                    prices.push(row.price);
                    quantities.push(row.quantity);
                    cold.push(row.cold);
                }
                Ok(Self::Soa {
                    prices,
                    quantities,
                    cold,
                })
            }
            _ => Err("layout must be aos or soa".into()),
        }
    }

    fn row(&self, index: usize) -> Row {
        match self {
            Self::Aos(values) => values[index],
            Self::Soa {
                prices,
                quantities,
                cold,
            } => Row {
                price: prices[index],
                quantity: quantities[index],
                cold: cold[index],
            },
        }
    }

    fn capacity_bytes(&self) -> usize {
        match self {
            Self::Aos(values) => values.capacity() * size_of::<Row>(),
            Self::Soa {
                prices,
                quantities,
                cold,
            } => {
                (prices.capacity() + quantities.capacity()) * size_of::<u64>()
                    + cold.capacity() * size_of::<Cold>()
            }
        }
    }

    fn allocation_requests(&self) -> usize {
        match self {
            Self::Aos(_) => 1,
            Self::Soa { .. } => 3,
        }
    }

    // Generator bounds prove this sum <= 1_000_000 * 99_999 * 100, below u64::MAX.
    // No unchecked external records enter this private fixture representation.
    fn notional(&self) -> u64 {
        match self {
            Self::Aos(values) => black_box(values.as_slice())
                .iter()
                .map(|row| row.price * row.quantity)
                .sum(),
            Self::Soa {
                prices, quantities, ..
            } => black_box(prices.as_slice())
                .iter()
                .zip(black_box(quantities.as_slice()))
                .map(|(price, quantity)| price * quantity)
                .sum(),
        }
    }
}

fn bounded_count(input: &str, maximum: usize) -> Result<usize, &'static str> {
    if input.len() > 20 {
        return Err("count text is too long");
    }
    match input.parse::<usize>() {
        Ok(value) if (1..=maximum).contains(&value) => Ok(value),
        _ => Err("count is invalid or outside the documented bound"),
    }
}

fn run() -> Result<(), Box<dyn std::error::Error>> {
    let args = std::env::args_os()
        .skip(1)
        .map(|value| value.into_string().map_err(|_| "arguments must be UTF-8"))
        .collect::<Result<Vec<_>, _>>()?;
    let [mode, rows, passes] = args.as_slice() else {
        return Err("usage: layout_profile <aos|soa> <rows:1..1000000> <passes:1..200>".into());
    };
    let rows = bounded_count(rows, MAX_ROWS)?;
    let passes = bounded_count(passes, MAX_PASSES)?;
    if cfg!(debug_assertions) {
        return Err("comparative measurements require --release".into());
    }
    let begin = Instant::now();
    let data = Data::new(mode, rows)?;
    let generation_ns = begin.elapsed().as_nanos();
    let begin = Instant::now();
    for index in 0..rows {
        if data.row(index) != fixture(index) {
            return Err("full fixture comparison failed".into());
        }
    }
    let expected: u64 = (0..rows)
        .map(|i| {
            let row = fixture(i);
            row.price * row.quantity
        })
        .sum();
    let validation_ns = begin.elapsed().as_nanos();
    for _ in 0..2 {
        if black_box(data.notional()) != expected {
            return Err("warm-up result differs from fixture oracle".into());
        }
    }
    let begin = Instant::now();
    let mut checksum = 0u64;
    for _ in 0..passes {
        checksum += black_box(data.notional());
    }
    let scan_ns = begin.elapsed().as_nanos();
    if checksum != expected * passes as u64 {
        return Err("measured result differs from fixture oracle".into());
    }
    println!(
        "layout={mode}\trows={rows}\tpasses={passes}\trow_bytes={}\tcapacity_bytes={}\tallocation_requests={}\tgeneration_ns={generation_ns}\tvalidation_ns={validation_ns}\tscan_ns={scan_ns}\tchecksum={checksum}",
        size_of::<Row>(),
        data.capacity_bytes(),
        data.allocation_requests()
    );
    Ok(())
}

fn main() -> ExitCode {
    match run() {
        Ok(()) => ExitCode::SUCCESS,
        Err(error) => {
            eprintln!("layout profile: {error}");
            ExitCode::FAILURE
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn layouts_preserve_every_field_and_analytics_for_boundary_sizes() {
        for count in [0, 1, 17, 99, 100, 101, 997, 1025] {
            let aos = Data::new("aos", count).unwrap();
            let soa = Data::new("soa", count).unwrap();
            for index in 0..count {
                assert_eq!(aos.row(index), soa.row(index));
            }
            assert_eq!(aos.notional(), soa.notional());
        }
        assert_eq!(Data::new("aos", 2).unwrap().notional(), 30_002);
        assert_eq!(fixture(0).cold.symbol, [b'A'; 16]);
        assert_eq!(fixture(26).cold.symbol, [b'A'; 16]);
    }
    #[test]
    fn limits_fail_before_allocating_and_modes_are_explicit() {
        for bad in ["0", "-1", "1000001", "NaN", "999999999999999999999"] {
            assert!(bounded_count(bad, MAX_ROWS).is_err());
        }
        assert_eq!(bounded_count("1000000", MAX_ROWS), Ok(MAX_ROWS));
        assert!(Data::new("typo", 10).is_err());
    }
}

The command validates a maximum of one million rows and 200 passes before allocation. Count text is bounded, non-Unicode arguments are rejected explicitly, and allocation reservation failures return errors. The fixture generates positive bounded integer prices and quantities. Those closed bounds keep the sum and repeated checksum inside u64; this is not a summation API for arbitrary external numbers.

Construction starts before reserving and filling the vectors. Validation reconstructs every complete record and compares it with the deterministic fixture, including metadata unused by the query. It also obtains an expected numeric result. Two warm-up scans precede the measured scans. The scan timer includes the repeated reductions and their accumulated checksum; it excludes construction, full-record validation, warm-ups, output, and final destruction. black_box discourages optimization based on visible inputs and outputs but is a best-effort tool, not a guarantee about generated instructions.

Guided checkpoint: profile one complete process

On macOS, build once and use the included resource-counter driver. Run from the course root; choose a new output directory for every investigation. The driver refuses an existing directory, alternates variant order across seven pairs, and invokes each sample in a separate process.

python3 projects/reference/p12-replay/profile-layout.py \
  --binary .local/native-target/release/examples/layout_profile \
  --output .local/layout-profile-first

This command assumes the course's mise configuration supplied the build target. If you selected a different target directory, pass the corresponding executable path. The Rust example is portable; this driver specifically uses macOS /usr/bin/time -l. On another operating system, choose its documented profiler and record its units instead of copying macOS counter interpretations.

The outer process timer includes startup, construction, validation, warm-ups, measured scans, output, destruction, and profiler overhead. Maximum resident set size is a process-wide peak. It includes more than vector elements and says nothing about how many allocation requests occurred. The installed macOS getrusage(2) manual identifies this counter's unit as bytes; GNU time commonly reports a different unit. Verify the actual tool rather than trusting a familiar-looking label.

Observed evidence and what it means

The historical recorded release run used Rust 1.99.0 on an Apple M3 Ultra with 28 logical CPUs and 96 GiB of memory. Every sample contained 750,000 records and 80 measured passes, with two warm-ups. All complete-record comparisons passed, and all 14 samples produced checksum 163062480000000. Background load, affinity, power, and thermal state were not controlled.

Measured quantityAoS medianSoA median
Construction4.204 ms5.166 ms
80 scans44.108 ms17.000 ms
Whole observed process58.530 ms31.150 ms
Maximum RSS49,872,896 bytes49,938,432 bytes

The SoA scan median is about 0.385 times the AoS scan median in this experiment. The scan ranges were 42.926–46.589 ms and 15.864–17.429 ms respectively. These are observations of a synthetic hot-field query. They do not establish a universal speedup, a service latency guarantee, or a lower memory requirement. Medians from separate phases should not be added as though they came from one representative execution.

This is resource profiling, not a call-stack or hardware cache-miss profile. Locality is a plausible explanation consistent with the access pattern, while code generation and vectorization are competing explanations. The measurements do not isolate their contributions. Use a suitable CPU profiler or inspect generated code if a decision requires that attribution. Raw process counters and all sample commands are preserved in the linked evidence.

Intentional mistake: time unequal work

In a disposable learner copy, remove the cold metadata vector from SoA and compare it with the original AoS. The full-record validation should prevent this reduced representation from being accepted as equivalent. Treat that failure as expected until you actually run the mutation. A faster program that forgot required data answers a different question. Another misleading comparison would include construction for AoS but time only the reduction for SoA; write both timer boundaries before accepting such a report.

Apply the problem-solving playbook

Observation: the actual SoA scan was faster, but its RSS was slightly higher. Hypothesis A says the improvement occurred because SoA discarded metadata and retained less memory. Hypothesis B says the same data was reorganized so the query accesses a smaller hot subset. Distinguish them by inspecting reserved capacities and comparing every reconstructed field. The actual run retained 48 MB of element storage in both representations and passed full-record comparisons, disproving A for this implementation.

B remains compatible with the evidence, but it is not a complete causal proof: the two loops also give the optimizer different opportunities. A next experiment could add a query that reads every field, holding row count and build profile fixed, or use cache-miss and instruction profiles. State the expected discriminator first. Capture the workload, raw samples, equality evidence, rejected hypothesis, and residual uncertainty in the problem-solving playbook. An AI review should explain those controls before recommending a representation rewrite.

Independent practice, hints, and worked direction

Measure 10,000 rows, then 750,000 rows with the same number of passes. Separately design a whole-record checksum query. Keep all logical fields and compare complete output before timing. Decide whether your application performs enough repeated scans to recover SoA's observed construction cost; do not infer that crossover from this one workload alone.

Hint 1: preserve the experimental cases

Keep samples of different row counts in different directories.

Hint 2: define equivalent work

A whole-record query must read metadata in both variants, not merely return the original notional sum.

Hint 3: choose the request boundary

Report per-sample construction-plus-query totals if that is the real request boundary.

Worked direction

First establish matching results, then repeat each controlled case, and finally choose a representation for the measured workload. A result showing no worthwhile improvement is a useful outcome.

When you get stuck

Run mise exec -- cargo test -p p12-replay --example layout_profile before examining timing. Confirm --release, the printed row count, and the payload capacity. If memory figures appear absurd, inspect the profiler's units and raw output. If a result differs, reduce to one or 17 records and compare reconstructed fields. Request review with both commands, all samples, equality checks, timer boundaries, and your two competing explanations.

Engineering decisions, evidence limits, and mastery

A bounded immutable fixture and separate phases make this experiment reviewable. Safe vectors and typed records suffice; unsafe pointer traversal or a custom allocator would add obligations without answering the current question. Three buffer reservations are a visible tradeoff for narrower query arrays. Evolve the design only when an actual workload requires different update, ownership, or latency behavior.
