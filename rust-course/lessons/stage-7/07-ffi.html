Foreign interfaces and environments without std

Make contracts explicit when Rust meets C or a target without an operating system.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Purpose: know what Rust cannot check for you

Rust code sometimes calls a library written in another language or runs on a target without an operating system. The compiler still checks Rust types and borrowing, but it cannot infer a foreign function's full contract or invent a hardware runtime. This specialization teaches how to make that missing contract explicit. It is not a prerequisite for every web application.

Plain model: agreeing on the boundary

An application binary interface, or ABI, specifies machine-level calling conventions such as parameter passing and symbol naming. An extern declaration tells Rust how a foreign function is expected to behave at that boundary. It is a claim made by the programmer. A wrong declaration can compile and still cause undefined behavior when called.

For pointer-based APIs, the contract must include validity, alignment, length, initialization, aliasing, ownership and duration. Does the function retain a pointer after returning? Who frees it, with which allocator? May it call back on another thread? Can it unwind? A null check does not answer those questions. Start with an established binding crate and vendor documentation when possible rather than writing broad declarations by guesswork.

Prediction: an innocent absolute value

The C function abs accepts a signed int. What happens for the most negative int, whose positive magnitude does not fit in the same signed type? Would wrapping its call inside a safe Rust function automatically make every input safe?

Prediction explained

A safe wrapper must prevent inputs that violate the foreign contract. C signed abs of the unrepresentable minimum has undefined behavior. The wrapper explicitly returns None before making that call. Calling a foreign function from safe-looking syntax does not repair an invalid precondition.

Run the narrow wrapper test

Working directory projects/: mise exec -- cargo test -p rust-specializations ffi_boundary. The course verifies this host ABI example on the recorded macOS target. Porting it requires checking that the C library exposes the declared symbol and compatible int representation on the new target.

The source's unsafe extern "C" block declares abs. c_int expresses the platform C int type. The wrapper rejects its minimum, then documents the proof immediately above the unsafe call. The safe baseline is Rust's checked_abs(). Ordinary Rust code should use that baseline; the foreign call exists only to teach a boundary that actual C integrations need.

Deliberate mistake: a wrapper without its guard

Do not run an unchecked minimum-input call as an ordinary demonstration. Undefined behavior is not an expected panic or a useful stable output. Instead, review a learner diff that removes the guard and identify the violated precondition. The safe test suite compares all supported representative inputs to the standard-library baseline and verifies the excluded case returns None. Tests exercise selected inputs; the written contract covers the entire intended input set.

Guided checkpoint: write the contract before the extern

In a learner branch, write a comment containing symbol name, ABI, input validity, output relation and failure representation. Implement the safe baseline first. Add the foreign declaration, guard and unsafe call only after the contract is clear. Keep the unsafe block as small as possible. Test zero, positive, negative, maximum and minimum inputs. Explain why each is chosen.

For a hypothetical buffer API, stop before implementation and write who owns the allocation and whether the foreign code keeps the pointer. Returning a Rust slice requires the referent to remain valid for the promised lifetime; an extern signature cannot supply that proof. Do not let a panic cross a boundary whose ABI does not permit unwinding. A maintained library may already encapsulate this complexity more reliably than a new wrapper.

What no_std does and does not mean

#![no_std] asks a crate to depend on core instead of automatically using the full standard library. Core provides fundamental types and algorithms that do not require operating-system services. An optional alloc crate can provide allocation-backed structures when a suitable allocator exists. no_std does not mean no heap, no panic, no unsafe or automatically suitable for every microcontroller.

A library is not a complete embedded executable. The executable needs a target, startup code, memory layout, panic behavior, often an interrupt model, and hardware-specific support. Peripheral access may involve volatile operations and device rules that ordinary RAM reasoning does not capture. Those target-specific requirements are outside this portable host lab.

exercises/specializations/no-std/src/lib.rs
#![no_std]
//! No allocator, OS, threads or I/O: a small portable data transform.
//! A library does not supply a panic handler; the final executable chooses one.
pub fn clamp_sample(value: u16, ceiling: u16) -> u16 { if value > ceiling { ceiling } else { value } }
#[cfg(test)]mod tests{#[test]fn limits(){assert_eq!(super::clamp_sample(1024,255),255);assert_eq!(super::clamp_sample(7,255),7);}}

Run mise exec -- cargo test --manifest-path exercises/specializations/no-std/Cargo.toml from the course root. This checks the pure transform using a host test harness. It does not flash hardware or verify timing, interrupts, power behavior or an embedded linker script.

Independent practice with hints

Extend the no_std transform with a checked calibration offset. Decide whether saturation or an error is correct for the stated sensor requirement. Then review a fictional C API that returns an owned buffer and requires a matching free function. Draw ownership from allocation to Drop before writing code.

Hint 1

“Never exceeds the display's range” and “must report an invalid measurement” are different contracts. Both saturation and errors can be appropriate under different requirements.

Hint 2

Model a foreign allocation with an owning wrapper whose Drop calls exactly the documented deallocator. Borrowed views cannot outlive that wrapper. A retained callback needs a separate lifetime and thread contract.

Reference approach

For an error-reporting sensor, checked addition returns Option or a domain Result and leaves invalid measurements distinguishable from maximum valid ones. For a display-only bounded gauge, saturation may be the correct visible policy. The C buffer wrapper needs length and pointer validity checks plus one owner; use a maintained crate if available. The ownership diagram is a design exercise, not a verified generic wrapper supplied by this course.

Engineering decisions and evidence

The executable FFI example has no pointer or allocator contract and excludes one invalid integer. That is a deliberately small proof obligation. The no_std example has no dependencies and no allocation because its operation needs neither. Actual host tests and compiler checks are recorded separately. Miri generally cannot execute arbitrary native foreign functions; its successful checks on the separate unsafe Rust buffer do not validate this C library. A real embedded target or pointer API justifies a new target-specific verification plan.

Playbook investigation: “no_std means this is a firmware image”

Observation: a library checks successfully but cannot be flashed as an application. Hypothesis A: the arithmetic transform is wrong. Hypothesis B: there is no executable entry point, linker layout or hardware target. Inspect Cargo's target kind and produced artifact before editing the function. If it is a library archive with no startup contract, A does not explain the missing image. The next sound step is to select documented board support and a minimal executable, not add random unsafe operations.

When you get stuck

Boundary report

Record target triple, compiler, C header/library version, ABI declaration, ownership diagram and the smallest linking command. For hardware, add board and linker information. Seek domain review when pointer, interrupt or allocator contracts are unclear; repeated host tests cannot substitute for missing expertise.

Mastery check

Explain every unsafe precondition in the wrapper and why the safe baseline is preferred in ordinary code. Distinguish what the no_std host test establishes from what a real device needs. Reject a proposed wrapper that hides missing lifetime evidence behind an invented static reference.

Current stable FFI capabilities

Rust 1.99 supports defining C and C-unwind variadic functions, in addition to calling foreign variadic functions. This does not validate the argument count, promoted argument types, ABI, or ownership contract for you. Prefer fixed signatures for new interfaces where possible. The course retains a fixed-signature host example so its safety argument stays small. Rust 1.99.1 also corrects an x86_64 FFI bool-return regression; compiler patch versions can affect ABI correctness without adding language syntax.
