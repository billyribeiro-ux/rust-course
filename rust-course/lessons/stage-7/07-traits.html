Purpose: express the needed relationship

An abstraction earns its place by making an important relationship explicit. A source produces one kind of item; a callback can borrow different inputs; a fixed-size packet has a length known to its type. These are useful constraints. They are not reasons to turn every function into a generic framework. This specialization is for library and systems boundaries that genuinely need these relationships.

Plain model: a contract has several dimensions

A trait's associated type lets an implementation choose an output type once. Our Source trait associates an Item with each source. A Countdown implements it with u8. A trait generic parameter instead permits different implementations for different parameter choices where coherence allows them. Choose the representation that reflects who makes the choice.

A dyn Source<Item = u8> is a trait object: the caller knows the interface and item type, while the concrete implementation is selected at runtime. Dynamic dispatch uses an indirect method call through implementation metadata. A generic function can use static dispatch and compiler specialization for concrete types. The performance difference depends on inlining, code size, memory access and workload; do not claim one always wins.

Prediction: can any trait become dyn?

A trait has fn encode<T>(&self, value: T). Can a single runtime method entry stand for every possible T? Predict the diagnostic when compiling exercises/specializations/dyn.rs.

Prediction explained

This method has an unconstrained family of type-specialized implementations, so the trait is not dyn-compatible as written. The Reference calls this dyn compatibility, formerly object safety. A method restricted with where Self: Sized can be excluded from the object interface, or a concrete input type can make the needed operation dispatchable. The right fix depends on what callers need.

Run and inspect the specialization lab

Working directory projects/:

mise exec -- cargo run -p rust-specializations --example dispatch
mise exec -- cargo test -p rust-specializations

The example prints a derived type name, a countdown sequence and a borrowed first word. The sequence is [2, 1, 0] for an initial count of 3; it stops before unsigned underflow. The reference uses checked subtraction because reaching zero is normal completion, not a programmer failure.

projects/reference/p17-specializations/examples/dispatch.rs
use rust_specializations::{Countdown, KindName, Packet, drain, with_first};
fn main() {
    println!(
        "{} {:?} {}",
        Packet::<u8, 4>::kind_name(),
        drain(&mut Countdown(3)),
        with_first("alpha beta", |s| s.split_whitespace().next().unwrap_or(""))
    );
}

Follow the type relationships

with_first accepts a callback bounded by for<'b> Fn(&'b str) -> &'b str. The for quantifies the lifetime: the callback must work for every input borrow lifetime rather than requiring one specific captured lifetime. It returns a slice tied to the input it receives. This is useful when a library repeatedly lends different temporary inputs to user code. It does not extend any input's lifetime.

Packet<T, const N: usize> stores an array whose size is part of the type. Packet<u8, 4> and Packet<u8, 8> are different types. This can express wire-size or hardware constraints, but it can also generate many instantiations and complicate APIs. A slice is often the appropriate choice for runtime-variable inputs. N = 0 is a valid case unless the contract explicitly excludes it; test it.

Pattern ergonomics infer borrowing in patterns matched against references. For example, matching a borrowed Option can bind a borrowed inner value without moving it. Edition 2024 tightens which explicit binding modifiers are allowed when the default binding mode has already become a reference. When confused, write the scrutinee's type and the binding's type. A pattern changes how you access the value; it does not create ownership from nowhere.

Intentional failure: implementing someone else's trait for someone else's type

Compile exercises/specializations/orphan.rs with rustc from the course root. It attempts to implement standard Display for standard Vec. The expected E0117 illustrates the orphan rules. Those rules help make trait resolution coherent across independently authored crates. A local newtype wrapper gives your crate a type whose formatting contract it owns.

mise exec -- rustc --edition 2024 exercises/specializations/orphan.rs

This file is intentionally rejected and listed in the expected-error manifest. It is never part of a successful project build. The supported correction is a local wrapper plus a Display implementation, not weakening compiler checks.

Guided checkpoint

Read the Source trait and Countdown implementation, then call drain through the trait object. Next change the caller to a generic function over S: Source<Item = u8> in your learner branch. Keep behavior tests identical. Explain which choice moves type selection to compile time and which supports a heterogeneous collection of implementations. Do not add a benchmark unless performance is an actual decision criterion.

Independent practice and hints

Implement a bounded slice source yielding borrowed items. Choose whether its Item is a reference and explain the lifetime. Wrap a Vec of bytes in a local type that prints its length without exposing contents. Add a zero-capacity Packet test.

Hint 1

The source struct can hold a slice and current index. Ownership of the backing allocation stays with the caller.

Hint 2

Use get and return Option at exhaustion. A reference item can carry the lifetime parameter from the source struct.

Reference direction

A source borrowing &'a [T] can yield &'a T by incrementing an index after a successful get. A local Bytes wrapper implements Display with a length-only message. These avoid cloning the payload and avoid a trait implementation that violates coherence. If the API must mutate or lend each item for a shorter borrow, a generic associated type may be the next requirement; do not introduce it before that need exists.

Engineering decisions and evidence

The lab isolates three real type relationships in one small crate and uses the standard library for its runtime behavior. Its tests check exhaustion, borrowed output, generic derive parameters and zero-sized arrays. Static and dynamic dispatch are alternatives with different extensibility and code-generation tradeoffs, not a hierarchy of professionalism. The verification log records actual checks; it contains no unmeasured dispatch speed claim. A new requirement for heterogeneous plugins would justify retaining dynamic dispatch; a tiny hot loop might justify a measured generic variant.

Playbook investigation: “the lifetime annotation owns the text”

Observed: returning a slice from a locally created String fails even after adding a named lifetime. Hypothesis A: the annotation forces the String to live longer. Hypothesis B: it only describes a borrowing relationship. Replace the local String with an input reference carrying that lifetime. If the input-based version compiles and the local version does not, A is disproved. The sound alternatives are returning owned data or borrowing from an owner that actually outlives the return value.

When you get stuck

Write the missing contract

Reduce to one trait method and one call. Annotate the concrete type, associated type and reference lifetime separately. Run mise exec -- rustc --explain E0038 for dyn compatibility or E0117 for coherence, then compare with the pinned compiler's Reference.

Mastery check

Explain why one proposed abstraction is unnecessary for a calculator but useful for a plugin boundary. Modify the lab and diagnose both expected failures without copying the reference. Show a hypothesis you revised and distinguish compilation evidence from API usability evidence.
