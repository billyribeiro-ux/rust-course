Measure a claim before optimizing

Use a repeatable release-profile experiment and correctness oracle to evaluate performance changes.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • Rendering, security and alternative clients
  • A bounded local health monitor
  • Define the measured workload and timing boundary
  • Separate compiler profile, workload shape and algorithm effects
  • Collect multiple local measurements without inventing guarantees
  • Reject optimizations that change semantics or weaken validation

Key terms: allocation · cancellation · capacity · compaction · mise · replay

Keep the problem-solving playbook open. Record observations before explanations, and save the experiment that changed your mind.

Purpose: turn “faster” into a testable statement

Performance work begins with a question whose conditions are explicit. “The replay is fast” has no workload, machine, profile or correctness requirement. A useful claim might say that one implementation processes a fixed synthetic stream with identical resulting state in less elapsed time under a recorded release build. P12 provides a small benchmark executable so you can practice constructing that evidence. It reports measurements from your machine when you run it. This course does not supply invented throughput numbers or suggest that a toy stream predicts production market-system performance.

Model: measured time includes a chosen boundary

The benchmark compares immediate streaming with a reusable buffer holding at most 1024 events. Both timed regions include synthetic generation and complete replay, including creation of a fresh Replay and any batch allocation. The timer stops when the selected variant returns. Full-state comparison, digest calculation, output and final state destruction happen afterward. One untimed reference run supplies the expected state. Each variant receives two warm-ups and seven measured trials, with first/second order alternating within each pair rather than randomized. The executable prints raw TSV sample rows; the recorded measurement report computes minimum, median and maximum from those observations. If you change this boundary, label the new measurement rather than treating it as equivalent work.

Predict what will change

Before running, predict why the comparison requires a release build, what a tiny versus large event count changes, and how two live orders differ from thousands of live orders. Explain why the last comparison could change allocation and tree-lookup behavior even when total event count stays constant. Predict that the digest should remain stable for the same count and generator rule; do not predict a particular elapsed time. Background activity, CPU power state, thermal behavior and filesystem cache effects can affect observations. Repetition helps reveal variation but does not eliminate all confounding factors.

Read the harness before trusting its output

projects/reference/p12-replay/src/bin/benchmark.rs
//! Compare immediate event application with a bounded, reusable event batch.
//! Both timed regions include synthetic generation and complete replay work.
use p12_replay::{Event, Replay};
use std::{hint::black_box, io, time::Instant};
const BATCH_EVENTS: usize = 1024;
const SAMPLES: usize = 7;
const WARMUPS_PER_VARIANT: usize = 2;
fn batched(count: usize) -> Result<Replay, p12_replay::Error> {
    let mut source = p12_replay::synthetic(count)?;
    let mut replay = Replay::new(4096)?;
    let mut batch: Vec<Event> = Vec::with_capacity(BATCH_EVENTS);
    loop {
        // The iterator is lazy; no more than BATCH_EVENTS events are retained.
        batch.extend(source.by_ref().take(BATCH_EVENTS));
        if batch.is_empty() {
            return Ok(replay);
        }
        for event in batch.drain(..) {
            replay.apply(event)?;
        }
        // drain preserves allocation capacity for the next bounded batch.
    }
}
fn run_variant(name: &str, count: usize) -> Result<Replay, p12_replay::Error> {
    match name {
        "stream" => p12_replay::run(count),
        "batch1024" => batched(count),
        _ => unreachable!("variant names come from the fixed internal pair"),
    }
}
fn require_same(actual: &Replay, expected: &Replay) -> io::Result<()> {
    if actual != expected {
        return Err(io::Error::other("complete replay states differ"));
    }
    Ok(())
}
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let arguments: Vec<_> = std::env::args_os().skip(1).collect();
    let count = match arguments.as_slice() {
        [] => 1_000_003,
        [text] => text
            .to_str()
            .ok_or("count must be UTF-8 integer text")?
            .parse::<usize>()?,
        _ => return Err("usage: benchmark [event_count 1..=10000000]".into()),
    };
    if !(1..=10_000_000).contains(&count) {
        return Err("benchmark count must be in 1..=10000000".into());
    }
    if cfg!(debug_assertions) {
        return Err("comparative measurement requires cargo run --release".into());
    }
    let expected = black_box(p12_replay::run(count)?);
    for warmup in 0..WARMUPS_PER_VARIANT {
        let order = if warmup % 2 == 0 {
            ["stream", "batch1024"]
        } else {
            ["batch1024", "stream"]
        };
        for variant in order {
            require_same(
                &black_box(run_variant(variant, black_box(count))?),
                &expected,
            )?;
        }
    }
    println!(
        "benchmark=replay profile=release events={count} samples_per_variant={SAMPLES} warmups_per_variant={WARMUPS_PER_VARIANT} untimed_reference_runs=1 batch_limit={BATCH_EVENTS}"
    );
    println!(
        "timed=generation_and_replay excluded=state_comparison_output includes_batch_allocation=true live_orders_peak=2"
    );
    println!(
        "sample\tposition\tvariant\telapsed_ns\taccepted\topen_orders\tdigest\tfull_state_equal"
    );
    for sample in 0..SAMPLES {
        let order = if sample % 2 == 0 {
            ["stream", "batch1024"]
        } else {
            ["batch1024", "stream"]
        };
        for (position, variant) in order.into_iter().enumerate() {
            let start = Instant::now();
            let state = black_box(run_variant(variant, black_box(count))?);
            let elapsed = start.elapsed().as_nanos();
            require_same(&state, &expected)?;
            println!(
                "{}\t{}\t{variant}\t{elapsed}\t{}\t{}\t{:016x}\ttrue",
                sample + 1,
                position + 1,
                state.accepted(),
                state.orders().len(),
                state.digest()
            );
        }
    }
    println!(
        "limit=local_observation_only no_disk_input=true randomization=false order=alternating_pairs"
    );
    Ok(())
}
#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn batch_boundaries_preserve_complete_state() {
        for count in [0, 1, 2, 3, 4, 1023, 1024, 1025, 2049, 10_003] {
            assert_eq!(
                batched(count).unwrap(),
                p12_replay::run(count).unwrap(),
                "count={count}"
            );
        }
    }
}

Argument parsing accepts an event count from one through ten million. The harness rejects a debug build so a profile mismatch cannot silently become comparative evidence. black_box discourages optimization based on visible inputs and outputs, but remains a best-effort barrier. require_same compares every completed Replay with the untimed reference, including orders, sequence, capacity and accounting. The printed digest is a convenient diagnostic, not the correctness gate. The batch-boundary regression also compares complete states at counts around 1024. These comparisons detect semantic divergence for the exercised inputs; they do not establish every possible workload or failure behavior.

Inspect the workload's hidden assumptions

The synthetic generator repeats two placements followed by their cancellations. Its live map never exceeds two orders. That is excellent for a bounded demonstration and poor evidence for lookup behavior in a large active book. Price values vary by a deterministic rule, and no network, exchange matching, latency distribution or real data feed is modeled. The benchmark includes allocation for inserted map entries, but its state-size distribution is unusually small. Record these facts beside each result. A performance conclusion should name this workload, not quietly generalize to all replay systems.

Intentional failure: make a misleading comparison

Run the comparative executable once without --release and predict its refusal before execution. That failure enforces the harness contract; it is not a Rust installation defect. Now review a fictional report comparing an old debug measurement with a new release measurement. The attribution is invalid because implementation and profile changed together. Repeat both real variants under one release profile and input count. Separately consider a “faster” implementation that skips duplicate-ID checks: run the rejection tests before interpreting its timing. Correctness is a constraint of the experiment, not a separate nice-to-have after optimization.

Playbook investigation: a claimed twofold improvement

You receive only a screenshot of one throughput figure and a patch replacing BTreeMap with another representation. Observations are incomplete: the screenshot does not establish event count, compiler version, profile, active-state size or whether validation still runs. Form at least three competing hypotheses. One may attribute improvement to the data structure, another to a release-profile change, and another to a smaller workload. Design a paired experiment that can disprove your favored explanation. For example, keep the old implementation but use the screenshot's build profile; if it improves similarly, the patch is not sufficient evidence for the claimed cause.

Choose the next investigation step independently. You might capture exact commands, inspect generated input counts, or compare complete resulting states. Do not begin by rewriting the program again. A defensible report includes raw observations, controls, at least one disproved hypothesis, and remaining uncertainty. A fix can be “correct the benchmark procedure and withdraw the unsupported claim.” Engineering progress does not always require a source-code change.

Guided checkpoint and independent practice

Write a measurement plan before execution: question, fixed inputs, build profile, timing boundary, correctness oracle, number of trials and environmental observations. Then add a second deterministic generator whose live set grows to a chosen bounded size before cancellations. Keep the original generator as a baseline. Independently evaluate one change such as reducing repeated lookups or adjusting representation. Preserve failure semantics, including unchanged state after rejection. Decide what variation would be too large to justify your conclusion and what additional experiment would resolve it.

Worked solution

A sound investigation first proves semantic equality on small adversarial streams, then repeats equivalent large workloads under one recorded profile. Retain rejected experiments in the log with the reason they were invalid. Do not select only the fastest trial as representative of normal behavior.

When you get stuck

Run the correctness tests, capture mise exec -- rustc -Vv, and read the benchmark's start and stop lines. Inspect std::hint::black_box's stated limitations. Ask for review with both commands, all reported samples, workload rule, digest and complete-state comparisons. “It feels slower” should become a reproducible observation before anyone proposes a low-level optimization.

Review, evidence and mastery

Submit the measurement plan, local output, a paired comparison and a limits paragraph. Mastery means making a causal claim no stronger than the experiment supports. You should be able to reject misleading evidence, preserve correctness while changing performance, and explain why a local median is useful without presenting it as a service-level guarantee or a prediction for an unrelated workload.

Engineering decisions and evidence

Current scope and invariants. The next sequence is exact, live order count is capped, fixed-point prices are validated, and rejected events preserve the entire replay state. All fallible accounting is checked before a placement is committed.

Why this is the current recommended shape. Newtypes separate event and order IDs; a private Price representation prevents invalid ticks entering through safe constructors. Replay accounting stays private behind read-only getters, so callers cannot bypass transition validation by assigning metrics. Integer arithmetic expresses the chosen scale exactly. A BTreeMap gives stable iteration, generators stream events, and full-state comparisons accompany digest checks.

Reasonable alternative and tradeoff. A hash map can offer different lookup costs, but deterministic output would need a separate ordering step and measurement on a representative workload. A mature decimal type is appropriate when varying scales or richer decimal operations become requirements. Neither abstraction is needed to express this fixed four-place bounded exercise clearly.

Evidence and limits. Native reference tests were run through mise in the coordinated course verification; inspect the current verification record for exact results. Exact decimal grammar and limits; full-state deterministic replay; duplicate and sequence rejection; capacity and absent cancellation; injected accounting overflow; bounded generated live state. The supplied generator keeps only two live orders. A digest can collide and omits internal details; it is not an equivalence proof. Local benchmark samples include generation and exclude final digest/destruction. No universal timing claims are made.

Requirement that would justify evolution. Revisit representation and benchmark workload when active-state size, persistence, out-of-order arrival or domain rules expand. This is a state-transition exercise, not a matching engine. Add an amendment only after specifying its accounting and identity semantics.

In your review, explain this choice in your own words, preserve the behavioral contract during changes, and name the evidence that would make you choose the alternative. Deliberately broken variants above are diagnostic exercises, never recommended implementation stages.
