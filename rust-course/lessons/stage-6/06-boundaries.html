Purpose: preserve the contract across clients

The backend should serve both the Rust dashboard and another client without moving its invariants into the browser. A new UI may change presentation and interaction, but it should not change what a valid order means. This lesson reviews boundaries and prepares you to evaluate frameworks without rebuilding the whole course.

Plain model: the browser is an untrusted participant

WebAssembly is executable code in a browser sandbox. It is not an encrypted vault for source, secrets or authorization rules. A user can inspect requests and bypass form validation. The server must authenticate an identity, authorize the action, validate input and apply domain transitions. The local demo tokens are public fixtures, chosen to test the read/write boundary. A deployed application should use a maintained identity system and established session or OAuth/OIDC mechanisms; designing one from a tutorial token is outside this lab's contract.

Cookies are automatically attached under browser rules and therefore require attention to SameSite, Secure, HttpOnly and cross-site request forgery. Bearer tokens grant access to their holder and can leak through unsafe storage or logs. TLS protects data in transit to an authenticated endpoint; it does not make a malicious client honest. The local course uses loopback HTTP for isolated fixtures. That is not a prescription for deployment.

Predict the rendering behavior

You disable JavaScript. Which remains readable: this static HTML course, the Leptos CSR dashboard, or server-rendered HTML? What part does hydration add?

Prediction explained

The course's authored HTML remains readable and its native details disclosures work. The CSR dashboard cannot construct its interactive DOM and shows a noscript explanation. Server-rendered HTML can provide initial content before JavaScript, while hydration adds interactive behavior. SSR alone does not guarantee that every form or control works without scripts; progressive enhancement must be intentionally implemented.

Runnable boundary experiments

Keep the console and backend running from the previous lesson. In the browser, temporarily disable JavaScript and reload both course and console. Then use the terminal to send a write request with Bearer demo-reader. The project’s boundary tests require it to be denied. Working directory projects/: mise exec -- cargo test -p p16-workbench. Read the authorization test and the handler it exercises.

Inspect a quote response without the UI. JSON is a serialization format: bytes describing strings, numbers, arrays and objects. It does not carry Rust's ownership information, and numbers can be interpreted differently by another language. The API uses integer cents and documented bounds; JavaScript's number type cannot exactly represent every i64 or u64. The pinned Rust client avoids a JavaScript number conversion when decoding: gloo-net 0.7.0 reads response text and passes that text to Rust serde_json. This preserves the Rust integer range or rejects an out-of-range value. We inspected that dependency's actual Response::json implementation; compilation alone would not establish this boundary. A JavaScript client that first calls JSON.parse can already lose precision before validation. The optional Svelte bridge therefore uses its documented lossless parser. Another valid wire-contract choice is validated decimal strings for large integers. Default small fixtures do not establish correctness at the representation limits.

Deliberate mistake: hiding a forbidden button

Hide the buy button when a client-side role says reader, but leave the server write handler unchecked. A direct request bypasses the visual restriction. The sound fix is server-side authorization, with the hidden or disabled button as a usability feature. Test both the visible role state and direct unauthorized HTTP request. One does not substitute for the other.

Guided project review

Trace a submitted order from its label and numeric input through serialization, proxy forwarding, actor selection, validation, domain transition, persistence and displayed snapshot. At each step name the owner, the maximum size and the error response. Record a table of which layer enforces each invariant. If the same invariant is validated twice, explain whether the client check is feedback and the server check is authority.

Independent client exercise

Design a second client that only reads snapshots and filters quotes. Keep the same HTTP schema. Describe how it presents loading, stale, empty and error states. Do not copy the reference UI's signals by name; write its state model first.

Hint 1

Framework state syntax changes; request identity, schema parsing and failure meanings do not.

Hint 2

Separate the transport function from the component. Test decoding with a fixture and an invalid response independently from click behavior.

Reference approach and optional Svelte 5 bridge

A second client should preserve the server’s identity, integer, resource and error contracts. The runnable Svelte 5 bridge connects to the same read-only snapshot API with exact integer decoding, bounded cancellable requests, a same-origin development proxy and tests. Follow its worked boundary investigation and independent watched-symbol exercise. Node and Svelte remain outside the Rust prerequisites; Leptos remains the main course framework.

The bridge pins Svelte 5.57.2 and Vite 8.3.4, with verified compatible tooling. It does not use SvelteKit. The shared backend needs no framework-specific domain changes.

Review: CSR versus hydration

CSR keeps the initial build path conceptually simple and works well for a local authenticated-style dashboard. Initial useful content waits for code download and execution. SSR provides an initial document and can improve first-content behavior, but introduces a server rendering path. Hydration must reconcile that document with client state, and both builds need compatible configuration. Decide based on the user's latency, accessibility and deployment needs rather than declaring one mode universally faster.

Playbook investigation: stale data looks current

Observation: the chart stops changing but the page still says Connected. Hypothesis A: the synthetic feed is stationary. Hypothesis B: polling failed but a previous status was retained. Inspect the latest successful request time and error path, then stop the backend intentionally. If the status still says Connected, A is disproved as a sufficient explanation. Keep last-success time and connection state distinct; a healthy transport can also carry old business data.

When you get stuck

Next experiment

Write two clocks: when the browser received the response and what sequence the server says it represents. Compare them during a stopped feed and a stopped server. Ask a reviewer to challenge the claimed freshness, not merely the CSS.

Evidence and mastery

Authorization tests support the implemented fixture boundary. They do not establish production identity security. A browser inspection supports observed keyboard and state behavior, not every screen reader. Independently review one UI state bug, one unauthorized request and one schema mismatch; explain the first failing boundary and one hypothesis you rejected.

Engineering decisions and evidence

The current interface contract is a local, simulated service client: semantic controls, explicit loading/error/empty states, bounded sequential polling and server-authoritative mutations. Leptos 0.8.22 is used because reactive Rust state is a learning objective; the course shell itself remains static HTML. Integer-cents formatting avoids floating-point price conversion, UUID identifiers use a maintained implementation, and ambiguous writes are not automatically retried. The WASM compiler check verifies the target-specific APIs; runtime browser behavior remains pending because the saved localhost permission setting blocks the browser tool. The reference source is embedded directly and hashed by the course renderer.

An SSR client would be a reasonable alternative if initial content without WASM became a requirement. A push stream would require measured polling costs plus a bounded reconnect and slow-consumer contract. These are requirement changes, not corrections to an intentionally poor first design. Your checkpoint must include a named state transition, a failure case and the evidence that distinguishes it from a plausible alternative cause.

Primary implementation reference: gloo-net 0.7.0 Response::json source. The installed pinned crate source was inspected on October 9, 2026. Compare the decode boundary with the native money_is_exact_integer_formatting_including_minimum test: exact display formatting and lossless transport are separate claims.
