Stage 06 / Rust in the browser

Reactive state has owners and lifetimes

Use Leptos signals to connect owned state to browser output.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

Prerequisites and learning objectives
  • The browser is a separate computer
  • Explain Leptos signals, event closures and reactive reads
  • Distinguish CSR, SSR and hydration
  • Bound UI tasks and avoid stale updates

Key terms: atomic · borrow · cancellation · closure · crate · DOM · enum · hydration

Keep the problem-solving playbook open. Record observations before explanations, and save the experiment that changed your mind.

Reconstruct this project’s runnable checkpoints. Each milestone states its own scope; learner scaffolds are separate assignments.

Purpose: keep the screen consistent with state

When a connection fails, the same state may affect a message, a button and a quote table. Manually updating unrelated DOM nodes can leave contradictory displays. A reactive model derives the visible document from explicit state and updates dependent parts when that state changes. It does not remove the need to design the states.

Choose one stable framework

The main Rust UI path uses Leptos 0.8.22 with its csr feature, compiled to WebAssembly. Its official documentation lists Rust 1.88 as the crate's minimum version; the course compiles with 1.99 and does not infer support for every feature combination on 1.88. A 0.9 prerelease existed during verification, but the course selects the stable series. Leptos lets the same Rust concepts of functions, closures and owned data appear in a UI while teaching a distinct reactive ownership model.

Client-side rendering (CSR) builds DOM nodes in the browser after the code loads. Server-side rendering (SSR) produces HTML on the server. Hydration attaches interactive behavior to server-produced HTML. Hydration requires server and client expectations to agree; inconsistent initial data or invalid HTML can break that agreement. This project's CSR mode avoids that extra boundary while learning signals. Its cost is that the interactive dashboard needs JavaScript and WASM before it appears.

Predict a reactive read

Consider a signal named filter. One view expression calls filter.get() immediately; another is a closure, move || filter.get(). Which expression can be re-run in a tracked reactive context when the signal changes?

Prediction explained

The closure provides computation that the framework can invoke while tracking reads. An eager call computes an ordinary value at that moment. A signal is not magic syntax that makes every prior string update. Learn where the framework establishes tracking rather than replacing every expression with a closure mechanically.

Runnable checkpoint: compile the real client

Working directory: the course folder. The browser target is additional standard-library support for the same compiler, not a different Rust language. Use mise to select the compiler first:

mise exec -- rustup target add wasm32-unknown-unknown
mise exec -- cargo check --locked --manifest-path projects/ui-console/Cargo.toml --target wasm32-unknown-unknown

The full source is ui-console/src/lib.rs. Locate the signal declarations in App, then the closures in the quote filter and pause button. This is real Rust checked against the browser target; a native build alone would not verify the WASM boundary.

Explain the state model

signal(value) creates a read handle and a write handle. The handles refer to state owned by a reactive owner; they are not independent clones of the value. get() reads and clones this owned value when used for our small snapshots. get_untracked() reads without subscribing the current effect or computation. It is appropriate in a polling loop whose lifetime is separately controlled, not as a universal cure for reactive loops.

The move keyword transfers captured handles into a closure. It does not force every captured payload to be deeply copied. set replaces a value; update modifies it through a short mutable callback. Keep synchronous work in those callbacks small and never hold a borrow across an asynchronous request. An asynchronous task lives beyond the event handler's stack frame; everything it uses must remain valid until completion or cancellation.

Reactive ownership and Rust borrowing complement each other. The compiler can check ownership of the handle, but a framework-owned slot can still be disposed when its component is removed. The client uses an independently owned cancellation flag, checked after awaited requests, to avoid updating disposed reactive slots. Requests have deadlines, so cleanup does not leave indefinitely waiting work. Relaxed atomic ordering is sufficient for this one flag because it does not publish other shared data. Do not infer lifecycle safety merely from a passing native unit test.

Deliberate mistake: freezing a derived label

In a learner copy, calculate a formatted pause label once before the view and render that fixed String. Press Pause. If the button label stays unchanged, the backend and network are not involved. Move the derivation into a tracked closure. Avoid keeping both a boolean and an independently mutated duplicate label unless they describe truly different state.

Guided step: derive a filtered list

Start from snapshot as optional data and filter as user text. In the view closure, obtain the current snapshot, select quotes whose symbols match the normalized filter, and render rows. Keep normalization separate from the remote quote contract. A missing snapshot is loading or disconnected, not an empty market. An empty quote vector after a successful response is a real empty state.

Independent decisions, with tiered hints

Add a clear-filter button. Then display the number of visible rows. Decide whether the count is derived or stored. Finally, keep stale quotes visible during a temporary connection failure and label them as stale.

Hint 1

Ask how many independent facts exist. If a value can be calculated from the snapshot and filter, storing it creates another synchronization obligation.

Hint 2

A failed poll should update error/connection state without necessarily replacing the last successful snapshot with an empty one.

Reference approach

Derive visible rows and their count from the same predicate. The clear button sets the filter to an empty String. Retain the previous snapshot on a failed poll and show an explicit disconnected message. Add a last-success observation timestamp for display only; do not use browser time to order market events. Test disconnect/reconnect while a filter is active.

Playbook investigation: a filter appears to lose data

Observed: zero rows appear after typing “rust,” but the API response contains “RUST.” Hypothesis A: the server discarded the quote. Hypothesis B: the client compares case-sensitive strings. Read the Network response, then try the same letters in uppercase without another mutation. If the quote reappears, A is disproved. The smallest fix normalizes the search predicate consistently. Do not change server identifiers to satisfy a presentation-only filter.

When you get stuck

Trace one dependency

Write which signal should change and which closure reads it. Inspect the event handler first, then the derived view. Run the WASM check and read the first diagnostic before adding clones or extra effects.

Ask for a focused review

Provide the signal creation, one event handler and one rendered expression. Ask whether the read is tracked and whether its owner still exists, not simply “why is Leptos broken?”

Review, evidence and mastery

An explicit finite set of loading, loaded, empty, stale and error states is clearer than several unrelated booleans that permit contradictions. The demo still uses separate signals where the relationship is simple; an enum is a worthwhile independent refactor. Compilation supports API and type compatibility. Browser tests must establish that events update the DOM. Explain which work happens in Rust, generated JavaScript and the browser, then debug a frozen derived value without revealing the reference.

Engineering decisions and evidence

The current interface contract is a local, simulated service client: semantic controls, explicit loading/error/empty states, bounded sequential polling and server-authoritative mutations. Leptos 0.8.22 is used because reactive Rust state is a learning objective; the course shell itself remains static HTML. Integer-cents formatting avoids floating-point price conversion, UUID identifiers use a maintained implementation, and ambiguous writes are not automatically retried. The WASM compiler check verifies the target-specific APIs; runtime browser behavior remains pending because the saved localhost permission setting blocks the browser tool. The reference source is embedded directly and hashed by the course renderer.

An SSR client would be a reasonable alternative if initial content without WASM became a requirement. A push stream would require measured polling costs plus a bounded reconnect and slow-consumer contract. These are requirement changes, not corrections to an intentionally poor first design. Your checkpoint must include a named state transition, a failure case and the evidence that distinguishes it from a plausible alternative cause.
