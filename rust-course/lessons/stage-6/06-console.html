Connect the operations console to a real service

Compile WASM, proxy a same-origin API, and inspect loading, error and stale states.

Read with a terminal open. Predict before revealing. Verified source versions: version ledger.

  • Trace HTTP requests and response schema validation

Key terms: authentication · authorization · cancellation · capacity · crate · deadline · idempotency · invariant

Purpose: a complete request lifecycle

The operations console uses the same backend later examined in the capstone. You can learn its interface without yet understanding every trading invariant. The visible lesson is the lifecycle: user intent becomes a request, a server decision becomes a response, and the interface renders the result. At each step the client may know less than the server.

Plain model: four separate responsibilities

The Rust compiler produces WASM. The matching wasm-bindgen tool generates JavaScript glue that loads the module and exposes browser interoperation. A small loopback server serves these assets and forwards a fixed set of API paths to the local Axum process. The Axum process owns persistent state. The proxy is a learning convenience for one origin; it is not a general public reverse proxy.

An origin consists of scheme, host and port. Browser security rules distinguish 127.0.0.1:8011 from localhost:4116 even on the same computer. Serving the UI and forwarding its API under one origin avoids a CORS configuration detour. CORS is a browser access policy, not authentication and not protection against non-browser clients.

Prediction: a lost response

The backend commits a simulated buy, but the browser loses its response. Does the client know the order failed? Should it immediately create a new order ID and submit again?

Prediction explained

The outcome is unknown. A new ID can create a second independent purchase. A retry protocol needs a stable ID and a backend that recognizes that ID. This client's explicit error tells you to inspect the ledger before resubmitting. It does not silently claim failure or automatically retry mutations.

In a third terminal, send one synthetic tick:

curl -sS http://127.0.0.1:4116/api/ticks  -H 'Authorization: Bearer demo-operator'  -H 'Content-Type: application/json'  -d '{"event_id":"console-tick-1","symbol":"RUST","price_cents":12345,"sequence":1}'

The dashboard should show RUST at $123.45 after the next successful poll. Repeating the same event is a useful idempotency experiment; changing its contents under the same ID is a separate conflict case. These fixture identities are deliberately public local teaching identities, not a production login design.

// The browser has one polling loop, one request at a time, and a 3-second timeout.
// The local fixture identity is visible client code: it is NOT a secret or production auth.
async fn get_json<T: serde::de::DeserializeOwned>(path: &str) -> Result<T, String> {
    let controller = web_sys::AbortController::new().map_err(|_| "AbortController unavailable")?;
    let abort = controller.clone();
    let timer = gloo_timers::callback::Timeout::new(3_000, move || abort.abort());
    let response = gloo_net::http::Request::get(path)
        .header("Authorization", "Bearer demo-reader")
        .abort_signal(Some(&controller.signal()))
        .send()
        .await
        .map_err(|_| "Request failed or timed out. Check the local API.")?;
    if !response.ok() {
        return Err(format!("API returned HTTP {}", response.status()));
    }
    let result = response
        .json()
        .await
        .map_err(|_| "The response does not match the expected response schema.".into());
    drop(timer);
    result
}

// The timeout limits one request; no mutation is retried automatically.
async fn send_mutation(method: &str, path: &str, body: &serde_json::Value) -> Result<u16, String> {
    let controller = web_sys::AbortController::new()
        .map_err(|_| "Browser cancellation unavailable".to_string())?;
    let abort = controller.clone();
    let timer = gloo_timers::callback::Timeout::new(3000, move || abort.abort());
    let request = if method == "PUT" {
        gloo_net::http::Request::put(path)
    } else {
        gloo_net::http::Request::post(path)
    };
    let result = match request
        .header("Authorization", "Bearer demo-operator")
        .abort_signal(Some(&controller.signal()))
        .json(body)
    {
        Ok(r) => r
            .send()
            .await
            .map(|r| r.status())
            .map_err(|e| e.to_string()),
        Err(e) => Err(e.to_string()),
    };
    drop(timer);
    result
}
// One command request is admitted at a time; errors never trigger automatic mutation retries.
fn command(
    method: &'static str,
    path: String,
    body: serde_json::Value,
    status: WriteSignal<String>,
    pending: ReadSignal<bool>,
    set_pending: WriteSignal<bool>,
    alive: Arc<AtomicBool>,
) {
    if pending.get_untracked() {
        return;
    }
    set_pending.set(true);
    leptos::task::spawn_local(async move {
        if !alive.load(Ordering::Relaxed) {
            return;
        }
        let result = send_mutation(method, &path, &body).await;
        if !alive.load(Ordering::Relaxed) {
            return;
        }
        status.set(match result {Ok(200..=299)=>"Accepted. The next refresh confirms persistent state.".into(),Ok(code @ (408 | 409 | 500..=599))=>format!("Outcome unknown (HTTP {code}). Inspect durable state before retrying."),Ok(code)=>format!("Not accepted: HTTP {code}. Inspect validation and authorization."),Err(_)=>"Outcome unknown. Inspect jobs/watchlist before retrying; no automatic retry was sent.".into()});
        set_pending.set(false);
    });
}

Request::get creates a browser request. The Authorization header selects the local read-only fixture. send().await waits for browser I/O without blocking the main event loop. The AbortController limits how long a snapshot request may remain active. Parsing into a typed Snapshot checks the expected shape; it does not prove values satisfy every business invariant. Those are enforced by the backend.

The polling loop awaits snapshot, history and job requests sequentially, then a two-second interval. It does not create a new task every timer tick, so a slow response cannot accumulate an unbounded pile of snapshot requests. The history endpoint returns at most 60 recent event positions to this view, from a server history retaining at most 1,024 points. The LAB chart uses persistent event data rather than claiming each browser poll captured every tick. The text values provide an equivalent data view. The same page can queue a five-tick synthetic replay, inspect its persisted job cursor, request cancellation, edit a watchlist and inspect recent order IDs.

Deliberate mistake: inventing an empty success

Replace every fetch error with an empty default snapshot in a learner copy. Stop the API while the UI is open. The screen now looks like zero positions or zero cash rather than unavailable data. Restore a separate error path and retain clearly labeled stale data if useful. Default values can be dangerous when absence and zero have different meanings.

Worked design

A confirmed-update form keeps an editable comma-separated input, validates bounded normalized symbols, sends one PUT with a symbols array, and changes the displayed watchlist only after success or a fresh snapshot. On failure it keeps the input and shows the response category. An optimistic form can feel faster but needs a rollback/conflict model; use the simpler policy first.

When you get stuck

Inspect the first broken boundary

Check generated pkg assets, browser console, Network status, proxy output and backend health in that order of request flow. Include one response status and a redacted body in the review request. Do not paste bearer credentials from a real application.

Review, evidence and mastery

A background interval that spawns requests without joining them is easy to write and hard to bound. A sequential loop has an obvious one-request budget. It can update less frequently under latency; that is an explicit tradeoff. Independently demonstrate disconnect and reconnect, explain why an HTTP success is separate from a durable business decision, and diagnose a wrong port without changing domain code.

Engineering decisions and evidence

The current interface contract is a local, simulated service client: semantic controls, explicit loading/error/empty states, bounded sequential polling and server-authoritative mutations. Leptos 0.8.22 is used because reactive Rust state is a learning objective; the course shell itself remains static HTML. Integer-cents formatting avoids floating-point price conversion, UUID identifiers use a maintained implementation, and ambiguous writes are not automatically retried. The WASM compiler check verifies target-specific APIs. The October 9 live Chrome checks exercised loading, empty/error states, orders, retained identity after connection failure, reconnect, cancellation and narrow layouts. The October 17 build record separately verifies the updated locked dependency graph and generated bindings. These are dated, scoped observations; the earlier browser run is not a new runtime test of every updated dependency. The October 17 runtime follow-up loaded these updated bindings in Chrome and repeated offline recovery, replay, orders, watchlist/filter and exact-identity retry checks against a fresh synthetic backend. The reference source is embedded directly and hashed by the course renderer.

An SSR client would be a reasonable alternative if initial content without WASM became a requirement. A push stream would require measured polling costs plus a bounded reconnect and slow-consumer contract. These are requirement changes, not corrections to an intentionally poor first design. Your checkpoint must include a named state transition, a failure case and the evidence that distinguishes it from a plausible alternative cause.

Reconcile a write before making another

A timeout describes the client’s observation, not whether a durable order exists. The reference keeps a PendingOrder containing one UUID, symbol and quantity. An uncertain response keeps that value and disables edits to the instruction. Retry sends the identical payload; Check exact ledger entry calls GET /api/orders/{id} even when the fill has fallen out of the latest-100 snapshot. A matching durable fill releases the pending state. A missing entry does not prove an earlier request cannot still finish. HTTP 408, 409 and server errors remain uncertain until reconciled; no mutation retries happen automatically.

This client retains an unresolved instruction only while the page remains open. Record the displayed ID before leaving or reloading. A production workflow that must survive browser crashes needs durable client command storage and a recovery UI; that is an explicit further requirement, not an inferred guarantee. Replay-job commands show their uncertain outcome and must be inspected in the durable job list before another job is created.

The native course-ui-model crate extracts transport schemas and pure decisions from the browser runtime. Its tests decode empty history with null cursors, distinguish uncertain HTTP outcomes and reject a sequence range that would overflow. These checks do not exercise clicking, focus or a browser’s network cancellation implementation.

pub fn write_outcome(status: Option<u16>, earlier_uncertain: bool) -> WriteOutcome {
    match status {
        Some(200..=299) => WriteOutcome::Accepted,
        Some(408 | 409 | 500..=599) | None => WriteOutcome::Unknown,

/// Five LAB ticks require five consecutive representable sequence numbers.
pub fn replay_ticks(job: &str, previous: u64) -> Result<Vec<serde_json::Value>, &'static str> {
    previous
        .checked_add(5)
        .ok_or("LAB sequence is exhausted; no job was submitted.")?;
    Ok((1..=5u64).map(|i| serde_json::json!({"event_id":format!("{job}-{i}"),"symbol":"LAB","price_cents":9975+i*25,"sequence":previous+i})).collect())
}

/// The open page retains the entire replay request until its outcome is known.
/// A refreshed quote must not change the payload of an uncertain retry.
#[derive(Clone, Debug, Default)]
pub struct ReplaySubmission {
    draft: Option<(String, serde_json::Value)>,
    earlier_uncertain: bool,
}
impl ReplaySubmission {
    pub fn job_id(&self) -> Option<&str> {
        self.draft.as_ref().map(|(id, _)| id.as_str())
    }
    pub fn prepare(
        &mut self,
        new_id: impl FnOnce() -> String,
        previous: u64,
    ) -> Result<serde_json::Value, &'static str> {
        if let Some((_, body)) = &self.draft {
            return Ok(body.clone());
        }
        let job_id = new_id();
        let ticks = replay_ticks(&job_id, previous)?;
        let body = serde_json::json!({"job_id":job_id,"ticks":ticks});
        self.draft = Some((job_id, body.clone()));
        Ok(body)
    }
    pub fn resolve(&mut self, status: Option<u16>) -> WriteOutcome {
        if self.draft.is_none() {
            return WriteOutcome::Unknown;
        }
        let outcome = write_outcome(status, self.earlier_uncertain);
        if outcome == WriteOutcome::Unknown {
            self.earlier_uncertain = true;
        } else {
            self.draft = None;
            self.earlier_uncertain = false;
        }
        outcome
    }
}

The proxy admits at most 16 connections before starting handler threads and uses a five-second idle socket timeout, a 16 KiB request-body limit and a 1 MiB upstream-response limit. An idle timeout bounds waiting between socket activity; it is not a total deadline against a client that drips bytes. The server stays loopback-only. A socket fixture verified excess admission returns 503 and idle bodies release capacity; it does not verify browser behavior.

Retain a replay request across an uncertain response

A timeout does not tell the page whether the server committed a replay job. The console therefore keeps a ReplaySubmission containing the exact job ID and all five ticks. After an uncertain response, the button becomes “Retry retained replay.” A newer quote must not change those ticks: the backend compares both identity and payload when deduplicating. A later validation rejection cannot disprove an earlier successful request whose response was lost, so it leaves the original request unresolved. A successful response clears it. This state lives in the open page; reloading loses it. Copy the visible ID and inspect durable jobs before leaving.

Work through the investigation: suppose the first response is lost and the LAB quote advances before you retry. Predict whether generating new tick sequences is safe. In course_ui_model::ReplaySubmission, the retry branch returns the retained body before it calls the ID generator or reads the new sequence. The native test replay_retry_retains_identity_and_ticks_across_new_quotes_and_rejections supplies an ID generator that deliberately panics if called on retry, changes the quote sequence, and checks that the whole request remains identical through timeout, conflict and rejection responses. The intentional panic belongs only to this test oracle. It is not recommended application error handling.

An alternative is persisting pending commands across reloads, which needs storage failure handling, expiry and identity reconciliation. This teaching client declares an open-page contract instead.
