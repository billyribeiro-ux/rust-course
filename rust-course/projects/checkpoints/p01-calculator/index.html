Engineering decisions at this checkpoint

The input strings are bounded before parsing, ordinary parse failure stays distinct from checked arithmetic overflow, and the entry point propagates its Result. Two small functions fit one operation; a generic arithmetic framework or CLI dependency adds no present capability. One combined helper would also be sound, but separating parsing makes the failure boundary easy to inspect. Unit tests distinguish unrepresentable text from an unrepresentable sum. Operator selection and unit algebra justify the next module boundary.

Output belongs to the checkpoint contract

The executable propagates both arithmetic and output errors. It uses writeln! and flush through a locked stdout handle. Its OS-pipe regression closes the read end before launching the executable and checks a failing exit without a panic. The small boxed error boundary carries either error kind; the library retains its explicit Number and Overflow variants.
