Append-only key-value store: engineering decisions

Author self-review completed; independent review pending. These decisions explain the reference's current scope, not a sequence of poor habits to undo later.

Current scope and invariants

One cooperating writer owns the separate lock; only a validated record changes the map or recovery boundary. A failed write leaves the last acknowledged map readable and blocks further mutations until reopen.

Chosen design and concrete Rust habits

A small binary protocol and BTreeMap keep framing and replay visible. Bounds precede allocation, typed io::Result values preserve failures, and owned File handles tie cleanup to scope. write_all and sync_all precede acknowledgment; compaction uses a separate lock inode and replaces the active data handle. The retained data path is made absolute at open so a later current-directory change cannot redirect compaction. Symlinks are not canonicalized; cooperating writers must use stable paths, without external path replacement.

Reasonable alternative and tradeoff

An embedded database would provide a broader tested storage contract and should be preferred when a real application needs transactions, indexing, migrations or concurrent readers. This implementation is appropriate for learning one explicit single-writer log protocol; adding a framework would conceal the decisions being studied.

Meaningful tests

CRC known vector; every truncated suffix of the tested record; checksum mismatch after a complete declared payload; invalid length; read failure; tombstones and empty values; tail repair; lock retention across compaction. Additional self-review regressions cover write-error poisoning and stale temporary files.

Evidence limits

The live map grows with the data set. CRC is not authentication. A bounded damaged length can resemble an incomplete payload and cause truncation of an originally complete record. Recovery assumes an interrupted append following unchanged valid prior records; preserve original bytes before inspecting suspected damage. Sync/rename tests do not reproduce every power-loss ordering. Unix compaction and cooperating advisory locks are explicit scope limits.

When requirements justify evolution

Adopt or evaluate an established storage engine when the requirements include multi-key atomicity, large state, coordinated concurrent readers or portable power-loss guarantees. Do not grow the current log by silently adding assumptions.

CLI boundary follow-up

The CLI validates exact arity, UTF-8 command/key/value text and byte limits before Store::open can create or repair a file. Paths remain native PathBuf values; successful get still follows the documented open/recovery policy. Process tests preserve a torn file and avoid creating a data or lock file on invalid input. Unicode paths round-trip; arbitrary-byte Unix names either round-trip on a supporting filesystem or produce an ordinary I/O error. The author filesystem rejects non-UTF-8 names.
