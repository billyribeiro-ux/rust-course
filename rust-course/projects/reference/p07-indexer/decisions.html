Bounded file indexer: engineering decisions

Author self-review completed; independent review pending. These decisions explain the reference's current scope, not a sequence of poor habits to undo later.

Current scope and invariants

At most the configured fixed number of workers count files, both channels are bounded, each file uses a fixed-size read buffer, and input paths plus collected results have explicit batch limits.

Chosen design and concrete Rust habits

Owned jobs move through channels; Arc is used only for shared cancellation and receiver ownership. Mutex scope covers dequeue, not file I/O. A pure streaming counter preserves state across reads, per-file status preserves partial failures, and final sorting makes entries deterministic.

Progress from the same result owner

index_with_progress invokes one synchronous coordinator callback before workers start, after each returned result, and after joining and sorting. The original index API uses a no-op callback. One fixed-size Progress value supplies separate indexed, too_large, failed, and cancelled counts; their sum equals received. The final observation supplies submitted, allowing queued work without a result and never-submitted work to be counted separately. These counts describe observed outcomes, not byte throughput or an estimated finish time.

No new queue or observer task is introduced. A slow callback applies backpressure through the existing result queue and must not wait for its own run to finish. The CLI writes progress to stderr, keeps deterministic results on stdout, and requests cancellation after a progress write failure while still draining and joining the workers. Callback panics are programmer failures; ordinary output failures are handled explicitly. File reads and caller callbacks can still block, so there is no hard cancellation deadline.

Reasonable alternative and tradeoff

A work-stealing library is a reasonable alternative for CPU-heavy independent jobs and may simplify scheduling. The explicit fixed worker pool is a good fit here because its bounded queues and shutdown dependencies are the subject and are small enough to inspect. Unbounded thread-per-file spawning is a deliberate rejected design, not an early recommended step.

An independently scheduled UI may need a bounded notification channel or a coalesced latest snapshot. That new boundary needs an explicit slow-observer policy; it is unnecessary for the current synchronous CLI. Per-byte or periodic progress likewise needs a new sampling contract.

Meaningful tests

Chunk-boundary counts; empty files; oversize and missing paths; cancellation before submission; queue-one termination; repeatable entries; invalid configuration. Progress tests cover initial, monotonic, and final observations; empty and invalid input; actual file errors and oversize results; cancellation before and during collection; coordinator-thread ownership; CLI stream separation; and a closed progress-output sink.

Evidence limits

The total bound includes capped path/result metadata, not just the 8192-byte buffers. Ordinary file reads can block cancellation. Files may change during a run. Partial counts from failed or oversized files are not complete-file statistics.

When requirements justify evolution

For recursive or effectively unbounded discovery, stream results to a sink and use bounded or external sorting instead of collecting an unlimited list. For hard shutdown deadlines, revisit the synchronous I/O boundary and supported file types.
