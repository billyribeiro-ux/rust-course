Bounded file indexer

Working directory: the portable course's projects directory.

mise exec -- cargo run -p p07-indexer -- reference/p07-indexer/src/lib.rs reference/p07-indexer/src/main.rs
mise exec -- cargo test -p p07-indexer

The CLI reports per-file progress on standard error while the coordinator collects results, then emits deterministic path-sorted entries and a summary on standard output. Duplicate paths remain separate jobs. Indexed means a whole file completed; TooLarge, Failed, and Cancelled entries are partial outcomes. Counts are bytes, newline-delimited lines including a final unterminated line, and words separated by ASCII whitespace; the fingerprint is not cryptographic authentication.

Budgets and lifecycle

Default limits are four workers, queue capacity eight, at most 4096 input paths, and 16 MiB per file. Library configuration permits at most 32 workers, queue capacity 1024, path length 4096 encoded bytes, and 64 MiB per file. Workers stream through 8192-byte buffers. Results and input metadata are bounded by the batch cap; total memory is not just the sum of worker buffers.

The library's index returns a final report. index_with_progress additionally calls an FnMut(Progress) observer on the coordinator. It sends an initial snapshot, one per received Entry, and a final snapshot after join and sort. No extra channel is allocated. A slow observer slows result collection and can block workers through existing bounded queues. Observers must not wait for this same run to finish.

Reading progress honestly

received = indexed + too_large + failed + cancelled. Only the final snapshot provides submitted. Then submitted - received identifies accepted jobs without a returned result, and total - submitted identifies unsubmitted jobs. A finished cancelled run can therefore have fewer received results than original inputs. Snapshot order and peak worker counts depend on scheduling; final entries for unchanged files are deterministic.

Library callers request cancellation through a retained atomic flag. It is checked between ordinary synchronous reads and job boundaries, so cancellation cannot force a blocked read to end. The CLI does not intercept Ctrl-C. If its progress output fails, it requests cancellation, drains and joins, then returns an error without a successful summary. Progress occurs per returned file, so a lone slow file may remain quiet between started and finished; it is not a timed heartbeat.

Evidence and decisions

Read engineering decisions and the focused verification report. Tests check category accounting, cancellation, empty/invalid inputs, actual I/O failures and CLI stream/error behavior. Existing benchmark evidence uses index with no progress output; no new speed claim is made. Author self-review is recorded separately from independent review, which remains pending.
