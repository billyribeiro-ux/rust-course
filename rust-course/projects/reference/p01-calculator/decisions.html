Engineering decisions and evidence

Requirements and invariants

The arithmetic form accepts signed i64 quantities and one supported operator. Addition and subtraction require equal units; products need a scalar; equal units cancel during division. Every successful result is representable. The conversion form, convert 1.5m cm, accepts at most 128 bytes of unit-bearing text and a target among mm, cm, m, and km. Private Length fields preserve a finite f64 value and recognized unit. Nonfinite input, real overflow, and a nonzero value rounding to zero are errors; explicit signed zero and finite nonzero subnormals are accepted. Conversion results are approximate binary floating-point measurements.

Chosen design and concrete habits

Quantity and Unit retain checked integer arithmetic. A separate Length and LengthUnit model handles fractional conversions without changing integer division. Parsing establishes syntax and finite-value invariants before conversion; scaling divides small unit factors before multiplying the input to avoid false intermediate overflow. Typed errors preserve ordinary failure categories. Main owns stdout, stderr, and exit status, and uses args_os with fallible Unicode conversion. Documentation examples propagate errors with ?, while assertion-only test unwraps express expected successes. No external dependency or generic numerical trait is required by this contract.

Meaningful alternatives and evolution thresholds

A dimensional type system or units library becomes useful for compound dimensions or larger scientific calculations. Exact decimal interchange would require an explicit scale and rounding policy and may justify fixed decimal arithmetic. A rational representation has different range and simplification tradeoffs. A CLI framework becomes worthwhile as options and subcommands grow. These are requirement-driven changes; changing the output format alone cannot make binary floating-point arithmetic exact.

Actual checks and remaining uncertainty

The earlier five-foundation-package audit passed 29 checks before the conversion capability existed, recorded in verification/patch001-foundations-tests.log. The added converter closes a real construction gap. Its scoped P01 verification passed 15 checks: eight library tests, five CLI tests, and two doctests, recorded in verification/conversion-tests.log. Clippy passed all P01 targets with warnings denied in conversion-clippy.log. The roundoff example was executed and its output is in conversion-roundoff.log. Tests cover all 16 unit pairs with explicit expected values; fractions, signs, scientific notation, invalid units, nonfinite inputs, range loss, zeros, exit streams, and unchanged integer arithmetic. These finite examples do not prove every float rounding property, a physical accuracy bound, or every operating-system argument case. Independent review is pending.

Output errors and evidence

Normal output uses fallible writeln! and an explicit flush. Closed output pipes return process failure instead of panicking. If stderr itself fails, the final diagnostic is best effort and failure remains visible through the exit status. The actual OS-pipe follow-up records normal and failed-output checks; independent review remains pending.
