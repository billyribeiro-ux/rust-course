Replay: immediate processing versus a reusable 1024-event batch

Both variants generated and applied 1,000,003 synthetic events inside timing. Streaming passed each generated event directly to Replay::apply. Batching temporarily collected at most 1024 events into a reusable Vec, drained that batch into the same apply method, and repeated. Neither collected the complete input. The generator keeps at most two live orders and ends with one, so final-state comparison includes a nonempty book. Derived full Replay equality, including sequence, accounting, capacity, and orders, was the correctness gate; a digest alone was not accepted.

The batch median divided by the streaming median was 1.087. Values above one mean batching took longer in this run. The measurement supports a local comparison for this generator and tiny live state. It does not show that batching is always worse or better. Batching could become useful if it amortized an external call or enabled a different algorithm; neither mechanism exists in this implementation. A profile would be needed to attribute the observed difference to allocation, copying, optimization, or another cost.

Indexer: one worker versus four workers

The generated fixture contains 64 files of 131072 bytes each: exactly 8388608 bytes, below the requested 10 MB disk budget. Files were created once outside timing. Each timed call includes path cloning, worker startup, file opening, reading, counting, bounded channels, collecting, and sorting results. File contents were warm in the filesystem cache after the reference and warmups. The one-worker median divided by the four-worker median was 3.453. This compares the same concurrent indexer with its worker limit changed, not a separate direct serial implementation.

Every field of every sorted Entry, plus submitted and cancelled, matched the reference. Peak worker count was measured separately because concurrency is supposed to change. The corpus generator is the benchmark source, and per-file SHA-256 hashes plus the manifest hash are recorded in benchmark-summary.json. Fixtures remain under .course-cache/benchmark-fixtures and are not included as course source artifacts; no space is claimed as reclaimed.

Investigation and engineering decision

Observation: compare the measured medians and ranges above, not a predicted universal speedup. Competing hypotheses for an indexer improvement include parallel CPU counting and warm-cache reads; a cold-storage explanation is not supported because the protocol warmed the same fixture. A distinguishing next experiment would change only fixture storage/cache conditions while retaining bytes and worker limits. For replay, the hypothesis that adding this batch buffer would reduce elapsed time was not supported: streaming had an 8.805 ms median and batching a 9.574 ms median, and batching was slower in all seven paired observations. Both generated the same events and produced the same complete state. This rules out skipped replay work as an explanation for the streaming result; attributing the cost to a particular CPU or allocator mechanism still requires profiling. Ask an AI reviewer for a competing explanation and a one-factor experiment, then preserve the original samples before rerunning.

The recommended decision is to keep the simple streaming replay unless a measured requirement justifies batching. The indexer worker count is a bounded configuration choice: select it against the actual workload, resource budget, and latency target. Seven pairs on one shared workstation do not establish tail latency, energy usage, cold-disk behavior, or a general scaling law. No peak-RSS, allocator, scheduler, or CPU profile was collected. Independent review remains pending.
