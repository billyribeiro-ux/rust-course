Maintaining this course

Teaching and engineering standard

This is the course's ongoing authoring contract, including patch 001. The established curriculum, investigation playbook and review gates remain in force. Change recommended source, its checkpoints and its explanation together. A policy page alone does not satisfy a correction.

The same professional standard from the first project onward

Every project must demonstrate idiomatic Rust and sound professional engineering from its first runnable checkpoint, regardless of how small or simple it is. This applies to setup, directory structure, source, dependencies, errors, tests, documentation, verification and the explanation of decisions. Knowledge and complexity grow; correctness, honesty, clarity and care apply from the beginning.

The ambition of distinguished or principal-level engineering means rigorous, evidence-backed judgment on every example. Prestige labels do not replace implementation, explanation or review. Teach the proper approach the first time, in small understandable steps. Do not recommend an avoidable poor habit with a promise to correct it later.

Professional quality is proportional to the problem. A small program deserves a small, clear implementation. Add abstractions, crates, asynchronous execution, services and configuration when actual requirements justify them. Explain both additions and omissions. A correct text buffer can evolve into a rope when editing costs justify it; a correct single-writer file can evolve into a database when concurrency and transactional requirements change. Such evolution differs from correcting a defective earlier lesson.

Engineering rules for all examples

  • Use safe Rust by default. Make ownership and invariants visible. Do not clone, share state or add lifetimes merely to silence diagnostics.
  • Handle ordinary input, I/O, network and database failures at introduction. Separate them from programmer invariants. Explain justified assertions, panics, unsafe blocks and process exit behavior.
  • Declare supported input, format, schema, resource bounds and failure guarantees. The implementation must meet its declared scope. Educational limits must be visible at the point of use.
  • Choose maintained dependencies for concrete capabilities; explain features, pinned compatibility and lockfiles. Do not delete capabilities to make dependency counts look better.
  • Keep names, visibility and modules cohesive. Introduce traits, layers or additional crates only when their benefits are concrete.
  • Introduce task ownership, bounded admission, synchronization, cancellation and shutdown with the first concurrent checkpoint. Keep synchronous lock guards out of await points.
  • Teach validation, consistency, parameterized SQL and authorization alongside the first relevant boundary. Public fixture identities are explicitly local teaching fixtures.
  • Run checks appropriate to behavior and risk. Compiler acceptance, Clippy, tests, Miri, benchmark measurements and human design review support different claims.
  • Use applicable Rust MCP tools only after establishing workspace access; otherwise use explicit Cargo commands. Consult version-matched primary documentation and review automatic suggestions.
  • Clearly label incomplete learner scaffolds and deliberate failures. Their reference outcomes must be explained and verified.

Required lesson sequence

Each lesson establishes purpose and a plain-English model, asks for a prediction, provides a runnable example with file and working directory, explains unfamiliar code, investigates an explicitly labeled mistake, guides a complete checkpoint, gives independent practice with tiered hints, reviews decisions, records evidence and requires explanation, modification and debugging for mastery. Every lesson applies the playbook to its own topic and includes a concrete next experiment when stuck.

Review: explain why the recommended implementation is idiomatic and appropriate to its current scope. Compare reasonable alternatives where useful. Present poor patterns only as explicitly labeled mistakes to diagnose, with the cause and correction explained. Do not recommend a substandard beginner implementation that the learner is expected to adopt and later unlearn.

Project-specific decisions and evidence

At every checkpoint identify current requirements and invariants; explain why the implementation fits; locate the Rust habits in source; compare a meaningful alternative; state actual verification and uncertainty; and name the requirement change that would justify a new design. Keep the calculator's record short and the persistence, concurrency and distributed records deeper. The learner must practice these decisions while building and investigating.

Preserve reviewable work

Canonical lesson text is in authoring/*.json; HTML fragments are in authoring/*.html. python3 scripts/build-course.py embeds exact runnable source and regenerates pages. python3 scripts/verify-site.py checks links and source correspondence. Keep learner work, databases and unrelated caches intact. The portable package excludes build caches and generated WASM; the build command restores them.

Maintain separate authored, author self-review, code verification and independent-review statuses. Independent review stays pending until a named, authorized reviewer assesses the material. Generation completion, course acceptance and demonstrated learner competence are distinct milestones.
