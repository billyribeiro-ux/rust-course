Optional specialization · outside the Rust prerequisites

One Rust backend, an optional Svelte 5 client

This bridge builds a small, real, read-only interface for the same simulated workbench used by the Leptos console. It teaches a network boundary: a client written in another language must preserve the backend's contracts, numeric meaning, permission boundaries, and resource budgets. The main Rust learning path continues to use Leptos. You do not need Svelte, Node, or this exercise to complete the Rust projects.

Prerequisites: browser foundations, HTTP/browser boundaries, and the workbench API contract. Optional JavaScript prerequisites are functions, objects, promises, and try/catch. A promise represents an eventual result; awaiting it suspends this function until it settles. JavaScript's garbage collector manages memory, but your code still owns the lifetime of requests and timers.

Purpose and plain-English model

The Rust server owns quotes, positions, cash, accepted orders, and durable events. The client receives a snapshot: a read model for display at one point in time. Filtering a table changes which rows are visible; it does not change the authoritative quote map. Replacing the UI framework does not move transaction rules into the browser.

Svelte compiles components written with markup, JavaScript, and scoped CSS. A rune is syntax understood by its compiler. $state makes a value reactive: assignments can update dependent markup. $state.raw is useful for the snapshot because this component replaces the whole response rather than mutating nested fields. $derived.by computes filtered rows from the current snapshot and filter. It is a calculation, not a place to start a request. onMount starts the initial read after mounting and returns a synchronous cleanup function. Cleanup cancels the request and prevents a late completion from updating a destroyed component. See the official state, derived-state, and lifecycle documentation.

This is client-side rendering. The build produces JavaScript that mounts into the page's root element; there is no server-generated component HTML to hydrate. Hydration means connecting client behavior to compatible HTML already rendered on the server. We do not introduce SvelteKit, server rendering, or another backend for this read-only experiment.

Prediction: a tiny number can expose a large boundary error

Predict what ordinary JavaScript JSON.parse does with the integer18446744073709551615, the largest Rust u64. Now predict whether clicking Refresh twice while one request is waiting should send one request or two. Finally, imagine that a component disappears before a response arrives: who cancels its request, and who prevents a stale state update?

Prediction answer

A JavaScript Number cannot represent every u64 exactly; ordinary parsing can round this integer. Our decoder parses integer tokens directly into bigint, then validates their Rust ranges. The client admits one outstanding request; the second call rejects without fetching. Component cleanup aborts the current request, and the disposed flag prevents an already-resolving continuation from updating state. Cancellation and a stale-result guard solve related but different lifecycle problems.

Decode and bound the network boundary

File: experiments/svelte-bridge/src/client.js. The existing JSON fields remain unchanged: simulated, cash_cents, quotes, positions, orders, watchlist, and events. The decoder validates collection budgets and identity uniqueness as well as integer ranges. It accepts u64 sequence values without truncation and formats cents using bigint division and remainder. This is display formatting, not a second trading engine. Do not convert these values through Number and then attempt to recover lost digits.

A request has one AbortController, a three-second timer, and a64KiB response limit. The same signal applies to receiving headers and reading the body. The timer is cleared in finally for success, failure, and cancellation. Streaming reads enforce the byte budget even when Content-Length is absent or inaccurate. The decoder rejects non-JSON responses, malformed data, duplicate identities, unsupported integer syntax, and invalid domain ranges before the component replaces its snapshot. A failed read therefore preserves the last valid display state.

The source uses lossless-json4.3.2's parseNumber option, verified against that installed package's type declarations and tests. Its README's earlier bigint example used a different property spelling at verification time; the checker and exact-integer test caught the mismatch. This is a practical reason to consult versioned APIs and executable evidence rather than copying an example blindly. See the maintainer's documentation alongside the pinned package.

The local same-origin proxy

The browser requests /api/snapshot from its own origin4176. Vite forwards that one route to the Rust server on4116. A small middleware admits at most four upstream response lifetimes, rejects writes and body-bearing requests, and refuses an unexpected Origin header. The upstream HTTP agent bounds sockets to four, uses three-second network timeouts, and destroys an outgoing request if the client connection closes. These are local development boundaries. They do not provide production login, TLS termination, or protection against an already hostile local machine. The credential shown in source is a public demo-reader fixture.

This proxy avoids requiring cross-origin access for the legitimate browser flow; it does not replace backend authorization. A native client can directly call4116. The strict endpoint and method rules limit what this particular local proxy forwards. Read the official Vite proxy documentation before changing routing or host settings. The generated dist directory is a build artifact; its files alone do not implement the proxy.

Deliberate mistake and guided change

Intentional failure to investigate: replace the custom decoder with ordinary JSON.parse and convert all numeric fields to Number. Run the large-sequence test. A page that displays rounded identifiers can look correct while corrupting a reconciliation or ordering decision. Restore the lossless boundary before continuing. Do not compensate by shortening the displayed number; formatting does not repair the value.

For a guided increment, add a read-only column showing each quoted symbol's current whole-share position. Derive a lookup from the existing positions array, keep the current keys, and use zero when the symbol has no holding. Do not request one network response per table row. The acceptance criteria are: one snapshot request still supplies all rows; an empty position list displays zero; changing the filter does not trigger network traffic; whole-share quantities remain exact bigint values.

Hint1: keep it derived

The lookup depends only on snapshot.positions. Compute it with a derived expression; do not synchronize a second mutable copy with an effect.

Hint2: preserve numeric meaning

A map from symbol to quantity can return bigint or undefined. Use 0n as the default and call toString for text.

Reference approach

Create a derived Map from the position entries and read (holdings.get(quote.symbol) ?? 0n).toString() in the new cell. Add the corresponding column header with scope=col. For this bounded32-symbol snapshot, either a map or a linear find is reasonable; explain the difference in setup and lookup cost before claiming a performance benefit.

Independent practice and playbook investigation

Specification: add a user-controlled “watched symbols only” checkbox. It must combine with the existing text filter, remain local to the component, and distinguish an empty watchlist from no filter matches. Preserve the one-request budget. Provide a prediction, a minimal acceptance test for your pure filtering function, and an accessibility review of the control. Do not extend the server API for a calculation already supported by the snapshot.

Incident evidence: a learner reports “Refresh failed; Rust lost the quote,” yet the old quote remains visible and the error contains HTTP503. Possible hypotheses are a committed-state loss, a temporarily unavailable backend, an overloaded proxy, or a stale frontend build. Distinguish them: inspect the server's exact snapshot response and event count using the reader fixture; check the client build/version; and reproduce the pure decoder with the captured synthetic response. If the server still returns the quote, that disproves state loss for that observation. A previous snapshot plus a visible error is intentional stale-state behavior, not a rollback.

For the parser incident, retain two plausible hypotheses: the backend changed its schema, or the client called the wrong versioned parsing option. Compare the installed type declaration with the decoder's object key, then run a focused exact-integer test. The fix is the supported option and a regression, not weakening validation until the response appears accepted. State what remains untested: browser lifecycle timing, actual screen-reader announcements, and the complete proxy path are not established by Node unit tests.

Engineering decisions, evidence, and limits

The bridge keeps server authority and uses a small read-only client because the learning objective is language interoperability. Manual refresh avoids introducing a second polling scheduler. One client request, four proxy admissions, bounded rows, and byte limits make resource reasoning visible. A maintained numeric parser is justified by the existing Rust integer contract; an alternative would be a versioned API that serializes selected integers as decimal strings. That alternative requires coordinated API evolution and tests, not a unilateral client assumption.

When you get stuck

From experiments/svelte-bridge, rerun mise exec -- npm run check, then mise exec -- npm test. If installation complains about Node, compare mise exec -- node --version with the pinned mise file. If the page reports a backend error, inspect the Rust process and use the reader fixture on /api/snapshot; never invent an empty successful response to hide the failure. For review, supply the minimal synthetic response, exact package versions, expected and observed statuses, and the smallest failing test. Do not include real credentials.

Mastery check

Explain the distinction between a reactive calculation and an owned async operation. Show why integer loss must be prevented before ordinary Number conversion. Modify the watched-symbol filter without adding requests. Debug a timeout while preserving the last valid snapshot, and explain what aborting the client does and does not guarantee about server work. Finally, compare this client to the Leptos version using correctness, lifecycle clarity, team skills, and measured maintenance cost rather than language loyalty.
